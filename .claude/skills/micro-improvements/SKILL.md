# 待ち時間の改善サイクル

実験の待ち時間は空き時間ではない（CLAUDE.mdの前提）。この手順で
細かい改善を回す。2026-08-30に確立した運用で、初日の実績は
Issue 9件作成・5件消化・PR 6本だった。

## 規模感と判断軸

**規模の下限はない**（2026-08-30オーナー指示）。全体への寄与が
0.01%に満たなくても、時間が空くくらいなら局所最適化をやる。
改善の価値は棋力の1軸で測らず、次の複数軸で見る。

- 対局への寄与（従来の軸）
- バルク処理のスループット（例: 合法手生成は対局では効かなくても、
  大量生成の場面で効く）
- メモリフットプリント（同じ命令数なら省メモリを選ぶ。将来の
  wasm化のような移植で効く）
- 保守性・コードの簡潔さ

## サイクル

1. 気になりを見つけたら、その場で `micro` ラベルのIssueに切る。
   既定値の食い違い・表示の粗・重複コード・CIの遅さ・使い捨て
   スクリプトの残留など、粒の小ささを理由に流さない
2. 待ち時間ができたら、走行中の仕事と資源が重ならないIssueを選ぶ
3. mainからブランチを切り、実装・検証・コミット・PR・CI待ち・
   squashマージ・Issueクローズまでを1サイクルで終える。
   マージ待ちは `hmwr ci wait <PR番号> && gh pr merge <PR番号> --squash`
   をバックグラウンドに置き、次の作業へ移る

## 資源の住み分け

着手前に、走行中の仕事と使う資源を照合する。

| 走行中の仕事 | 占有 | 併走できる作業 |
|---|---|---|
| SPRT（並列8） | CPU 8/10コア | ネットワーク・文書・軽いビルド |
| 学習 | GPU＋CPU1＋ページキャッシュ | 文書・軽いビルド。**大きなファイルを読み書きする仕事は避ける** |
| 静止化・rank導出 | 指定した並列数＋ディスク帯域 | 残りコアの範囲でビルド・分析 |
| 取得（fetch） | ネットワーク | ほぼすべて |

時間制の対局（SPRT）と重いCPU仕事を重ねない。判定を歪めるためで、
物理10コアなら並列8のSPRT中は2コアまでに抑える。

**学習と大きなファイルの生成を重ねない**（2026-09-02の失敗）。学習は
教師とランキング群をmmapで読むので、ページキャッシュを外れると1ステップ
300ms規模の待ちになる（issue #409）。11GBを書く生成を4並列で走らせた
ところ、学習は10分以上たっても最初の100ステップへ届かなかった。CPUの
コア数だけを見て「学習はCPU1本だから併走できる」と判断すると外す。

NPSの計測も同じ理由で重ねない。SPRT走行中に測ると絶対値が7割へ落ち、
差も過大に出る（[ADR-0195](../../../docs/adr/0195-reorder-on-late-positions.md)で
+2.11%と出た差が、空いてから測ると+1.14%だった）。

## 検証の型

- 等価な書き換えは等価性を機械で示す。基準は3つ。旧実装との
  バイト一致（例: psv quiet jobs=1）、決定的環境での出力一致
  （例: CPUのloss5桁一致）、決定論の契約の明示（例: 並列出力は
  jobs固定で決定論）
- 等価でない変更は改善サイクルの対象外。実験（ADRの事前登録、
  CLAUDE.mdの実験の規律）へ回す。バッチサイズ変更のような
  ハイパーパラメータは典型例
- エンジン内部も対象にしてよい。ただし「命令数やメモリ往復を削っても
  NPSに出ない」は4件の実測で行き止まりが確定している（ROADMAP注力2）。
  この教訓はNPS向上を主張する変更への警告として残る。主張する軸を
  メモリ量・バルク処理・簡潔さへ置けば着手できる。その場合も等価性と
  NPS非劣化は確かめる
- push前に `cargo fmt`・`cargo clippy --all-targets -- -D warnings`・
  `cargo test`・`python3 -m pytest tests -q`・`hmwr doc lint` を
  ローカルで通す。CIで初めて落とすのは1往復の無駄になる

## 委任

- 独立した実装や監査はサブエージェントへ出す。並列にできるものは
  同時に起動する。作業ツリーの競合を避けるため、監督が同じ
  チェックアウトを使う間はworktree分離を指定する
- 分析と実装は2段に分ける。まず計測・分析だけを依頼して数値で
  候補を出させ、監督が採否を決めてから実装を依頼する。同じ
  エージェントを続けて使うと文脈が残る
- 委任した検証はやり直さず、監督は差分レビューと等価性の論理の
  確認だけを行う

## 事故から学んだ約束

- 使い捨てスクリプトでツールを直接呼ぶとき、既定値の食い違いが
  事故になる（max-plies事故、ADR-0192）。頻用の手順はhmwrへ
  コマンド化するIssueを切る
- 長時間ジョブはツールのバックグラウンドでなくnohupで切り離し、
  完了マーカーと軽い監視ループで検知する
- `rm` は使えない。削除はツールのconsume系オプションに寄せるか、
  ユーザーへコマンドを提示して依頼する
