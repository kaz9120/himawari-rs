# 参照実装からの移植

このスキルは、他エンジンの機能を本エンジンへ移すときの手順を扱う。
2026-07-30から08-01にかけて、やねうら王への追従を11群で行った経験に基づく
（[ADR-0109](../../../docs/adr/0109-reference-parity.md)）。

**単発の改善を積むときは使わない。** その場合は
[ADR-0089](../../../docs/adr/0089-improvement-criteria.md)の3軸で選ぶ。

## 中心の原則

**移植の単位は「依存の閉包」である。**

移植元の機能は周辺の仕組みと組で成立している。1本だけ移すと、支えを失った側が
損をする。過去に5件の棄却があり、いずれも実装も測定も正しく、欠けていたのは
組み合わせだった。

| 棄却 | 何が足りなかったか | 揃えた結果 |
|---|---|---|
| LMRのcutNode項（-1.1） | 12項のうち強める1本だけ | +124.0 |
| capture history（+4.0） | 振り分け閾値と枝刈りマージンへ繋がっていない | +88.5 |
| ponder 3件（-117.8ほか） | 4本の支えのうち1本ずつ | +19.3 |
| razoring・RFP・NMP | improvingの定義を触らず数値だけ | +41.1 |

**棄却の記録は「効かない」ではなく「その形では効かない」と読む。**

## 手順

### 1. 群を切る

相互依存する機能をまとめる。群に求めるのは「単独で効く仮説」ではなく、
**その群の機能が読む値をすべて群内で供給できること**である。

群が負けたら二分割して切り分ける。分け方は依存の閉包を保つ最小の単位で、
**着手前にADRへ書く。** 切り分けは1回まで。二分割した両方が負けたらそこで
測るのをやめ、保留としてブランチに残す（棄却しない）。

### 2. 依存の棚卸し（実装前）

**これを飛ばすと前提が欠けたまま実装が進む。** 実際にG5とG6で2群連続で
踏んだ。

洗い出すのは3つ。

- その群が読む値（オプション、局面の属性、他の機能の出力）
- その群が呼ぶ関数
- **その機能が依存する前提**（発動頻度、コストの水準、値を守っている仕組み）

3つ目が最も落ちやすい。G6では「1手詰め判定が安い」という前提が成立して
おらず、本体が `do_move` を使う実装のまま呼び出し側だけを移していた。

棚卸しで見つかった不足は実装範囲に含める。

### 3. ベースラインを用意する

```
git switch -c feat-adrNNNN-<slug>
RUSTFLAGS="-C target-cpu=native" cargo build --release
cp target/release/himawari data/bin/base-<群名>
```

`data/` はgitignore対象なのでコミットに入らない。

### 4. 作業指示書を書いて委譲する

**指示書は「何を移すか」と「原典のどこを見るか」に徹する。** 係数と条件は
ワーカーが原典から直接読む。

指示書と原典の食い違いは9群すべてで出た。合計30箇所以上、すべて原典が
正しかった。**要約は必ず細部を落とす。**

指示書に必ず書くこと。

- 原典のパスと該当箇所（file:line）
- **原典の読み方**（下の「原典の罠」を丸ごと引用する）
- `docs/` は触らない（監督がADRを並行して書く）
- `git add` はファイルを明示する
- PRは作らない
- 小さく刻んでこまめにコミットする。やり切れなければ未完了項目を報告する
- 時間に依存するテストを書かない
- 測定の内容（機能検証、発動率、NPS）

委譲は `general-purpose`（opus）で行う。

### 5. 測る

**機能検証**（[ADR-0074](../../../docs/adr/0074-feature-verification.md)）

```
scripts/verify-feature.sh data/bin/base-<群名> target/release/himawari
```

等価変換ならノード数の完全一致が成功条件。それ以外は変わることが成功条件で、
変わらなければ移植が効いていない。

**発動率**を枝刈り・延長ごとに測る。0.1%を下回るものは明示する。群として
入れる方針ならそれだけを理由に外さない。

**NPSは同一実行内で比べる。** 別セッションの値と比べると数%ずれる。

**時間管理の群は固定深さで測れない。** 1手あたりの消費時間、到達深さの分布、
時間切れの有無を自己対局で測る。

### 6. SPRTを回す

```
scripts/sprt-run.sh <base> <cand> <名前> [再試行の上限] [追加引数...]
```

Bashツールの `run_in_background: true` で起動する。注意が3つある。

- **`nohup ... &` で立てるとツール呼び出しの終了に巻き込まれる**
- **パイプ（`| head` など）を繋ぐとSIGPIPEでSPRTが死ぬ**
- バックグラウンドジョブは10分で止められる。棋譜は残るので `sprt-run.sh` を
  再実行すれば続きから回る

**既定条件で測れない変更がある。** 条件を変えるか非劣性検定（elo0=-5、elo1=0）
へ落とす。変えたら、なぜ既定で測れないかをADRに書く。

### 7. 記録する

群ごとにADRを1本起こす。H0でも書く。含めるもの。

- Context: なぜこの群が要るか。過去の棄却があれば、その原因の再解釈
- Decision: 何を移したか（原典のfile:line付き）
- 測定: 機能検証、発動率、NPS
- SPRT: 条件と結果
- Consequences: 何が変わったか、何を保留したか、次の群への影響

採択したらコミットに `SPRT:` トレーラを付け（CHANGELOGへ載る）、
`docs/adr/README.md` の索引を更新する。着手した候補を `docs/ROADMAP.md` から
消す。**過去の結論が覆ったらROADMAPの記述を直す。**

## 原典の罠

指示書へそのまま引用する。

**無効化されたコードが混じっている。** `#if OLD_CODE` / `#if STOCKFISH` /
`#if 0` の中身は無効な場合がある。`OLD_CODE` は一度も定義されておらず、
`STOCKFISH` は `config.h` でコメントアウトされている。移す前に有効な
プリプロセッサ分岐にあるか確かめる。

**原典の日本語コメントも誤りうる。** NMPの検証探索は「同じ深さで探索しなおして」と
書かれているが、コードは `depth - R` を渡す。コメントとコードが違えばコードに従う。

**C++のtruthinessに依存した書き方がある。** `if (tm.search_end && ...)` は
負値も「予約済み」として扱う。0比較で移すと挙動が変わる。

**その値が何に守られているかを見る。** 忠実に移して裏目に出た例が2件ある。

- optimumからNetworkDelayを引かないのは、床（1880ms）が保護を含むから。床を
  下げると保護まで消え、終盤の到達深さが8ply落ちた
- bestMoveInstabilityは、root探索1回ごとの安定ソートに守られている。並べ替えが
  ないと同じ入れ替わりを数え直し、係数が膨らむ

**参照実装の値が本エンジンで成立しないことがある。** 2件出た。singular率
（設計点1割に対し本エンジンは43.5%）と時間配分の分母（move horizon方式が2度とも
通らない）である。**該当部分だけを据え置き、残りを採る。** 群全体が負けたら、
まずこの可能性を疑って二分割する。

**番兵をそのまま移す。** `meanSquaredScore` の初期値 `−VALUE_INFINITE²` は、
窓幅の式に入ると窓を全開にする。深さ1でaspirationを無効にする仕掛けである。
0で初期化すると無駄な再探索が入る。

## 原典の行数を移すことが目的ではない

`mate_1ply` は原典2,185行に対して約250行で同じ効果を得た。本エンジンの
`attackers_to` が「指した後の利き」を占有の演算だけで返せるため、原典の
駒種別の巨大な分岐が要らなかった。

**再現とは同じ挙動を得ることで、同じコードを持つことではない。** 構造
（候補を絞る表、avoidを除いた利き）を借りつつ、実装は本エンジンの基盤に
合わせてよい。

## 副産物を見逃さない

差分を洗う作業は、本エンジン単独のバグを見つける経路にもなる。3件出た。

- ttPvのTTへの書き戻しが `is_pv` のままで伝播が閉じていなかった
- lmrDepthの基準に延長を込みにしていた（原典は常に `depth − 1`）
- 除外手つき探索で合法手が尽きたとき `mated_in` を返していた（原典は `alpha`）

## テストを書くときの注意

**CIはローカルより遅い。時間に依存するテストを書かない。**

G8では `sleep(300ms)` 中にinfoが出ない環境で落ちた。待つならポーリングにし、
判定はマシンの速度に依存しない量で行う。「反復深化が再起動したか」は、
経過時間ではなく**同じ深さの確定infoが2回出たか**で判定できる。
