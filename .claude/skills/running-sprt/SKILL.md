# SPRTの実行・監視・後処理

棋力が変わる変更はすべてこの手順で測る（ADR-0028・0154）。
毎回やることなので、起動方法・ログの場所・後処理を固定する。
条件の意味と例外（時間管理など既定で測れない変更）はCLAUDE.mdの
「SPRTゲート」を正とする。

## 名前の規則

`<名前>` は `adrNNNN-<slug>`（例: `adr0153-superior`）。この名前で
4つの場所が決まる。

| 置き場 | パス |
|---|---|
| 経過ログ | `data/logs/sprt-<名前>.log`（追記） |
| 棋譜 | `data/sprt/<名前>.jsonl`（状態のすべて。ADR-0087） |
| **完了マーカー** | `data/sprt/<名前>.result`（判定が出たときだけ。ADR-0175） |
| バイナリ | `data/bin/base-<名前>` / `data/bin/cand-<名前>` |

## 1. 起動

```
hmwr sprt run <名前>                     # 既定条件
hmwr sprt run <名前> --noninferiority    # 非劣性（ADR-0163）
hmwr sprt run <名前> --tc 60+0.6         # 条件を変える
```

**この1コマンドが3つを順に行う**（ADR-0179）。ペアのビルド、機能検証、
切り離しての起動である。順番を飛ばすには明示が要る形にしてある。

1. base（origin/main）とcand（HEAD）を同条件でビルドする
2. 固定深さでノード数を比べる。**全局面で一致したら起動せずに止まる**
   （ADR-0074）。飛ばすには `--no-verify` を付ける
3. 新しいセッションへ移して起動し、すぐ戻る

**切り離してよいのは、状態がファイルにあるからである**（ADR-0175）。進捗は
ログ、完了は `.result` で分かるので、プロセスを手元で掴んでおく必要がない。
起動したらそのまま別の作業へ移る。ツールのバックグラウンド実行のまま走らせると
数十分で強制終了されるため、切り離しは省けない（2026-08-18に2回）。

- **verifyの4局面は序盤に偏っている**。終盤にしか現れない機能（詰み・入玉
  など）は、この4局面で一致しても「影響なし」と結論しない。終盤局面を別に
  用意して測る（ADR-0174で実際に起きた）
- 対立仮説は着手時に決め、実行後に変えない（ADR-0163）。棋力向上を主張する
  変更は既定、参照追従で「害がなければ入れたい」変更は非劣性
- **既定の上限は10,000ペア**（`SPRT_MAX_PAIRS`、ADR-0217）。判定に至らなければ
  「見送り」として結果ファイルに書き、mainへ入れない。判定済みの過去の実行は
  すべてこの中で決着している。変えるなら `--max-pairs` で宣言し、理由をADRに
  書く
- 条件を変えた理由はADRに書く
- **局数の見積もりは要らない**。判定か上限まで走る。約490ペア/時なので、
  上限は約20時間になる
- CLIが持たない条件で1回だけ試すときは、下位のスクリプトを直接叩く

## 2. 監視

**完了したかは `.result` の有無で判定する**。プロセスの生死やセッションの
継続に依存しない（ADR-0175）。

```
hmwr sprt show <名前>               # 今の値を1回表示
hmwr sprt show                      # 新しい順に10件
hmwr sprt wait <名前>               # 判定が出るまで待つ
```

- 一覧の「未完了」は `.result` がないという意味で、走っているとは限らない。
  判定前に打ち切った過去の実行もここに入る
- summaryは判定前でも最後のpairs行から途中経過を出す（判定欄は「判定前」）
- 経過の読み方: `LLR +2.94` でH1採択、`-2.94` でH0採択。中間で漂うのは
  真のEloがelo0とelo1の**中点**の近くにある兆候で、長期戦になる。中点は
  既定条件で約+2.5、非劣性で約−2.5である
- `show` の末尾に終局理由の内訳が出る。**切れ負けが1%を超えると警告が出る**。
  過去の実行は0.5%未満で、超えたら対局の環境を疑う。同じマシンでCPUを使う
  仕事（学習・ビルド・別の対局・再解析）が重なっていないか、電源が
  AC接続かを確かめる。両側に同じように出るので判定の向きは歪まないが、
  感度が落ちる。2026-09-18の実行で、最初の200ペアの46%が切れ負けだった
- 走らせたまま他の作業へ移ってよい。セッションが切れても棋譜は残るので、
  次に `hmwr sprt run <名前>` を叩けば続きから走る。判定済みなら即座に
  結果を返す

## 3. 終了後

終了コード: 0=H1、1=H0、2=上限まで走って判定に至らず（見送り）。

```
hmwr sprt show <名前>
```

が「コミットのトレーラ」「結果の表」を整形して出すので、これを使う。

- H1採択なら、featコミットの件名にEloを入れ、`SPRT:` トレーラを付けて
  PRを出す（棋力向上テンプレート）。結果（対局数、W-D-L、Elo±CI、LLR）を
  ADRへ追記し、Statusをacceptedにする
- H0採択なら、棄却として結果をADRへ記録する。棄却の記録も成果物
  （CLAUDE.md）。コードはmainに入れない
- **判定が出た日に、draft PRの状態も決める**。H1ならマージ、H0か見送りなら
  `gh pr close` で閉じてブランチを残す。ADRへの記録とPRのクローズを
  同じ作業で行う。2026-09-20にADR-0211のdraftが閉じ忘れで残った
- 上限まで走って判定に至らないなら「見送り」である。真のEloが中点の近くに
  あり、その対立仮説では答えが出ない。局数を積まず、数字と判断をADRへ
  記録する（ADR-0163・0217）。見送りは棄却と別の状態で、後で群にして
  測り直せる（ADR-0160）
- どの結果でも、結果の一次情報はADRとコミットのトレーラに残す。棋譜と
  バイナリは30日で `hmwr clean` が消す（ADR-0189）。`.result` は残る

### マージの本文はファイルで渡す

squashマージのコミット本文が、CHANGELOGとgit logの一次情報になる。組み立てを
シェルの展開に任せない。

```
gh pr merge <PR番号> --squash --delete-branch --body-file <ファイル>
```

`--body "$(printf ...)"` と書くと、本文の `%` をprintfが書式指定として
解釈する。2026-09-02に「NPSが4.29%上がった」でそこから先が切れ、末尾の
`SPRT:` トレーラごと落ちた（issue #455）。件名にEloが入っていたので
CHANGELOGは無事だったが、git logからは結果を機械で拾えなくなっている。

マージの後に `git log origin/main -1 --format=%B` で本文を読み、トレーラが
入っているかを見る。履歴は後から直せないので、確認はその場で行う。

### Eloの読み方

**SPRTが保証するのは「真のEloが中点より上か下か」だけで、点推定の精度では
ない**。逐次検定は閾値を超えた瞬間に止まるので、上振れしたタイミングで
停止しやすく、H1採択時の点推定は真値より高めに偏る。早く決着した実行ほど
CIも広い。

換算率のような精度の要る数値（「速度1%あたり何Elo」など）は、SPRTではなく
局数を固定した測定で求める。逐次停止しなければこのバイアスは入らない。
