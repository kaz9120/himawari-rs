# ロードマップ

着手を決めるときに読む文書。5つの節で構成する。**現在地**は一次情報の置き場を
示す。**注力**はいま力を入れている方向、**運用**は回り続ける手順である。
**次に着手する**はセッションの入口、**候補**は未着手の案の一覧である。
注力は絞り、思いつきの置き場は候補が持つ。

なぜそうしたかは[ADR索引](adr/README.md)、何が入ったかは
[CHANGELOG.md](../CHANGELOG.md)にある。この文書に過去の経緯・変わり続ける
数値・やらないと決めたことは書かない（棄却の記録はADRが持つ）。
着手を決めた案はADRを起こし、候補から消す。

### 制約

- 計算資源は手元の開発機（M4 Pro、RAM 48GB）で、PCの新調はしない。AWSは
  当たったレシピの最終実行と選手権のリハーサルに限る
  （[ADR-0207](adr/0207-roadmap-focus-eval.md)）
- 教師の局面はtanuki- 2024の78.6億局面である（[ADR-0192](adr/0192-tanuki2024-teacher.md)）。
  評価値はdlshogi 2021版の推論1回で付け直す（[ADR-0215](adr/0215-dl-relabel-pilot.md)）。
  付け直しは先頭20億まで済んだ（[ADR-0219](adr/0219-relabel-2b-in-place.md)）。
  開発機の速さは約2,400局面/秒で、残り58.5億に約28日かかる。残りはAWSで
  付け直す方向にした。実験用のアカウントと予算はオーナーが用意する（2026-10-04）。
  自己生成の継続学習は1回+15で頭打ちになった（[ADR-0201](adr/0201-loop-recipe.md)）
- 学習にかかる時間はデータの規模で決まる。78.6億のpsvは293GBあり、ページキャッシュに
  載らない。等価高速化後の実測は48kサンプル/秒で、1エポック50時間かかる。
  dlshogiのラベルでの実験は、1億局面の小規模学習（学習0.6時間＋対局1.9時間）で
  回す。1億の結果は20億へ持ち越せた（ADR-0215の+99.4が、ADR-0219で+113.0）
- 持将棋のルールが2028年の選手権から27点法→24点法へ変わる見込み
  （2026-07-20オーナー共有）。影響するのは宣言勝ちの判定
  （[ADR-0030](adr/0030-nyugyoku-declaration.md)）、自己生成の勝敗ラベル、
  selfplayの入玉局面裁定の3か所である
- x86_64でのperft・ベンチ再計測は持ち越している。選手権のリハーサルで
  AWSを使うときに測る

## 注力

いま注力している方向は1本である（[ADR-0207](adr/0207-roadmap-focus-eval.md)の
棚卸しで絞った）。

### 評価関数の学習と構造

上位との差は棋力そのもので、その本体は評価関数にあると見る。探索は参照
実装への追従が一巡し、8スレッドの並列効率も参照と同等に達した
（[ADR-0202](adr/0202-smp-loss-diagnosis.md)）。探索で発明的な発見を狙うのは
難しい。探索と時間管理の案は候補に置き、後で戻る。

掘り方の材料は実績にある。評価関数の構造は8月後半に7件続けて空振りし、
どれも「ネットは新しい項を使うが、対局に変換されない」という同じ壁に
当たった。当たったのは学習の側である。いちばん大きいのはdlshogiによる教師の
付け直し（[ADR-0222](adr/0222-promote-dl20.md)、現行に+74.8）だった。ほかに教師の
置き換え（[ADR-0192](adr/0192-tanuki2024-teacher.md)、+43.2）、ランキング損失
（[ADR-0185](adr/0185-sibling-ranking-loss.md)、+28.9）、静止化
（[ADR-0136](adr/0136-quiet-teacher-positions.md)、+20.3）がある。

**構造は凍結し、学習側に集中する**（[ADR-0213](adr/0213-freeze-structure-focus.md)、
2026-09-18オーナー判断）。末端ノードで呼ばれる評価関数の骨格は、差分更新が
できる形に縛られている。オーナーが描く「焦点」「役割」「類似局面」はベクトルの
中身の話になる。中身を決めるのはトークンの定義と学習の目的で、後段の形では
ない。候補の評価関数の表は残すが、ADR-0213の測定が終わるまで着手しない。
ラベルの質は量に勝った。dlshogiのラベルの20億が、tanukiのラベルの78.5億に
+67.9で勝っている（[ADR-0219](adr/0219-relabel-2b-in-place.md)）。局面とラベルを
切り離して扱えるようになったので、次に掘るのは**教師の局面集合の作り方**である
（2026-10-04オーナーとの議論）。ラベルは1局面ごとに費用がかかるので、同じ予算で
どの局面を選ぶかが棋力を左右すると見る。最初の問いは、付け直し済みの20億から
1億を選ぶベンチで測る（[ADR-0224](adr/0224-selection-bench.md)）。

学習の測定で守ることは変わらない。検証損失は採否の指標にならず
（[ADR-0158](adr/0158-mirror-factorizer.md)・[ADR-0172](adr/0172-multihot-input.md)）、
採否は対局で決める。

## 運用

回り続ける手順。着手の対象ではなく、止まっていたら再開する。

- **実戦の定点観測**（[ADR-0152](adr/0152-floodgate-cycle.md)）。floodgateの
  棋譜を回収し、評価値系列から問題を掘り、定跡を足す。桂の3段目不成の
  生成漏れ（+11.2 Elo、[ADR-0173](adr/0173-knight-non-promotion-movegen.md)）は
  この観測が見つけた。CSAに残る評価値系列は、再解析より安い診断材料になる。
  次に見るのは定跡の追加（`book seed`）と、崩壊局面の盲点ベンチマーク化
  （[ADR-0191](adr/0191-blindspot-benchmark.md)、大悪手の全量解析の後継）
- **探索定数のSPSA**（[ADR-0143](adr/0143-spsa-tuning.md)、第1群+32.0）。
  再走は毎世代ではなく機を見て行う（大きな構造変更の後や選手権前）。
  残る作業はSEE駒価値を組み込むかの判断と第2群の対象決め
- **実験キュー**（[ADR-0209](adr/0209-workflow-layers.md)）。specとADRをmainへ
  入れて `hmwr exp queue` かIssueフォーム「実験」で積むと、開発機のlaunchdが古い順に1件ずつ
  走らせる。手順は `hmwr` のコマンド列で書く
  （[ADR-0208](adr/0208-hmwr-resource-verbs.md)）。止まっていたら
  `hmwr queue status` と `data/logs/queue-launchd.log` を見る
- **クラウドの定期実行**（[ADR-0209](adr/0209-workflow-layers.md)）。Claude Code
  Routinesが `micro` の消化（毎晩）、巡回（週次）、Stockfishの未採用PRの
  調査（週次）を回す。手順と止め方は `.claude/routines/README.md` にある。
  GitHub Actionsは文書の整合検査とレートの定点記録を週次で回す
- **測定の手順はスキルが持つ**。SPRTはrunning-sprt、ビルド・計測・SPSAは
  himawari-cliを使う
- **細かい改善のIssueサイクル**。小さな気になる点を `micro` ラベルの
  Issueへ即時に切り、実験の待ち時間に消化する。手順は
  micro-improvementsスキルが持つ
- **成果物の掃除**（[ADR-0189](adr/0189-artifact-retention.md)）。月1回を
  目安に `hmwr clean --apply` を回す。保持は30日で、現行の評価関数の系列と
  結果の要約は残る

## 次に着手する

**局面の選び方のベンチ**（[ADR-0224](adr/0224-selection-bench.md)）。付け直し済みの
20億から1億を3通りに選び、重複の除去と決着圏の間引きの効きを対局で測る。20億の
先頭1億では盤面の7.67%が重複し、dlshogiの勝率で決着圏の局面が47.3%ある。
キューで、20億の2周（[ADR-0223](adr/0223-dl20-two-epochs.md)）の後に走る。
結果の読み方は事前登録してあり、次の20億をどう作るかに使う。

**残り58.5億の付け直し**は、AWSのアカウントと予算が決まってから設計する。
付け直しの入力は、ベンチの結果で選び方を決めてから作る。重複除去が効けば、
付け直しの前に重複を除いて費用を削れる。

dl20のネットでは、大差の局面の探索が膨らむ（issue #653）。王手延長に
手数の上限がなく、勝負のついた局面で手数60より深くまで読み続ける。直すなら
探索の変更なのでADRとSPRTが要る。

外から見る役は、公開ページ（`himawari.y-kaz.com`、[ADR-0221](adr/0221-public-site.md)）が持つ。
このリポジトリは公開用データを書き出すところまでを持ち、表示はHidokoで作る。
段A（開発の記録）の形を決めて、Hidokoへ要件を渡すのが次の一手である。
R2のバケットと、放流機のUSIログを運ぶ経路はオーナーに決めてもらう。

開発環境の再設計（[ADR-0220](adr/0220-dev-environment-redesign.md)）は、状態の
出力仕様が入った。残りはコマンドの棚卸し（`sprt` を `match` へ統一）と、記録の
無人化の続きである。

## 候補

未着手の案を1案1行で置く。**やってみたい案だけを書く**。思いついただけの
汎用パラメータや、単独で効く仮説を書けない案は載せない（2026-08-22オーナー方針。
消した案はgitの履歴から掘り起こせる）。着手を決めたらADRを起こして
ここから消す。完了・棄却した案も残さない（経緯と結果はADRが持つ）。

検証手段の略記は、SPRT=マージ判定の対局、loss=検証損失、NPS=速度計測とする。
表の並び順は優先度を表さない。

単発の候補は[ADR-0089](adr/0089-improvement-criteria.md)の3軸（速度・
ノード効率・終盤の正確さ）で選ぶ。どの軸に効くかを示せない候補と、単独で効く仮説を
書けない候補には着手しない。過去にSPRTで棄却した案のうちP3期（駒割評価）の
測定は条件が違い、singular extensionがP3の−16.0からP8で+12.6へ反転した
先例がある。NNUE後の再測定には意味がある。
