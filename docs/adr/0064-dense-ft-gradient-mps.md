# 0064: FT勾配をdenseにし、学習をMPSで回す

- Status: accepted
- Date: 2026-07-26
- 関連ADR: [0040](0040-training-infra-v2.md), [0043](0043-pyo3-bridge.md), [0061](0061-psv-memmap-dataset.md)

## Context

学習データを19億局面へ拡大するにあたり、学習速度が制約になった。
現行構成は41,000 samples/sである。19億局面の1エポックに13時間かかり、
複数エポックやハイパラ比較が現実的でない。

そこで1ステップの内訳を実測した。batch=16384、bench200k.psvの
先頭16384局面を固定入力とし、10回の平均を取った。

| 区間 | 所要 |
|---|---|
| forward | 8.8ms |
| forward + backward | 62.3ms |
| forward + backward + optimizer | 279.6ms |

`SparseAdam.step()` が217msを占めていた。全体の76%である。
forwardは9msにすぎず、計算量そのものは問題ではない。

原因は疎勾配の扱いにある。FTは `nn.EmbeddingBag(sparse=True)` で、
勾配はインデックス付きの疎テンソルになる。batch=16384では
622,592個のインデックスが立ち、うちユニークは40,804個だった。
`SparseAdam` はこれをcoalesceしてから更新するため、
重複の解消にコストがかかる。

データローダは制約ではなかった。1プロセスで117,000 rec/sを出す
（`extract_features` 単体は269,000 rec/s）。4 workerなら計算側の
上限を上回る。

## 選択肢と比較

同一入力・同一バッチで実測した。数値は1ステップあたりの所要と、
そこから換算したスループットである。

| 構成 | fwd | fwd+bwd | +optimizer | スループット |
|---|---|---|---|---|
| 案A: CPU + sparse（現行） | 8.8ms | 62.3ms | 279.6ms | 58,600/s |
| 案B: CPU + dense | 8.7ms | 64.4ms | 75.1ms | 218,000/s |
| 案C: MPS + dense | 7.6ms | 20.5ms | 31.6ms | 518,500/s |
| 案D: MPS + sparse | 7.5ms | 319.4ms | 353.3ms | 46,400/s |

### 案A: 現行維持

変更が要らない。ただし19億局面の学習が13時間/エポックのままで、
実験の回転数が上がらない。

### 案B: CPU + dense

FTを `sparse=False` にし、通常の `Adam` で更新する。
optimizerのコストが217msから11msへ落ちる。3.7倍速い。
デバイス依存の数値差が出ない利点がある。

### 案C: MPS + dense

案Bに加えてMPSへ載せる。backwardが64.4msから20.5msへ落ち、
合計31.6msになる。現行比8.8倍である。

### 案D: MPS + sparse

疎勾配のMPS実装が未成熟で、backwardがCPUの5倍遅い。現行より遅い。

## Decision

案CをMPS上で採る。ただしoptimizerは素の `Adam` ではなく、
自前の `MaskedAdam` を使う。`--dense-ft` と `--device mps` で選ぶ。

決め手は8.8倍という差の大きさである。19億局面の1エポックが
13時間から2時間の水準に変わり、複数エポックとハイパラ比較が
実験計画に入る。

素の `Adam` をそのまま使う案は退けた。`SparseAdam` と更新の
意味論が違うためである。`SparseAdam` はそのステップに出現した行
だけモーメントを進める。`Adam` は全125,388行を毎ステップ更新する
ので、出現しなかった行もモーメントの慣性で動く。HalfKPの特徴は
疎で、1局面あたり38個しか立たない。

この差は小さいデータでは現れなかった。20M局面の比較では
素のAdamが0.53934、現行が0.53994で、denseの方が良い。
370M局面で回すと逆転した。

| 構成 | best valid loss | 所要 |
|---|---|---|
| CPU + SparseAdam（現行、halfkp_370M） | **0.50947** | 6354秒 |
| MPS + 素のAdam | 0.51065 | 868秒 |
| MPS + MaskedAdam | 0.50959 | 1151秒 |

素のAdamは0.00118劣った。学習曲線を見ると、step 8000までは
現行と互角で、lrが下がる後半に差が開く。稀にしか出現しない行の
重みが、モーメントの慣性で削られるためと見られる。

そこで `training/optim.py` に `MaskedAdam` を書いた。勾配の行が
全要素ゼロかどうかで出現を判定し、出現した行だけモーメントと重みを
更新する。疎テンソルを作らないのでMPSで動く。bias correctionの
掛け方も `SparseAdam` に合わせた（epsを平方根の外に出す点が
`torch.optim.Adam` と違う）。両者が同じ更新をすることは、
200ステップ後の重みの最大差7.45e-08で確認した。fp32の丸め誤差の
範囲である。

`MaskedAdam` は現行と同等の0.50959を出し、所要は5.5倍速い。
残る0.00012の差は実行間のばらつきと区別できない。

MPS自体の数値も確かめた。同一バッチのFT勾配はCPUと相対差
1.8e-06で一致し、出現しなかった行の移動量はゼロだった。

## Consequences

- 学習の上限がデータローダへ移る。計算側は518,500 samples/sで、
  4 workerのローダ（実測468,000 rec/s相当）とほぼ拮抗する。
  ローダ側の改善は[ADR-0065](0065-large-scale-dataloader.md)で扱う
- FT重みは125,388×256 = 3210万パラメータである。dense化により
  勾配128MBとAdam状態256MBが常駐する。48GBのunified memoryでは
  問題にならない
- MPSはfp32で動き、CPUと数値が完全には一致しない。学習結果の
  再現性はデバイス指定に依存する
- `MaskedAdam` は自前の実装であり、PyTorchの更新に追随する保守が要る。
  行単位のマスクに32Mパラメータ分の要素演算が加わり、1ステップは
  素のAdamより12ms重い。それでも現行の5.5倍で回る
- 疎更新に戻す条件は、19億局面の学習が `halfkp_370M` に対して
  SPRTで有意勝ちしなかった場合とする。速度と引き換えに精度を落とす
  取引はしない
