# 0076: LMRのリダクションを固定小数化する（ttPv項は棄却）

- Status: accepted（固定小数化のみ。ttPv項は棄却）
- Date: 2026-07-28
- 関連ADR: [0028](0028-pruning-extensions.md), [0055](0055-lmr-terms.md), [0022](0022-transposition-table.md), [0074](0074-feature-verification.md)

## Context

本エンジンのLMRは `r = 0.5 + ln(depth)·ln(count)/2.25` を整数へ丸めた
表引きで、調整項は「PVノードなら-1」の1つしかない。やねうら王は同じ
基礎式に11項を加減する。

[ADR-0055](0055-lmr-terms.md)でimproving項とhistory項を等重み±1で加える
案を試し、960局で-9.0の不採択だった。原因は項の選択ではなく粒度にある。
リダクションが整数のため、最小の調整単位が1である。基礎式の値は
depth 8・count 8で約2.5であり、そこへ±1を足すのは40%の変更にあたる。
細かい重み付けができない。

やねうら王は1024倍の固定小数で扱い、各項を数百から数千の重みで加減する。
`r/1024` で整数の深さに落とすため、実効的には小数のリダクションになる。

スケールが一致するかを確認した。本エンジンの式を1024倍すると `512 + 455·ln(d)·ln(c)` になる。
やねうら王の `reductions[i] = (2763/128)·ln(i)` からは
`reductionScale ≈ 466·ln(d)·ln(mn)` が出る。係数は455対466で2.4%しか
違わない。したがって、固定小数化すればやねうら王の項の重みを
そのまま使える（[ADR-0074](0074-feature-verification.md)が求める
スケール前提の確認）。

## 選択肢と比較

### 案A: 固定小数化とttPv項を1つのSPRTで入れる

固定小数化は単体では等価変更に近く、棋力に現れにくい。
[ADR-0028](0028-pruning-extensions.md)は「単体では強さに現れない配管は、
それを使う最初の機能と合わせて1つのSPRTで検証してよい」と定めている。

最初の項にはttPvを選ぶ。置換表にPVフラグを保存済みでありながら
探索で一度も読んでいないため、配管が不要である
（`tt.rs` の `TtData::pv`、[ADR-0022](0022-transposition-table.md)）。
やねうら王での重みも -2819 から -5632 と大きく、効果が見えやすい。

### 案B: 固定小数化だけを非劣性SPRTで入れる

変更が1つで切り分けやすい。ただし丸めの違いしか生まないため、
elo0=-5/elo1=0 の非劣性判定になる。差が小さいぶん対局数はかさむ。
[ADR-0072](0072-history-pruning.md)の再挑戦を280局で打ち切った経緯からも、
効果の見えない検証に時間を使うのは避けたい。

### 案C: 項を一度に複数入れる

cutNode・statScore・moveCountなども同時に入れる。効果は最大だが、
1機能=1SPRTの規約に反する。H0のとき原因を切り分けられない。
cutNodeとstatScoreは配管が要るぶん、変更も大きくなる。

## Decision

案Aを採る。

### 固定小数化

リダクション表を1024倍の整数で持つ。

```
r = 1024·(0.5 + ln(depth)·ln(count)/2.25)
PVノードなら r -= 1024
実際の削り幅は (r/1024) を0以上に丸めた値
```

`is_pv` の -1 は -1024 に対応する。ここまでは既存の挙動と等価である。

### ttPv項

置換表のPVフラグが立つ局面は、過去にPV上で探索された。そこでは
リダクションを弱める。やねうら王の式から、本エンジンに存在しない
`cutNode` の項を除いて用いる。

```
ttPv が真なら
  r -= 2819 + is_pv·973 + (tt_value > alpha)·905 + (tt_depth >= depth)·935
```

重みはやねうら王の値をそのまま使う。上記のとおり基礎式のスケールが
2.4%差で一致するため、換算は挟まない。

### 検証

[ADR-0074](0074-feature-verification.md)の規約に従い、SPRTの前に
固定深さでのノード数変化を測る。あわせてttPv項が実際に適用される割合
（LMR適用時にttPvが真である割合）を測り、0.1%を下回らないことを確かめる。

SPRTは[ADR-0028](0028-pruning-extensions.md)の既定条件。elo0=0、elo1=5。

H0だった場合は、固定小数化とttPv項のどちらが原因かを切り分ける。
固定小数化のみを非劣性SPRTにかけ、等価であることを確かめてから
項を選び直す。

## 結果（2026-07-28）

### ttPv項はH0で棄却

235ペア（470局）で Elo -43.8 [-74.9, -13.5]、LLR -0.98。信頼区間の上限が
負であり、有意に悪い。打ち切った。

原因はバランスの欠如である。ttPv項はリダクションを弱める方向にしか
働かない。やねうら王では cutNode 項（`+3611 + 985·!ttMove`）が反対方向へ
効いて釣り合いを取っているが、本エンジンには cutNode の概念がない。
片側だけを入れたため、全体のリダクションが不足して探索が浅くなった。

機能検証でも兆候は出ていた。ノード数が2局面で+69%、+85%と増えており、
「同じ時間で浅くなる」形だった。ただし1局面は-29%で増減が混在したため、
棄却の判断はSPRTに委ねた。

### 固定小数化は完全な等価変更だった

ttPv項を外したビルドで機能検証を行うと、3局面すべてでノード数・評価値・
最善手が変更前と一致した。

| 局面 | 変更前 | 固定小数化のみ |
|---|---|---|
| 1 | 616,335 | 616,335 |
| 2 | 4,839,402 | 4,839,402 |
| 3 | 335,817 | 335,817 |

丸めの違いすら生じていない。探索が同一である以上、棋力も同一である。
[ADR-0028](0028-pruning-extensions.md)は等価リファクタに非劣性SPRT
（elo0=-5/elo1=0）を求めるが、本件は挙動の同一性を測定で直接示せたため、
SPRTを省いて取り込む。

[ADR-0074](0074-feature-verification.md)の機能検証は「変わったこと」を
確かめる手順として定めたが、「変わらないこと」の証明にも使える。
等価リファクタの検証コストを下げる用途として記録しておく。

## Decisionの改訂

固定小数化のみを採る。ttPv項は入れない。

ttPv項の再挑戦は、cutNode を導入して反対方向の項を揃えてから行う。
単独では釣り合いが取れない。[ROADMAPの候補](../ROADMAP.md#候補)へ依存関係とともに
残す。

## Consequences

以後のLMR項追加が1項=1SPRTで積めるようになる。ROADMAPの候補に残る項目は、すべてこの土台の上に乗る。rootDelta・
moveCount・correction値・cutNode・ttCapture・cutoffCnt・ttMove一致・
statScore・allNodeである。
[ADR-0055](0055-lmr-terms.md)で不採択になったimproving項とhistory項も、
粒度を得たうえで再挑戦できる。

リダクション表の型がu8からi32へ変わる。表は64×64で、メモリの増加は
16KBに満たない。

ttPvを読むことで、置換表の`pv`フラグが初めて探索へ影響する。
[ADR-0022](0022-transposition-table.md)が保存していた情報の回収点になる。

`r`が負になりうる。0で下限を切るため、リダクションなしと同じ扱いになる。
延長側へ振る設計（やねうら王も同様に負のrはd増加に使わない）は
本ADRの範囲外とする。
