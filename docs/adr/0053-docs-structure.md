# 0053: ドキュメントの役割分担とメンテナンスルールを定める

- Status: accepted
- Date: 2026-07-21
- 関連ADR: [0001](0001-adr-process.md), [0027](0027-sprt-framework.md), [0042](0042-training-log-registry.md)

## Context

ROADMAP.mdが「現在地」「フェーズ表」「フェーズ別のやること」
「各フェーズの成果」「直近の残作業」「実測の記録」を1ファイルに
抱え、表が分裂して管理コストが上がっている。P8の探索改善
キャンペーンでSPRT結果の行が増え続け、悪化が加速している。
時系列（起きた順）とフェーズ別（構造）のどちらを軸にするかが
曖昧なことが根本原因で、軸を文書ごとに1つに固定する。

## 選択肢と比較

### 案A: 文書ごとに軸を1つに固定し、計測ログを分離する

- ROADMAP.md: 軸=未来。現在地・フェーズ表・残作業だけに
  スリム化する
- docs/RESULTS.md（新設）: 軸=時系列。計測・検証結果の
  append-onlyログ。過去の書き換えをしない
- ADR: 軸=決定単位（現行どおり）
- ROADMAPの候補 / DATASETS.md: 現行どおり（候補台帳／データ台帳）

### 案B: ROADMAP.mdをフェーズ別に全部持たせる（現状の整理のみ）

1ファイルで完結する利点はあるが、時系列の計測ログと前向きの
計画が同居する構造は変わらず、増え続ける行で再び崩れる。

### 案C: 実験レジストリ方式（ADR-0042の再来）

機械可読なレジストリはP6でrejected済み（過剰と判断）。
人間が読む1行ログで足りる。

## Decision

案Aを採用する。各文書の役割と更新タイミングを次のとおり
固定する。

| 文書 | 軸 | 持つ情報 | 更新タイミング |
|---|---|---|---|
| ROADMAP.md | 未来 | 現在地、フェーズ表（1行/フェーズ）、直近の残作業 | フェーズ出入り、残作業の増減 |
| docs/RESULTS.md | 時系列 | 計測・検証の1行ログ（日付、対象、条件、結果、コミット） | SPRT判定、NPS計測、外部照合のたび |
| docs/adr/ | 決定 | 設計判断と経緯 | 決定・棄却のたび |
| docs/ROADMAPの候補 | 候補 | 1案1行の受け皿 | 追記・ADR化・棄却のたび |
| docs/DATASETS.md | 資産 | データの所在と前処理 | 取得・生成のたび |
| README.md | 入口 | 人間向けの概要・ビルド・学習・対局の手順、workspace構成 | 手順が変わったとき |
| CLAUDE.md | 規約 | エージェント向けの作業規約（ゲート運用、コミット規律、配置ルールの要点）。詳細は各文書へリンク | 規約が変わったとき |

### data/ の配置ルール

data/は現在平置きで、生データ・加工済みデータ・ネットが
混在している。次の配置に分ける（すべてgitignore対象のまま）。

```
data/
  raw/<データセット名>/   DLした生データ（例: raw/hao_depth9/*.bin）
  train/                  加工済みpsv（train_*.psv、valid_*.psv、bench*.psv）
  nets/                   学習済みネット（<実験名>.hmwr[.best]）
  sprt/                   selfplayの棋譜ログ（jsonl。2026-07-23追記）
  bin/                    比較用に残すビルド済みバイナリ
  book/                   定跡db
  logs/                   スクリプトの実行ログ（2026-08-08追記。ADR-0149）
```

- 学習チェックポイント（*.pt）はdata/に置かず、従来どおり
  training/checkpoints/に置く
- ネットのファイル名は実験名を含める（例: halfkp_180M.hmwr.best）。
  hao_v1〜v6のような世代名だけの命名はしない
- 物理的な移設は実行中のSPRT（EvalFileがdata/直下を参照）の
  完了後に行い、DATASETS.md・README.mdのパスも同時に更新する

運用ルール:
- 同じ情報を2文書に書かない。参照はリンクで行う
  （例: ROADMAPの現在地からRESULTSの該当行へ）
- RESULTS.mdはappend-only。訂正が必要なら訂正行を追記する
- フェーズ表はROADMAP.mdを正とする。ADR索引（adr/README.md）
  冒頭の重複したフェーズ表は削除する
- ROADMAPにあった「各フェーズの成果」「実測の記録」は
  RESULTS.mdへ移設する。移設時に情報は削らない

## Consequences

- ROADMAP.mdが1画面に収まり、現在地の把握が速くなる
- 計測結果はRESULTS.mdをgrepすれば時系列で追える。コミット
  メッセージとの二重管理は残るが、コミットは変更単位・
  RESULTSは計測単位で役割が違うため許容する
- 移設の初回コストが1回かかる（本ADR採択時に実施）
- 見直しトリガー: RESULTS.mdが数百行を超えて読みにくく
  なったら、年別またはフェーズ別の分割を検討する
