# 0221: 開発の記録と実戦のテレメトリを、himawari.y-kaz.com で公開する

- Status: accepted（2026-09-24、方向はオーナーが決めた。データの形は段ごとに詰める）
- Date: 2026-09-24
- 関連ADR: [0152](0152-floodgate-cycle.md), [0180](0180-hmwr-cli-in-python.md), [0182](0182-readme-audience.md), [0199](0199-roadmap-inventory.md), [0220](0220-dev-environment-redesign.md)

## Context

[ADR-0220](0220-dev-environment-redesign.md)の3段目で、状態を見るポータルを
`portal/` に作った。オーナーはそれを開いて、方向を変えることにした
（2026-09-24）。手元の運用画面ではなく、誰でも読める公開ページにする。

ADRもコードもすでにGitHubで公開している。ただ、読むにはリポジトリを
たどる必要がある。公開ページでは、次の問いに1か所で答える。

- これまで何を試し、SPRTでどうなったか
- 次に何をしようとしていて、今どの実験が走っているか
- floodgateで今どう戦っていて、レーティングはどう動いてきたか
- 1局の中で、エンジンが何をどこまで読んでいたか

最後の問いは、floodgateのページでは答えられない。floodgateのCSAには、
各手の評価値と最終の読み筋だけが残る。反復深化の途中で読み筋がどう
入れ替わったか、何ノードを何NPSで読んだか、時間の計画と実績はどうだったかは
残らない。オーナーはこれを1局ごとのUSIログから復元し、テレメトリとして
扱いたいと考えている。

同じログは開発にも要る。切れ負けの切り分け（Issue #545）は、放流機の
USIログがないために止まっている。公開のための収集が、そのまま診断の
材料になる。

## 選択肢と比較

### 案A: ポータルを公開用に作り替え、Tunnelで外へ出す

`portal/` の画面を公開向けに直し、開発機からCloudflare Tunnelで出す。
開発機が止まるとページも止まる。開発機への入口を外に開けるので、守りも要る。

### 案B: 公開用のデータを書き出し、表示はHidokoのアプリが担う

このリポジトリは公開してよいデータだけをCloudflare R2へ置く。表示は
オーナーの個人開発の基盤（Hidoko、`~/Hobby/hidoko`）のアプリとして作り、
`himawari.y-kaz.com` で配信する。開発機からは外向きの書き込みしか
起きないので、開発機に入口を作らない。開発機が止まっても、最後に置いた
データでページは見える。

### 案C: 表示もこのリポジトリで作る

案Bの表示部分を、このリポジトリの中に作る。Hidokoのデザイン基盤
（packages/ui）を使えず、ドメインの配信も別に用意することになる。

## Decision

案Bを採る。決め手は、開発機に入口を作らずに済むことと、見せ方をHidokoの
基盤で作れることである。

### 1. 役割を分ける

| 担当 | 持つもの |
|---|---|
| このリポジトリ | 公開用データの生成と、R2への書き込み。エンジンと補助のコードに閉じる |
| Hidoko（`apps/himawari`） | R2を読んで表示する。実装はHidokoのリポジトリで、別のセッションが行う |

2つの間の境界は、R2に置く版付きのJSONだけにする。Hidokoはこの
リポジトリもfloodgateも直接読まない。形を変えるときは版を上げる。

### 2. ADR-0220の4段目と5段目を取りやめ、portal/ を消す

外から見る役は公開ページが持つ。公開ページは読むだけで、操作はしない。
TunnelとAccess（4段目）と遠隔操作（5段目）は要らなくなる。`portal/` も
消す。このリポジトリはエンジンと補助のコードに絞る（オーナー判断）。

`hmwr status` と状態ファイル（ADR-0220の1・2段目）は残す。手元で状況を
見る入口であり、公開用データの材料にもなる。

### 3. 公開する情報と、しない情報

公開するものを名指しで決め、それ以外は出さない。書き出す側（`hmwr`）で
項目を選び、公開しない項目はR2へ届く前に落とす。

| 公開する | 公開しない |
|---|---|
| ADRの本文と索引、ROADMAPの注力・次に着手する・候補 | ディスクの空き・pid・パス・ログの置き場 |
| SPRTの結果（Elo・信頼区間・局数・LLR・判定） | 開いているPR、キューの常駐の状態 |
| 実験の一覧とステップの進み具合、学習の損失の推移 | 放流機やネットワークの設定（IP・ホスト名） |
| floodgateの対局一覧・棋譜・レーティングの推移 | USIログの `setoption` のうち、パスを含むもの |
| 1局ごとのテレメトリ（下の4） | 教師データ・ネットの実体（ファイル） |

### 4. 実戦のテレメトリ

放流機は `DebugLogFile` でUSIの入出力を常時残す。行ごとにミリ秒の
時刻が付くので、CSAの開始時刻と着手で局ごとに切り出せる。1局を手ごとに
構造化し、次を持たせる。

- 反復ごとの `info`。深さ・選択的深さ・評価値・ノード数・NPS・hashfull・経過時間・読み筋
- 時間の計画と実績（`info string time plan`）、`go` の持ち時間
- `bestmove` と `ponder`、ponderhitの有無
- CSAの着手・消費時間と、手番の対応

局の要約（平均NPS・平均深さ・読み筋が最後に入れ替わった反復など）も付ける。
対局の途中経過は出さず、終わった局だけを置く。対局中の読み筋を相手に
見せないためである。

### 5. 段階

各段で、書き出すJSONの形をこのADRの経過に書き足す。Hidokoへの依頼は、
その段の形が決まってから渡す。

| 段 | 内容 | 前提 |
|---|---|---|
| A | 開発の記録。ADR・ROADMAP・SPRTの結果・実験の一覧を書き出す | R2のバケットと書き込み用のトークン |
| B | floodgate。対局一覧・棋譜・レーティングの推移・CSAの評価値と読み筋 | Aと同じ |
| C | テレメトリ。放流機のUSIログを局ごとに構造化する | 放流機のログを開発機へ運ぶ経路 |
| D | 今の実験。状態ファイルから公開してよい項目を数分ごとに書き出す | Aと同じ |

### 6. オーナーに決めてもらうこと

- R2のバケットの作成と、書き込み用トークンの発行（Cloudflareのアカウント操作）
- 放流機のログを開発機へ運ぶ経路。放流機はWindowsのSurface Pro 9で、GUIから
  エンジンを動かしている。共有フォルダやクラウドの同期フォルダが候補になる
- 公開を始める時期。段Aの形が決まれば、Hidoko側の実装を始められる

## 公開ページの要件（Hidokoへの依頼の元）

Hidokoのセッションへ渡す要件である。データの形は段ごとに経過へ書き足し、
ここは画面の要件だけを持つ。

- 読み手は、コンピュータ将棋に関心のある人とオーナー自身である。スマホでも読める
- 読むだけで、操作の機能は持たない。ログインもない
- 画面は5つを想定する
  - 概要。今の注力・走っている実験・floodgateの直近の成績を1画面で
  - 取り組み。ADRの一覧と本文。テーマ別に引け、SPRTの結果（Elo）を並べる
  - 実験。走っている実験のステップと進み具合、終わった実験の結果
  - floodgate。レーティングの推移、対局一覧（相手・勝敗・手数・終局理由）
  - 棋譜。盤面と着手に合わせて、評価値のグラフ、各手の反復ごとの読み筋の推移、深さ・NPS・時間の計画と実績を見せる
- 数値の読み方をページ内で説明する。Eloの信頼区間、LLR、見送りの意味など

## Consequences

- 開発機にも放流機にも、外からの入口を作らない。書き込みは外向きだけになる
- 公開用データの形が、このリポジトリの新しい外部インターフェースになる。
  版を付け、壊す変更は版を上げて行う
- 放流機が `DebugLogFile` を常時取るようになる。1局あたりのログは数MBと
  見込み、放流機のディスクは日毎のファイルを消して保つ（README の手順）
- ADRが公開ページの本文になる。内部向けの書き方のままでよいが、読み手に
  外の人が加わる。用語を自然な技術用語へ揃えた2026-09-23の作業（#608）が
  前提になる
- 見直しのトリガーは、R2の読み書きの費用が無料枠を超えたときと、公開した
  情報に問題が見つかったときである。後者は、その項目を書き出しから外す
