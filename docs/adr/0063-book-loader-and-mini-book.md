# 0063: 定跡ローダと最小規模の定跡生成

- Status: accepted
- Date: 2026-07-25
- 関連ADR: [0060](0060-opening-book-policy.md), [0019](0019-usi-architecture.md), [0033](0033-ponder.md), [0032](0032-multipv.md)

## Context

ADR-0060で定跡の方針を決めた。定跡は持つ、読み込みを先に入れる、
形式はやねうら王のdb互換、データは配布物に含めない、の4点である。
本ADRはその読み込みと、最小規模の定跡生成を決める。

floodgateの実測（2026-07-24〜25、30局）では、初手に18秒を消費して
いた。負け11局はすべて使用可能な時間の90%以上を使い、終盤10手が
7〜9秒に落ちている。序盤の数手を定跡で置き換えれば、その分がまるごと
終盤に回る。初手から数手だけの小さな定跡でも、30〜50秒の節約になる。

「まず小さく作って動かす」ことを優先する。大規模な定跡の生成、
定跡の掘り下げ、合流検出、千日手回避といった論点は本ADRでは決めない。

## 選択肢と比較

### 定跡を引く層

#### 案A: USI層で引く

`crates/usi/src/main.rs` の `go` 処理（247行〜）で、探索を開始する前に
定跡を引く。ヒットしたら `bestmove` を直接返し、ThreadPoolを起動しない。
探索器に定跡の概念が入らない。

#### 案B: 探索器（engine）で引く

`ThreadPool::go` の中、あるいは `iterate()` の冒頭で引く。探索器が
定跡を持つため、selfplayツールなど他の利用側からも透過的に効く。
関心が混ざる。

### 定跡手の選択

#### 案C: 評価値が最大の手を選ぶ

決定的に動く。同じ相手と同じ進行を繰り返す。

#### 案D: 出現回数や評価値で重み付けしてランダムに選ぶ

進行が散る。floodgateで同じ相手に同じ負け方を繰り返さない。乱数の
分だけ再現性が落ちる。

## Decision

案Aと案Cを採用する。

USI層で引くのは、探索器に定跡を持ち込まないためである。定跡は
「思考する前に答えを返す」機構で、探索アルゴリズムとは無関係に扱える。
ponderとの相互作用（ADR-0033）もUSI層で閉じる。

手の選択は評価値最大の決定的な方式にする。ランダム化は進行を散らす
利点があるが、まず小さく作って動かす段階では再現性を優先する。
必要になれば別ADRで足す。

### 定跡ファイルの形式

やねうら王のdb形式に互換とする。テキストで、局面ごとに次の形を取る。

```
#YANEURAOU-DB2016 1.00
sfen lnsgkgsnl/1r5b1/ppppppppp/9/9/9/PPPPPPPPP/1B5R1/LNSGKGSNL b - 1
7g7f 3c3d 42 24 1
2g2f 8c8d 38 24 1
sfen <次の局面>
...
```

`sfen` 行に続けて、候補手を1行1手で並べる。各行は
`指し手 相手の予想応手 評価値 探索深さ 出現回数` である。sfen行の手数は
1に正規化する（局面の同一性を手数に依存させないため）。

### ローダ

`crates/usi/src/book.rs` に置く。起動時ではなく、`BookFile` が設定された
時点でファイル全体を読み、`HashMap<String, Vec<BookEntry>>` に載せる。
キーは手数を除いたsfen文字列とする。Zobristキー（ADR-0015）で引くほうが
速いが、db形式の外部資産をそのまま読めることを優先する。数百局面の
規模では文字列比較のコストは問題にならない。

### USIオプション

| 名前 | 型 | 既定 | 意味 |
|---|---|---|---|
| `BookFile` | string | （空） | 定跡ファイルのパス。空なら定跡を使わない |
| `BookDepth` | spin | 24 | この手数を超えたら定跡を引かない |

既定を「定跡なし」にするのは、過去の計測結果（NPS、bench、SPRT）との
比較可能性を保つためである（ADR-0060）。

### 定跡ヒット時の挙動

`go`（ponderでない）を受けたとき、`game_ply <= BookDepth` かつ定跡に
局面があれば、評価値最大の手を `bestmove` として即座に返す。ThreadPoolは
起動しない。`info` 行は `info string book hit` の1行だけ出す。

ponderは行わない。定跡エントリの予想応手をponder手として返す案もあるが、
定跡が続く限りponderの価値は小さい。定跡から外れた局面では通常どおり
探索とponderが動く。

`go ponder` を受けたときは定跡を引かない。相手の手番を読む処理であり、
定跡で答えるべき局面ではない。

### 生成ツール

`crates/tools/src/bin/book.rs` に `book gen` を作る。

```
book gen --out data/book/mini.db --eval data/nets/halfkp_370M.hmwr.best \
         --ply 8 --width 2 --depth 24
```

平手初期局面から幅優先で展開する。各局面をMultiPV=`width`（ADR-0032）で
深さ`depth`まで探索し、上位`width`手を記録する。記録した各手を指した
局面を、`ply`に達するまでキューに積む。同一sfenの局面は一度だけ探索する。

規模は `width=2, ply=8` で内部ノード255・葉256の計511局面になる。

探索はThreadPool経由でLazy SMP（ADR-0031）を使う。深さ24の初期局面で
単スレッド48.5秒に対し8スレッドで9秒と、5.4倍速くなった。

置換表は局面をまたいで再利用する。BFSで親から子へ展開するため、親の
探索で読んだ子局面の情報がそのまま効く。TTのエントリは深さ付きなので、
浅い探索の結果が深い探索に流用されることはなく、品質は下がらない。
ただし探索順序への依存が生じる。BFSの順序を変えると結果が変わりうる。

先手番・後手番の両方の局面を含める。自分の手番の局面だけでは、相手の手を
経由して到達できないためである。

### 検証

SPRTでは測れない。ADR-0027の枠組みは `openings/` の開始局面から対局を
始めるため、平手初期局面の定跡が使われない（ADR-0060で確認済みの
非対称性）。

代わりに次の3点を確認する。

1. `BookFile` 未指定で、探索のノード数とbestmoveが変わらないこと
2. 定跡ヒット時に探索が起きず、bestmoveが定跡ファイルの評価値最大手と
   一致すること
3. floodgate条件（300秒＋10秒加算）で初手から数手を指させ、消費時間が
   0秒近くになること。ADR-0059の実測で使った手順を流用する

棋力への効果はfloodgateの実戦成績で見る。ただし数十局では有意差が出ない
ため、定跡投入の前後で「終盤10手の平均消費時間」を比較する。これは
負け11局に共通していた7〜9秒という指標で、時間が終盤に回ったかを直接
測れる。

## Consequences

- 序盤の数手で思考時間が0になり、その分が終盤に回る。ADR-0059の
  難易度スケールと効果は加算的である
- 定跡から外れた直後の局面は、自分の探索で作った局面なので評価が
  極端に外れることはない。ただし相手が定跡外の手を指した場合、
  そこから先は通常の探索になる
- 定跡の規模が小さいため、`BookDepth=24` でも実際に使われるのは
  最初の8手程度である。定跡を掘り下げるかは実戦の結果を見て決める
- 生成は非決定的である。Lazy SMPはスレッド間の探索順序が実行ごとに
  変わるため、同じコマンドでも定跡の内容が変わりうる。深さ24の初期局面
  では、単スレッドが2g2f（評価18）、8スレッドが6i7h（評価17）を最善と
  した。序盤は候補手の評価差が小さく、順位が入れ替わりやすい。
  定跡は今後も繰り返し作り直すため、再現性より生成効率を優先する
  （2026-07-25オーナー判断）。`--threads 1` は必要になったときの逃げ道
  として残す。生成された定跡ファイル自体は固定なので、対局中の挙動は
  決定的である
- 決定的に手を選ぶため、同じ相手との対局で同じ進行が繰り返される。
  floodgateで特定の相手に不利な変化に入ると、繰り返し負ける危険がある。
  発生したらランダム化を別ADRで検討する
- db形式互換にしたので、将来やねうら王等の公開定跡を試せる。ただし
  ライセンスの検討はそのときに行う（ADR-0060）
- 定跡ファイルはHashMapに全展開する。数百局面では無視できるが、
  数百万局面の公開定跡を読むとメモリを圧迫する。その時点でZobrist
  キー化やmmapを検討する
