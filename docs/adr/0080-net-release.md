# 0080: 学習済みネットをGitHub Releaseで独立に配布する

- Status: accepted
- Date: 2026-07-28
- 関連ADR: [0069](0069-release-notes-automation.md)（配布方針を改める）, [0037](0037-nnue-file-format.md), [0071](0071-release-please.md)

## Context

[ADR-0069](0069-release-notes-automation.md)は「評価関数はリリースに
含めない」と決めた。リリースをバイナリと評価関数の組にすると、
バイナリだけの更新でも巨大なファイルを再添付することになるためである。
ADR索引のバックログには「学習済みネットの管理・配布方法」が
未起草のまま残っている。

この判断を見直す必要が生じた。開発機をApple M4 ProからWindows機
（Core i7-1255U）へ移す。学習済みネットはリポジトリに含めず
（`data/` はgitignore）、再現にも149分以上かかるため、
マシン間で受け渡す手段が要る。

現状はローカルファイルとしてしか存在しない。ファイルサイズは
FT256で61MB、FT512で122MBである。GitHub Releaseのアセット上限
（1ファイル2GB）に対して十分小さい。

## 選択肢と比較

### 案A: バイナリのリリースへ同梱する

[ADR-0069](0069-release-notes-automation.md)が退けた案である。
release-pleaseはSPRT採択のたびにリリースを作るため、ネットの更新頻度
（数週間に1度）と釣り合わない。同じ61MBを何十回も再添付することになる。

### 案B: ネット専用のリリースを独立したバージョン体系で作る

タグを `net-v<N>` とし、バイナリの `v0.7.x` とは別系統にする。
ネットを学習したマシンから `gh release create` で直接作る。CIは介さない。

更新頻度の差を吸収できる。バイナリのリリース一覧にネットが混ざるが、
タグのプレフィックスで区別できる。

### 案C: 外部ストレージ（HuggingFace等）へ置く

HuggingFaceはモデル配布の標準的な置き場で、大きなファイルにも向く。
教師データの取得元でもある。

ただしアカウントとトークンの管理が増える。GitHubは既にPATを
設定済みで（[ADR-0071](0071-release-please.md)）、`gh` CLIも入っている。
61MBならGitHubで足りる。

## Decision

案Bを採る。

### バージョン体系

タグは `net-v<N>` とする。`N` は1から始まる単調増加の整数。
semverは使わない。ネットに「後方互換」の概念がなく、MINORとPATCHを
分ける基準がないためである。

バイナリのタグ `v0.7.x` とはプレフィックスが違うため、release-pleaseの
動作に干渉しない。同ツールはmanifestとsemverタグを見る。

### 配る条件（2026-08-08に追記）

**SPRTでH1採択され、現行構成になったネットだけを配る。** 配布物は
「これを使えば現行の棋力が出る」という約束である。実験用のネットは
その約束にならない。3億局面の測定台で作るネット
（[ADR-0127](0127-net-shape-bench.md)以降で常用）は、条件の比較にしか
使わないので配らない。

番号は現行構成になった順に1つずつ増やす。**棄却したネットは番号を
消費しない。** 番号の欠番があると「消されたリリースがある」と読まれる。

**過去のリリースは消さない。** SPRTの再現には対戦相手のネットが要る。
`data/bin/` のバイナリと同じ扱いで、比較の土台として残す。

ファイルのフォーマット版（[ADR-0037](0037-nnue-file-format.md)の版番号）と
`net-v<N>` は別物である。前者はファイルの読み方、後者は配布の番号を表す。
1つのフォーマット版で何世代も配ることがあり、逆にフォーマット版が上がっても
棋力が変わらなければ配らない。

### リリースの作り方

学習を回したマシンから `scripts/release-net.sh` で作る。CIは介さない。
学習の成果物はそのマシンにしか存在せず、CIへ渡す手段がないためである。

```
scripts/release-net.sh <netファイル> <バージョン番号> [追記するノート]
```

スクリプトは次を行う。

1. ネットのファイルからlineage文字列を読む（[ADR-0037](0037-nnue-file-format.md)の
   ヘッダに埋まっている。学習データ・局面数・step・valid loss・
   バッチサイズ・lr・λが入る）
2. リリースノートを組み立てる
3. `gh release create net-v<N> --latest=false` でアセットを添付する

`--latest=false` を必ず付ける。GitHubの「Latest」はタグの新しさで決まる
ため、これを省くとネットのリリースがバイナリのリリースを覆い隠す。
利用者が最初に見るのはエンジン本体であるべきである。

### アセット名

`data/nets/` での実験名をそのまま使い、`.best` を外す。
`halfkp_1900M_fact.hmwr.best` は `halfkp_1900M_fact.hmwr` として配布する。
`.best` は学習中のベストチェックポイントを指す作業上の接尾辞であり、
配布物には要らない。

### リポジトリでは管理しない

`data/nets/` はgitignoreのままとする（[ADR-0053](0053-docs-structure.md)）。
Gitはバイナリの差分を扱えず、61MBのファイルを履歴に積むと
クローンが重くなる。

どのリリースがどのネットかは、リリースノートとRESULTS.mdで追う。

## Consequences

マシン間でネットを受け渡せるようになる。新しい開発機では
`gh release download net-v<N>` で取得できる。

[ADR-0069](0069-release-notes-automation.md)の「評価関数はリリースに
含めない」は、「バイナリのリリースには含めない」へ意味を狭める。
独立したリリースとしては配布する。

リリース一覧にネットが混ざる。`--latest=false` で既定の表示は
守れるが、一覧をたどると両方が並ぶ。タグのプレフィックスで
区別できるため許容する。

ネットのリリースは手動操作になる。学習を回した人が忘れれば
配布されない。CIで強制する手段はない（成果物がローカルにしかない）。

将来ネットが大きくなる場合（FT512で122MB、さらに拡大すると数百MB）、
GitHubのアセット上限2GBに近づく前に案C（HuggingFace）へ移す。
移行のトリガーは1ファイル500MBとする。
