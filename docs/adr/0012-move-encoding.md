# 0012: Moveエンコーディング

- Status: proposed
- Date: 2026-07-17
- 関連ADR: [0008](0008-square-coordinates.md), [0009](0009-piece-encoding.md)

## Context

指し手の表現は、指し手生成のバッファ、置換表への格納、historyの添字、
NNUE差分計算（DirtyPiece）の構築材料になる。将棋の指し手は
「盤上の移動（成り選択あり）」と「駒打ち」の2種で、移動元・移動先・
成りフラグ・打つ駒種を符号化する。マス81個は7bitに収まる。

置換表のエントリ幅（P2で起草）を圧迫しないことと、探索のホットパス
（historyの添字計算、DirtyPiece構築）で盤面の再参照を減らすことが
相反する要求としてある。

## 選択肢と比較

### 案A: 16bit単一（Stockfish流）

`to 7bit | from 7bit | promote 1bit | drop 1bit` の16bit。
駒打ちはfromフィールドに駒種を入れ、dropビットで区別する。
メモリは最小だが、「動かした駒」が指し手から分からないため、
historyの添字（駒×移動先）やDirtyPiece構築のたびに盤面を引く。

### 案B: 32bit（下位16bitに案A、上位に駒情報）

下位16bitは案Aと同一。上位に「移動後の駒」（成りなら成駒、打ちなら
打った駒。先後込み5bit）を持つ。指し手生成の時点で駒は分かっている
ため、詰める コストはゼロ。置換表には下位16bitだけを格納し、
TTから取り出した指し手は盤面と照合して復元する。
やねうら王がこの構成（Move16/Move）で、continuation history・
DirtyPiece構築で盤面参照を1回ずつ削る。

## Decision

案Bを採用する。定義は次のとおり。

```
bit 0..=6   to（移動先、0..=80）
bit 7..=13  from（移動元、0..=80）。駒打ちでは駒種（OSL配列の9..=15）
bit 14      promote（成り）
bit 15      drop（駒打ち）
bit 16..=20 移動後の駒（Piece、先後込み。成りなら成駒、打ちなら打った駒）
bit 21..=31 予約（0）
```

- 型は `Move(u32)` と `Move16(u16)` のnewtype二本立て。探索・生成は
  `Move`、置換表は `Move16` を使う。`Move16` から `Move` への復元は
  盤面参照を伴うメソッドとしてPositionに置く
- 特殊値はfrom==toの非合法パターンに割り当てる。
  `NONE = 0`、`NULL = (1<<7)|1`、`WIN = (2<<7)|2`、`RESIGN = (3<<7)|3`。
  通常の指し手は移動でfrom≠to、駒打ちでdropビットが立つため衝突しない
- USI文字列との相互変換（`7g7f`、`P*5e`、成りは`+`接尾）は
  `Move` のメソッドとする

駒打ちのfromフィールドはOSLの駒種の値（金9〜飛15）をそのまま入れる。
変換なしで駒種が取れ、7bitに収まる。

## Consequences

- historyの添字（移動後の駒×to）とDirtyPiece構築が指し手単体で
  完結し、盤面の再参照が要らない
- 捕獲された駒はMoveに含めない。do_moveが盤面から読み、undo用に
  StateInfo（PositionのADRで起草）へ保存する
- MoveList（最大約600手）は32bit×600 ≒ 2.4KBで、1手番あたりの
  スタック消費として問題ない
- 置換表から来た `Move16` は現局面で非合法の可能性がある。復元時の
  擬似合法性検査が必須（探索実装時の規約）
