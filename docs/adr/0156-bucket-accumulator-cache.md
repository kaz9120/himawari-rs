# 0156: 玉位置ごとのaccumulatorキャッシュで全計算を差分に置き換える

- Status: accepted
- Date: 2026-08-12
- 関連ADR: [0035](0035-nnue-accumulator.md), [0074](0074-feature-verification.md), [0124](0124-hot-path-allocs.md), [0127](0127-net-shape-bench.md), [0138](0138-ft-i8-quantization.md), [0151](0151-speedup-sweep.md)

## Context

NNUEのFT更新は探索時間の24.0%を占める（[ADR-0151](0151-speedup-sweep.md)の
第3次プロファイル、`ensure` の行）。ここは[ADR-0151](0151-speedup-sweep.md)で
一巡した挙動不変の高速化のうち、いちばん大きく残った枠である。

HalfKPの特徴は自玉の位置で重みが切り替わる。**自玉が動いた視点は差分の連鎖を
遡れないので、[ADR-0035](0035-nnue-accumulator.md)は全計算に落としている**。
外部の解説（[asteri.sm、2024-06-01](https://asteri.sm/files/2024-06-01-nnue#bucket-accumulator-caching-or-finny-tables)）
がある。この全計算を玉位置ごとのキャッシュとの差分に置き換える手
（Finny tables）でNPSが15%改善すると報告している（2026-08-12オーナー提示）。

### 全計算がどれだけ出ているか

着手前のmainに計装を入れ、`bench` の4局面を深さ19（局面3は16）で読ませた。

| 量 | 値 |
|---|---|
| `evaluate` の呼び出し | 650,701回 |
| 全計算（片視点） | 336,586回（`evaluate` 1回あたり0.517回） |
| 差分適用（片視点1段） | 1,358,763段（同2.088段） |
| 全計算で触るFTの行 | 12,790,268行（1回あたり38.0行） |

**評価2回に1回はどちらかの視点が全計算になっている**。差分適用は1段あたり
最大2行なので、FTの行アクセスは全計算側が76%を占める。ここを削れば効くはず、
というのが着手時の見立てだった。

## 選択肢と比較

### 案A: 現状維持

全計算のまま置く。追加のメモリは要らない。FT更新の24.0%はそのまま残る。

### 案B: 玉位置ごとにaccumulatorをキャッシュする（Finny tables）

視点色と玉の升ごとに、最後に作ったaccumulatorを1件だけ残す。HalfKPの特徴は
玉位置を固定するとBonaPieceの集合で決まるので、キャッシュとの集合の差だけ
足し引きすれば全計算と同じ値になる。代償はキャッシュのメモリで、
`2色 × 81升 × (acc 512B + 集合 200B)` の115KBがスレッドごとに要る。

### 案C: 視点ごとに直近の1件だけキャッシュする

メモリは1.4KBで済む。ただし玉が2か所を往復する筋（探索木では普通に起きる）で
毎回ミスする。案Bを実装して測ると差分は1回あたり6.93行に収まっており、
玉位置で分けた粒度に局所性が出ている。115KBはL2に収まる量なので、
ここを削る理由が弱い。

## Decision

**案Bを採る**。集合はBonaPieceの1548ビットのビットセットで持ち、XORで差を取る。
キャッシュは引くと同時に現局面へ更新するので、書き戻す手順は要らない。空の
ときはバイアスを置いて全特徴を足す形になり、従来の全計算と同じ経路をたどる。

正しさの根拠は加減算がラップであることによる。順序に依らないので、全計算と
ビット一致する。テストは既存の差分照合に加え、別局面を挟んで同じ玉位置へ
戻る経路（`bucket_cache_matches_full_computation_across_positions`）を足した。

## 測定

機能検証（[ADR-0074](0074-feature-verification.md)）は4局面すべてでノード数が
一致した。探索は1ビットも変わっていない。

同じ計装をキャッシュ導入後にかけると、`evaluate`・全計算・差分適用の回数は
1つも変わらない。**全計算で触る行だけが12,790,268行から2,334,154行へ減った**
（1回あたり38.0行 → 6.93行、−82%）。FTの行アクセス全体では約16.9Mから
約6.4Mになる（−62%）。

NPSは深さ22・12周・1スレッドで、4本を交互に測った（Apple M4 Pro、FT重みi8
ビルド）。後述の列挙の改善は独立に効くので、寄与を切り分けるため単独の
バイナリも並べた。

| バイナリ | NPS（12周の平均） | main比 |
|---|---|---|
| main | 1,886,478 | — |
| 列挙のみ | 1,916,018 | +1.57% |
| キャッシュのみ | 1,914,988 | +1.51% |
| 両方 | 1,936,600 | +2.66% |

キャッシュ単体は深さ19・3周で+1.11%、深さ22・5周で+1.17%も得ている。
3つの条件で符号が動かない。単発では誤差（±1.5%）に埋もれる大きさなので、
対で交互に測る必要がある。

**2つを合わせると足し算より小さい**（1.57 + 1.51 = 3.08 に対し実測2.66）。
どちらも全計算の同じ経路を削るため、片方が削った分だけもう片方の取り分が減る。

## 効果が見積もりより小さい理由

**行を82%減らしてもNPSは1%しか動かない**。原因を追うため、キャッシュ導入後の
プロファイルを取り直した（深さ25・1スレッド・2000Hz、[ADR-0099](0099-nnue-dot-sdot.md)の手順）。

| 行 | 中身 | self時間 |
|---|---|---|
| `nnue_acc.rs:291` | 現局面の駒の列挙とビットセット構築 | 5.94% |
| `nnue_acc.rs:318` | キャッシュ差分の重み行の加減算（`ft_update`） | 1.52% |
| `nnue_acc.rs:167` | 差分適用の連鎖（`ensure_both`） | 5.03% |
| `nnue_acc.rs:174` | `clip_to_u8` | 3.08% |
| `nnue_acc.rs:176` | 隠れ層（`forward_hidden`） | 8.95% |

**全計算のコストは重み行の加算ではなく、局面から特徴を取り出す側にあった**。
削った加減算は1.52%まで落ち、代わりに列挙が最上位に浮かんでいる。着手時の
見立て（行アクセスの76%が全計算側にある）は量としては正しかったが、
時間の配分がそれに比例していなかった。

理由は3つに割れる。

- **削った量そのものが小さい**。全計算で減らしたのは 10.5M行 × 256バイト =
  2.7GB の読み出しで、探索3.1秒に対し0.87GB/秒でしかない。L1・L2に収まる
  範囲で流れる量である
- **減らない側が残る**。差分適用は1.36M段あり、段ごとにaccを512バイト読んで
  書く。合計1.4GBで、キャッシュでは減らない
- **出典との前提の差**。チェスで15%を報告するのは、あちらのFT幅が1024〜3072と
  広く、全計算1回のコストが本エンジン（FT256）の4〜12倍あるためである。
  **削減量はFT幅に比例するが、本エンジンの幅ではその比例定数が小さい**

[ADR-0127](0127-net-shape-bench.md)が測った「FT 256→512 で増える時間の3分の2は
FT更新」という結果と向きは揃う。FTを太らせるほど、この改善の取り分は増える。

### 列挙をbitboard走査に変える

プロファイルが指した5.94%へそのまま手を入れた。盤上の列挙は81升の総なめで、
空升の判定が3分の2を占めていた。occupancyから玉2枚を除いたbitboardを走ると、
回る回数が実際の駒数（38前後）に減る。

**この改善はキャッシュとは独立に効く**。全計算の回数は変わらないので、
キャッシュがなくても同じ列挙が同じ回数走る。実際、mainへ単独で入れても
+1.57%で、キャッシュ単体（+1.51%）とほぼ同じ大きさになった（上の表）。

**プロファイルが指した先は、着手時に狙っていた場所ではなかった**。出典の手を
そのまま移すだけなら、この5.94%は見つからないままだった。移した先で測り直す
ことに意味がある。

## FT幅で取り分がどう伸びるか

上の理由づけ（削減量はFT幅に比例する）を実測で確かめた。FT768のネット
（`train-768x16x32`、[ADR-0127](0127-net-shape-bench.md)の資産）は
[ADR-0138](0138-ft-i8-quantization.md)より前の学習でi8に収まらないため、
**4本ともi16ビルドで揃えた**。ノード数固定300万・8周・4本交互で測る。

| バイナリ | NPS（8周の平均） | FT256のmain比 |
|---|---|---|
| FT256 / main | 1,782,346 | — |
| FT256 / 本ADR | 1,901,637 | +6.69% |
| FT768 / main | 1,205,925 | −32.34% |
| FT768 / 本ADR | 1,452,459 | −18.51% |

**取り分はFT幅にほぼ比例した**。FT256で+6.69%、FT768で+20.44%になり、
比は3.06でFT幅の比3.0と一致する。全計算で触る量が幅に比例することの直接の
確認になる。i16ではi8より行が重いので、同じ改善がFT256でも+6.69%（i8では
+2.66%）まで大きく出る。

**FT768の速度低下は0.677倍から0.764倍へ縮んだ**。
[ADR-0127](0127-net-shape-bench.md)はFT768（L1半減）を「ノード数固定で
+31.4 Elo、速度の代償98 Elo、i8で取り返せるのは+27 Elo、差し引き−40」と
見積もって見送っている。**その−40を埋める方向に、この改善が効く**。

ただし採否をここで決めない。i8での実測にはFT768を `--ft-clip` 付きで学習し
直す必要があり、i8は行が半分の重さなので取り分もi16より小さく出る。
**FT768の再判断は、i8での再学習と300+10での測定を揃えてから行う**。

## Consequences

- スレッドあたり115KBのメモリが増える。1スレッドのNPSで効果が正なので、
  L2の圧迫が上回ってはいない。`Threads=4` 以上での影響は
  [ADR-0151](0151-speedup-sweep.md)の群Eと同じ枠で別に測る
- 挙動不変なので単独ではSPRTにかけない（[ADR-0151](0151-speedup-sweep.md)と
  同じ運用、コミットはfix型）。次に挙動不変の改善をまとめるときへ合算する。
  合算対象は+2.66%である
- 見直しのトリガーは**FT幅を広げる決定**である。FT768案
  （[ADR-0127](0127-net-shape-bench.md)、ノード数固定で+31.4 Elo）は速度の
  代償98 Eloで落ちているが、その代償はこのキャッシュで縮む（上の実測で
  0.677倍→0.764倍）。**次の一手はFT768を `--ft-clip` 付きで学習し直し、
  i8で測ることである**。300+10での再測定と組みで判断する
- 玉位置ごとのキャッシュはEffectBucket（[ADR-0147](0147-effect-bucket-features.md)）
  とは独立に働く。特徴indexの分割が入っても、集合の差を取る構造は変わらない
