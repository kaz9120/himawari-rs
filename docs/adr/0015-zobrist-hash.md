# 0015: Zobristハッシュ設計

- Status: proposed
- Date: 2026-07-17
- 関連ADR: [0005](0005-static-tables.md), [0009](0009-piece-encoding.md), [0013](0013-hand-packing.md), [0014](0014-position-structure.md)

## Context

局面のハッシュは置換表のキー、千日手検出、優等・劣等局面の判定に使う。
将棋はチェスと違い手駒があるため、「盤面が同一で手駒だけ違う局面」を
区別しつつ、優等判定（盤面一致＋手駒の全種で以上）のために盤面部分を
独立に比較できる構造が要る。do_moveでの差分更新が数命令であることも
要件になる。

## 選択肢と比較

### 案A: 単一キー（盤・手駒・手番をすべてXORで畳む）

Stockfish流の最小構成。差分更新は速いが、盤面だけの一致が
キーから判定できず、優等局面の検出に盤面の直接比較が要る。

### 案B: board_key／hand_key分離＋手駒も乱数（やねうら王式）

盤面はマス×駒の乱数XOR、手駒は（駒種×枚数）ごとの乱数の加算で
持つ。加算式なので枚数の増減が加減算1回になる。盤面一致は
board_keyの比較で判定できる。手駒キーは乱数由来のため、
理論上の衝突が手駒部分にも存在する。

### 案C: board_keyはZobrist、hand_keyは生の値（提案）

手駒はADR-0013で両者合わせて64bit（u32×2）にパックされている。
これをそのままhand_keyにすれば、手駒部分は単射でハッシュ衝突が
原理的に存在しない。差分更新も不要（Handそのものがキー）。
置換表用の合成キーは乱数性が要るため、乗算で拡散してから
board_keyと合成する。

## Decision

案Cを採用し、手番は案Bの発展形であるbit 0トリックで持つ。

- `board_key: u64`。乱数テーブルは（駒32 × マス81）の20KBで、
  seed固定のsplitmix64によりconst fn生成する（ADR-0005）。
  全乱数はbit 0を0にして生成し、do_moveごとに `key ^= 1` する。
  これで **board_keyのbit 0 = 手番** が常に成り立ち、千日手検出の
  遡りで手番違いの局面が自動的に不一致になる
- `hand_key: u64 = hands[先手].0 | (hands[後手].0 << 32)`。
  生の値なので単射。更新はHandの更新そのもので追加コストゼロ
- 置換表キー: `board_key ^ (hand_key × 0x9E3779B97F4A7C15)`。
  乗算1回で手駒ビットを全64bitに拡散する。probeのたびに計算し、
  保存はしない（2命令）
- 優等・劣等判定: `board_key` 一致（手番bit込み）を確認したうえで、
  hand_keyから復元したHand同士を `is_superior_or_equal`（ADR-0013）で
  比較する。手駒部分に偽陽性がないため、判定は正確
- null moveは `board_key ^= 1` のみ（盤・手駒は不変）
- 駒割（material）と同様、両keyはStateInfoに保持し差分更新する
  （ADR-0014）。SFEN読み込み時に全計算し、property testで
  「差分更新＝全計算」の一致を検証する

## Consequences

- 千日手・優等判定の手駒比較が正確になり、衝突の心配が
  board_key側の64bitだけに減る
- 置換表キーの品質は拡散乗算に依存する。定数はsplitmix64の
  増分定数（奇数）を使う。置換表実装時（P2）に、実測の
  ハッシュ分布（クラスタ占有率）を確認するテストポイントを置く
- 手駒枚数の上限がHandのフィールド幅で保証されるため、
  hand_keyのオーバーフローは構造的に起きない
- bit 0トリックのため、乱数生成時のマスク忘れがバグ源になる。
  const fnの生成結果に対する単体テスト（全エントリのbit 0が0）で防御する
