# 0141: singular率を設計点へ較正し、多段延長を再訪する

- Status: rejected
- Date: 2026-08-04
- 関連ADR: [0050](0050-singular-extension-retry.md), [0074](0074-feature-verification.md), [0114](0114-g5-singular.md), [0128](0128-round-robin-league.md)

## Context

[ADR-0114](0114-g5-singular.md)（G5）はsingularの多段延長（double/triple）を
入れて−99.0 Eloになり、+1打ち止めへ戻して+48.2でH1採択した。多段は
ROADMAP候補へ保留され、再訪の条件は「singular率を設計点へ寄せる方法が
見つかったとき」とされた。

数字を再掲する。本エンジンのsingular率は判定対象の43.5%で、参照実装の
設計点（約1割）から4.4倍外れている。マージン係数を2〜8倍へ振っても
10〜20%までしか下がらず、当時は評価値分布の違いと結論した。

ADR-0114の結論は「係数の問題ではない。係数では（設計点1割へ）届かない
ため、判定そのものの作り方を変える必要がある」だった。ここで見直したいのは
前提のほうである。**多段延長を安全にする目的なら、設計点への厳密な一致は
要らない**。多段が積まれる機会を数分の1へ絞れれば足り、係数8倍で
10〜20%まで下がる実測はすでにある。当時、大きく振った係数の条件で
測ったのは率だけで、その条件の棋力は測っていない。評価値分布が違うと
結論した以上、参照実装の係数値そのものを保つ根拠も薄い。**合わせにいく
べきは係数の値ではなく、率という設計点である**。

多段延長の失敗（triple爆発で局面3が7.2倍に膨張、到達深さ4段落ち）も、
率43.5%のまま+3まで積める構造が原因だった。率を1割へ寄せれば、
多段の積まれる機会そのものが参照実装の設計点に揃う。

## 選択肢と比較

### 案A: 率を測って較正し、その上でdoubleを再測定する（2段）

第1段でマージン（`SINGULAR_MARGIN`・`SINGULAR_MARGIN_TTPV`・
`SINGULAR_MARGIN_DIV`）を率10〜15%になる点へ較正し、単独でSPRTにかける。
第2段で、較正済みの土台にdouble延長（tripleなし、深さ条件つき）を載せて
もう1回SPRTにかける。どちらで効いたか・落ちたかが分離できる。

### 案B: 較正と多段を1つのSPRTで測る

対局数は半分で済むが、H0のとき原因を切り分けられない。
G5の1回目（−99.0）で切り分け不能に苦しんだ経緯に反する。

### 案C: 保留を続ける

singularは発動率が高い（判定対象の43.5%）ぶん、較正の影響も大きい。
探索側で「参照実装と同じ構造なのに設計点が4.4倍ずれている」と
分かっている箇所はここだけで、放置する理由が弱い。

## Decision

案Aを採る。手順は率の測定から始める。

1. **率の較正**。[ADR-0074](0074-feature-verification.md)の枠で、
   マージン系3定数を振って深さ13・複数局面のsingular率を測り、
   10〜20%の帯へ下げる組を決める（係数8倍で届くことはADR-0114が実測済み）。
   較正した定数の出典・前提は本ADRに追記する
2. **第1段SPRT**。較正のみを既定条件で測る。率を絞ることは延長を
   減らすことなので、単独ではマイナスもありうる。非劣性（elo0=−5、
   elo1=0）も許容する。ここがH0大敗なら較正の前提が誤りで、閉じる
3. **第2段SPRT**。double延長（`singular_ext = Some(2)` 相当、triple
   なし）を載せ、既定条件で測る

**Elo見込みの根拠は、参照実装が多段延長を保持していること
（+の実測があるから残っている）と、本エンジンでの失敗原因が
率の乖離として特定済みであることである**。

**撤退ライン**。第2段がH0なら、多段延長は「率を揃えても本エンジンでは
効かない」として保留を棄却へ格上げし、以後再訪しない。

## 率の較正（2026-08-05）

現行ネット（`halfkp_2990M_fact`）で、深さ13・16局面のsingular率を測った。
判定対象は検証探索を走らせたノード、singularは検証値が `singular_beta` を
下回った回数である。

マージンは `SINGULAR_MARGIN` と `SINGULAR_MARGIN_TTPV` に倍率を掛けて振った。

| 倍率 | マージン | singular率 | multicut率 |
|---|---|---|---|
| ×1（現行） | 60/66 | 31.3% | 55.4% |
| ×8 | 480/528 | 22.6% | 50.1% |
| ×12 | 720/792 | 14.1% | 36.3% |
| **×16** | **960/1056** | **9.9%** | **29.3%** |
| ×20 | 1200/1320 | 7.4% | 24.4% |
| ×24 | 1440/1584 | 7.6% | 20.5% |

**×16で9.9%になり、参照実装の設計点（約1割）に乗る**。

### ADR-0114の「係数では届かない」は誤りだった

[ADR-0114](0114-g5-singular.md)は「係数を2〜8倍へ振っても10〜20%までしか
下がらない」「係数では届かないため、判定そのものの作り方を変える必要がある」と
結論した。**振り幅が足りなかっただけである**。8倍で22.6%と頭打ちに見えるが、
12倍から先で再び下がり、16倍で設計点に入る。

現行率も測り直した。ADR-0114の43.5%に対し、新ネット・16局面では31.3%である。
**率はネットの世代と局面集合で動く**。単一の値として引用しない。

## SPRT結果（2026-08-05、第1段）

較正のみを載せて測った。延長を減らす変更なので単独ではマイナスもありうると
見て、非劣性（elo0=−5、elo1=0）で判定した。

**H0採択。−81.2 Elo [−105.1, −58.1]、884局（442ペア）、LLR −3.01**。
W-D-Lは +327 =27 −530 である。

−5すら守れない。**較正の前提が誤りだった**。

## Decision（改訂）

**棄却する**。率を設計点へ寄せる案を捨て、`SINGULAR_MARGIN` 系は参照実装の
値のまま据え置く。第2段（double延長）へは進まない。

**前提の何が誤りだったか**。本ADRは「率43.5%は設計点から外れているので
揃えるべき異常だ」と読んだ。実測は逆で、**本エンジンでは高い率が効いている**。
G5が+1打ち止めで+48.2 Eloを得たのは、率が高いままだったからである。
参照実装と同じ率にすると、その分がまるごと失われる。

**機構としての見落としもあった**。`singular_beta` は3分岐すべての軸である。
検証値がこれを下回れば延長、βを超えればmulti-cut、間ならnegative extensionに
なる。マージンを16倍にするとmulti-cut率も55.4%から29.3%へ落ちた。
**singular率だけを動かすことはできない**。本ADRは「率を絞ることは延長を
減らすこと」と書いたが、実際には枝刈り（multi-cut）も半分に減らしていた。
−81.2 Eloの内訳はこの両方である。

### 多段延長を棄却へ格上げする

本ADRの撤退ラインは「第2段がH0なら多段延長を棄却へ格上げする」だった。
第1段で土台が作れないと分かったので、同じ結論を前倒しする。

**多段延長は再訪しない**。[ADR-0114](0114-g5-singular.md)が−99.0 Eloで
外し、率を揃える道も−81.2 Eloで閉じた。ROADMAPの「保留」から外す。

### 参照実装との付き合い方

**設計点は移植できない**。本ADRは「合わせにいくべきは係数の値ではなく、
率という設計点である」と書いた。実測はどちらも移らないことを示した。
係数をそのまま使うと率が3倍になり、率を揃えると81 Elo失う。

移るのは係数の値のほうだった。**参照実装の定数は、その値が生む率ではなく
値そのものが本エンジンでも最適に近い**。[ADR-0116](0116-g7-timeman.md)・
[ADR-0118](0118-g9-aspiration.md)が「その値が何に支えられているか」で失敗した
2件とは向きが逆の教訓である。あちらは値だけ移して支えを落とした。こちらは
支え（設計点）に合わせようとして値を壊した。

## Consequences

- 探索定数が参照実装の値から意図的に離れる最初の例になる。
  以後、参照実装の定数更新へ機械的に追従できなくなる箇所として
  コードにコメントを残す
- 率の較正はデータ（ネットの世代）に依存する。評価関数を更新したら
  率を測り直す運用が要る。[ADR-0143](0143-spsa-tuning.md)のSPSA基盤が
  入れば、この定数群もそこへ移せる
- 第1段・第2段で最大2回のSPRTを消費する
