# 0186: 千日手判定の走査を16手で打ち切る

- Status: accepted（既定SPRTで+14.3のH1。下の「測定・SPRT」）
- Date: 2026-08-26
- 関連ADR: [0026](0026-repetition.md), [0074](0074-feature-verification.md), [0089](0089-improvement-criteria.md), [0153](0153-superior-repetition-root-gate.md), [0155](0155-reference-walkthrough.md), [0163](0163-sprt-hypothesis-choice.md)

## Context

現行の千日手判定（[ADR-0026](0026-repetition.md)）は、探索の各ノードで
履歴を後ろへ線形走査する。走査に手数の上限がなく、`plies_from_null` の
許す範囲すべてを見る。1エントリごとにStateInfoをまたいで飛び飛びに
読むので、200手級の対局では毎ノード約20KBのストライド走査になる。
floodgateの300+10は200手級が珍しくなく、対局が長引くほど全ノードが
重くなる。**性能バグである**。

[ADR-0155](0155-reference-walkthrough.md)の群4がこの箇所を監査済みで、
性能のほかに2つの意味論の課題が記録されている。

1. 相互連続王手の千日手で、現行は手番側の勝ち扱い（危険側）になっている
2. 参照実装は走査を16手で打ち切る。参照コメントに「初手まで遡ると
   R40弱くなる」とあり、遠い一致まで千日手・優等劣等を拾うと探索が
   歪むという測定痕がある

群4は参照整列としては閉じたが（0155の「線を閉じた判断」）、この項目
だけは性能バグの解消として単独で残した。ROADMAPの候補から着手する。

## 選択肢と比較

### 案A: 現行の走査に16手キャップだけ足す（採用）

走査コストが定数に収まる。毎ノードの走査自体は残るが、長さが履歴に
比例しなくなる。

### 案B: do_move時の前計算へ置き換える

`do_move` で直前の一致だけを探して距離と種別をStateInfoへ記録し、
探索中の判定はO(1)の読み出しにする。起草時はこちらを採る予定だった。
根拠は「走査は1手につき1回で、探索ノード数よりずっと少ない `do_move`
回数に比例する」だったが、**この前提が誤っている**。探索では
`do_move` の回数と判定の回数がほぼ1対1で、回数は減らない。

減るのは1回あたりの走査長だけで、それは案Aでも同じである。実装して
測った結果は下の「測定・案Aと案Bの比較」にある。

## Decision

**案Aを採る**。`repetition_state` の走査を `REPETITION_SCAN_MAX = 16`
手で打ち切る。

### 探索と裁定を分ける

キャップを一律に掛けると、対局ルールの裁定が同一局面の4回目を
取りこぼす。裁定に使う `repetition_state_all` は上限なしのまま残し、
走査の本体を `scan_repetition(ply, scan_max)` に切り出して2つの
入口から呼ぶ。裁定の呼び出しは1局面につき1回なので、走査の重さは
問題にならない。

キャップの根拠は参照実装のコメント（初手まで遡るとR40弱くなる）に
あるが、本エンジンでの実測では**探索木は1ノードも変わらなかった**。
16手を超える距離でだけ成立する一致は、探索の中でほぼ現れない。
よって本エンジンでこの変更が主張するのは速度だけになる。

### 意味論の修正は分離する

起草時は相互連続王手のLOSE優先を同じ変更に含める予定だった。分離
する。速度と意味論を同時に動かすと、SPRTの結果がどちらに由来するか
切り分けられない（[ADR-0163](0163-sprt-hypothesis-choice.md)の
「動かす変数は1つ」）。LOSE優先は別ADRで測る。

## 測定・機能検証（2026-09-02）

### 長手数局面の測定台を用意した

組み込みの検証4局面はすべてSFENで、履歴を持たない。履歴が空だと走査は
0手から始まるので、この変更の効果は測れない。過去のSPRTの棋譜（jsonl）
から手順つきの局面を4つ選び、`openings/longgame_positions.txt` へ
置いた。手数は100・150・200・250で、直近のSPRT（adr0192-tanuki、
1,682局）の分布を覆う。同SPRTの手数は平均100.4・中央98・90%点136・
最大253だった。

`verify` と `bench` に `--positions` を足し、この局面リストを渡せる
ようにした。

### ノード数は全局面で一致した

| 局面 | 変更前 | 変更後 | 変化 |
|---|---|---|---|
| 100手 | 26,206 | 26,206 | +0% |
| 150手 | 277,937 | 277,937 | +0% |
| 200手 | 41,611 | 41,611 | +0% |
| 250手 | 35,997 | 35,997 | +0% |

固定深さ13。評価値と最善手も全局面で同じだった。探索木は同一である。

### NPSは長手数局面で4.29%上がった

深さ17・4周・1スレッド。ノード数は4周とも14,807,846で一致している。

| バイナリ | NPS（4周の平均） | 変更前比 |
|---|---|---|
| base | 1,482,446 | — |
| cand | 1,545,992 | +4.29% |

組み込み4局面（履歴が空）では差が出ない。深さ19・3周で−0.75%だったが、
1周目は両者が同値で、残りの周も1%以内に収まる。走査が短い局面では
変わらないという読みと整合する。

速度の換算率1%あたり3.12 Elo（[ADR-0171](0171-ft-pairwise-product.md)まで
の実測）を当てると+13.4 Eloになる。ただし換算率は序盤中心の測定から
出ており、対局の全体では手数の分布ぶん薄まる。**期待値の上限として
読む**。

## 測定・案Aと案Bの比較（2026-09-02）

案Bを実装し、案Aと並べて測った。案Aは走査に `.min(16)` を足すだけの
1行で、案BはStateInfoへ2フィールドを足し、`do_move` の末尾で前計算する。

| バイナリ | NPS（4周の平均） | 変更前比 |
|---|---|---|
| base | 1,486,625 | — |
| 案A（キャップのみ） | 1,547,557 | +4.10% |
| 案B（前計算＋キャップ） | 1,549,598 | +4.24% |

差は0.14%で、周ごとのばらつきに埋もれる。ノード数は3本とも一致した。
**前計算の追加利得はない**。理由はContextに書いたとおりで、`do_move`
の回数と判定の回数がほぼ等しいため、前計算にしても走査の回数は減らない。

案Aを採る。得るものが誤差の範囲なら、StateInfoの拡張と前計算の
複雑さを負う理由がない。案Bが持つ「距離を記録できる」利点は、それを
使う機能が現れてから取りに行く。

## SPRTの事前登録（2026-09-02）

判定を見てから読み方を決めないよう、走らせる前に4点を書く。

1. **仮説**。走査の打ち切りで長手数局面のNPSが4.29%上がる。この速度差が
   棋力へ変換され、10+0.1の対局で正のEloになる
2. **動かす変数**。千日手判定の走査上限だけである。探索木が同一なことは
   機能検証で確認した
3. **固定するもの**。評価関数（`pairrank_7860M_q1_reorder`）、ビルド条件
   （`hmwr build pair` の同条件・PGOなし）、定跡、時間制御、並列度を
   変えない。ペアは同じコミットから作る
4. **読み方**。H1なら採択してmainへ入れる。H0なら「速度は上がるが10+0.1の
   対局では棋力に変換されない」が結論になる。その場合でも300+10では効くと
   見込めるので、非劣性で入れ直すかを検討する

条件は既定（`--tc 10+0.1 --concurrency 8 --adjudicate 2000,8`、elo0=0、
elo1=5）にする。速度改善は棋力向上の主張なので、非劣性は選ばない
（[ADR-0163](0163-sprt-hypothesis-choice.md)）。

機能検証は全局面でノード数が一致するため、`hmwr sprt run` の既定ゲートに
掛かる。ゲートは「探索に影響しない変更は中立」を前提にしているが、速度
改善は探索木を変えずに棋力を動かす。`--no-verify` で明示的に飛ばし、
かわりにNPSの測定を上に残した。

## 測定・SPRT（2026-09-02、既定条件）

| 項目 | 値 |
|---|---|
| 比較 | `base-adr0186-rep`（origin/main）対 `cand-adr0186-rep` |
| 条件 | `--tc 10+0.1 --concurrency 8 --adjudicate 2000,8`、elo0=0、elo1=5 |
| 対局数 | 5,772（2,886ペア） |
| W-D-L | +2835 =340 -2597 |
| Elo [95%CI] | **+14.3 [+5.6, +23.0]** |
| LLR | +3.02（**H1採択**） |

事前登録の読み方どおり、H1なので採択する。NPSの+4.29%に換算率
1%あたり3.12 Eloを当てた見積もりは+13.4で、実測の+14.3とほぼ重なる。
**速度の改善がそのまま棋力へ変換された**。

### 途中経過を結論にしない

900局の時点で−23.4 [−45.4, −1.6] まで振れ、信頼区間の上限が負に入った。
そこで「16手キャップは本エンジンでは害で、参照実装の主張は当てはまらない」
と読みかけたが、逆だった。1,468局で+0.9へ戻り、最終的に+14.3で決着した。

[ADR-0175](0175-sprt-until-decision.md)の「判定が出るまで走らせる」が
効いた事例になる。**途中経過のCIが片側へ寄っても、それは判定ではない**。
逐次検定は閾値に触れるまで結論を出さない設計で、途中で読むと符号すら
逆に見えることがある。

## Consequences

- 探索は距離16を超える一致を見ない。ルール上の千日手は
  `repetition_state_all` が拾うので、対局と教師生成の裁定は変わらない
- 探索と裁定で判定の範囲が違う状態になる。`scan_repetition` の
  呼び出し元は2つだけなので、差の所在はコードで追える
- 効果は履歴の長さに比例する。10+0.1のSPRTは平均100手なので効果が
  乗るが、floodgateの300+10ではさらに大きくなる
- ADR-0026の走査は残る。この変更が置き換えるのは走査の範囲だけである
