# 0013: Hand（手駒）のパック表現

- Status: proposed
- Date: 2026-07-17
- 関連ADR: [0009](0009-piece-encoding.md)

## Context

手駒は7駒種（歩香桂銀金角飛）の枚数の組で、最大枚数は
歩18・香4・桂4・銀4・金4・角2・飛2。do_move/undo_moveでの増減、
駒打ち生成での駒種列挙、そして優等・劣等局面の判定
（盤面が同一で手駒だけ多い局面は探索上で勝ち扱いにできる）で使う。
優等判定は千日手検出（P2で起草）のホットパスに入るため、
全駒種の一括比較が少数命令で書けることが要件になる。

## 選択肢と比較

### 案A: 配列 [u8; 7]

素直で読みやすい。増減は添字アクセス1回。ただし優等判定
（全駒種で h1 ≥ h2）が7要素のループになり、Positionのコピーや
Zobrist計算でも駒種ごとの処理が必要になる。

### 案B: u32へのビットフィールドパック＋borrowガード

各駒種の枚数をu32内のフィールドに詰め、フィールド間に1bitの
ガード（borrow bit）を置く。`(h1 - h2) & BORROW_MASK == 0` が
「全駒種で h1 ≥ h2」と同値になる（どの駒種でも借りが発生しない
ことをガードビットで一括検出する）。優等判定が減算1回＋AND1回。
増減は駒種ごとのシフト定数で `h ± (1 << SHIFT[kind])`。
Bonanza以来の定石で、やねうら王も同方式。

## Decision

案Bを採用する。レイアウトは次のとおり（計32bitちょうど）。

```
bit  0..=4   歩（5bit、最大18）   bit 5  ガード
bit  6..=8   香（3bit、最大4）    bit 9  ガード
bit 10..=12  桂（3bit、最大4）    bit 13 ガード
bit 14..=16  銀（3bit、最大4）    bit 17 ガード
bit 18..=20  金（3bit、最大4）    bit 21 ガード
bit 22..=23  角（2bit、最大2）    bit 24 ガード
bit 25..=26  飛（2bit、最大2）    bit 27 ガード
bit 28..=31  未使用（0）
```

- 型は `Hand(u32)` のnewtype
- 駒種→シフト量はOSL駒種（金9〜飛15、ADR-0009）を添字にした
  const配列で引く。フィールドの並び順自体に意味は持たせない
- 優等判定: `fn is_superior_or_equal(self, other) -> bool` を
  `(self.0.wrapping_sub(other.0)) & BORROW_MASK == 0` で実装する。
  呼び出し側で盤面一致（board_key一致）を確認済みであることが前提
- 「その駒種を持っているか」は `h & FIELD_MASK[kind] != 0`、
  駒打ち生成の駒種列挙は金9〜飛15の固定順ループとする
- ガードビットは常に0を維持する（増減操作の不変条件。debug_assertで防御）

## Consequences

- 優等・劣等判定が2命令になり、千日手検出のループに置ける
- Handのコピー・比較・ハッシュ材料化がu32の値渡しで済む
- 枚数の加減算はシフト定数経由になり、配列添字より1段間接的になる。
  読みやすさはメソッド名（`add(kind)` / `sub(kind)` / `count(kind)`）で担保する
- 32bitに7駒種＋ガードがちょうど収まっており、拡張余地はほぼない。
  変則将棋への対応が必要になった場合はこのADRを見直す
