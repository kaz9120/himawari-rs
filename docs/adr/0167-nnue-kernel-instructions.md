# 0167: NNUE推論の命令数を削る2案を測り、どちらも見送る

- Status: rejected
- Date: 2026-08-15
- 関連ADR: [0074](0074-feature-verification.md), [0099](0099-nnue-dot-sdot.md), [0151](0151-speedup-sweep.md), [0164](0164-bona-piece-bitset.md), [0166](0166-movepick-frame.md)

## Context

[ADR-0166](0166-movepick-frame.md)で `MovePicker::next` の呼び出しコストを
削ったのに続き、もう一方の大項目 `NnueState::evaluate`（self時間17.43%）を
命令アドレス単位で見直した。既に入っている最適化は次のとおりで、実装が
mainにあることをコードで確かめてある。

| 群・ADR | 中身 |
|---|---|
| [ADR-0151](0151-speedup-sweep.md)群A・N | FT差分の融合カーネル、両視点1パス |
| ADR-0151群C | 隠れ層の8行束ね、出力層 `dot` のSDOT化 |
| ADR-0151群L | 列駆動スパースL1、分岐なしの非ゼロ列挙 |
| [ADR-0099](0099-nnue-dot-sdot.md) | SDOT経路 |
| [ADR-0138](0138-ft-i8-quantization.md) | FT重みi8 |

逆アセンブルすると、LLVMが既に済ませていることも2つ分かった。`ft_apply` の
i8符号拡張は `saddw`/`ssubw`/`saddl` に畳まれており、スパースL1の出力clipは
`tbl.16b` でベクトル化済みである。手で書き直す余地はない。

残る余地として、命令数を数えて2案を立てた。

## 選択肢と比較

### 案A: clipped ReLUを飽和縮小命令へ置き換える

`clip_to_u8` は移植版（`std::simd`）で16要素あたり `ldp`・`smax`2・`smin`2・
`uzp1`・`str` の7命令に展開され、32グループで224命令になる。

`sqxtun`／`sqxtun2` はi16を `min(max(v, 0), 255)` でu8へ落とす。続けて127で
`umin` を取れば `clamp(v, 0, 127)` と一致し、i16の全域で移植版と同じ値を
返す。1グループが5命令になり、224→160命令へ29%減る。

### 案B: 非ゼロ列挙のpopcountを表引きにする

`find_nnz` の `mask.count_ones()` は、aarch64で `fmov`→`cnt.8b`→`fmov`→
`umov` の4命令に落ちる。GPRとNEONを往復する形で、ループ本体39命令のうち
2か所で8〜10命令を占める。マスクは8ビットなので、256バイトの表を引けば
`ldrb` 1命令で済む。

## Decision

**どちらも見送る。案Bは明確に遅く、案Aは効果が測れない。**

実装と正しさの検証は両方とも通っている。案Aは移植版を
`clip_to_u8_portable` として残し、境界値（i16の両端・±128・127・255）と
乱数64周で一致を照合した。`cap` を128にする故障注入でこのテストが落ちる
ことも確かめてある。機能検証（[ADR-0074](0074-feature-verification.md)）は
深さ13・20で全4局面のノード数・評価値・最善手が一致した。**落ちたのは
速度だけである。**

### 測定

| 構成 | base先行 | cand先行 | 対照 |
|---|---|---|---|
| 案A＋案B | −2.01% | −0.82% | −0.61% / −0.48% |
| 案Aのみ（1組目） | +0.54% | +0.29% | −0.14% |
| 案Aのみ（2組目） | +0.30% | −0.19% | +0.68% |

**案Bは差し引き−1.7%前後の悪化になる。** 案Aのみと案A＋案Bの差である。

**案Aは4回中1回が負で、平均+0.235%は対照の幅（−0.14〜+0.68%）に収まる。**
[ADR-0165](0165-bona-block-layout.md)・ADR-0166で採用した「方向を入れ替えた
測定4回すべてで正」の基準を満たさない。

### 案Bが負けた理由

命令数は減るが、ループのクリティカルパスが伸びた。

`count` は次の反復の `vst1q_u16(nnz.as_mut_ptr().add(count), …)` の書き込み
アドレスを決める。`cnt.8b` を含む4命令はすべてレジスタ内で完結してレイテンシが
短いのに対し、**表引きはL1ヒットでも3〜4サイクルのロード遅延を依存チェーンへ
直列に入れる。** 4KBの `NNZ_LUT` と並んでもう1つ表を引くぶん、キャッシュの
圧も増える。

### 案Aを採らない理由

命令数は確実に29%減るのに、速度は動かない。原因は特定していないが、
clipは直前に `ft_apply` が書いたaccを読むので、ストア→ロードの待ちが
命令数の差を覆っている可能性がある（推測）。取り切るにはclipを
`ft_apply` の最終段へ融合し、accの書き戻しを跨がない形にする必要がある。
それは `apply_range`・`apply_range_both`・`refresh_top` の3経路すべてに
手番依存の出力先を通す設計変更で、この枠には入らない。

**効果が測れないまま、unsafeなintrinsicsと2本目の実装とテストを増やすのは
割に合わない。** 同じ理由で、残していた2案も着手しない。

- `affine_relu` の列数const generic化（見込み+0.1〜0.4%）。案Aと同規模の
  命令削減なので、同じく測れないと判断する
- 出力層 `dot` の固定長化（見込み+0.05〜0.15%）。`last` を作る3経路すべてを
  固定長配列へ変える必要があり、費用対効果が合わない

## Consequences

- `evaluate` の命令数を削る線はここで閉じる。**残る軸は「回る回数を減らす」
  ほうで、ROADMAPのFT出力次元の並べ替え（全ゼロチャンク率を上げる）に
  なる。** そちらは前提の実測から始める
- **命令数を削っても速くならない例が3件目になった。** 理由は毎回違う。
  [ADR-0164](0164-bona-piece-bitset.md)はメモリのread-modify-write、
  ADR-0166の案Bは走査のパス数、本ADRの案Bは依存チェーンのレイテンシである。
  **逆アセンブルして命令を数えるのは着手の根拠になるが、成果の見積もりには
  ならない。** 数えた命令が何の待ちに隠れているかを見ないと外す
- 案A・案Bのコードはmainへ入れない。ADR-0151群M・ADR-0166案Bと同じ扱いである
