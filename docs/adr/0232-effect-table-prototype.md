## Context

[ADR-0230](0230-board-op-profile.md)で、Bitboardを残して利きを差分で併せ持つと決めた。
本ADRはその試作の設計である。[ADR-0229](0229-roadmap-visible-focus.md)の段階1の
合格の条件「NPSの代償と、それで安くなる処理を数字で示す」をここで書き切る。

材料は3つある。

- ADR-0230の測定。利きを引く処理（`attackers_to`・`attacks`）は探索時間の14〜23%を占める。
  大半は1手詰めとSEEである
- [ADR-0148](0148-effect-table.md)の部品 `EffectTable`（`crates/core/src/effect.rs`）。
  差分更新は作り直しとの一致をテストで確かめてある。`Position` へ載せた版は、
  使う側なしでNPSを7.19%落として撤退した。undoの方式は記録に残っていない
- 技巧と山田将棋の読解（Issue #743）。下の節にまとめる

接続点は、PR #817で探索の手の進め戻しを集めた `Worker::make_move`・`unmake_move` である。

## 技巧と山田将棋の読解

### 技巧（C++版）

[技巧のC++版](https://github.com/gikou-official/Gikou)（2016〜2017年）を読んだ。
ライセンスはGPLv3で、本リポジトリ（GPL-3.0-or-later）と両立する。それでもコードは写さず、
設計だけを参考にする。

利きは `ExtendedBoard` が持つ。色ごと・升ごとに16bitの `Control` を置く。下位8bitが
利き数、上位8bitが「この升へ入ってくる飛び利きの方向」の8方向ビットである。
升は筋ごとの縦並びで、端の升を越える読み書きは前後の詰め物と端の補正マスクで吸収する。

更新は駒を「置く」「除く」の2つの操作に分解する。

- 短い利き: 駒種ごとに、5行×3列の近傍のパターンを3本のSSEレジスタで持つ。
  置くなら加算、除くなら減算を3回で済ませる
- 飛び利き: 置いた升の方向ビットを見て、その方向へ1升ずつ利きを切る。
  除いた升では同じ方向へ延ばす。どの駒の利きかを知らなくても切り延ばしができる。
  方向ビットが逆引きの役を果たす

undoは複写で行う。`StateInfo` が `ExtendedBoard` を丸ごと持ち、`MakeMove` で前の局面から
複写してから差分を当てる。`UnmakeMove` は添字を1つ戻すだけで、利きの計算をしない。
複写は1手あたり約0.6KBである。

読み出しは8近傍・15近傍をまとめて行う。`pshufb` で近傍の利き数を1本のレジスタへ集め、
「利き数が2以上の方向」を `movemask` でビット集合にする。

利きを使う処理は次のとおりである。

| 処理 | 使い方 |
|---|---|
| 1手詰め | 敵玉の8近傍の利き数から、動かす手の行き先（攻め2以上・受け1以下）と、打つ手の行き先を方向ビットで絞る。打つ手は256×256の事前表で駒種ごとの候補方向を引く。絞った後の確認はBitboardで行う |
| 玉の移動の合法性判定 | 行き先の相手の利き数が0か。移動元へ入る相手の飛び利きの方向で、玉の背後へ抜ける利きを拾う |
| 評価関数 | 駒・升・先手の利き数（3で打ち切り）・後手の利き数の組を特徴にする。玉の8近傍の利き数と駒で玉の安全度を引く |
| 指し手の確率モデル | 行き先の利き数、取られる駒への飛び利きの方向などを特徴にする |
| SEE | 使わない。Bitboardの `AttackersTo` で数える |

SEEに使わないのは、利き数の表からは攻め駒の位置が取れないためと読める。

### 山田将棋

第20〜36回のアピール文書の要約（`research/wcsc_appeals/`）と、第20回の原文を読んだ。
ソースは公開されていない。

盤は配列で、bitboardは使わない（第36回）。駒に1〜40の背番号を振る。
升ごとに「利いている駒の背番号ビットのOR」を64bitで持ち、空いたビットに飛び利きの
方向ビットを同居させる（第21回）。利き数も別に持つ。局面を進める・戻すたびに差分更新する
（第21回）。使い道は手生成とオーダリングで、8近傍の利き位置の表と合わせて使う。
undoの方式と1手あたりの手数は、文書に書かれていない。

## 選択肢と比較

決めることは3つある。表の置き場所、undoの方式、表の形である。遅延させるかも併せて決める。

### 置き場所

#### 案P1: `Position` に持たせる

ADR-0148の工程3の形である。`is_legal`・`see_ge`・王手駒の計算（`update_checkers`）が
`Position` の中から表を引ける。

欠点は払う範囲が広いことである。perft・局面の生成・定跡の生成・教師データの処理も
`Position::do_move` を通るので、全員が維持費を払う。局面を複製するたびに表も付いて回る。
ADR-0148はこれを理由の1つに挙げていた。

#### 案P2: 探索のワーカーに、評価関数の隣で持たせる

`Worker` に表を1つ置き、`make_move`・`unmake_move` で更新する。`Position` は変えない。
払うのは探索だけになる。

欠点は2つある。使う側は表を引数で受ける版が要る（`see_ge` と `is_legal` は `Position` のメソッドである）。
`update_checkers` は `do_move` の中で走るので、表引きへ置き換えられない。
ADR-0230の「王手判定」と「do_move・undo_move」のうち利きの分（合わせて2%前後）は、
取り返す対象から外れる。

### undoの方式

#### 案U1: 複写（技巧の方式）

手ごとに表を複写し、戻しは添字を戻すだけにする。`EffectTable` は2.6KBあるので、
1手で41本のキャッシュラインを書く。技巧の4倍強である。表の形を小さくしないと割に合わない。

#### 案U2: 戻した盤面で同じ差分更新を当て直す

`undo_move` の後に、同じ指し手で `EffectTable::update` を呼ぶ。触れる駒の集合は、進めた後の表の
逆引きで決まり、戻した盤面で利き先を計算し直す。移動元・移動先へ利く飛び駒は
進める前後で同じなので、集合が一致する。新しいコードは要らない。

戻しの手数は進めと同じだけかかる。

#### 案U3: 変えた升の旧値を積む

進めるときに、触れた駒の旧い利き先を積む。戻すときは積んだ値と今の値の差で逆引きを
立て下ろす。利き先の計算をしないので、戻しは進めより安い。積む場所と、その整合の
検査が増える。

### 表の形

#### 案T1: 既存の `EffectTable`（位置のBitboard、両方向）

検証済みの部品をそのまま使える。攻め駒の位置が取れるので、SEEの最初の攻め駒の集合を
表から引ける。利き数は `popcount` で取る。8近傍の利き数を一度に読むことはできない。

#### 案T2: 技巧型のバイト表（利き数と方向ビット）

0.4KBほどで、複写のundoと相性が良い。8近傍の利き数をまとめて読めるので、1手詰めの
絞り込みは速い。攻め駒の位置が取れないので、SEEには使えない。新しく書き、検証し直す必要がある。

#### 案T3: 駒番号のビット（山田将棋・オーナー案）

ADR-0148で案Cとして比べ、駒番号の管理が `Position` の不変条件を増やすとして採らなかった。
今回もその理由は変わらない。

### 遅延させるか

評価関数のaccumulatorのように、使うときまで更新を遅らせる形もある。手ごとの表か、
変更の記録を積む必要がある。使う側（1手詰め・SEE・合法性判定）は置換表で切れなかった
ノードのほぼすべてで呼ばれるので、遅らせて省ける分は小さい見込みである。

## Decision

**案P2・案U2・案T1で、常時更新の試作を作る**。

決め手は、使う側の書き換えまで含めた正味を最小の新規コードで測れることである。
表の形と更新の本体は、検証済みの `EffectTable` をそのまま使う。undoも同じ関数を当て直す
だけで済む。合格しなかったとき、替える箇所が分かる並びにしてある。
維持費が重ければ案U3、1手詰めの絞り込みが足りなければ案T2へ進む。

案P1を採らないのは、探索の外の経路まで維持費を払わせるためである。案P2で失う
`update_checkers` の分（2%前後）は、案P1へ移す理由になるほど大きくない。

### 書き換える処理

書き換えは、**返す値を1ビットも変えない範囲に限る**。探索の木が変わらないので、
固定深さのノード数で正しさを確かめられる。木が変わる書き換えは棋力の変更になり、
本ADRの外とする。

| 処理 | 書き換え | ADR-0230の「うち利き」（序中盤／終盤寄り、1T） |
|---|---|---|
| 1手詰め | 敵玉の8近傍の利き数で、候補の行き先を先に絞る（技巧の絞り込みの考え方）。確認は今のBitboardの手順のまま | 5.4%／10.7% |
| SEE | 最初の攻め駒の集合を表から引く。駒を除くたびに背後の飛び利き（X線）だけを足す | 2.2%／2.8% |
| 玉の移動の合法性判定 | 行き先へ利く相手の駒を表から引く。移動元へ利く相手の飛び駒のうち、玉の背後へ抜けるものを足す | 0.7%／1.7% |
| 合計 |  | 8.3%／15.2% |

### 統制群: SEEのX線の差分

SEEの書き換えには、表と無関係な改善が混ざる。駒を除くたびに `attackers_to` を
全部計算し直す代わりに、X線だけ足す差分である。これはADR-0151で表なしでもできる候補として
挙がっている。表の効果と混ぜないため、X線の差分だけを入れたビルドを統制群にする。

### 仮説と固定するもの（実験の規律の4点）

1. 仮説: 利きの表を探索のワーカーで常時維持し、上の3処理を表引きにすれば、維持費を
   取り返し、正味のNPSの低下が1%以内に収まる
2. 動かす変数: 利きの表とその利用の有無だけ。比べるのは統制群（c1）と候補（c3）である
3. 固定するもの: 評価関数（`hmwr/config.py` の現行）、局面の組（組み込みの4局面と
   `openings/profile_late_positions.txt`）、深さ（19と18）、置換表256MB、1スレッド、
   機械（開発機のM4 Pro）、交互測定の周回数（7周）。キューは止め、ほかのワーカーの
   ビルドが走っていない時間に測る
4. 事前登録: 下の「合格の条件」と「結果の読み方（事前登録）」

ビルドは4本で、1本ごとに1つだけ足す。

| 記号 | 中身 | 比べる相手と読む値 |
|---|---|---|
| c0 | origin/main（実装を始める時点） | — |
| c1 | c0＋SEEのX線の差分 | c0と比べる。ADR-0151の候補の効き（参考値） |
| c2 | c1＋利きの表の常時維持（使う側なし） | c1と比べる。**維持費** |
| c3 | c2＋3処理の表引き | c2と比べると**浮いた分**、c1と比べると**正味** |

### 見込み

ADR-0148の維持費は−7.19%だった（2026-08のエンジン）。いまのエンジンでも5〜8%と見る。
浮いた分は「うち利き」の半分（序中盤4.2%、終盤寄り7.6%）と見る。
正味の見込みは、序中盤の−1〜−4%と、終盤寄りの−1〜+3%である。
合格するとは限らない。

### 合格の条件

- Eloの判定: 本ADRではSPRTにかけない。探索の木を変えない変更なので、対局の差は
  NPSの差だけから来る。[ADR-0151](0151-speedup-sweep.md)と同じく、ノード数の一致とNPSで決める
- Elo以外の条件:
  - 正しさ: `hmwr verify` で、2組の全局面のノード数・評価値・最善手が c0 と c3 で一致する。
    デバッグビルドでは、手を進め戻すたびに表を作り直しと突き合わせる
  - 1手詰めの返り値: 書き換え前の `mate_1ply` と、テストの全局面で一致する
  - 速さ: c1に対するc3の正味のNPSが、2組の平均で−1.0%以上である
- 採否: 正しさと速さの両方を満たしたら、c3までをmainへ入れる（fix型）。
  −1.0%の代償は[ADR-0089](0089-improvement-criteria.md)の換算で1 Elo弱にあたる。
  段階3の利き数の入力の土台として前払いする

### 結果の読み方（事前登録）

| 結果 | 読み方と次の手 |
|---|---|
| 正味が−1.0%以上 | 合格。mainへ入れ、段階1を閉じる |
| 正味が−1.0%〜−3.0% | 単独では入れない。ブランチに残し、段階3の利き数の入力と同じSPRTで代償込みで測る |
| 正味が−3.0%未満、かつ維持費が5%超 | 維持費が重い。案U3（旧値を積むundo）で c2・c3 を作り直して測る |
| 正味が−3.0%未満、かつ浮いた分が「うち利き」の半分未満 | 使う側の書き換えが足りない。1手詰めの候補の絞り込み率を数え、案T2（技巧型のバイト表）を検討する |
| 案U3・案T2でも−3.0%未満 | 利きの常時維持を棄却し、本ADRをrejectedにする。段階3は利きを都度計算する入力から始める |

−3.0%を棄却の線にするのは、段階3の入力でどれだけ取り返せるかが分からない段階で、
3 Elo相当を超える固定費を払わないためである。ADR-0148の撤退ライン（5%）は、使う側を
含めない維持費の線だった。正味の線はそれより厳しくする。

c0とc1の差（X線の差分の効き）は、合否に使わない。+1%を超えたら、表と切り離して
先に入れる（ADR-0151の続き）。

## 測定（2026-10-17）

**正味は2組の平均で−4.3%だった**。合格の線（−1.0%）にも、段階3と一緒に測る線（−3.0%）にも
届かない。事前登録の読み方では、3行目（維持費が5%超）と4行目（浮いた分が「うち利き」の半分未満）の
両方に当たる。次の手は3行目に従い、案U3で c2・c3 を作り直して測る。Statusはproposedのままにする。

### 正しさ

`hmwr verify` の深さ13で、c1・c2・c3のどれもc0と比べて、組み込みの4局面と終盤寄りの12局面の
全局面でノード数・評価値・最善手が一致した。
デバッグビルドの `cargo test --workspace` では、手を進め戻すたびに表を作り直しと突き合わせて通った。
1手詰めは、表を引く版と引かない版が `mate_tests.rs` の全局面で同じ手を返した。
ランダム対局の4万局面と、疎な乱数局面の4万局面がこれに含まれる。

### 速さ

### 読み

- 維持費が重い。−8.7%はADR-0148の−7.19%より大きい。案U2は戻しにも進めと同じ計算を払う。
  戻しの利き先を計算し直さない案U3が、この分を削る
- 浮いた分も小さい。終盤寄りの+5.70%は「うち利き」の半分（7.6%）に届かない。
  1手詰めの「うち利き」は10.6%から7.4%へ減っただけで、3.2ポイントしか消えていない。
  候補の行き先を利き数で絞る技巧型の絞り込みは、表を位置で持つ案T1ではしていない
- 統制群のX線の差分（c1）は−1.1%で、表と無関係に遅くなった。最初に両色の攻め駒を集めるぶん、
  交換が1〜2手で終わる多くの呼び出しで損をする。SEEの割合はADR-0230の4.7%からc1で6.4%へ増えた。
  +1%の線を下回るので、mainへは入れない

次は事前登録の3行目に従う。案U3（変えた升の旧値を積む戻し）で c2・c3 を作り直し、
同じ手順で測る。それでも−3.0%未満なら4行目の案T2を検討し、両方で届かなければ5行目に従って棄却する。

利きの表を使うADR-0233〜0236は、どれもまだ判定が出ていない。いまはmainに表がないので、
各ADRの「ADR-0232が合格しない場合」の節に従って進める。

## ADR-0239で組み替えた（2026-10-17）

上の事前登録の続き（案U3、次に案T2）は走らせない。[ADR-0239](0239-effect-options.md)で、
実装の選択肢を6案で比べ直し、順を「都度作る利きの地図（案E）→技巧型のバイト表を複写で戻す（案T2に当たる案B）」へ組み替えた。

組み替えた理由は2つある。1手詰めの候補は、維持しない利きの地図だけで94〜96%が落ちると数えた。
表で浮く分の大半は表なしでも取れるので、表はその地図と比べて測る必要がある。
もう1つは、案U3が直すのは戻しの二重払いだけで、正味の見込みが序中盤で−3〜+1%にとどまることである。
案U3は棄却ではなく保留とし、再開の条件はADR-0239に書いた。本ADRの測定の記録はそのまま残す。

## Consequences

- ADR-0148の `EffectTable` が初めて探索から呼ばれる。ADR-0148のStatusは本ADRへ引き継ぐ
- `Worker` に、局面に付いて回る状態が1つ増える。`make_move` の契約（進めたら必ず対で更新する）に
  表も加わる
- `see_ge`・`is_legal`・`mate_1ply` に、表を受ける版ができる。探索の外は今の版を使い続ける。
  2つの版の一致はテストで保つ
- 段階3（利き数の入力）では、利き数が変わった升の集合が要る。今の `update` はそれを返さない。
  要るのは段階3なので、そのADRで足す。そのとき、升ごとの利き数を一度に読める形（案T2）も
  併せて比べる
- 技巧の評価関数は、利き数を3で打ち切って駒・升と組にした特徴を持っていた。段階3の入力の
  設計で先行例として参照する
- 見直しのトリガーは、評価関数の推論の割合が大きく変わったときである。浮いた分と
  維持費の比が動く
