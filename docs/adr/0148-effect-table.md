# 0148: 盤面の利きを差分で持つ

- Status: proposed
- Date: 2026-08-08
- 関連ADR: [0018](0018-perft.md), [0035](0035-nnue-accumulator.md), [0093](0093-mate1ply-in-search.md), [0124](0124-hot-path-allocs.md), [0133](0133-effect-pretraining.md), [0139](0139-mate1ply-in-search-retry.md), [0147](0147-effect-bucket-features.md)

## Context

**利きを都度計算している。** `attackers_to(c, sq, occ)` は呼ばれるたびに
そのマスへの利きを数え上げる。盤面全体の利きを保持していないので、
「どのマスに何枚利いているか」を知りたければ81マス分を呼ぶことになる。

[ADR-0147](0147-effect-bucket-features.md)のEffectBucketはこれを要求する。
特徴indexを被利き数で分割するので、accumulatorの差分更新のたびに
「利き数が変わったマス」が要る。都度計算では成り立たない。

用途はEffectBucketだけではない。SEEは駒の取り合いを毎回展開しており、
mate_1plyの見逃し（[ADR-0139](0139-mate1ply-in-search-retry.md)で近傍10.4%・
遠隔16.0%と実測）も利きの情報が薄いことに起因する。
[ADR-0140](0140-king-line-features.md)の玉ライン特徴も同じ土台に乗る。

**オーナーから駒番号による管理の提案があった**（2026-08-08）。将棋の駒は
40枚で増減しないので、各駒に番号を振り、マスごとに「利きを持つ駒番号の
ビット」を64bitで立てる。数はpopcountで取る。

## 差分計算で本当に効くもの

1手で利きが変わるのは3種類ある。

1. **動いた駒の利き。** 移動前の利きを消し、移動後の利きを足す
2. **取られた駒の利き。** 消す
3. **占有が変わったマスを通る飛び駒の利き。** 移動元が空いて伸び、
   移動先が埋まって縮む

**3つ目が本体である。** 1と2は動いた駒が分かれば済むが、3つ目は「fromと
toに利いている飛び駒は誰か」を知る必要がある。

ここに逆引きが効く。マスごとに「利きを持つ駒」を保持していれば、`from` と
`to` の2マスを見るだけで対象が決まる。保持していなければ、8方向を走査して
飛び駒を探すことになる。

**逆引きのキーは駒番号でなくてもよい。** 駒の位置でも同じ結果が得られる。

| 方式 | メモリ | 逆引き | 追加で要る管理 |
|---|---|---|---|
| 利き数だけ持つ | 162B | 不可（8方向を走査する） | なし |
| 位置のBitboard | 2.6KB | 可 | なし |
| 駒番号のビット | 648B | 可 | 盤上と駒台の付け替え |

## 選択肢と比較

### 案A: 利き数だけを持つ

`count: [[u8; 81]; 2]` で162バイト。いちばん小さい。ただし差分更新のたびに
`from` と `to` から8方向を走査して飛び駒を探すことになる。走査は占有に
当たれば止まるので短いが、1手ごとに16回（2マス×8方向）走る。

### 案B: マスごとに利きを持つ駒の位置をBitboardで保持する

```
to_sq:   [Bitboard; 81]  // sq に利きを持つ駒の位置
from_sq: [Bitboard; 81]  // sq の駒が利いているマス
```

両方向を持つ。利き数は `(to_sq[sq] & pos.pieces_of(c)).count_ones()` で取れる。
`from_sq` があるので、駒の利きを消すときに再計算が要らない。

Bitboardは `u128` なのでマスあたり16バイト、両方向で2.6KBになる。L1に収まる。

**既存のBitboardインフラをそのまま使える。** 駒番号を新設しないので、
`Position` の構造も `DirtyPiece` も変わらない。

### 案C: 駒番号のビットで保持する（オーナー案）

各駒に0〜39の番号を振り、`to_sq: [u64; 81]` にビットを立てる。648バイトで
案Bの4分の1、演算も `u64` 単発で済む。

代償は駒番号の管理である。駒が取られたら盤上から駒台へ、打たれたら駒台から
盤上へ番号を移す。`do_move` / `undo_move` の両方で整合を保つ必要があり、
`Position` に新しい状態が増える。参照実装（やねうら王のPieceNumber）は
評価関数の差分計算で同じ仕組みを持っており、実績はある。

## Decision

**案Bを採る。**

理由は導入の重さである。案Cのメモリ利得（2.6KB→648B）はどちらもL1に収まる
範囲で、棋力に効くとは考えにくい。一方、駒番号は `Position` の不変条件が
1つ増える。**利きテーブルの正しさと駒番号の整合を同時に疑う状況を作りたく
ない。**

案Aを採らないのは、走査を書くより逆引きを持つほうが差分更新の記述が短く、
誤りを見つけやすいためである。メモリの差（162B対2.6KB）はどちらもL1に収まる。

**案Cへ移る道は残る。** `to_sq` の型を差し替えるだけなので、利きテーブルが
正しく動いてから、速度を詰める段階で検討すればよい。

### 差分更新の手順

```
1. 影響を受ける駒の集合 S を作る
   - from の駒（動く駒）
   - to の駒（取られる駒。なければ空）
   - to_sq[from] と to_sq[to] に含まれる飛び駒
2. S の各駒について、from_sq[p] の各マスから p を落とし、from_sq[p] を空にする
3. 盤面を進める
4. S の各駒（移動後の位置）について利きを計算し、from_sq と to_sq へ書く
```

**駒打ちは `from` がないので to だけを見る。** 成りは駒種が変わるので、
移動後の利きが変わるだけで手順は同じである。

`undo_move` は逆順に戻す。`Position` は既に手番ごとの状態をスタックで
持っているので、利きテーブルもそこへ載せる。

### 遅延させるかどうかは後で決める

accumulatorは遅延方式で、`push` ではDirtyPieceを積むだけ、`ensure` で必要に
なったときに遡って計算する（[ADR-0035](0035-nnue-accumulator.md)）。評価が
呼ばれない枝ではFT更新を払わない設計である。

利きテーブルも同じ形にできるが、**まず常時更新で作る。** 遅延は状態の遡りが
増えて実装が重くなり、正しさの検証も難しくなる。常時更新でNPSの落ち幅を
測ってから、遅延が要るかを判断する。

### 検証

**full recomputeとの一致をテストで縛る。** 各マスの利きを `attackers_to` で
数え直したものと、差分更新で維持したテーブルが一致することを確かめる。
perft（[ADR-0018](0018-perft.md)）の経路に検査を差し込めば、数百万局面を
自動で通せる。

飛び駒の伸縮が絡む局面を明示的に入れる。飛車の前の駒が動く、角の利きが
開く、香の前で駒を取る、といった形である。

### 撤退ライン

**NPSが5%を超えて落ちるなら、常時更新を捨てて遅延方式へ移る。**
[ADR-0089](0089-improvement-criteria.md)の換算では5%の低下が5 Elo前後に
あたる。EffectBucketの効果が未知の段階で、それ以上の固定費は払えない。

遅延にしても落ち幅が戻らないなら、利きテーブル自体を棄却する。

## Consequences

- `Position` に状態が増える。`do_move` / `undo_move` の両方で整合を保つ
  必要があり、**利きテーブルは局面のコピーにも付いて回る**。`book gen` や
  `gensfen` のように局面を複製する経路でコストが増える
- 正しさの検証コストが継続的にかかる。探索の枝刈りは局面が壊れていても
  それらしい値を返すので、テーブルの不整合は気づきにくい
  （[ADR-0136](0136-quiet-teacher-positions.md)で似た経験がある）
- 効果があれば用途は広い。EffectBucket（[ADR-0147](0147-effect-bucket-features.md)）、
  SEE、mate_1plyの見逃し（[ADR-0139](0139-mate1ply-in-search-retry.md)）、
  玉ライン特徴（[ADR-0140](0140-king-line-features.md)）が同じ土台に乗る
- **単独では棋力を上げない。** 利きテーブルは基盤で、乗せるものがあって
  初めて価値が出る。単体でSPRTにかける対象ではない
- **[ADR-0147](0147-effect-bucket-features.md)の学習側とは独立に進められる。**
  学習は1局面あたりの予算が探索より2桁ゆるく、特徴を作るときに利きを
  都度計算しても回る。テーブルが要るのは推論側だけなので、2つの実装は
  並行できる

## 工程

1. **構造とfull recompute。** `Position` へ載せず、独立した型として作る。
   `attackers_to` を81マス分呼んだ結果と一致することをテストで縛る
2. **差分更新。** `do_move` / `undo_move` に対応する更新を書き、perftの
   経路でfull recomputeとの一致を数百万局面ぶん確かめる
3. **`Position` への統合とNPS測定。** 常時更新でどれだけ落ちるかを出す。
   撤退ラインは5%である
