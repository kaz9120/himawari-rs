# 0115: qsearchを参照実装へ揃え、mate_1plyを指さない方式へ書き換える（G6）

- Status: accepted
- Date: 2026-07-30
- 関連ADR: [0109](0109-reference-parity.md), [0093](0093-mate1ply-in-search.md), [0094](0094-mate1ply-speedup.md), [0029](0029-mate-search.md), [0077](0077-qsearch-futility.md), [0054](0054-qsearch-tt.md), [0028](0028-pruning-extensions.md), [0022](0022-tt-design.md)

## Context

[ADR-0109](0109-reference-parity.md)の追従キャンペーンの第7群。qsearchを
参照実装へ揃える。

qsearchは全ノードの大半を占めるため、差の影響が大きい。参照実装との差は
TTカットの条件・stand patの作り方・返り値の丸め・fail-softの下限・取る手の
選別・1手詰め判定・TT storeの扱いに及ぶ。

### 実装の途中で前提の漏れが分かった

qsearchへ1手詰め判定を組み込んだところ、**qsearchノードの8割前後で呼ばれて
NPSが1割落ちた。** 参照実装の条件（TTミスかつ非王手）をそのまま写しても
絞れていない。

原因は `mate_1ply` の実装方式だった。**本エンジンは候補手ごとに駒を動かす。**
`gives_check` で弾いた後、`do_move` → `generate(Evasions)` → `undo_move` を
行う。参照実装は `do_move` を1回も使わず、テーブルと利きの計算だけで判定する
（`source/mate/mate1ply_without_effect.cpp`、2,185行）。

[ADR-0093](0093-mate1ply-in-search.md)は探索への組み込みを-57.5 Eloで棄却した
とき「桁を変えるには指さずに判定する方式への書き換えが要る」と記録していた。
[ADR-0094](0094-mate1ply-speedup.md)で16%削ったが方式は同じままだった。

**ADR-0109の付録の作り方に原因があった。** 付録は `yaneuraou-search.cpp` を
Step単位で棚卸ししたもので、`source/mate/` 配下を対象に含めていない。呼び出し側
（S:4756-4784）だけが載っていて、本体の2,185行が視界に入っていなかった。

これは[ADR-0114](0114-g5-singular.md)（G5）と同じ構造である。あちらは
「singular率1割」という発動頻度の前提が成立しないままマージンを移して-99.0に
なった。こちらは「1手詰め判定が十分に安い」という前提が成立しないまま呼び出し
箇所を合わせた。**移植では、その機能が依存する前提条件も移植対象に入れる必要が
ある。**

## Decision

qsearchの差分を揃え、あわせて `mate_1ply` を指さない方式へ書き換える。

### qsearchの変更

| 項目 | 変更点 |
|---|---|
| TTカット | 非PV限定へ。窓との照合を原典の形へ |
| stand patのTT値上書き | TTヒットかつ非決着スコアのとき、boundの向きが合えば採用 |
| staticEvalの記録 | 非王手のときStackへ記録。王手中は据え置き |
| stand patのβ寄せ | 非決着スコアなら `(best+beta)/2` |
| 末尾のβ寄せ | `best > beta` かつ非決着スコアで同様 |
| futility時のbestValue引き上げ | 参照実装どおり引き上げる。`multi_pv > 1` のときだけ抑える |
| SEE不足時のbestValue引き上げ | 同上 |
| 取る手でない手の一律スキップ | 入口plyの静かな王手生成（[ADR-0028](0028-pruning-extensions.md)の項目7）を捨てた |
| 取る手のSEE下限 | −73。歩=90のスケールが一致するので絶対値のまま |
| 枝刈りの発動条件 | `!in_check` から `!is_loss(bestValue)` へ |
| TT store | Exactを書かない。詰み時はTTへ書かずに返す |
| 深さ引数 | 廃止 |

`QCapture` の `see_ge(m, 0)` フィルタも外した。原典は無条件で、損な取り合いの
切り捨てはSEE下限−73が担う。外さないと−73が意味を持たない。

### mate_1plyを指さない方式へ

`CHECK_CAND` 表（`[色][玉のマス]` の162エントリ、各 `[Bitboard; 16]`、計41,472
バイト）で候補の移動元を絞る。占有なしの最大到達で玉の近傍へ届く升を総当たりで
求めるため、任意の占有に対する上位集合になり取りこぼさない。

判定は4段で、すべて駒を動かさない。

1. 王手になっているか（`attackers_to` で王手駒の集合を求める。開き王手も拾う）
2. 玉の逃げ場が全部塞がっているか（隣接8マスを、玉を占有から抜いて問う）
3. 玉以外で王手駒を取れないか（取った後に王手が残るかを再計算する）
4. 合駒（玉と王手駒の間が空いていて相手に持ち駒があれば詰みとしない。安全側）

要点は移動元を除いた利きの計算である。占有を `(occ ^ from) | to` とし、移動元の
駒はビットマスクで外し、移動先の駒の利きは別に足す。玉の逃げ場を見るときは
さらに玉を抜く。原典コメントの `slide = pos.slide() ^ from ^ king | to` と同じ形に
なった。

**原典の2,185行は移していない。** 原典は `PieceTypeCheck` の区分と駒種別の
巨大な分岐で候補を列挙するが、本エンジンには `attackers_to(色, マス, 占有)` が
あり、マスクと占有の演算だけで「指した後の利き」が正しく出る。同じ効果を約250行で
得た。原典の構造（`CHECK_CAND_BB` とavoid付き利き）だけ借り、列挙の分岐は
移していない。原典の `can_king_escape` / `can_piece_capture` と判定の骨格が
一致することは確認した。

捕獲の判定は原典より厳しくした。原典はpinと `aligned` で素抜きを見るが、本実装は
捕獲側の駒を占有から抜いて王手の残りを再計算する。捕獲した駒が開き王手を作る筋も
正しく扱える。

### TTのdepth欄に負の値を持たせた

参照実装はstand patのstoreに `DEPTH_UNSEARCHED`（−2）を書き、`DEPTH_QS`（0）より
小さいことで「この記録ではTTカットしない」を表現する。本エンジンのdepth欄はu8で
これを表せなかった。

参照実装自身が内部でゲタを履かせて符号なしで持つため、同じ表現に変えた。深さの
比較はすべて差なので置換方針（[ADR-0022](0022-tt-design.md)）は変わらない。

## 測定

### mate_1ply単体のコスト

5,325局面（ランダムプレイアウトの非王手局面）。

| | 総時間 | 1回あたり | ベンチ枠を除く |
|---|---|---|---|
| 書き換え前 | 940.4 µs | 176.6 ns | 174.1 ns |
| 書き換え後 | 144.8 µs | 27.2 ns | 24.7 ns |

**6.5倍（実質7.0倍）。** 内訳は候補列挙8.4ns、検証11.5ns、駒打ち4.2ns。
桁には一歩届かない。

### 探索全体のNPS

深さ17、1スレッド、同一実行内で交互に測定。

| 比較 | NPS | 差 |
|---|---|---|
| 旧mate_1ply込みのG6 | 1,319,713 | — |
| 新mate_1ply込みのG6 | 1,484,041 | **+12.45%** |
| G5完了時点（qsearchに1手詰めなし） | 1,445,383 | — |
| 新mate_1ply込みのG6 | 1,457,577 | +0.84% |

**G6が失ったNPSを全額回収した。** 1手詰め判定を入れないG5完了時点と同等に
なっている。ノード数は旧版と完全一致で、探索木は変わっていない。

### 正しさ

玉2枚＋攻め駒1〜4枚＋遠隔駒0〜2枚＋守り駒0〜2枚＋持ち駒の疎な乱数局面を
40,000局面流した。

**偽陽性は0。** 返した2,891件すべてが実際の詰みで、オラクルとも一致した。
現行の仕様「返した手は詰みであることが保証される（見逃しはあり得る）」を
保っている。

見逃し率は10.43%（近傍のみ）と16.03%（遠隔駒あり）で、**書き換え前と完全に
一致した**（同じ2,891/552）。合駒を安全側に倒した判断は、この40,000局面では
1件も損をしていない。

### 1手詰め判定の呼び出し回数

qsearchノード比で、深さ13は77〜91%、深さ19も同程度である。深さを上げても比率は
動かない。「TTミスかつ非王手」の条件はほとんど絞れていない。

**絞れていないことが問題ではなくなった。** 1回27nsなら8割で呼んでも
NPSへの影響は0.84%に収まる。

### qsearchの発動率

深さ19。TTカット2.5〜8.3%、stand patのTT値上書き0.3〜1.2%、stand patのβ寄せ
27〜47%、末尾のβ寄せ6〜11%、futility時の引き上げ2.6〜58%、SEE不足時の引き上げ
2.3〜19%、取る手でない手のスキップ4.7〜9.6%、SEE下限で捨てた8.4〜33%。

すべて基準の0.1%を大きく上回る。

## SPRT

既定条件（10+0.1、elo0=0、elo1=5、α=β=0.05）でG5完了時点のバイナリと比べた。

```
H1採択 | 1448局 | +740 =157 -551 | Elo +45.6 [+28.5,+62.9] | LLR +2.89
```

**+45.6 Eloで採択した。** 6群の単純加算で+442.6になる。

**mate_1plyを書き換える前に一度測りかけていた。** 286局の時点で中断し、棋譜を
破棄した。旧mate_1plyのままではNPSが1割落ちる状態で、参照実装が前提とする
「1手詰め判定が安い」が成立していない。前提を揃えてから測るのが正しいと
判断した。

## Consequences

**1手詰め判定が実質無料になった。** [ADR-0093](0093-mate1ply-in-search.md)が
-57.5で棄却した理由は呼び出しコストだった。それが消えたので、通常探索への
組み込み（原典のS:2896-2960）も再訪できる。この群には含めていない。

**原典の行数を移すことが目的ではない。** 2,185行に対して約250行で同じ効果を
得た。本エンジンの `attackers_to` が「指した後の利き」を占有の演算だけで返せる
ためである。参照実装の構造（候補を絞る表と、avoidを除いた利き）を借りつつ、
列挙の分岐は本エンジンの基盤に合わせた。**再現とは同じ挙動を得ることで、同じ
コードを持つことではない。**

`mate_1ply` の見逃し率は10〜16%のまま変わらない。原典は遠打ちの合駒不能判定や
王手クラスをより広く扱うため検出率が高い。検出率を上げるのは別の変更で、独立に
SPRTが要る。

棄却した最適化を2件記録する。`gives_check` を検証の先頭に置く案は147.6→165.5 µsで
悪化した（`attackers_to` 1回のほうが安い）。玉の近傍を守る利きを局面ごとに1回だけ
前計算する案は145→284 µsで大幅に悪化した（候補が0本の局面でも前計算が走る）。
**元が安いと前計算が乗らない。**

TTのdepth欄の表現を変えた。[ADR-0022](0022-tt-design.md)の置換方針は変わらないが、
depth欄を直接読むコードがあれば影響する。

付録の漏れが2群連続で出た（G5の返り値、G6のmate_1ply本体）。**付録は
`yaneuraou-search.cpp` 中心に作ったため、他ファイルの依存と横断的な項目が
落ちている。** 残りの群（G7〜G10）は `timeman.cpp` と `book/` を対象に含めて
あるが、指示書では「その機能が読む値・呼ぶ関数がすべて揃っているか」を先に
確かめる手順を入れる。
