# 0010: Bitboardレイアウト

- Status: accepted
- Date: 2026-07-17
- 関連ADR: [0003](0003-toolchain.md), [0008](0008-square-coordinates.md)

## Context

81マスの盤面を表すbitboardの内部表現を決める。座標系はADR-0008で
筋優先（`sq = file * 9 + rank`）に確定しており、bit i = Square i とする。
候補は単一の u128 と、C++系将棋エンジンの伝統である2ワード分割
（[u64; 2]、1〜7筋の63bit＋8〜9筋の18bit）の2つ。

C++で2ワード分割が主流だったのは、当時native 128bit整数がなく
SSE2レジスタで扱う設計だったためだ。Rustにはnative u128があり、
x86_64/aarch64ともGPRペアにコンパイルされる。前提が変わっているため、
実測して決める。

## 選択肢と比較

計測は `crates/core/benches/bb_layout.rs`（criterion）。ランダム盤面
1024個への一括適用の時間。環境は Apple Silicon（aarch64、NEON）、
nightly-2026-07-17、`-C target-cpu=native`。

| 操作 | u128 | [u64;2] | 差 |
|---|---|---|---|
| 段方向シフト ±1（歩の利き） | 303〜309 ns | 265〜267 ns | 分割が約14%速い |
| 筋方向シフト +9 | 285 ns | 321 ns | u128が約13%速い |
| popcount | 258 ns | 338 ns | u128が約24%速い |
| ビット走査（素朴実装） | 16.5 µs | 7.3 µs | 分割が2.2倍速い |
| ビット走査（u128をワード分割で走査） | 6.96 µs | — | u128でも同等以上 |
| 香の利き（Qugiy式・増加方向） | 759 ns | 936 ns | u128が約19%速い |

読み取れることは3つ。

1. ビット走査の2.2倍差は表現の差ではない。u128のまま走査ループだけ
   64bit×2本に分割すれば逆転する（`trailing_zeros` と `v &= v-1` が
   128bit演算だと桁借り伝播で重いため）
2. 香の利き（Qugiy式の減算）はu128が速い。分割側はマスクがどちらの
   ワードにあるかの分岐を持つ。u128は81bit全体に桁借りが1命令で伝播する
3. 残る差は±1シフトの約14%（分割はワードまたぎの桁上がりが構造的に
   不要）と、popcount・+9シフトでのu128優位。いずれも1盤面あたり
   0.1ns未満の差で、決定打にならない

## Decision

u128の単一ワード表現を採用する。`Bitboard(u128)` のnewtypeとし、
bit i = Square i、bit 81〜127は常に0を維持する。

決め手は2つ。性能が実測で同等以上であること（走査はワード分割実装で
回収できる。利きの減算トリックはむしろ速い）、そしてコードの単純さだ。
マスク定数が1個で済み、ワードまたぎの場合分けが表現から消える。

あわせて実装規約を1つ定める。ビット走査（指し手生成のシリアライズ等の
ホットループ）は、u128を64bitワード2本に分けて回す実装とし、
`Bitboard` のイテレータ／for_each系メソッドの内部に閉じ込める。
利用側はこの規約を意識しない。

## Consequences

- 盤面演算のコードから2ワードの場合分けが消え、Qugiy式の利き
  （P1の利き生成ADRで詳細化）が81bit一括の減算で書ける
- 走査の性能はイテレータ実装の規約に依存する。実装時にベンチで
  素朴実装との差（約2.3倍）を確認するテストポイントになる
- 計測はaarch64のみ。対局・学習環境のx86_64では128bitシフトの
  命令構成が異なるため、P1実装完了後にx64でperft/ベンチを再計測し、
  傾向が逆転していればこのADRを見直す
- u128のアラインメントは16バイト。bitboardテーブルのメモリ配置は
  キャッシュライン境界に乗りやすく、悪くない副作用
