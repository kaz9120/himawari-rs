# 0116: 停止を予約する構造へ移し最小思考時間を入れる（G7）

- Status: accepted
- Date: 2026-07-31
- 関連ADR: [0109](0109-reference-parity.md), [0021](0021-time-management.md), [0102](0102-move-horizon.md), [0059](0059-easy-move-scaling.md), [0074](0074-feature-verification.md), [0028](0028-pruning-extensions.md)

## Context

[ADR-0109](0109-reference-parity.md)の追従キャンペーンの第8群。時間管理を
参照実装（やねうら王）へ揃える。

**参照実装は上限超過を検知してもその場で止めない。** 停止時刻を `search_end` へ
予約し、最小思考時間と秒単位の切り上げが下支えする。本エンジンは
`over_maximum()` でその場でstopを立てる。

参照実装の時間管理は5つの部品の連鎖で成立している。配分式、最小思考時間の床、
秒単位の切り上げ、停止の予約、ponderの会計である。**本エンジンが持つのは配分式
だけだった。**

2026-07-29の時間管理キャンペーンで6案すべてを棄却したのは、この連鎖の途中の
1本だけを移していたためである（[ROADMAP.md](../ROADMAP.md)）。

## Decision

支えを先に入れ、配分式は最後に判断する。この順序は
[ADR-0102](0102-move-horizon.md)の反省による。あちらは配分式の分母だけを
move horizon方式へ変えて-107.2だった。参照実装ではその小ささを最小思考時間の
加算項と秒単位切り上げの1000ms下限が受け止める。

### 依存の棚卸し

実装の前に、この群が読む値と呼ぶ関数を洗い出した。[ADR-0114](0114-g5-singular.md)（G5）と
[ADR-0115](0115-g6-qsearch.md)（G6）で前提条件の漏れが2群連続で出たためである。

読む値で6つ、関数で4つ不足していた。

| 不足 | 内容 |
|---|---|
| `MinimumThinkingTime` | オプションなし。既定2000で追加 |
| `SlowMover` | オプションなし。既定100で追加 |
| `RoundUpToFullSecond` | オプションなし。既定trueで追加 |
| `max_moves_to_draw` | Worker側にはあったが**TimeManagerへ渡っていなかった**。0を100000へ読み替える処理もなかった |
| `startTime` | go受領時刻を持っていない。G8で必要になる |
| `abortedSearch` | 探索が中断で終わったかのフラグがない |
| `round_up()` / `set_search_end()` / `minimum()` / `use_time_management()` | いずれもなし |

**棚卸しは効いた。** `max_moves_to_draw` がTimeManagerへ渡っていない件は、
配分式のMTG計算に直接効く。移してから気づいていたら原因の切り分けが難しかった。

### 入れたもの

| 項目 | 原典 | 内容 |
|---|---|---|
| オプション3つ | T:47, 52, 55 | 既定値は原典どおり |
| `round_up()` | T:312-344 | 秒単位で切り上げ、最小思考時間を下限とし、NetworkDelayを引く |
| `set_search_end()` | T:347-373 | 停止時刻の予約 |
| 反復深化末尾の予約 | S:2041-2048 | `break` を予約に置換 |
| 定期チェックの予約 | S:5553-5558 | 新規 |
| 即停止条件を3つへ | S:5541-5558 | movetime超過・nodes超過・`search_end <= elapsed` のみ |
| abortedSearchのロールバック | S:1864-1893 | 中断時に前の反復のPVとスコアへ戻す |
| `SlowMover` | T:280 | optimumの係数 |
| `isFinalPush` | T:291-302 | 秒読みで持ち時間が尽きかけたら使い切る |
| 切れ負けのmax_ratio抑制 | T:270-276 | 5分を切ったら比率を下げる |

### 配分の分母は現行式を据え置く

**参照実装のmove horizon方式は本エンジンで成立しなかった。**

支えをすべて揃えたうえで測っても、10+0.1で730局・-15.7 Elo [-41.1, +9.5]
だった。分母だけを移した[ADR-0102](0102-move-horizon.md)は-107.2で、支えを
足しても中立までしか戻らない。

分母は現行式（`max(48 − ply/2, 16)`、[ADR-0021](0021-time-management.md)）を
据え置き、支えだけを参照実装から採る形にした。切れ負け時のmax_ratio抑制は
分母に依らない安全弁なので採り、倍率は現行の3倍を据え置いた。

[ADR-0114](0114-g5-singular.md)のsingular率に続いて、**参照実装の値が本エンジンで
成立しない2例目**である。

## 実装のバグを1件潰した

切り分け版（配分式=現行）でも10+0.1で1984局・-25.1 Elo [-40.5, -9.8]だった。
支えだけのはずなのに、move horizon版より悪い。原因を実測で特定した。

**犯人はoptimumの定数項だけだった。**

参照実装はoptimumからNetworkDelayを引かない。あちらは
`minimumTime = MinimumThinkingTime − NetworkDelay`（既定1880ms）がoptimumへ
加算されるため、**床の中に遅延の保護が含まれている。** SPRTのために
`MinimumThinkingTime=1` へ下げると、床と一緒に保護まで消える。

結果、optimumが常に121ms大きくなった。10+0.1では `avail` が42〜600msしか
ないので1.6〜2.8倍の下駄になる。

対応のある測定（同じ12局面へ同じ残り時間を与える）の結果である。

| 残り時間 | base | G7現状 | 候補5だけ無効 |
|---|---|---|---|
| 3500ms | 127ms | 307ms（2.41倍） | 156ms |
| 2500ms | 87ms | 228ms（2.62倍） | 119ms |
| 1400ms | 42ms | 123ms（2.94倍） | 53ms |

全局対局では、**序盤に0.7ply得をして終盤で8ply損**をしていた（ply120以降で
baseの19.6に対し11.5）。残り1.6秒未満で指した手はbaseの12%に対し36%だった。
勝敗が決まる場所で浅くなる。

### 構造は無害だった

同時に4つの候補を潰した。いずれも損をしていない。

| 候補 | 発生率 | コスト |
|---|---|---|
| 予約して次の反復に入る | 63%の手 | 平均1.00ms・1191ノード |
| maximum超過で即停止しない | 27%の手 | 切り上げ無効時は予約が即停止と同じ |
| abortedSearchのロールバック | 0.08%（2539手中2件） | 無関係 |
| movetimeからNetworkDelayを引かない | 未行使 | SPRTは `go btime` しか使わない |

**停止の予約という構造そのものは10+0.1でも害を出していない。** 害は配分式の
定数項だけから出ていた。

### 修正

optimumからもNetworkDelayを引く。あわせて[ADR-0021](0021-time-management.md)に
あった安全弁を2つ戻した。`minimum_time` を0以上にクランプし（全手で-119に
なっていた）、maximumがoptimumを下回らないようにする（32%の手で下回っていた）。

`MinimumThinkingTime=2000` では `1880 + avail − 120` となり、参照実装と6%以内で
一致する。長い持ち時間での挙動はほぼ保つ。

## 測定条件の限界

**この群は既定条件（10+0.1）では本来の効きを測れない。**

参照実装の `MinimumThinkingTime=2000` は実戦の持ち時間を前提にした値である。
10+0.1で既定値のまま計算すると次のようになる。

```
ply=1  残り10000ms → min=1880 opt=2188 max=2880
ply=30 残り 6000ms → min=1880 opt=2161 max=2880
ply=60 残り 2500ms → min=1380 opt=1380 max=1380
```

初手に10秒中2.9秒を使う。300+10で同じ計算をすると現行との差は+0.6〜0.8%に
とどまる。**参照実装は10秒の持ち時間を想定していない。**

そのためSPRTは `--copt MinimumThinkingTime=1 --copt RoundUpToFullSecond=false` で
回す。床を外して構造の価値だけを測る条件である。既定値そのものの妥当性は
floodgateでの実戦で確認する。

## SPRT

床を外した条件（`--copt MinimumThinkingTime=1 --copt RoundUpToFullSecond=false`）で
3回測った。

| 回 | 内容 | 結果 |
|---|---|---|
| 1 | 配分式=move horizon方式 | 730局 -15.7 [-41.1,+9.5] |
| 2 | 配分式=現行式（バグあり） | 1984局 -25.1 [-40.5,-9.8] |
| 3 | 配分式=現行式（バグ修正後）、非劣性 | **6000局 +1.8 [-6.5,+10.1] LLR +1.19** |

3回目は非劣性検定（elo0=-5、elo1=0）で、3000ペアの上限まで回して判定に
至らなかった。**LLRは+1.19で悪化していない側へ向かっているが、判定には
+2.94が要る。**

### H1を得ないまま取り込む判断

[ADR-0109](0109-reference-parity.md)は「mainへ取り込む条件は変えない。SPRTで
H1採択した変更だけを入れる」と定めた。G7はこの条件を満たさない。それでも
取り込む。根拠は4つある。

**測定条件が参照実装の前提と桁違いである。** 10+0.1で既定値のまま計算すると
初手に10秒中2.9秒を使う。300+10なら現行との差は+0.6〜0.8%にとどまる。
参照実装は10秒の持ち時間を想定していない。床を外した条件で測るしかなく、
その条件では構造の価値が現れにくい。

**6000局で中立を示した。** +1.8 [-6.5,+10.1]である。害がないことは十分な
局数で確かめた。判定まで回すにはさらに1万局規模が要り、時間対効果が見合わない。

**構造が無害であることを実測で確かめた。** 停止の予約は63%の手で発生するが
コストは1手あたり1ms、abortedSearchのロールバックは0.08%しか発動しない。
SPRTとは独立に、時間の使い方の実測で裏づけた。

**G8の前提である。** ponderの会計・探索継続・`stopOnPonderhit` は停止の予約が
あって初めて成立する。ここで止めると追従が進まない。

この判断はオーナーの合意による（2026-07-30）。「短い時間で効果がないだけで、
全体観点では棋力が向上しており、G8も必要な改修だ」という見立てで、原因が
バグなら潰してから入れるという条件がついた。バグは潰した。

**既定値の妥当性はfloodgateでの実戦で確認する。** 本エンジンの既定は参照実装
どおり `MinimumThinkingTime=2000`・`RoundUpToFullSecond=true` のままにする。
floodgateは300+10なので、この値が本来の想定に近い。

## Consequences

**G8の前提が揃った。** ponderの会計・探索継続・`stopOnPonderhit` は、停止の予約が
あって初めて成立する。2026-07-29に棄却した3件（[ADR-0104](0104-ponderhit-time-accounting.md)の
-117.8、[ADR-0106](0106-ponderhit-continue.md)の-54.3、[ADR-0107](0107-ponder-optimum-bonus.md)）は
4本の支えのうち1本ずつを移したもので、4本目がこの群にあたる。

`abortedSearch` のロールバックは実質バグ修正である。中断した探索で得た詰み負けの
スコアは、残りのroot手を読めば覆りうる。発動は0.08%と稀だが、発動する局面は
「負けが見えた」局面である。

**移植の忠実さが害になる例が出た。** optimumからNetworkDelayを引かないのは
参照実装のとおりだが、それは床が保護を含むという前提の上に成り立つ。前提を
変えると忠実さが裏目に出る。[ADR-0074](0074-feature-verification.md)の
スケール前提の確認は、係数の単位と発動頻度に加えて**「その値が何に守られて
いるか」**も見る必要がある。

配分の分母を据え置いたので、参照実装との差が残る。この差は
[IDEAS.md](../IDEAS.md)へ戻さない。move horizon方式は2度測って2度とも
通らなかったためである（-107.2と-15.7）。再訪するなら、本エンジンの現行式が
なぜ釣り合っているかを説明できてからにする。
