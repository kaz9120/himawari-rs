# 0031: Lazy SMP

- Status: proposed
- Date: 2026-07-19
- 関連ADR: [0020](0020-search-threading.md), [0022](0022-transposition-table.md), [0028](0028-pruning-extensions.md)

## Context

探索は現在単一スレッド。マルチコアを使う並列化方式を決める。
P3出口条件に「NPSスケーリング確認」がある。決めるのは
共有物の範囲、スレッドごとの多様化、最終手の選び方、
検証方法。

## 選択肢と比較

探索木を分割するYBWC系は実装が複雑で、現代のエンジンは
ほぼすべてLazy SMP（全スレッドが同じ探索をTT共有で走らせ、
探索順序の揺らぎで自然に分担する）に収斂している。
Lazy SMPを採用する。実質の論点は多様化と集約の2点。

### スレッドの多様化

案A: ワーカーごとに開始深さ・aspiration窓をずらす。
案B: 何もずらさない（TT到着順の揺らぎだけに任せる）。
Stockfishは明示的なずらしを廃止して案Bに移行した経緯があり、
実装も単純なので案Bから始める。効果不足ならSPRTでずらしを足す。

### 最終手の選び方

案A: メインスレッドの結果をそのまま使う。
案B: 全ワーカーの(深さ, スコア)で投票する。
案Aから始めて、案Bを1機能=1SPRTで検証する。

## Decision

- ThreadPool（ADR-0020）をNワーカーに拡張する。共有は
  Shared一式: TT（ロックレス、ADR-0022）、stopフラグ、
  nodes集計。history・killers・counter・評価器は
  スレッドローカル
- 時間管理・info出力・stop判定はメインワーカーだけが行う
  （ADR-0020/0021の責務分担を維持）。他ワーカーはstopフラグに
  従うだけ
- bestmoveはメインワーカーの結果を使う（案A）
- USIオプションThreadsは既存宣言（1〜512）をそのまま生かす
- 検証は2系統。強さ: Threads=4 vs Threads=1をSPRT
  （時間制一定なので並列効果がEloに出る）。スケーリング:
  固定局面セットでThreads=1/2/4/8のNPSを計測しROADMAPに記録
- 乱数種などの決定性は放棄する（並列探索は本質的に非決定）。
  nodesモードの再現性はThreads=1に限る旨をselfplayの
  ドキュメントに明記する

## Consequences

- selfplayゲートは今後もThreads=1で行う（変更の効果測定に
  並列の揺らぎを混ぜない）。並列自体の検証だけThreads指定で行う
- TTの世代・置換ポリシーが並列で劣化する可能性がある。
  hashfullとNPSスケーリングの計測で監視する
- 探索のバグ再現が難しくなる。単スレッドで再現してから
  直す運用を基本とする
