# 0166: MovePickerの生成段を切り出してフレームを縮める

- Status: accepted
- Date: 2026-08-15
- 関連ADR: [0074](0074-feature-verification.md), [0124](0124-hot-path-allocs.md), [0151](0151-speedup-sweep.md), [0164](0164-bona-piece-bitset.md), [0165](0165-bona-block-layout.md)

## Context

[ADR-0165](0165-bona-block-layout.md)の起草時に、残る2大項目
（`MovePicker::next` 18.65%、`NnueState::evaluate` 17.43%）を
「[ADR-0151](0151-speedup-sweep.md)が測って候補外」と書いた。**これは
誤りだった。** プロファイルを関数単位でしか見ておらず、ADRの記述を
確かめずに書いた。

命令アドレス単位でサンプルを逆アセンブルへ帰属させ直すと、`next` の
18.665%の内訳はこうなる。

| 箇所 | self時間 |
|---|---|
| `partial_insertion_sort`（3か所合計） | 7.87% |
| `score_quiets` のループ | 6.08% |
| `next` の入口（プロローグ） | 1.23% |
| `select` | 1.02% |
| `next` の出口（エピローグ） | 0.49% |
| 段のジャンプテーブル | 0.44% |

ADR-0151が測ったのはソートの挿入方法（群M）とprefetch
（[ADR-0056](0056-tt-prefetch.md)経由）だけで、**呼び出しごとの入口・出口は
手つかずだった。**

## 選択肢と比較

### 案A: 生成段を切り出してフレームを追い出す

`next` の入口は `sub sp, sp, #0xaa0`（2,720バイト）でフレームを確保し、
`stp` 6本で呼び出し元保存レジスタ12本を退避する。2,720バイトの正体は
`MoveList`（`[MaybeUninit<Move>; 608]` ＋ len、約2.4KB）で、生成段3か所
（`CaptureInit` 系・`QuietInit`・`EvasionInit`）がスタックに置いている。

**生成段を通るのは `next` の呼び出し5〜6回に1回である**（プロローグ1.23%と
`score_quiets` 6.08%の比から逆算）。残りは手を1つ返すだけで、この領域を
使わない。LLVMが `loop { match }` のループ不変量として巻き上げた結果、
毎回の呼び出しがフレーム確保とレジスタ退避を踏む。

生成段を `#[inline(never)]` のメソッドへ切り出せば、巻き上げが止まる。

### 案B: ソートの挿入判定をビットマスクへ落とす

ソートのサンプルは分岐ターゲットに集中している。シフトループの脱出
（2.64%）、その本体先頭（1.73%）、limit判定の両方の落ち先（0.84%＋0.57%）
である。**分岐予測ミスのskidの典型で、7.87%のうち実データ移動は2.3%前後、
残る約4%は予測ミスのペナルティと読める。**

群Mはシフト長の分布（3以下が61.5%）を測って「比較と移動を減らす」方向へ
動き、3通りとも負けた。律速が分岐なら、二分探索が別の予測不能な分岐を
作るので負けたのは辻褄が合う。

そこでlimit判定を64要素ぶんのビットマスクへ分岐なしに落とし、立っている
ビットだけを走査する。挿入ループには触らないので、群Mが失敗した場所は
通らない。

## Decision

**案Aを採り、案Bは棄却する。**

### 案A: +0.83% NPS（採用）

フレームは2,720バイトから144バイトになった（`sub sp, #0xaa0` →
`#0x90`）。方向を入れ替えた7周の交互測定を2組取った。

| 測定 | candの優位 |
|---|---|
| base先行（1組目） | +0.77% |
| cand先行（1組目） | +1.02% |
| base先行（2組目） | +1.48% |
| cand先行（2組目） | +0.06% |
| 対照（同一バイナリ、3回） | −1.07% / +0.43% / −0.30% |

**4回すべてで正、平均+0.83%。** ばらつきは大きいが対照は符号が定まらず、
順序効果では説明できない。[ADR-0165](0165-bona-block-layout.md)・
ADR-0151群Nと同じ判定になる。

機能検証（[ADR-0074](0074-feature-verification.md)）は深さ13・20で全4局面の
ノード数・評価値・最善手が一致した。コードの移動だけで、生成順もスコアも
変えていない。

### 案B: −0.31〜−1.01% NPS（棄却）

案Aを適用したバイナリをbaseにして直接測った。

| 測定 | 案Bの優位 |
|---|---|
| base先行 | −1.01% |
| cand先行 | −0.31% |
| 対照 | −0.63% |

**両方向で負である。** 並びが旧実装と完全一致することはテストで確かめて
あり、正しさの問題ではない。

負けた理由は走査のパス数と見る。元の実装は判定と挿入を1ループでやるが、
マスク版はマスク生成とビット走査の2パスになる。**分岐予測ミスの
ペナルティ（推定1.4%）より、全要素を舐める追加パスのほうが高くついた。**

これで `partial_insertion_sort` の高速化は4通り目の失敗になる（群Mの3通り
＋本案）。**分岐予測という別の根拠から攻めても効かなかった。** self時間
7.87%のうち約4%が予測ミスだという観測は変わらないが、それを取りに行く
コストが利得を上回る構造になっている。次に着手する人は、この関数に
触る前に「1パスを保ったまま分岐を消せるか」を先に示すべきである。

## Consequences

- `next` の本体から生成の詳細が消え、段の遷移だけが残った。参照実装
  （movepick.cpp）は生成をその場に書いているので、構造は少し離れる。
  離れる理由をこのADRが持つ
- 案Bのコードはmainへ入れない。ADR-0151群Mと同じ扱いである
- ADR-0165の起草時の誤り（「手が尽きた」）は同日中に訂正した。
  **関数単位のプロファイルだけで「もう無い」と判断すると間違える。**
  帰属先が呼び出し行に集まると、その内側の構造もADRの記述も見えなくなる。
  行単位・命令単位まで落として初めて、1手返すたびに2.4KBのフレームを
  確保していることが見えた
- 残るのは `score_quiets`（6.08%）である。1手あたり7回の境界検査と、
  レジスタに乗り切らない5面ぶんの面先頭のスタック再読み込みがある。
  ただし時間の一部はhistoryロードの待ちで、命令を削っても
  [ADR-0164](0164-bona-piece-bitset.md)と同じくメモリ待ちに隠れる公算が
  ある。ROADMAPの候補に残す
