# 0243: 手の並べ替えを、生成の順に依存しない形にする

- Status: proposed
- Date: 2026-10-21
- 関連ADR: [0241](0241-mailbox-board-research.md), [0235](0235-quiet-ordering-hanging.md), [0074](0074-feature-verification.md), [0163](0163-sprt-hypothesis-choice.md), [0217](0217-sprt-pass-cap.md)

## Context

探索の盤が配列盤になった（[ADR-0241](0241-mailbox-board-research.md)）。配列盤の速さの手直しは、これまで探索の木を変えない形に限ってきた。
木が同じなら、`hmwr verify` のノード数の一致で正しさを確かめられ、NPSだけで入れられるためである。
木を変える手直しは1件ごとにSPRTが要り、数%の速さを確かめるのに開発機を半日〜1日使う。

木を変えない縛りのせいで、効く見込みの手直しが2件、既定の外で止まっている（ADR-0241の第16回）。

| 手直し | 効き（命令数） |
|---|---|
| 盤上の駒を駒種ごとに回す生成（`HIMAWARI_MB_ORDER=type`） | 生成 −11.3%、盤面操作の全体 −4.6% |
| 取る手を行き先の側から引く生成 | 取る手の生成 −7.4% |

生成する手の集合は同じで、変わるのは生成の順だけである。それでも木は大きく動く。
`hmwr verify` の組み込み4局面で、ノード数は −17%〜+42% 変わった。

原因は手の並べ替えにある（Issue #872）。`partial_insertion_sort`（`crates/engine/src/movepick.rs`）は、閾値以上の手だけを点数で並べる。
並べ方は3つの点で生成の順に依存する。

1. 同じ点数の手の前後が、生成の順で決まる
2. 閾値未満の手は並べず、生成の順のまま残る。しかも挿入のたびに入れ替わるので、残り方は列の中身次第になる
3. 取る手と王手回避は全数を並べるが、1と同じく同点の前後が生成の順で決まる

閾値未満の手が並ぶ順は、LMRとmove count pruningで「何番目の手か」を通して木を動かす。
並べ方が生成の順に依存しなければ、生成をどう作り替えても木は変わらない。以後の生成の手直しは、再び `verify` とNPSだけで入れられる。

## 選択肢と比較

### 案A: 部分ソートを安定にする

閾値以上の手を並べるときに、閾値未満の手の順を保つ。2の入れ替わりは消える。
ただし、閾値未満の手は生成の順のまま残る。1も残る。生成の順に依存しない形にはならない。

### 案B: 全部の手を、点数と手の符号の順で並べる

点数の降順に並べ、同点なら手の符号（`Move` の値）の昇順で並べる。順序が全順序になるので、生成の順に依存しない。
静かな手は閾値未満の手も並ぶ。点数（history）の順で後ろの手が並ぶので、並べ替えそのものが変わる。
費用は、静かな手を全数並べる分だけ増える。

### 案C: 閾値以上は点数と符号の順、閾値未満は符号の順

閾値以上の手は案Bと同じに並べ、閾値未満の手は手の符号だけで並べる。生成の順に依存しない。
閾値未満の手の並びは、今の生成の順とも点数の順とも違う、任意の固定の順になる。

## Decision

**案Bと案Cを候補に実装し、費用と並べ替えの質を測ってから1つに決める**。決めた形でSPRTを1回だけ回す。
決め方は次の順に見る。

1. 生成の順に依存しないこと（下の「合格の条件」の検査）。両案とも満たすはずである
2. 静かな手の生成のあるノードでの費用。命令数で、現行に対する増分が小さいほう
3. first move cutoff率（[ADR-0235](0235-quiet-ordering-hanging.md)の機能検証と同じ200局面・深さ12）が、現行より下がらないほう

費用が同じくらいなら、案Bを採る。後ろの手を点数で並べるほうが、並べ替えとして筋が良いと考えるためである。
決めた形と数値は、SPRTの前にこのADRへ書く。

### 合格の条件

- Eloの判定: 非劣性（elo0=−5、elo1=0）。この変更の価値は、生成を作り替えても木が変わらなくなることにある。棋力の向上は主張しない（[ADR-0163](0163-sprt-hypothesis-choice.md)）
- 生成の順に依存しないこと: 既定の生成と `HIMAWARI_MB_ORDER=type` の生成でエンジンを作り、`hmwr verify` で比べる。組み込み4局面と `openings/profile_late_positions.txt` の12局面の全部で、ノード数・評価値・最善手が一致する
- 速さ: 局面ごとのNPS（niceなし、交互の周の中央値）で、組み込み4局面と開始局面集の8局面の中央値が、現行の−1.0%以上
- 採否: 3つとも満たしたときだけ入れる。上限と中点の規則は[ADR-0217](0217-sprt-pass-cap.md)の追記に従う

### 結果の読み方（事前登録）

| 結果 | 読み | 次の一手 |
|---|---|---|
| H1 | 並べ方を変えても弱くならない | mainへ入れる。続けて、駒種ごとの生成と行き先からの取る手を、木を変えない手直しとしてNPSで入れる |
| H0 | 並べ方の変更が弱くした | 入れない。閾値未満の手の並びが探索に効いていたと読む。案A（安定にするだけ）を、生成の順を固定したまま使う形を検討する |
| 上限で中点より上 | 効きは判定の幅の中 | ADR-0217に従い延ばす |
| 上限で中点以下 | 弱くなっている側 | 見送りとして記録する |

## 候補の決定（2026-10-21）

**案Bを採る**。両案とも生成の順に依存せず、first move cutoff率も現行と変わらなかった。費用は案Bのほうが小さい。

### 実装

並べ方を全順序にするため、次の4か所を変えた。

- 採点済みの手（`ExtMove`）を、点数と手の符号を詰めた64ビットの鍵1つで持つ。鍵の大小が「点数の降順・同点なら符号の昇順」になる
- 取る手と王手回避は、鍵の順に全数を挿入ソートで並べる
- 静かな手は、閾値以上の手を鍵の順で先に並べる。閾値未満の手は、`select` が読む直前に、先頭から8手ずつ選んで並べる（`select_nth_unstable` と挿入ソート）。
  良い静かな手を探す段は、悪い静かな手に当たったら止める。点数の降順なので、残りもすべて悪い静かな手である。返す手の順は全部を並べた形と同じになる
- root手の初めの並びを、手の符号の昇順にする。root手は反復ごとに安定ソートするので、同点の前後が生成の順のまま残っていた

ほかに生成の順が効く場所も調べた。悪い取る手の退避は、並べた順に読みながら先頭へ寄せるだけなので、並びが決まれば決まる。
ProbCutと静止探索の取る手は、並べた順に `select` で拾うだけである。1手詰めは生成を使わない。

### 生成の順に依存しないこと

既定の生成と `HIMAWARI_MB_ORDER=type` の生成でエンジンを作り、`hmwr verify`（深さ13）で比べた。
組み込み4局面と `openings/profile_late_positions.txt` の12局面の全部で、ノード数・評価値・最善手が一致した。

| 並べ方 | 組み込み4局面 | 終盤12局面 |
|---|---|---|
| 案B（決めた形） | 4局面とも一致 | 12局面とも一致 |
| 案C | 4局面とも一致 | 12局面とも一致（8局面目は深さ11で詰みを読み切って止まるので、最後のinfo行で比べた） |

### 費用（命令数）

並べ方の違いで木が変わるので、1ノードあたりの命令数をそのまま比べられない。そこで現行の木の上で、静かな手・取る手・王手回避の並べ替えだけを写しの列でもう1回行い、増えた命令数を測った。
案Bの写しは、静かな手を返すたびに、返した数に追いつくまで並べる。組み込み4局面×200万ノードで、`icount.py` で測った（診断の版はコミットしていない）。

| 並べ方の仕事 | 1ノードあたりの命令数 |
|---|---|
| 現行（部分挿入ソート） | 163.6 |
| 案B（閾値以上を先に、残りを8手ずつ） | 327.6 |
| 案C（閾値以上を先に、残りは符号の順に全数ソート） | 669.0 |

増分は、案Bが+164.0、案Cが+505.4命令/ノードである。
案Cは、良い静かな手を探す段が閾値未満の手を全部読むので、全部を先に並べる必要がある。
案Bは点数の降順なので、悪い手に当たったところで止められる。

手を64ビットの鍵1つで持つ形は、並べ方を変えなくても命令数を減らした。現行の並べ方のままでは、mainの13,244.4から13,102.6命令/ノード（−1.1%）だった（診断のカウンタ入り）。
合わせた見積もりは、案Bが13,266.6命令/ノードで、mainに対して+0.17%である。
案Bのエンジンを実際に回すと11,770.7命令/ノードだった（ノード数は6,791,939で、mainの6,056,935と違う木）。

閾値未満の手を1手ずつ選ぶ形（毎回残りを全部見て最大を選ぶ）は+196.5命令/ノードで、8手ずつ選ぶ形より重かった。
案Bを全数ソートで並べる形は、鍵を詰める前の実装で+1,268命令/ノードだった。

### first move cutoff率

`openings/actdump_positions.txt` の200局面を深さ12で探索し、本探索のβ超えのうち1手目で起きた割合を数えた。
差は局面ごとの差の平均と95%区間である。5局面は探索が途中で返り、率が取れなかった（有効195局面）。

| 並べ方 | 全β超えの合算 | 局面ごとの平均 | 現行との差 |
|---|---|---|---|
| 現行 | 82.84% | 82.04% | |
| 案B | 83.05% | 82.07% | +0.03pt ±0.45（上がった93・下がった100） |
| 案C | 82.81% | 82.13% | +0.08pt ±0.46（上がった104・下がった89） |

どちらも現行から下がっていない。両案の差は区間の中にある。

### 決め方に照らした読み

1. 生成の順に依存しないこと: 両案とも満たした
2. 費用: 案Bの増分は案Cの3分の1だった。案Bを採る
3. first move cutoff率: 両案とも現行と同じだった

SPRTは事前登録どおり非劣性（elo0=−5、elo1=0）で回す。速さの条件は、監督が局面ごとのNPSで確かめる。

## Consequences

- 生成の順を変える手直しが、`verify` の一致とNPSだけで入れられるようになる
- 静かな手の並べ方が変わるので、ADR-0235のような並べ替えの項の測定は、この後の並べ方の上でやり直す
- 費用が見込みより大きく、速さの条件を満たさないときは、閾値未満の手の並べ方（案Bか案Cか）を見直す
