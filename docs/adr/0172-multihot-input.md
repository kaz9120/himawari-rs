# 0172: 入力を玉と駒のマルチホットにして表を75分の1にする

- Status: rejected
- Date: 2026-08-17
- 関連ADR: [0034](0034-nnue-architecture.md), [0035](0035-nnue-accumulator.md), [0066](0066-halfkp-factorizer.md), [0156](0156-bucket-accumulator-cache.md), [0157](0157-king-mirror-buckets.md), [0164](0164-bona-piece-bitset.md), [0171](0171-ft-pairwise-product.md)

## Context

[ADR-0171](0171-ft-pairwise-product.md)で、FT出力の対を掛けると駒対の
相互作用が低ランクで入ることを確かめた。**入力側で直積を持つ理由が薄れる。**

HalfKPは玉81 × BonaPiece1548の直積で125,388行を持つ。同ADRの分解では、
盤上の表の90.77%は駒単独の成分で、玉との交互作用は8.82%しかない。
**残る8.82%のために81倍の行数を払っている。**

積は玉と駒の交互作用も低ランクで表現できる。展開すると
`y_j = Σ_{i,m} W_ji W'_jm x_i x_m` で、玉の成分と駒の成分の積がそのまま
現れる。K-Pブロックは81×1548でランク上限81なので、512本の積は
ランクの上では余る。

**表は128MBから1.7MBになり、L2に全部載る。**「NNUE推論はメモリ待ちが
律速」という観測が4件続いているが、この構成ではその前提が消える。

## 選択肢と比較

### 案A: 現状維持

直積のまま置く。表は128MBで、1特徴あたり1KBの行を散らばった位置から読む。

### 案B: 入力を玉と駒のマルチホットにする

視点ごとに、自玉81・相手玉81・BonaPiece1548の1,710次元とし、40本の
ビットを立てる。玉と駒の組み合わせは積が担う。

- **表が1.7MBになる。**ネットのファイルも128MBから1.7MBになる
- **玉が動いても全計算が要らない。**変わるのは玉の1特徴だけで、
  差分は2行で済む。[ADR-0156](0156-bucket-accumulator-cache.md)の
  玉位置キャッシュ（視点2×81件、各1024のi16）が丸ごと不要になる
- **相手玉が入る。**HalfKPは自視点に相手玉を持たず、玉と玉の関係は
  後段のL1（16次元）しか通っていなかった
- パラメータが128Mから1.75Mへ、73分の1になる。**ランクが足りることと
  表現力が足りることは別である**
- [ADR-0066](0066-halfkp-factorizer.md)のfactorizerが使えない。仮想特徴は
  玉位置をまたいで駒の価値を共有する仕組みで、玉バケットが消えると
  共有する相手がいなくなる。**+28.1 Eloの実績がある道具を1つ失う**

### 案C: 玉バケットを減らす（45・32など）

直積のまま行数だけ削る。[ADR-0157](0157-king-mirror-buckets.md)がミラー45で
測って負けている。**中間は両方の悪いところを取る。**表は小さくならず、
自由度だけ落ちる。

## Decision

**案Bを採ったが、測定で覆って棄却した**（下の「測定」）。以下は着手時の判断である。

**案Bを採る。**

決め手は、[ADR-0171](0171-ft-pairwise-product.md)が「入力の直積は要らない」
側の証拠を出したことである。同ADRは駒対を低ランクで持てることを+65.4 Eloで
示した。玉と駒の組も同じ機構に乗る。

**採択される見込みは高くない。**パラメータが73分の1になる賭けで、
[ADR-0157](0157-king-mirror-buckets.md)は行数を44%削るだけで負けている。
それでも測る価値があるのは、**負け方が情報になる**からである。大差で負ければ
「直積の8.82%は低ランクでは代替できない」が分かり、僅差なら容量と速度の
交換比率が分かる。

### 相手玉が入るのは副作用である

差分の構造を両視点で揃えるために入れる。自玉だけを特徴にすると、
玉が動いたとき片方の視点だけ本数が変わり、両視点をまとめて処理する
融合カーネル（[ADR-0151](0151-speedup-sweep.md)群N）に乗らない。

両玉を入れれば、どちらの玉が動いても各視点で1本ずつ入れ替わる。
**構造が揃うほうが実装が短く、情報も増える。**ただし利得の切り分けは
できなくなる。切り分けたいなら、HalfKPへ相手玉だけを足す実験を別に置く。

### 実装

特徴インデックスは3区画にする。視点cから見た升は、後手視点で180度回す。

| 区画 | 範囲 | 中身 |
|---|---|---|
| 自玉 | `[0, 81)` | 視点側の玉の升 |
| 相手玉 | `[81, 162)` | 相手側の玉の升 |
| 駒 | `[162, 1710)` | BonaPiece（[ADR-0034](0034-nnue-architecture.md)のまま） |

| 場所 | 中身 |
|---|---|
| `core/bonapiece.rs` | 玉の特徴インデックスと、区画の起点 |
| `engine/nnue.rs` | `FT_IN`、活性特徴の列挙に玉を足す |
| `engine/nnue_acc.rs` | 玉を普通の駒として差分に載せる。玉位置キャッシュと全計算の特別扱いを消す |
| `training/model.py` | factorizerを外す（`FE_END` の割り算が成り立たない） |

### 検証

1. 機能検証。スカラーとSIMDの一致、差分計算と全計算の一致
2. 3億局面で学習し、`pairprod_300M_q1` と比べる
3. NPS計測。ノード数固定300万・8周・交互
4. 3億ネット同士の直接対局。時間制とノード数固定の両方

**対照はfactorizerを使っている。**案Bは使えないので、負けたときに
「マルチホットが悪い」のか「factorizerを失った」のかが分からない。
**僅差で負けた場合だけ、factorizerなしのHalfKP対照を追加で学習する。**
大差で負けたら切り分けても意味がない。

### 撤退ライン

3億の時間制で負けたら棄却する。速度は上がる方向なので、負けるとしたら
評価の質である。

## 測定（2026-08-17、3億の測定台）

対照は `pairprod_300M_q1`（[ADR-0171](0171-ft-pairwise-product.md)の積あり
HalfKP）。データ・seed・設定は同じで、違いは入力の作りとfactorizerの有無になる。

| | 積＋HalfKP | 積＋マルチホット | 差 |
|---|---|---|---|
| 最終valid loss | 0.49240 | 0.49397 | +0.00157 |
| FTパラメータ | 128M | **1.75M** | 1/73 |
| ネットのファイル | 128MB | **1.77MB** | 1/72 |
| 学習時間 | 4,837秒 | **1,823秒** | 0.38倍 |

**73分の1のパラメータで、lossの差は0.00157しかない。**初期値のばらつき
（0.00136、[ADR-0158](0158-mirror-factorizer.md)）をわずかに超える程度である。
直積125,388行が担っていた情報の大半は、1,710次元と低ランクの積で置き換わる。

### 表を1/73にしてもNPSは2.42%しか上がらない

ノード数固定300万・8周・交互。

| バイナリ | NPS（8周の平均） | 変化 |
|---|---|---|
| 積＋HalfKP | 1,509,750 | — |
| 積＋マルチホット | 1,546,279 | **+2.42%** |

**「表が128MBだからメモリ待ち」は誤読だった。**HalfKPでも1視点が触るのは
玉を固定した1.58MBのスライスだけで、もともとL2に収まっている。表全体の
大きさは効いていない。[ADR-0171](0171-ft-pairwise-product.md)に書いた
「L2に全部載るのでメモリ待ちの前提が消える」という期待は外れである。

**同ADRの+15.88%も表の大きさではなく活性の疎さから来ていた。**並べ替えを
両者に当てると+5.14%へ縮んだ事実と整合する。

|---|---|

| 対局数 | 1,214（607ペア） |

**lossがほぼ同じで、対局だけ52 Elo負ける。**[ADR-0136](0136-quiet-teacher-positions.md)は
「lossが0.0285悪いのに+20.3 Eloで勝つ」を記録した。**今回はその裏返しで、
lossが誤差の範囲なのに大きく負けている。**valid lossを足切りに使わない運用
（[ADR-0158](0158-mirror-factorizer.md)）の根拠がまた1件増えた。

## Decision（改）

**棄却する。**

## なぜ負けたか

切り分けは済んでいない。−52.2には2つの要因が混ざっている。

1. **直積が持っていた玉と駒の交互作用**（表の8.82%）を、ランク512の積で
   代替しきれていない
2. **factorizerを失った。**[ADR-0066](0066-halfkp-factorizer.md)は+28.1 Eloの
   実績がある。しかもデータが少ないほど共有は効くので、3億の測定台では
   +28.1より大きい可能性がある

**2の寄与が半分あるなら、マルチホット自体の損は−25前後になる。**それでも
勝ちには遠いので、切り分けの実験は行わない。**「僅差なら切り分ける」と
着手時に決めていたが、−52.2は僅差ではない。**

### lossが動かないのに棋力が動く理由の仮説

valid lossは局面ごとの評価値の平均的な当たり具合を測る。**探索が使うのは
兄弟局面の相対順序である。**低ランク近似は平均を合わせやすく、細かい差を
潰しやすい。同じlossでも、順序を保つかどうかは別に決まる。

この仮説は測っていない。ただし**損失関数を順序側へ寄せる案**（教師の指し手を
使った兄弟局面のランキング損失）が未着手で残っており、そちらの動機になる。

## Consequences

- **コードはmainへ入れない。**ブランチ `feat-adr0172-multihot-input` に残す。
  実装は動いており、機能検証も通っている。**再挑戦するなら学習側から始められる**
- **入力側の直積は当面そのままにする。**[ADR-0157](0157-king-mirror-buckets.md)の
  ミラー45（行数を44%削減）が−16.0、本ADRのマルチホット（1/73）が−52.2で、
  **削る量と損の大きさが揃っている。**入力の行数は素直に効いている
- **副産物の実装は残す価値がある。**玉を普通の特徴にすると玉位置キャッシュ
  （[ADR-0156](0156-bucket-accumulator-cache.md)）が要らなくなり、
  `nnue_acc.rs` が197行減った。HalfKPのままでは使えないが、入力設計を
  変える実験を再びやるときの土台になる
- 学習が2.65倍速い（4,837秒→1,823秒）。**入力側の実験を回すときは、
  この構成を測定台に使うと回転が上がる**
