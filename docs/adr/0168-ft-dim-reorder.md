# 0168: FT出力次元を並べ替えて第1層の空回りを減らす

- Status: accepted
- Date: 2026-08-15
- 関連ADR: [0122](0122-tooling-language-split.md), [0127](0127-net-shape-bench.md), [0131](0131-frozen-ft-light-head.md), [0137](0137-output-buckets.md), [0151](0151-speedup-sweep.md), [0159](0159-ft-width-1024.md), [0167](0167-nnue-kernel-instructions.md)

## Context

FT1024の採否は速度だけで決まる。ノード数固定では現行ネットに+70.6 Elo
[+49.2, +92.5] 勝っており（[ADR-0159](0159-ft-width-1024.md)）、評価関数
としての実力は測定済みである。時間制で負けるのは速度の代償が容量の効きを
上回るためで、速度1%あたり3.5 Elo（10+0.1）という換算率も同ADRで得ている。

**距離は着手時に開いていた**。現行mainで測り直すと、速度比は
ADR-0159の0.709倍から0.690倍へ落ちていた。

| バイナリ | NPS（ノード数固定200万・6周） | FT256比 |
|---|---|---|
| FT256（現行ネット） | 2,072,644 | — |
| FT1024 | 1,415,646 | **−31.70%** |

理由は探索側の高速化が進んだことにある。[ADR-0151](0151-speedup-sweep.md)の
後半・[ADR-0165](0165-bona-block-layout.md)・[ADR-0166](0166-movepick-frame.md)は
どれも探索の時間を削るので、評価の比重が大きいFT1024では改善の割合が薄まる。
**探索を速くするほどFT1024の不利は広がる**。

代償は31.70 × 3.5 = 110.9 Eloで、容量の効き+70.6に対して差し引き−40.3に
なる。黒字にはNPSを+16.9%、H1採択（elo1=5）には+19.0%上げる必要がある。

### プロファイルの的は第1層である

深さ25・1スレッド・27,226サンプルで取った（[ADR-0099](0099-nnue-dot-sdot.md)の手順）。

| 箇所 | FT1024 | FT256 |
|---|---|---|
| `evaluate` 合計 | **31.77%** | 17.10% |
| ├ `forward_hidden`（第1層が主） | **23.10%** | 9.09% |
| ├ `clip_to_u8` | 6.59% | 4.88% |
| └ その他 | 1.97% | 3.06% |
| `refresh_top` | 8.99% | 7.14% |
| `apply_range` | 2.50% | — |

第1層は `CONCAT × L1_OUT`（2048×32）の積和で、幅に比例する。
[ADR-0167](0167-nnue-kernel-instructions.md)で命令数を削る線は閉じており、
残る軸は「回る回数を減らす」ほうになる。

## 選択肢と比較

### 案A: FT出力次元を並べ替える

第1層は[ADR-0151](0151-speedup-sweep.md)群Lの列駆動で、活性の4列チャンクの
うち全ゼロのものを飛ばす。**飛ばせる数は次元の並び順で変わる**。出力次元の
並びは学習で決まる任意順なので、ゼロが同時に起きる次元を同じチャンクへ
寄せれば、飛ばせるチャンクが増える。

`ft_w` の列・`ft_b`・`w2` の入力列へ同じ置換を入れると、積和の項の集合が
変わらないので**評価値はビット一致する**。エンジンのコードは変えず、
ネットを作り直すだけで済む。

### 案B: 後段のL1を半減する（`1024x16x32`）

第1層の演算がそのまま半分になる。[ADR-0131](0131-frozen-ft-light-head.md)が
L1を32→16にしてもvalid lossは0.0006しか動かないと実証しており、精度の
根拠もある。ただし2026-08-13のオーナー判断で保留している。この先教師を
さらに増やすにあたり、Stockfishで実績のある後段の形を保ちたいためである。

### 案C: 出力バケット（[ADR-0137](0137-output-buckets.md)）

駒数などで後段を切り替える。計算量は変わらないので速度の手ではない。

## Decision

**案Aを採る**。案Bはオーナー判断で保留中であり、案Cは速度に効かない。
案Aは評価値がビット一致するので棋力を損なう余地がなく、外れても失うのは
ツール2本の実装だけである。

**着手前に前提を実測する条件をつけた**。ROADMAPの候補として書いたとき、
[ADR-0151](0151-speedup-sweep.md)群Lの「4列チャンクの28.4%が全ゼロ」は
要素のゼロ率0.731からの導出（0.731⁴）でしかなく、実測ではなかった。
独立仮定どおりなら寄せる余地がないので捨てる、という条件である。

**FT256では2026-08-15に見送っている**（オーナー判断、局所的すぎる）。
FT1024で取り上げ直すのは、第1層の比重が9.09%から23.10%へ2.5倍に増えて
いるためで、同じ削減率でも効き方が変わる。

## 測定（2026-08-15）

### 実測すると、ゼロは独立ではなく寄せる余地があった

第1層へ入る活性の非ゼロパターンを集めた。深さ25の探索から251回に1回
記録し、12,500サンプル取っている（局面は `bench` と同じ4つ）。

| | FT1024 | FT256 |
|---|---|---|
| 要素のゼロ率 | 0.7833 | 0.7398 |
| 独立仮定の全ゼロチャンク率 | 0.3765 | 0.2996 |
| **実測の全ゼロチャンク率** | **0.3716** | **0.2788** |
| 並べ替え後（貪欲法） | **0.6880** | 0.5469 |
| L1が回るチャンク | 321.7 → **159.7** / 512 | 92.3 → 58.0 / 128 |
| L1の削減 | **50.3%** | 37.2% |

実測は独立仮定をわずかに下回る。**ゼロは独立でも正の相関でもなく、学習が
決めた並びは寄せる前の状態そのものだった**。捨てる条件（独立仮定どおり）
には当たらない。

**幅の3割が働いていない**。FT1024では147次元（14.4%）が12,500サンプルすべて
でゼロ、ゼロ率0.99以上が300次元、0.95以上が513次元ある。FT256でも
0.95以上が51次元（20%）で、幅を4倍にしても死んだ次元の割合はむしろ増えた。
この事実は速度とは別に、学習側の課題として残る。

### 置換は測った局面の外でも効く

置換を決めるのに使ったのはベンチ4局面の探索である。別の局面で効かなければ
測定への過学習になるので、`openings/start_sfens_ply32.txt` の先頭8局面を
深さ22で探索し、同じ置換を当てた。

| | 全ゼロチャンク率 | L1が回るチャンク |
|---|---|---|
| そのまま | 0.3631 | 326.1 / 512 |
| 並べ替え | 0.6372 | 185.8 / 512 |

**削減は43.0%で、決めた局面での50.3%から7.3ポイント落ちるだけである**。
どの次元が死んでいるかは局面によらずネットの性質で決まる、と読める。

### 探索は一致する

同じバイナリで評価ファイルだけを替え、2局面を深さ18で読ませた。反復ごとの
ノード数・評価値・PV・bestmoveがすべて一致した（startposで318,689ノード、
`bestmove 7g7f`）。**評価値のビット一致が探索の一致として確かめられた**。

### NPSは+13.19%上がった

ノード数固定200万・6周・交互で測った。3本を同じ走行で交互に測っている
（NPSの絶対値は走行ごとに1.5%前後動くので、走行をまたいで比べない）。

| バイナリ | NPS（6周の平均） | FT256比 |
|---|---|---|
| FT256（現行ネット） | 2,072,644 | — |
| FT1024 | 1,415,646 | −31.70% |
| **FT1024（並べ替え）** | **1,602,379** | **−22.69%** |

FT1024どうしで比べると**+13.19%**になる。プロファイルでも第1層が減っている。

| 箇所 | 並べ替え前 | 並べ替え後 |
|---|---|---|
| `forward_hidden` | 23.10% | **14.69%** |
| `clip_to_u8` | 6.59% | 7.23% |
| `evaluate` 合計 | 31.77% | 24.29% |

第1層は8.41ポイント減った。`clip_to_u8` の割合が上がって見えるのは、
絶対時間の変わらないまま全体が速くなったためである。

### 黒字までの距離は4分の1になった

| 項目 | 並べ替え前 | 並べ替え後 |
|---|---|---|
| 容量の効き（ノード数固定） | +70.6 | +70.6 |
| 速度の代償（3.5 Elo/%） | −110.9 | **−79.4** |
| **差し引きの見込み** | **−40.3** | **−8.8** |

**31.5 Elo回収した**。黒字にはあと3.3%、H1採択（elo1=5）にはあと5.1%の
NPS改善が要る。着手前の16.9%・19.0%からは手の届く範囲へ入った。

### 並べ替えたネットの作り方

3工程になる。以下はFT1024での実行例で、この手順どおりに
`ft1024_2990M_q1_reorder.hmwr` を作った。

```sh
# 1. 活性を集めるビルドを作り、探索させてダンプを書く
HIMAWARI_ARCH=1024x32x32 RUSTFLAGS="-C target-cpu=native" \
  cargo build --release -p himawari-usi --bin himawari \
  --features himawari-engine/actdump
HIMAWARI_ACT_OUT=data/profile/act_ft1024.bin \
  target/release/himawari < 局面とgoを並べたUSI入力

# 2. 置換を決める（渡すのは片視点の活性次元。ADR-0171以降は FT_OUT/2 = 512）
python3 scripts/ft-reorder.py data/profile/act_ft1024.bin 1024 \
  --out data/profile/perm_ft1024.txt

# 3. ネットを並べ替える（makenetは同じ構成でビルドしたものを使う）
makenet --reorder data/profile/perm_ft1024.txt \
  --from data/nets/ft1024_2990M_q1.hmwr.best \
  --out data/nets/ft1024_2990M_q1_reorder.hmwr
```

置換の当たり具合は `--perm` で別のダンプへ当てて確かめられる。上の
ホールドアウトはこれで測った。

## Consequences

- **ネットごとに置換を測り直す必要がある**。どの次元が死ぬかは学習の結果で
  決まるので、ネットを作り直すたびに活性統計と並べ替えの2工程が挟まる。
  手順は3つで、`--features himawari-engine/actdump` のビルドで活性を集め、
  `hmwr net reorder` で置換を出し、`makenet --reorder` でネットを作る
  （置換のスクリプトは[ADR-0180](0180-hmwr-cli-in-python.md)でhmwrへ移った）
- **エンジンのコードは変わらない**。通常のビルドに入るのは `#[cfg]` の
  1行だけで、生成されるバイナリは着手前と同一である。棋力への影響もない
  （評価値がビット一致する）
- 活性ダンプはビルドfeatureで隔離した。ホットパスの `evaluate` に測定用の
  分岐を常設しないためで、`actdump` を付けないビルドにはコードが残らない
- **FT1024の採用判断はまだ出せない**。見込みは−8.8 Eloで、H1採択には
  5.1%足りない。次の的は `clip_to_u8`（7.23%）と `refresh_top`（9.79%）で、
  第1層の残り14.69%にも列駆動の入口（`find_nnz`）が含まれる。
  （追記: その後[ADR-0159](0159-ft-width-1024.md)は互角で採択し、
  [ADR-0170](0170-l1-half.md)・[ADR-0171](0171-ft-pairwise-product.md)で
  勝ち越した）
- **死んだ次元の多さは学習側の宿題になる**。FT1024で147次元がすべてゼロ、
  513次元がゼロ率0.95以上である。ここを活かせれば同じ幅でノード効率が
  上がるので、速度側の投資とは独立に効く
- 置換は貪欲法で決めている。最適解ではないので、より良い置換が見つかれば
  同じ手順で作り直せる。全ゼロチャンク率の上限は測っていない
