# 0020: 探索スレッドモデル

- Status: proposed
- Date: 2026-07-18
- 関連ADR: [0014](0014-position-structure.md), [0019](0019-usi-architecture.md)

## Context

並列探索（Lazy SMP）を最初から実装する方針のため、スレッド構造は
P2の時点でマルチスレッド前提の形にしておく。後からスレッドを
足せない構造（探索関数がグローバル状態を触る等）を作らないことが
このADRの目的になる。P2の運用はThreads=1。

## 選択肢と比較

### 案A: goのたびにスレッドをspawnする

実装は簡単だが、毎手のspawnコスト（ms級）が短時間対局で効く。
スレッドローカルのhistory類が毎回消え、Lazy SMPの前提と合わない。

### 案B: 常駐ワーカープール

起動時（またはThreads変更時）にスレッドを立て、goで起こし、
探索終了後はcondvarで待機に戻る。history等のスレッドローカル
状態が対局を通じて保持される。Stockfish型。

## Decision

案Bを採用する。構成は次のとおり。

- `ThreadPool` がメイン探索スレッド1本＋ワーカーN−1本を所有する。
  各スレッドは `Mutex + Condvar` のidle loopで待機する
- 各スレッドが占有する状態: Positionのclone（探索開始時に
  ルート局面を複製。ADR-0014）、探索スタック、history類。
  これらへの参照を跨スレッドで共有しない
- スレッド間で共有する状態: stopフラグ（AtomicBool、Relaxed）、
  ponderhitフラグ、探索ノード数の集計（AtomicU64）、
  置換表（次のADRで起草）
- stopの検査は各ノードの冒頭で行う（Relaxed load 1回。
  計測済みの分岐予測が効くコスト）。時間切れ判定はメイン探索
  スレッドだけが数千ノードごとに行い、stopフラグを立てる
- bestmoveの決定はP2ではメイン探索スレッドの結果のみ。
  複数スレッドの結果集約（投票制等）はLazy SMPのADR（P3）で決める
- `Threads` オプション変更時はプールを作り直す（isreadyで反映）

## Consequences

- P3のLazy SMP導入時は「ワーカーにも探索を回す＋結果集約」の
  追加だけで済み、スレッド構造の作り直しが発生しない
- 探索関数はスレッドローカル状態への&mutと共有状態への&だけを
  受け取る署名になり、コンパイル時にデータ競合が排除される
  （置換表内部のatomicは除く。ADR-0004）
- 単スレッド運用でもcondvar待機のコードが常に通るため、
  起床・待機のバグはP2の段階で洗い出される
- スレッドごとのPosition複製は探索開始時の1回だけで、
  コストは無視できる
