# 0128: 3つ以上の候補は総当たりリーグ戦で順位づける

- Status: proposed
- Date: 2026-08-01
- 関連ADR: [0027](0027-sprt-framework.md), [0028](0028-pruning-extensions.md), [0089](0089-improvement-criteria.md), [0122](0122-tooling-language-split.md), [0127](0127-net-shape-bench.md)

## Context

[ADR-0127](0127-net-shape-bench.md)でネットワーク構成を7つ学習した。速度は測ったが、
**どれが強いかは対局しないと分からない。** valid lossは棋力の代理でしかなく、
[ADR-0126](0126-mate-score-in-training.md)は「valid lossで足りない可能性がある」と
明記している。

いまある道具は `selfplay` だけで、これは2本の比較に特化している
（[ADR-0027](0027-sprt-framework.md)）。ベースラインと候補を突き合わせ、GSPRTのLLRが
閾値に届いたところでH1かH0を返す。**答えは二値で、どれだけ強いかも、候補同士の
上下関係も返さない。**

候補が3つ以上あるとき、この形では足りない。

## 選択肢と比較

### 案A: ベースラインへのガントレット

`selfplay` を候補の数だけ回す。ベースラインを固定し、候補を1つずつぶつける。
実装が要らず、SPRTの早期打ち切りが効くので、負ける候補は短く終わる。

ただし得られるのは「ベースラインに勝てるか」だけである。候補同士がどう並ぶかは、
それぞれのElo推定値を並べて眺めるしかない。推定値の区間は広く重なり合うので、
2位と3位の判別はつかない。

### 案B: 総当たりリーグ戦

参加者すべての組で固定局数を戦い、勝敗表からレーティングを解く。**誰と当たって
何点取ったかを織り込める**ので、対戦相手の強さを補正した順位が出る。候補同士の
直接対決も入るため、上位の判別が案Aより効く。

対局数は参加者数の2乗で増える。7人なら21カードで、案Aの6カードの3.5倍になる。

## Decision

案Bを採る（2026-08-01オーナー判断）。

**決め手は再利用である。** 複数候補を並べて比べる場面はネットワーク構成に限らない。
学習のハイパーパラメータ（lr・λ・エポック数）も、枝刈りの係数も、候補を並べて
上から試す形になる。そのたびにガントレットの結果を目で突き合わせるより、順位を返す
道具を1つ持つほうが速い。

**マージの判定は変えない。** mainへ入れるにはSPRTでH1採択が要る
（[ADR-0028](0028-pruning-extensions.md)）。リーグ戦は候補を絞る道具で、ゲートではない。
リーグ戦で1位になった構成を本学習し、現行ネットとSPRTで決着をつける。

### 固定局数で回す

SPRTの早期打ち切りは使わない。打ち切ると候補ごとに対局数が変わり、レーティングの
確からしさが揃わなくなる。1カードあたりのペア数を `--pairs` で決め、全カードを
同じ数だけ戦う。

### レーティングは勝敗表から最尤で解く

参加者iがjに勝つ確率をロジスティック関数 `1/(1+10^((r_j-r_i)/400))` とし、各参加者の
期待得点が実得点に一致するところまで反復する。引き分けは0.5点として数える。

BayesEloやOrdoを外部プロセスとして呼ぶ選択肢もあるが、**依存を増やしてまで得るものが
ない。** 引き分け率を別パラメータに持つBayesEloの精密さは、候補を絞る用途には過剰である。
反復は50行で書けて、既知のレーティングを復元できることをテストで確かめられる。

### 対局の並列はカード単位で回す

ワーカーはカードを1つ取り、その2本のエンジンを起動して `--pairs` 回ぶんを消化してから
次のカードへ移る。対局ごとにエンジンを起動し直すと、置換表の確保と評価ファイルの
読み込みが毎局に乗る（FT1024の評価ファイルは257MBある）。

## Consequences

- 候補を絞る道具ができた。ネットワーク構成のほか、学習条件の比較にも使える
- **対局数が参加者数の2乗で増える。** 7人・25ペアで1050局になる。参加者を増やすときは
  ペア数を減らすか、明らかに落ちる候補を事前に外す
- 引き分けを0.5点として扱うので、引き分けの多い条件ではレーティングの差が圧縮される。
  勝率が0か1に張り付く組み合わせがあるとレーティングが発散するが、`MAX_STEP` で
  1回の更新幅を抑えて止めている
- `selfplay` の対局処理（`game.rs`）をライブラリへ移した。`selfplay` と `league` が
  同じ終局判定を使う。片方だけ直して条件がずれる事故を防ぐ
- 長い対局は停止ファイルで止められる（[ADR-0123](0123-stop-and-resume.md)）。
  途中で止めるとカードの結果が欠け、そのぶん推定が粗くなる
