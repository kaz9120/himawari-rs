# 0009: Piece/PieceTypeエンコーディング

- Status: accepted
- Date: 2026-07-17
- 関連ADR: [0008](0008-square-coordinates.md)

## Context

駒の数値表現は、指し手生成の分岐、手駒のパック（Hand、P1で起草）、
駒割評価のテーブル添字、NNUEの特徴量計算のすべてに現れる。
成り・先後の判定と変換が少数命令で書けること、例外規則が少なく
バグを生みにくいことが要件になる。

## 選択肢と比較

### 案A: やねうら王/Apery式（成りビットを上位に加算）

`PieceType`: 歩=1、香=2、桂=3、銀=4、角=5、飛=6、金=7、玉=8、
成駒 = 元の駒 + 8（と=9、成香=10、成桂=11、成銀=12、馬=13、龍=14）。
`Piece` = PieceType + 後手ビット（+16）で5bit。

bit 3が「成り」を意味するが、玉=8が同じビットを使うため一貫しない。
成駒判定は `pt >= 9` なら1比較で書けるものの、`& 8` は玉で誤判定する。
生駒に戻す操作 `& 7` も玉が0（NO_PIECE）になる例外を持つ。
捕獲された駒を手駒に戻す経路では玉が現れないため実害は限定的だが、
「この演算はこの駒には使えない」という規約を複数持ち歩くことになる。

### 案B: GPS将棋/OSL式（成駒を下位、生駒を上位に配置）

GPS将棋のライブラリOSLの `Ptype`（osl/core/osl/basic_type.h で確認）。

```
EMPTY=0, (EDGE=1), と=2, 成香=3, 成桂=4, 成銀=5, 馬=6, 龍=7,
玉=8, 金=9, 歩=10, 香=11, 桂=12, 銀=13, 角=14, 飛=15
```

bit 3の意味が「生駒である（成っていない）」で全16値にわたり一貫する。
玉と金は「成れないので対の成駒スロットが存在しない」だけで、例外では
なく配列の自然な帰結になる。OSLでの演算定義は次のとおり。

- 成駒判定 `isPromoted`: `pt < 8`（例外なし）
- 成れる駒か `canPromote`: `pt > 9`（金・玉が自動的に除外される。例外なし）
- 成り `promote`: `- 8`（canPromoteが前提）
- 生駒に戻す `unpromote`: `| 8`（全駒に適用可能な全域関数。玉8→8、金9→9で無変更）
- 大駒（角飛馬龍）判定: `(pt | 8) >= 14`（1命令+1比較）
- 手駒に持てる駒種: 金9〜飛15の連続範囲（ループ・配列添字が素直）

EDGE=1はOSLがパディング付き盤面の盤外判定に使っていたもので、
bitboardエンジンでは不要。空きスロットになる。

先後の付与について、OSLは後手を負数（−16）にする符号方式だが、
これは案Aと同じ +16 オフセットに置き換えられる。配列の利点とは独立。

### 両案の演算比較

| 操作 | 案A | 案B |
|---|---|---|
| 成り | `\|8`（金玉玉除外は呼び出し側） | `−8`（同左） |
| 成駒判定 | `pt >= 9`（`&8`は玉で誤る） | `pt < 8` |
| 生駒に戻す | `&7`（玉が0になる例外） | `\|8`（例外なし・全域） |
| 成れる駒か | `1 <= pt <= 6`（減算+1比較） | `pt > 9`（1比較） |
| 金の動きの駒 | マスク定数 {7,9,10,11,12} | マスク定数 {2,3,4,5,9} |
| 大駒判定 | `(pt&7)==5 or 6`（減算+1比較） | `(pt\|8) >= 14` |
| 手駒種の範囲 | 1〜7で連続 | 9〜15で連続 |
| 未使用スロット | 0, 15 | 0, 1 |
| 先後 | +16 | +16 |
| 定数照合できる現役実装 | やねうら王/Apery | なし（GPS将棋は開発終了） |

## Decision

案B（GPS将棋/OSL式）を採用する。

演算コストはほぼ互角だが、案Bはbit 3の意味が全値で一貫し、
成り系の演算に例外規約がひとつもない。エンコーディングは今後
すべてのコードが暗黙に依存する層であり、「使ってはいけない演算」の
規約を持たない配列のほうが良い設計だと判断した。
やねうら王との定数照合は失うが、正しさの検証はperftと素朴実装との
突き合わせ（ADR-0006）で行う計画であり、定数レベルの照合に依存しない。

定義は次のとおり。

- `PieceType(u8)`: 上記の案B配列。EMPTY=0、1は未使用（予約）
- `Piece(u8)`: 先手 = PieceTypeと同値、後手 = +16。5bit
- 演算はOSL定義に従う（isPromoted / canPromote / promote / unpromote）
- 手駒種（金歩香桂銀角飛 = 9〜15）の順序をHandのフィールド順の
  既定とするかは、HandのADRで優等判定のビット配置と併せて決める
- BonaPiece等の外部番号体系との対応は変換テーブルで吸収する
- Rust表現はADR-0008と同じくnewtype＋関連定数

## Consequences

- 成り系の演算から例外規約が消え、debug_assertは値域検査だけで済む
- やねうら王のコード断片を移植する際は駒定数の読み替えが必要になる。
  移植は設計の参考にとどめ、コードはOSL配列前提で書き下ろす
- 未使用スロット1（旧EDGE）は将来の拡張用に予約する
- 評価関数ファイルのやねうら王互換（P4で判断）を選ぶ場合も、
  変換テーブル1枚で対応でき、この決定は障害にならない
