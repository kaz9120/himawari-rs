# 0009: Piece/PieceTypeエンコーディング

- Status: proposed
- Date: 2026-07-17
- 関連ADR: [0008](0008-square-coordinates.md)

## Context

駒の数値表現は、指し手生成の分岐、手駒のパック（Hand、P1で起草）、
駒割評価のテーブル添字、BonaPiece計算のすべてに現れる。
成り・先後の判定と変換が少数命令で書けること、参考実装と照合できる
ことが要件になる。

## 選択肢と比較

### 案A: やねうら王/Apery式 5bit

`PieceType`: 歩=1、香=2、桂=3、銀=4、角=5、飛=6、金=7、玉=8、
成駒 = 元の駒 + 8（と=9、成香=10、成桂=11、成銀=12、馬=13、龍=14）。
`Piece` = PieceType + 先後ビット（後手 = +16）で5bitに収まる。

- 成りが `| 8`、先後反転が `^ 16`、種別抽出が `& 15` の1命令ずつ
- 金の動きをする駒（金・と・成香・成桂・成銀）の判定が
  ビットマスク定数1個で書ける（bit 7, 9〜12を立てたu16と照合）
- やねうら王と定数が一致し、利きテーブル・Zobrist・評価値の
  突き合わせデバッグが容易
- 玉=8が成りビットと同じ位置を使う非対称性がある。「成駒か」の判定は
  `pt >= 9`（と〜龍の範囲）で行い、`& 8` は使わない規約にする

### 案B: 独自配列（例: 成りビットを最下位に置く、金を6番に詰める）

ビット演算の回数は案Aと大差なく、玉の非対称性を解消できる配列も
作れる。そのかわり参考実装との定数照合を全面的に失う。デバッグ効率の
損失が利点を上回る。

## Decision

案Aを採用する。定義は次のとおり。

- `PieceType(u8)`: NO_PIECE_TYPE=0、歩1 香2 桂3 銀4 角5 飛6 金7 玉8、
  と9 成香10 成桂11 成銀12 馬13 龍14
- `Piece(u8)`: 先手 = PieceTypeと同値、後手 = +16。5bit
- 成り: `| 8`（玉・金に適用しないことを呼び出し側が保証し、
  `debug_assert!` で防御）。成駒判定: `9 <= pt && pt <= 14`
- 先後: 抽出 = `>> 4`、反転 = `^ 16`、種別抽出 = `& 15`
- 金の動きをする駒の判定: ビットマスク定数
  `GOLDS = (1<<7)|(1<<9)|(1<<10)|(1<<11)|(1<<12)`
- 手駒に持てる駒種の順序（Handのビットフィールド配置）と
  BonaPieceの駒順は本ADRの並びと一致しない。それぞれのADR
  （Hand、NNUE特徴量）で変換テーブルを定義して吸収する

Rustでの表現はADR-0008と同じくnewtype＋関連定数とする。

## Consequences

- 成り・先後・種別の操作がすべて1命令で、参考実装との照合も保たれる
- 玉=8の非対称性は残る。成り操作と成駒判定の規約（`|8` の適用条件、
  `pt >= 9` 判定）をコードに明記し、debug_assertで守る
- 5bit表現のため、Moveエンコーディング（P1で起草）で駒種を載せる
  場合のビット幅が確定する
- 15（金+8）と31は未使用値になる。テーブルを16/32要素で確保する際の
  パディングとして扱う
