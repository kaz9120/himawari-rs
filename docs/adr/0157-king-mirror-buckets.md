# 0157: HalfKPの玉位置を左右ミラーで45バケットへ畳む

- Status: rejected
- Date: 2026-08-12
- 関連ADR: [0034](0034-nnue-architecture.md), [0066](0066-halfkp-factorizer.md), [0127](0127-net-shape-bench.md), [0131](0131-frozen-ft-light-head.md), [0135](0135-teacher-data-3b.md), [0156](0156-bucket-accumulator-cache.md)

## Context

将棋盤は左右対称である。駒の動きに左右の別はなく、キャスリングのような
非対称なルールもない。**局面を左右反転しても強さは変わらない**。

ところがHalfKPは玉位置を81通りそのまま持つので、この対称性は構造では
保証されず、学習で近似するしかない。獲得できているかを測った。

### 現行ネットは左右対称性を獲得していない

`halfkp_2990M_q1`（現行ネット、29.9億局面で学習）で、局面とその左右反転像の
評価値の差を測る（`nnue::tests::mirror_lr_gap`）。

| 局面集 | 件数 | ミラー差の平均 | 中央 | p90 | p99 | 比較: 評価値の規模（平均 \|score\|） |
|---|---|---|---|---|---|---|
| `start_sfens_ply24` | 30,053 | **91** | 74 | 189 | 334 | **50** |
| `start_sfens_ply32` | 26,273 | **102** | 82 | 216 | 378 | **59** |
| ランダム局面（20〜100手） | 2,000 | 295 | 234 | 634 | 1,074 | 975 |

歩=90スケールなので、実戦的な局面で**平均1.0歩ずれる**。

**序盤では信号よりノイズのほうが大きい**。ply24で評価値そのものの規模が50、
ミラー差が91である。定跡を抜けた直後の最も重要な帯で、同じ強さの局面に
1歩の食い違いが出ている。ランダム局面のほうが差の絶対値は大きいが、
教師データの分布から外れた領域なので、実戦的な局面集の値を正とする。

### 参照実装は畳んでいる

Stockfishの `HalfKAv2_hm` は玉位置を左右ミラーで畳み、入力次元を22,528まで
落として、浮いた予算をFT幅（1024/視点）へ振っている。本エンジンは
125,388次元 × FT256で、**FTのパラメータ総数はむしろ多い**（32.1M対23.1M）。
差は幅であり、幅を作る余地は入力側の重複にある。

## 選択肢と比較

### 案A: 現状維持

対称性は学習で近似させ続ける。実装は要らないが、上の1.0歩は残る。

### 案B: 特徴側で玉位置を45バケットへ畳む

自玉の筋が6〜9なら盤面全体を左右反転し、玉の筋を1〜5に正規化する。
玉バケットは5筋 × 9段 = 45で、FT入力は 45 × 1548 = 69,660 になる
（現行の55.6%）。

- **対称性が構造で保証される**。ミラー差は定義上ゼロになる
- **FTパラメータが44%減る**（32.1M → 17.8M）
- **玉バケットあたりの実効サンプルが約2倍になる**。教師データを使い切った
  今（[ADR-0135](0135-teacher-data-3b.md)）、データ効率の改善は増量と同じ
  意味を持つ
- 玉が5筋の局面は反転しないので、45のうち9バケットは対称化されない
- 既存ネットと互換が切れる。公開評価関数の読み込み（`nnue_compat`）も
  81バケット前提なので、ミラービルドでは無効になる

### 案C: 学習時のミラーデータ拡張

教師データに左右反転した局面を足す（ROADMAPの候補にあったもの）。実装は
軽い。ただし**対称性は構造で保証されず、近似のままである**。パラメータも
減らないので、幅へ振り替える余地も生まれない。案Bの下位互換になる。

## Decision

**案Bを採ったが、測定で覆って棄却した**（下の「測定」と「なぜ棄却するか」）。
以下は着手時の判断である。

**案Bを採る**。案Cは案Bが失敗したときの退避先として残す。

決め手は2つある。1つは上の実測で、**近似での獲得に失敗していることが
数字で出た**こと。もう1つは容量で、44%の削減がそのままFT幅の原資になる。
[ADR-0127](0127-net-shape-bench.md)が「FTを太らせると速度で潰れる」と結論し、
[ADR-0156](0156-bucket-accumulator-cache.md)がその速度側を一部戻した。
**入力側の重複を削るのは、同じ壁への3本目の道になる**。

### 実装の方針

反転は視点ごとに、それぞれ独立して決める（Stockfishと同じ）。視点cの自玉の筋が6〜9なら、
その視点の全特徴で升を左右反転する。手駒は升を持たないので変わらない。

変更は7か所になる。

| 場所 | 中身 |
|---|---|
| `core/bonapiece.rs` | 升の左右反転と、45バケットの `halfkp_index` |
| `engine/nnue.rs` | `FT_IN`、`for_each_bona_piece` の升変換 |
| `engine/nnue_acc.rs` | `diff_rows` の視点に反転の有無を持たせる |
| `py/lib.rs` | `KING_BUCKETS` の公開 |
| `training/model.py` | `FE_END = FT_IN // 81` の81を `KING_BUCKETS` へ |
| `nnue_compat` | 削除（81バケット前提で、畳むと意味を失う） |

ビルド時フラグは作らなかった。**互換を切ってよい**とオーナーが判断した。
45バケットを唯一の実装にするほうが分岐は減る。81バケットとの比較は、
mainのビルドとブランチのビルドを並べて行う（[ADR-0127](0127-net-shape-bench.md)と
同じやり方）。

**玉が5筋と6筋の間を動くと、その視点の全特徴が反転する**。これは
バケットが変わるのと同じ扱いになり、既存の「玉が動いた視点は遡れない」
構造がそのまま受ける。[ADR-0156](0156-bucket-accumulator-cache.md)の
玉位置キャッシュも、反転後の座標系で一貫するので変更なしで働く。

ファイル形式は変えない。`FT_IN` がヘッダの `dims[0]` に載るので、
既存のアーキ不一致チェックが誤読を弾く。

### 検証の順序

**足切りをvalid lossだけで通さない**（2026-08-12オーナー指摘）。lossが
小さくても弱い場合があるためで、3段に分ける。

1. **ミラー差がゼロになること**を確かめる（構造の確認、`mirror_lr_invariance`）
2. **3億局面で学習し、3つの物差しで比べる**（[ADR-0135](0135-teacher-data-3b.md)の手順）
   1. valid loss。81バケット版を同条件で学習して並べる
   2. NPS。FT重みが32.1MBから17.8MBへ減るのでキャッシュの効きが変わり、
      ミラーの判定ぶんは増える。**探索が変わるので
      [ADR-0074](0074-feature-verification.md)の機能検証（ノード数一致）は
      使えない**
   3. 3億ネット同士の直接対局（SPRT）。それぞれの最良構成をぶつける
3. 通れば29.9億で本学習し、あらためてSPRTにかける

**2で負けたら棄却する**。対称性が正しくても、45バケットへ畳むことで
「左右で違う戦型の区別」が失われる可能性は残る。局面の優劣は左右対称でも、
教師データ（探索値）には非対称なノイズが乗っているためである。

#### valid lossの比較はこの実験では成立する

[ADR-0136](0136-quiet-teacher-positions.md)は「lossでネットを選べない場面が
ある」と記録している。**あれは教師データの分布を変えて物差しごと動いた
ケースである**。本ADRが変えるのは特徴の定義だけで、教師（`train_300M_q1`）も
検証集合（`valid_385M_q1`）も的も損失関数も同じものを使う。同じ局面を同じ的で
測るので、比較の土俵は動かない。

**それでもlossは2つを見ない**。探索が必要とする候補手の相対的な順序と、
速度である。上の2-2と2-3はその2つを埋めるために置く。

#### `--resume` は1エポックの学習では使えない（2026-08-12に判明）

足切りの学習が94.5%（step 17300/18311）で落ちたので `--resume` で再開したが、
**stepが27100まで伸び、学習率が下がりきったあとで再上昇した**。
`train.py` の再開はエポック単位で、`start_epoch = ckpt["epoch"]` としか
戻さない。エポック途中で落ちるとそのエポックを頭から回し直す一方、
stepカウンタとschedulerは復元した値から進むので、cosineの終端を越える。

本エンジンの学習は `epochs=1` が既定（[ADR-0135](0135-teacher-data-3b.md)）
なので、**この再開は常に壊れる**。落ちたら最初からやり直す。
[ADR-0123](0123-stop-and-resume.md)の停止と再開はこの経路を覆っていない。

#### 3億での結果は楽観に振れる

ミラーの利得は玉バケットあたりの実効サンプルが2倍になることなので、
**データが少ないほど効く**。[ADR-0136](0136-quiet-teacher-positions.md)の
静止化が3億の+35.8から29.9億で+13.9へ薄まったのと同じ筋である。
3億で僅差なら、本学習では消える見込みとして扱う。

## 測定（2026-08-12）

### 足切り1: valid loss は通った

3億局面（`train_300M_q1`）で両方をフル18,311ステップ学習した。seed・lr・
バッチ・λはすべて同じで、違いは特徴の定義だけである。

| | ミラー45 | 81バケット（現行） | 差 |
|---|---|---|---|
| 最終valid loss | **0.49424** | 0.49536 | **−0.00112** |
| 学習時間 | 2,809秒 | 3,082秒 | −8.9% |
| FTパラメータ | 17.8M | 32.1M | −44% |
| ネットのファイル | 17.85MB | 32.1MB | −44% |

**9つの検証地点すべてでミラーが良く、符号が一度も反転しない**（差は
−0.00085〜−0.00223）。参考として[ADR-0135](0135-teacher-data-3b.md)は
データを10億増やして0.00202の改善で+24.8 Eloを得ている。

> **訂正（2026-08-12、[ADR-0158](0158-mirror-factorizer.md)で判明）**。
> このloss差は改善と断定できない。`FT_IN` が125,388から69,660へ変わると
> `nn.EmbeddingBag` の乱数消費量が変わり、**以降の層の初期値がすべて
> 違ってしまう**。初期値の系列だけが違う2本でvalid lossは0.00136動く
> （ADR-0158の実測）。**この差は初期値のばらつきと同じ規模である**。
> 下の対局の結果は直接の比較なので、棄却の結論は変わらない。

### 足切り2: NPSは1.53%落ちた

ノード数固定300万・8周・交互で測る（それぞれの最良ネットを載せる）。

| バイナリ | NPS（8周の平均） | 変化 |
|---|---|---|
| 81バケット | 1,894,436 | — |
| ミラー45 | 1,865,394 | **−1.53%** |

FT重みが32.1MBから17.8MBへ減った利得より、**ミラーの判定コストが上回った**。
`board_bona_piece` は差分計算でも呼ばれるので、1手ごとに分岐が乗る。

### 足切り3: 対局では負けた

| 項目 | 値 |
|---|---|
| 条件 | `--tc 10+0.1 --concurrency 8 --adjudicate 2000,8`、elo0=0、elo1=5 |
| 対局数 | 2,070（1,035ペア） |
| W-D-L | +961 =53 -1056 |
| Elo [95%CI] | **−16.0 [−30.8, −1.2]** |
| LLR | −1.63（判定に至らず、打ち切り） |

**信頼区間がゼロを跨がない**。LLRはH0側へ進んでいたが、確定を待つより
原因の切り分けへ時間を回すため2,070局で打ち切った。

**lossは良いのに対局では負ける**。これは足切りをvalid loss単独にしない
判断（上の「検証の順序」）が実際に効いた例である。lossだけで通していれば、
29.9億の本学習（8〜9時間）へ進んでから気づくことになっていた。

### 切り分け: 速度か構造か

ノード数を1手30万に固定して測り直した（[ADR-0127](0127-net-shape-bench.md)と
同じ土俵）。速度差が消えるので、評価関数の質だけが残る。

| 条件 | 対局数 | Elo [95%CI] |
|---|---|---|
| 時間制（10+0.1） | 2,070 | −16.0 [−30.8, −1.2] |
| ノード数固定（30万） | 1,600 | **−5.6 [−22.6, +11.3]** |

**答えは「両方」だった**。ノード数を揃えても中立からわずかにマイナスで、
そこへ速度の代償が10 Elo前後乗って時間制の−16.0になる。差の10 Eloは
NPS −1.53%から期待される−6.7とおおむね揃う。

## なぜ棄却するか

### valid lossの改善が棋力に変わらない

**これがこの実験でいちばん重要な結果である**。valid lossは0.00112良い。
[ADR-0135](0135-teacher-data-3b.md)の換算（0.00202で+24.8 Elo）を当てれば
+14 Elo相当が期待できるが、速度差を消した土俵でも出てこない（−5.6）。

> **訂正（2026-08-12）**。上のとおりloss差は初期値のばらつきと区別が
> つかない。**正しくは「lossの差自体が誤差だった可能性が高く、棋力も
> 動かなかった」である**。以下の「系統誤差だから探索の選択を動かさない」
> という説明は、lossが本当に改善していた場合の解釈として残す。

理由は誤差の性質にあると見ている。**ミラーが消したのは系統誤差である**。
同じ局面の左右像に違う値を付ける誤差で、局面の絶対評価としては明確な欠陥
だが、探索は常に兄弟局面どうしを相対比較する。**左右像が同時に候補へ並ぶ
ことはないので、この誤差は探索の選択をほとんど動かさない**。

lossは「絶対値の平均的な正しさ」を測り、探索が要るのは「候補手の相対的な
順序」である。両者の一致しない場面があることは
[ADR-0136](0136-quiet-teacher-positions.md)が記録していた。あれは物差しの
動いたケースだった。**本ADRは物差しを固定したまま両者が乖離した例である**。

### 速度は取り戻せるが、届かない

NPSの−1.53%は消せる見込みがある。`View` をconst genericsで単相化すれば
ミラーの分岐が消え、変換表を引く形にもできる。ただし**取り戻しても
ノード数固定の−5.6が上限**で、勝ち越しには届かない。投資の価値が薄い。

## Consequences

- **mainへは入れない**。実装はブランチ `docs-adr0157-king-mirror` に残す。
  ADRのこの記録が成果物である（CLAUDE.md）
- 公開評価関数の互換（[ADR-0034](0034-nnue-architecture.md)）を切る判断は
  オーナーから得ていた（2026-08-12。「やねうら王のRustコピーが作りたい
  わけではない」）。**棄却したのでmainの `nnue_compat` はそのまま残る**
- **原資としては生きている**。FTパラメータ44%減は、幅へ振り替えれば
  FT384でも26.7Mで現行の32.1Mより小さい。
  [ADR-0127](0127-net-shape-bench.md)が測った「FTを太らせる代償」を
  パラメータ増なしで払える道は残る。ただし本ADRの結果は
  **ミラー単独では棋力が動かない**ことなので、**再訪するならFT幅の拡大と
  セットで、幅の効果として測る**。ミラーはその前提条件でしかない
- 案C（学習時のミラーデータ拡張）は**取り下げる**。案Bが構造で対称性を
  保証してなお棋力が動かなかった以上、近似で同じ性質を入れる案Cが効く
  見込みはない。ROADMAPの候補からも外す
- **loss単独で足切りしない運用を続ける**。本ADRは物差しを固定したまま
  lossと棋力が乖離した実例になった。[ADR-0136](0136-quiet-teacher-positions.md)
  の「物差しが動く」場合と合わせ、**lossは足切りの必要条件であって
  十分条件ではない**
