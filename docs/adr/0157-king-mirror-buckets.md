# 0157: HalfKPの玉位置を左右ミラーで45バケットへ畳む

- Status: proposed
- Date: 2026-08-12
- 関連ADR: [0034](0034-halfkp-features.md), [0066](0066-virtual-features.md), [0127](0127-net-shape-bench.md), [0131](0131-frozen-ft-light-head.md), [0135](0135-teacher-data-3b.md), [0156](0156-bucket-accumulator-cache.md)

## Context

将棋盤は左右対称である。駒の動きに左右の別はなく、キャスリングのような
非対称なルールもない。**局面を左右反転しても強さは変わらない。**

ところがHalfKPは玉位置を81通りそのまま持つので、この対称性は構造では
保証されず、学習で近似するしかない。獲得できているかを測った。

### 現行ネットは左右対称性を獲得していない

`halfkp_2990M_q1`（現行ネット、29.9億局面で学習）で、局面とその左右反転像の
評価値の差を測る（`nnue::tests::mirror_lr_gap`）。

| 局面集 | 件数 | ミラー差の平均 | 中央 | p90 | p99 | 比較: 評価値の規模（平均 \|score\|） |
|---|---|---|---|---|---|---|
| `start_sfens_ply24` | 30,053 | **91** | 74 | 189 | 334 | **50** |
| `start_sfens_ply32` | 26,273 | **102** | 82 | 216 | 378 | **59** |
| ランダム局面（20〜100手） | 2,000 | 295 | 234 | 634 | 1,074 | 975 |

歩=90スケールなので、実戦的な局面で**平均1.0歩ずれる**。

**序盤では信号よりノイズのほうが大きい。** ply24で評価値そのものの規模が50、
ミラー差が91である。定跡を抜けた直後の最も重要な帯で、同じ強さの局面に
1歩の食い違いが出ている。ランダム局面のほうが差の絶対値は大きいが、
教師データの分布から外れた領域なので、実戦的な局面集の値を正とする。

### 参照実装は畳んでいる

Stockfishの `HalfKAv2_hm` は玉位置を左右ミラーで畳み、入力次元を22,528まで
落として、浮いた予算をFT幅（1024/視点）へ振っている。本エンジンは
125,388次元 × FT256で、**FTのパラメータ総数はむしろ多い**（32.1M対23.1M）。
差は幅であり、幅を作る余地は入力側の重複にある。

## 選択肢と比較

### 案A: 現状維持

対称性は学習で近似させ続ける。実装は要らないが、上の1.0歩は残る。

### 案B: 特徴側で玉位置を45バケットへ畳む

自玉の筋が6〜9なら盤面全体を左右反転し、玉の筋を1〜5に正規化する。
玉バケットは5筋 × 9段 = 45で、FT入力は 45 × 1548 = 69,660 になる
（現行の55.6%）。

- **対称性が構造で保証される。** ミラー差は定義上ゼロになる
- **FTパラメータが44%減る**（32.1M → 17.8M）
- **玉バケットあたりの実効サンプルが約2倍になる。** 教師データを使い切った
  今（[ADR-0135](0135-teacher-data-3b.md)）、データ効率の改善は増量と同じ
  意味を持つ
- 玉が5筋の局面は反転しないので、45のうち9バケットは対称化されない
- 既存ネットと互換が切れる。公開評価関数の読み込み（`nnue_compat`）も
  81バケット前提なので、ミラービルドでは無効になる

### 案C: 学習時のミラーデータ拡張

教師データに左右反転した局面を足す（ROADMAPの候補にあったもの）。実装は
軽い。ただし**対称性は構造で保証されず、近似のままである。** パラメータも
減らないので、幅へ振り替える余地も生まれない。案Bの下位互換になる。

## Decision

**案Bを採る。** 案Cは案Bが失敗したときの退避先として残す。

決め手は2つある。1つは上の実測で、**近似での獲得に失敗していることが
数字で出た**こと。もう1つは容量で、44%の削減がそのままFT幅の原資になる。
[ADR-0127](0127-net-shape-bench.md)が「FTを太らせると速度で潰れる」と結論し、
[ADR-0156](0156-bucket-accumulator-cache.md)がその速度側を一部戻した。
**入力側の重複を削るのは、同じ壁への3本目の道になる。**

### 実装の方針

反転は視点ごとに独立に決める（Stockfishと同じ）。視点cの自玉の筋が6〜9なら、
その視点の全特徴で升を左右反転する。手駒は升を持たないので変わらない。

変更は7か所になる。

| 場所 | 中身 |
|---|---|
| `core/bonapiece.rs` | 升の左右反転と、45バケットの `halfkp_index` |
| `engine/nnue.rs` | `FT_IN`、`for_each_bona_piece` の升変換 |
| `engine/nnue_acc.rs` | `diff_rows` の視点に反転の有無を持たせる |
| `engine/build.rs` | `HIMAWARI_MIRROR` フラグと `KING_BUCKETS` 定数 |
| `py/lib.rs` | `KING_BUCKETS` の公開 |
| `training/model.py` | `FE_END = FT_IN // 81` の81を `KING_BUCKETS` へ |
| `nnue_compat` | ミラービルドでは無効化（81バケット前提のため） |

**玉が5筋と6筋の間を動くと、その視点の全特徴が反転する。** これは
バケットが変わるのと同じ扱いになり、既存の「玉が動いた視点は遡れない」
構造がそのまま受ける。[ADR-0156](0156-bucket-accumulator-cache.md)の
玉位置キャッシュも、反転後の座標系で一貫するので変更なしで働く。

ファイル形式は変えない。`FT_IN` がヘッダの `dims[0]` に載るので、
既存のアーキ不一致チェックが誤読を弾く。

### 検証の順序

**足切りをvalid lossだけで通さない**（2026-08-12オーナー指摘）。lossが
小さくても弱い場合があるためで、3段に分ける。

1. **ミラー差がゼロになること**を確かめる（構造の確認、`mirror_lr_invariance`）
2. **3億局面で学習し、3つの物差しで比べる**（[ADR-0135](0135-teacher-data-3b.md)の手順）
   1. valid loss。81バケット版を同条件で学習して並べる
   2. NPS。FT重みが32.1MBから17.8MBへ減るのでキャッシュの効きが変わり、
      ミラーの判定ぶんは増える。**探索が変わるので
      [ADR-0074](0074-feature-verification.md)の機能検証（ノード数一致）は
      使えない**
   3. 3億ネット同士の直接対局（SPRT）。それぞれの最良構成をぶつける
3. 通れば29.9億で本学習し、あらためてSPRTにかける

**2で負けたら棄却する。** 対称性が正しくても、45バケットへ畳むことで
「左右で違う戦型の区別」が失われる可能性は残る。局面の優劣は左右対称でも、
教師データ（探索値）には非対称なノイズが乗っているためである。

#### valid lossの比較はこの実験では成立する

[ADR-0136](0136-quiet-teacher-positions.md)は「lossでネットを選べない場面が
ある」と記録している。**あれは教師データの分布を変えて物差しごと動いた
ケースである。** 本ADRが変えるのは特徴の定義だけで、教師（`train_300M_q1`）も
検証集合（`valid_385M_q1`）も的も損失関数も同じものを使う。同じ局面を同じ的で
測るので、比較の土俵は動かない。

**それでもlossは2つを見ない。** 探索が必要とする候補手の相対的な順序と、
速度である。上の2-2と2-3はその2つを埋めるために置く。

#### 3億での結果は楽観に振れる

ミラーの利得は玉バケットあたりの実効サンプルが2倍になることなので、
**データが少ないほど効く。** [ADR-0136](0136-quiet-teacher-positions.md)の
静止化が3億の+35.8から29.9億で+13.9へ薄まったのと同じ筋である。
3億で僅差なら、本学習では消える見込みとして扱う。

## Consequences

- 既存ネットは読めなくなる。現行の `halfkp_2990M_q1` は81バケットのままなので、
  ミラービルドと通常ビルドは別系統になる。比較は同じ教師データからの
  学習同士で行う
- 公開評価関数の互換（[ADR-0034](0034-halfkp-features.md)）は失われる。
  **切ってよいとオーナーが判断した**（2026-08-12。「やねうら王のRustコピーが
  作りたいわけではない」）ので、`nnue_compat` と `makenet --import` は消した
- 成功した場合の次の一手は**幅への振り替え**である。FT384でもパラメータは
  26.7Mで現行の32.1Mより小さい。[ADR-0127](0127-net-shape-bench.md)が
  測った「FTを太らせる代償」を、パラメータ数を増やさずに払える
- 棄却した場合は案C（データ拡張）へ落とす。実装は軽く、近似の精度は上がる
