# 0262: 他のスレッドが読んでいる手を後回しにして、並列探索の重複を減らす

- Status: rejected
- Date: 2026-11-09
- 関連ADR: [0031](0031-lazy-smp.md), [0200](0200-thread-scaling.md), [0202](0202-smp-loss-diagnosis.md)

## Context

オーナーの指示（2026-11-09）は、1スレッドの探索を変えずに、複数スレッドでの
自己対局の棋力を上げることである。素朴なLazy SMPはスレッドを増やすと早く
頭打ちになる、という見立てが出発点にある。手段は問わず、最後はSPRTで確かめる。

現状の数字は[ADR-0200](0200-thread-scaling.md)と[ADR-0202](0202-smp-loss-diagnosis.md)にある。
8スレッドの並列効率は、深さのずらしを入れて0.50になった。それでも同じ深さに
1スレッドの2.8〜3.0倍のノードを使う。ADR-0202は、参照実装（やねうら王）も
0.49なので、Lazy SMPとして普通だと結論した。ただしそれは参照と同じ方式の
上限であって、方式を変えたときの上限ではない。ずらしと置換表の大きさでは
重複は減らず、残りの重複は「同じ部分木を同時に読む」こと自体から来ている。

## 選択肢と比較

### 案A: 他のスレッドが読んでいる手を後回しにする（Simplified ABDADA）

Tom Kerrigan が提案した、ABDADAの簡略版である。共有の小さな表に「いま読んでいる
(局面, 手) の組」を書く。ノードの2手目以降を読む前に表を引き、他のスレッドが
同じ組を読んでいれば、その手を後回しにして他の手を先に読む。生成した手を出し切ったら、
後回しにした手を読む。

最初の手は必ず自分で読む。YBWCの「長男を先に読む」と同じ理由で、窓が決まる前に
兄弟を後回しにしても得がない。Lazy SMPの骨格（置換表の共有、反復深化、投票）は
そのまま残る。表は32,768升のu64で256KiBである。

利点は、重複の発生源に直接効くことである。欠点は、後回しにした手が後で読まれる
とき手数が増え、LMRで深く削られることである。それが損か得かは測るまで分からない。

### 案B: YBWCへ書き換える

分割点で兄弟をヘルパーへ渡す。重複は最も少ないが、分割点の同期と待ちが重い。
探索の構造（singular、NMP検証、バッファの貸し借り）を全面的に書き換えることになり、
1スレッドの探索を変えない条件を守るのも難しい。案Aが効かなかったときの手として残す。

### 案C: historyのスレッド間共有

ROADMAPの候補にある（Issue #430）。重複を減らす案ではなく、ヘルパーが学んだ
手の順序を共有する案である。重複の多さが今の損失の主因なので、先に案Aを測る。

## Decision

案Aを実装し、8スレッドで測る。2スレッド以上でだけ表を引き、1スレッドの探索は
変えない。後回しの判断は残り深さ3以上のノードに限る（`DEFER_MIN_DEPTH`）。

後回しにした手は、生成順での本来の順番を持ち越して読む。後で読むときの
手数をそのまま使うと、LMRで深く削られ、置換表の手でも浅く読まれてしまう。
持ち越せば、読む順だけが変わり、削り方と枝刈りは1スレッドのときと同じになる。

外部の報告では、texelの作者が自己対局で比べ、ABDADAがLazy SMPより
4コアの24+0.24で約+8 Elo、複数の条件でおおむね+10 Elo上回った
（[TalkChessのスレッド](https://talkchess.com/viewtopic.php?p=728060)）。
本エンジンで同じだけ出る保証はない。texelは深さのずらしを持たない。

### 実験の設計

1. 仮説: 他のスレッドが読んでいる手を後回しにすると、同じ部分木の重複が減り、
   8スレッドの自己対局で強くなる
2. 動かす変数: 後回しの有無だけ
3. 固定するもの: 1スレッドの探索（固定深さのノード数が全局面で変更前と一致する
   ことを確かめる）。深さのずらし・aspirationの窓・投票は現行のまま。
   対局条件はADR-0202の8対8と同じで、10+0.1、置換表256MB、同時1局、
   `start_sfens_ply24`、裁定2000cp×8手、320手上限
4. 事前登録は次のとおり
   - 深さ到達（`hmwr bench --threads 8 --hash 256`、先頭8局面、深さ26）は
     足切りに使わず、仕組みが動いているかの確認に使う。ノード比が下がれば
     重複が減っている
   - 8対8の既定SPRT（elo0=0、elo1=5、実行名 `adr0262-abdada-t8`）でH1なら
     採択する。H0なら棄却し、
     `DEFER_MIN_DEPTH` の変更や後回しの条件の緩和を別の実行として設計する

### 合格の条件

- Eloの判定: 既定（elo0=0、elo1=5）。Threads=8の対局で測る
- Elo以外の条件: 1スレッドの固定深さのノード数が全局面で一致すること
- 採否: 両方を満たしたときだけ入れる

## 測定

### 起動前の診断（2026-11-09）

計測用の一時的なカウンタで、8スレッドの1手0.2秒の探索（`start_sfens_ply24` の
100〜139行目の40局面）を見た。判定のたびに、同じ (局面, 手) を他のスレッドが
いま読んでいるかを数えた。

| ノードの残り深さ | 最初の手が重なる率 | 2手目以降が重なる率 |
|---|---|---|
| 3〜5 | 0.4〜0.5% | 0.07〜0.08% |
| 10 | 3.1% | 0.14% |
| 15 | 7.4% | 0.34% |
| 20以上 | 11〜13% | 0.7〜1.5% |

重なりは深いノードの最初の手に集中する。2手目以降は深くても1.5%以下で、
古典的なABDADAが後回しにする対象は少ない。ただし深いノードの部分木は大きく、
重なった状態で入った部分木のノードは全体の13%を占めた。最初の手の分は、
根に近いPVノードで全スレッドが重なるため、ほぼ探索全体が数えられてしまい、
重複の量の指標にならなかった。

各スレッドの到達深さも見た。メインは22〜23で常に最も浅く、深さを飛ばす
ヘルパーが24〜26まで進む。投票は40局面の大半でヘルパーを選んだ。

### 深さ到達（2026-11-09）

`hmwr bench --threads 8 --hash 256`、先頭8局面、深さ26、6周の平均で比べた。

| 版 | ノード合計 | 所要 |
|---|---|---|
| 現行 | 1.83億 | 20.6秒 |
| 2手目以降を後回し（手数は後で読むときの値） | 1.93億 | 22.7秒 |
| PVノード以外は最初の手も後回し（本来の順番を持ち越す） | 1.88億 | 21.0秒 |

周ごとの揺れは同じ版でも±10%あり、3本の差はその範囲にある。後回しで
深さ到達は縮まなかった。後回しにした手は戻ってきたときもまだ他のスレッドが
読んでいることが多く、重複は消えずに順番だけが変わると見ている。

Lazy SMPの棋力は深さ到達と一致しない（ADR-0202）ので、事前登録どおり
対局で決める。測るのは外部の報告がある古典形（最初の手は後回しにしない、
本来の順番を持ち越す）である。最初の手も後回しにする版は、古典形の結果を
見てから別の実行で測る。

### 対局（2026-11-09）

古典形を8対8の既定SPRT（`adr0262-abdada-t8`）で測った。

| 項目 | 値 |
|---|---|
| 対局数 | 1848（924ペア） |
| W-D-L | +785 =229 -834 |
| Elo [95%CI] | −9.2 [−23.3, +4.9] |
| LLR | −1.13（判定前） |

判定の前に、オーナーの判断で打ち切った。8スレッドの対局は1時間に約150局で、
H0の判定までさらに半日以上かかる見込みだった。区間の上端は+4.9で、対立仮説の
+5に届かない。H1は採れないと判断して棄却する。

## 結論

棄却する。後回しで深さ到達は縮まず、対局でも強くならなかった。点推定は
−9.2で、外部の報告（texelの+8〜10）と符号が逆になった。本エンジンは深さの
ずらしでヘルパーが既に散っており、後回しで減らせる重複が少ないと見ている。

事前登録の続き（`DEFER_MIN_DEPTH` の変更、最初の手も後回しにする版）は測らない。
1案の判定に1〜2日かかる割に、伸びしろの根拠がない。コードは
`feat-adr0262-smp-defer` ブランチに残し、mainへは入れない。

## Consequences

- 1スレッドで回す通常のSPRTには影響しない。並列の変更は、今後も8対8で測る
- 表の升の数とクリアの時機は、64スレッド以上の環境（選手権のAWS）で
  見直す可能性がある
