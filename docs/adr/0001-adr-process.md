# 0001: ADRテンプレートと運用

- Status: accepted
- Date: 2026-07-17
- 関連ADR: なし

## Context

本プロジェクトは、設計要素ごとにADR（Architecture Decision Record）を書いてから実装する。
盤面表現・Move構造・置換表など、後から変更すると手戻りが大きい決定が多いためだ。
最初に、ADRそのものの書式と運用ルールを決める。

## 選択肢と比較

### 案A: Nygard形式（Context / Decision / Consequences のみ）

最小構成で書くコストが低い。ただし選択肢の比較過程が残らず、
「なぜ他の案を捨てたか」を後から追えない。

### 案B: MADR完全版

Decision Drivers、Pros/Cons表など項目が多い。個人開発には過剰で、
1本あたりの執筆コストが高くなり運用が続かないリスクがある。

### 案C: MADR簡略版（Nygard + 選択肢比較）

Nygard形式に「選択肢と比較」を加えた構成。比較過程が残り、かつ1本30〜60分で書ける。

## Decision

案Cを採用する。書式は `template.md` のとおり。運用ルールは次の5点。

1. 1ファイル1決定。ファイル名は `NNNN-slug.md`
2. 番号は全体の通し番号4桁とし、起草した順に採番する。
   フェーズ分割とバックログは `README.md`（索引）で管理する
3. 関連ADRには既に存在するADRだけを書く。将来書く予定の決定に触れるときは、
   本文中で番号を付けずに主題名で言及する（例:「置換表のADR（P2で起草）」）
4. Statusは proposed → accepted → superseded と遷移する。
   却下した提案は rejected として残す
5. accepted後に実装まで済んだ決定は書き換えない。変更するときは新しいADRを書き、
   古い方を superseded にして相互リンクする
6. ADRを追加・更新したら索引 `README.md` を同じコミットで更新する

## Consequences

- 設計判断の理由と捨てた選択肢が記録として残り、将来の見直しが容易になる
- 実装前にADRを書くコストが発生する。1本30〜60分を超えそうな場合は、
  論点を分割して複数のADRにする
- 通し番号のため、番号からフェーズは読み取れない。フェーズとの対応は
  索引 `README.md` で管理する
