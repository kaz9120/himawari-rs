# 0099: NNUE隠れ層の内積をSDOTで4行ずつ計算する

- Status: accepted
- Date: 2026-07-29
- 関連ADR: [0089](0089-improvement-criteria.md), [0036](0036-nnue-quantization-simd.md), [0074](0074-feature-verification.md), [0081](0081-portability.md), [0003](0003-toolchain.md)

## Context

[ADR-0089](0089-improvement-criteria.md)の軸1（速度）の入口として、
探索のプロファイルを取った。samplyで4局面・深さ19を1スレッド探索し、
約35,000サンプルを集めた（局面は[ADR-0074](0074-feature-verification.md)の
4つ。時間が偏る局面3だけ深さを3浅くした）。

self時間の上位は次のとおりだった。

| 箇所 | 割合 |
|---|---|
| NNUE `forward_hidden` | 23% |
| `MovePicker::pick_best` | 17% |
| FT差分更新 `ft_add`/`ft_sub` | 14% |
| FT全計算 `refresh_top` | 7% |
| `attacks` | 6% |

首位の `forward_hidden` は32→32→1の3層を計算する。積和の総数は
32×512 + 32×32 + 32 = 17,440で、i8重みとu8活性の内積が本体である。
現行の `dot`（`nnue_simd.rs`）は、両者をi32へ広げてから8要素ずつ
掛けている。

```rust
let mut acc = Simd::<i32, 8>::splat(0);
for (wc, xc) in w.as_chunks::<8>().0.iter().zip(x.as_chunks::<8>().0) {
    let wv = Simd::<i8, 8>::from_array(*wc).cast::<i32>();
    let xv = Simd::<u8, 8>::from_array(*xc).cast::<i32>();
    acc += wv * xv;
}
```

1バイトの値を4バイトへ広げるため、レジスタあたりの処理量が本来の
1/4に落ちる。ARMv8.4のSDOTは、この形の積和を1命令で16要素ぶん
処理する。SDOTはi8×i8だが、活性は `clip_to_u8` が0..127へ丸めた値
なので符号ビットが立たず、i8として読んでも値が変わらない。

## 選択肢と比較

候補を `crates/engine/benches/nnue_dot.rs` で比較した。第1層
（32行×512列）と第2層（32行×32列）を1回ぶん計算する時間である。
`RUSTFLAGS="-C target-cpu=native"`、Apple M4 Pro。

| 案 | 第1層 | 第2層 | 倍率（第1層） |
|---|---|---|---|
| A: 現行（i32へ広げて8レーン） | 525 ns | 48 ns | 1.00 |
| B: 同じ形で16レーン | 545 ns | 40 ns | 0.96 |
| C: 積をi16で持つ | 670 ns | 48 ns | 0.78 |
| D: SDOT（行ごと） | 289 ns | 19 ns | 1.82 |
| E: SDOT（4行同時） | 129 ns | 10 ns | 4.06 |

案BとCは移植可能なまま幅を稼ぐ試みだが、どちらも効かなかった。
`std::simd` のレーン数を増やしても、生成されるのは128bitのNEON命令の
反復であり、1バイト値を広げるコストは消えない。

案Dと案Eの差は水平加算の回数にある。案Dは行ごとに `vaddvq_s32` を
呼ぶため、32行で32回になる。案Eは4行ぶんのアキュムレータを並べて
持ち、活性のロードを4行で共有する。SDOTの結果依存が4本に分かれる
ため、パイプラインも埋まりやすい。

x86_64にも同じ構造の命令がある。AVX-VNNIの `_mm256_dpbusd_epi32` は
u8×i8をi32へ直接積和し、AVX2しかない環境でも `_mm256_maddubs_epi16`
と `_mm256_madd_epi16` の組で同じ計算になる。移行先として想定している
Core i7-1255U（Alder Lake、[ADR-0081](0081-portability.md)）は
AVX-VNNIを持つ。

## Decision

案Eを採る。aarch64かつdotprodが有効なときだけSDOT経路を使い、
それ以外は現行のportable実装を残す。

決め手は倍率である。第1層で4.06倍、第2層で5.05倍になり、案Dの
2倍以上の差がついた。`forward_hidden` 全体では573 nsから139 nsへ減る。
プロファイルの23%が5〜6%になる計算で、NPSは15%前後の改善を見込んだ。
実測は868k→1046k（+20.5%）で見込みを上回った。

x86_64にも同じ構造で実装する。内側だけを `maddubs`（u8×i8をi16へ積和）
と `madd`（i16をi32へ畳む）の組に差し替え、4行同時と水平加算の形は
そのまま使う。

命令の選択はAVX2に留める。AVX-VNNIなら `dpbusd` 1命令になるが、
GitHub Actionsのランナーは世代が混在しており、実行できる保証がない。
AVX2なら現行のランナーで確実に動き、移行先のAlder Lakeでも当然動く。
1命令ぶんの差より、正しさを機械で守れることを優先する。

速度は測れない。x86_64の実機がないためである。ARM側の測定で構造の
効果は確かめてあり、命令数の比（8要素/命令→32要素/2命令）も同じ向きに
働く。ただし数字としては未検証であり、実機を得たら測り直す。

### 正しさをCIで守る

x86_64経路は開発機では実行されないため、テストが通ったかどうかを人が
確認できない。CIに `-C target-feature=+avx2` を付けたジョブを足し、
`forward_hidden_matches_scalar` がAVX2経路で回るようにする。既定の
x86-64ターゲットはSSE2までで、追加しなければこの経路はコンパイルすら
されない。

### 出力が変わらないことの根拠

積和の順序が変わるだけで、値は変わらない。SDOTは4要素ずつの部分和を
4レーンに分けて持ち、最後に水平加算する。i32の範囲でオーバーフロー
しなければ、加算の順序は結果に影響しない。

値域は次のとおり。重みは-128..127、活性は0..127なので積は絶対値
16,256以下、第1層の512要素を全部足しても8.3M以下で、i32（21億）に
対して十分小さい。

検証は3段構えで行う。既存のスカラー実装との一致テスト
（`nnue_simd.rs` のテスト）、ベンチ内での案Aとの一致確認、そして
[ADR-0074](0074-feature-verification.md)の機能検証で4局面すべての
ノード数が変わらないことである。ノード数が1つでも動いたら、
評価値が変わったことを意味する。

## Consequences

NNUEの推論にアーキテクチャ固有のintrinsicsとunsafeが入る。これまで
`nnue_simd.rs` は `std::simd` だけで書かれており、移植性の面では
後退する。フォールバックを残すため動作環境は狭まらないが、SDOT経路と
portable経路の2本を維持する必要が生じる。両者の一致はテストで守る。

経路が3本（SDOT・AVX2・portable）になり、どれが使われるかはビルド時の
ターゲットで決まる。CIはportableとAVX2の2本を検証するが、SDOT経路の
一致は開発機（Apple Silicon）での実行に依存する。ARMランナーを足すか、
ローカル実行を前提とするかは、[ADR-0081](0081-portability.md)の移行先が
決まってから判断する。

速度改善は探索の出力を変えないため、固定深さでの棋力は動かない。
効果は時間制でのみ現れる。SPRTは **+59.7 [+39.7,+80.2]**（1104局、
LLR +2.82でH1採択）だった。

NPS +20.5%が+59.7 Eloになった。eval hash（[ADR-0049](0049-eval-hash.md)）は
NPS +10.4%で+54.1 Eloだったので、NPS 1%あたりのEloは半分ほどである。
eval hashは評価の呼び出し自体を減らすため、NPSの伸び以上にノードあたりの
仕事が軽くなっていたと考えられる。軸1で測るときは、NPSの伸び率をそのまま
Eloの期待値に読み替えないほうがよい。

FT側（`ft_add`/`ft_sub`、14%）はi16の加減算であり、SDOTの対象外である。
こちらはメモリ帯域が効いており、IDEAS.mdの「量子化の再検討」で扱う。
