# 0160: 棄却した参照追従を1群にまとめて測り直す

- Status: rejected（前提の誤り。5件ともADR-0109の群で導入済みだった）
- Date: 2026-08-13
- 関連ADR: [0075](0075-razoring-margin.md), [0096](0096-rfp-margin.md), [0109](0109-reference-parity.md), [0111](0111-g2-lmr.md), [0113](0113-g4-eval-pruning.md), [0114](0114-g5-singular.md), [0141](0141-singular-rate-calibration.md), [0143](0143-spsa-tuning.md), [0155](0155-reference-walkthrough.md), [0159](0159-ft-width-1024.md)

## Context

[ADR-0159](0159-ft-width-1024.md)でFT幅1024のネットを作った。教師29.9億で
学習し、現行ネットに対して**ノード数固定で+70.6 Elo [+49.2, +92.5]**
（H1採択）である。評価関数としての実力は明確に上がった。

ところが時間制では負ける。速度が0.709倍に落ちるためで、10+0.1で−21.0、
60+0.6でも同水準にとどまる。**評価関数単体では採択に届かない**。

そこで問いが変わる。**精度の高い評価関数を活かして、ほかに何をすれば
強くなるのか**（2026-08-13オーナー提起）。

### 評価の精度は「枝刈りを強める権利」を生む

futility・razoring・RFPはいずれも「静的評価とalpha/betaの距離」を
マージンで測る。**マージンの適正値は評価誤差の大きさで決まる**。誤差が
小さくなれば、狭めても取りこぼさない。singular extensionも同じで、
延長の率が高いのは「TTの手が本当に良いか確信が持てない」ことの裏返しに
なる。

**本エンジンはこの権利をまだ行使していない**。

### 棄却した案は、ほとんどが参照追従だった

過去に棄却したADRを2つの軸で分けた。

| ADR | 内容 | 出自 | 評価精度への依存 |
|---|---|---|---|
| [0141](0141-singular-rate-calibration.md) | singular率を参照の設計点へ較正 | 参照追従 | **直撃** |
| [0096](0096-rfp-margin.md) | RFPのマージンと深さ上限 | 参照追従 | **直撃** |
| [0075](0075-razoring-margin.md) | razoringのマージンを2次式に | 参照追従 | **直撃** |
| [0105](0105-ttpv-propagation.md) | ttPvの伝播をRFPの安全弁に | 参照追従 | あり |
| [0084](0084-lmr-cutnode.md) | LMRにcutNode項 | 参照追従 | あり |
| [0155](0155-reference-walkthrough.md)群1〜3 | 参照への構造整列 | 参照追従 | 薄い |
| [0093](0093-mate1ply-in-search.md) | 1手詰めを探索へ組み込む | 参照追従 | なし |

**独自の案は3件だけで、残りはすべて参照実装とのギャップである**。

### 3件は同じ形で棄却された

上の表で「参照追従 × 評価精度に直撃」が重なるのは3件で、**どれも同じ結末**を
たどった。参照の値へ寄せると弱くなり、本エンジンの保守的な値が残った。

- [ADR-0141](0141-singular-rate-calibration.md): 率を参照の設計点（10〜20%）へ
  下げる較正だけで**−81.2 Elo**。「本エンジンでは高い率が効いている」
- [ADR-0096](0096-rfp-margin.md): 参照の式（`76×depth − 152×improving`、
  depth < 15）へ揃える案を棄却
- [ADR-0075](0075-razoring-margin.md): 参照の式へ揃える案を機能検証で棄却。
  **前提の誤りも記録されている**。本エンジンの300は参照の808〜3256より
  10.9倍「保守的」なのではなく、10.9倍「緩い」設定だった

[ADR-0155](0155-reference-walkthrough.md)は、この繰り返しを一般化して
こう結論している。

> 参照の構造と定数は**参照の評価関数と生態系**で最適化されており、自前ネットの
> 本エンジンには独自の平衡がある。

**ここから2つの仮説が立つ**。

1. **評価関数を差し替えれば平衡が動く**。参照並みの精度になれば、参照の値が
   効くようになる
2. **個別移植だから壊れた**。参照の値は互いに支え合っており、条件を欠いたまま
   数値だけを移せば機能しない

下の調査で分かったとおり、**効いているのは2のほうである**。本ADRは2を主軸に
据え、1は測定の順序へ織り込む。

## ただし真因は別々だった

着手前に3件の棄却理由を読み直した。**表面は同じ形（参照へ寄せると弱くなる）だが、
真因はそれぞれ違い、どれも「評価関数の精度」ではなかった**（2026-08-13の調査）。

| ADR | 棄却の真因 |
|---|---|
| [0141](0141-singular-rate-calibration.md) | `singular_beta` は延長・multi-cut・negative extensionの3分岐すべての軸である。マージンを上げると**multi-cut率も55.4%から29.3%へ落ちた**。−81.2 Eloの内訳は延長減と枝刈り減の合算で、後者は精度と無関係 |
| [0096](0096-rfp-margin.md) | 参照のRFPには `!ss->ttPv`（過去にPVだったノードでは刈らない）が付く。**本エンジンはttPvをTTに保存しているが探索で読んでいない**。安全弁がない状態で、安全弁を前提にしたマージンへ寄せた |
| [0075](0075-razoring-margin.md) | 前提の誤り。本エンジンの値は参照より10.9倍「保守的」なのではなく10.9倍**「緩い」**（＝既に攻めている）。参照へ寄せると保守的になる |

[ADR-0096](0096-rfp-margin.md)の残した一文が本質である。

> **マージンの数値は、それを支える条件と組でしか意味を持たない**。数値だけを
> 比べて「緩い・きつい」を判断してはいけない。

**部分移植が失敗するのは当然だった**。RFPのマージンにはttPvの安全弁が要り、
singular率にはmulti-cutとの整合が要る。参照実装は全体で1つの平衡をなしており、
条件を欠いたまま数値だけを移せば壊れる。

CLAUDE.mdの規約も同じことを言っている。

> 単発の変更は1機能=1SPRT。**参照実装への追従は1群=1SPRT**（[ADR-0109](0109-reference-parity.md)）

**個別に拾おうとしたこと自体が、この規約から外れていた**（2026-08-14オーナー指摘）。

## Decision

**残っている乖離を1群にまとめ、1つのSPRTで測る**。

| 項目 | ADR | 何が欠けているか |
|---|---|---|
| ttPvの伝播 | [0105](0105-ttpv-propagation.md) | RFPの安全弁。保存はしているが探索で読まない |
| RFPのマージンと深さ上限 | [0096](0096-rfp-margin.md) | 安全弁を前提にした値 |
| razoringのマージン | [0075](0075-razoring-margin.md) | 参照の2次式 |
| LMRのcutNode項 | [0084](0084-lmr-cutnode.md) | 削減量を決める条件 |
| singular率の較正 | [0141](0141-singular-rate-calibration.md) | multi-cutと連動する軸 |

**これらは互いに支え合う**。ttPvが安全弁になってRFPを攻めさせ、cutNodeがLMRの
削減を決め、`singular_beta` がmulti-cutと連動する。1つずつでは壊れ、揃えば
機能する可能性がある。

### 測定の順序

**1. FT256（現行構成）で測る**。

「個別では棄却されたが、まとめてならどうか」は**評価関数に依らない問い**である
（2026-08-14オーナー指摘）。現行のバイナリとネットをそのまま使えるので、
評価関数を変数から外して探索の平衡だけを測れる。**効けばそれ自体が採択候補で、
[ADR-0159](0159-ft-width-1024.md)とは独立に価値がある**。

**2. 棄却されたら、FT1024でも測る**。

[ADR-0159](0159-ft-width-1024.md)のネット（`ft1024_2990M_q1`）とバイナリは
揃っているので、**追加の学習コストはない**。評価値の改善で以前棄却された
パラメータが有効になる、という筋を常に残しておく（同オーナー方針）。

FT256で棄却されFT1024なら通るとき、それは「参照の平衡は参照並みの評価精度を
要求する」ことの証拠になり、[ADR-0159](0159-ft-width-1024.md)の採否にも直結する。

### 見立て

**まとめても効かない前例がある**。[ADR-0155](0155-reference-walkthrough.md)は
群1〜3（`depth == 0` の入口・TTの追従・ムーブループの終端）をまとめて測り、
3030局で−6.7だった。ただしあれは**構造の整列**であって、本ADRのマージン系とは
別の群である。

## Decision（改訂、2026-08-14）

**棄却する。Decisionに挙げた5件は、すべてすでにmainへ入っている**。

着手にあたって現在のコードを読んだところ、5件とも
[ADR-0109](0109-reference-parity.md)の追従キャンペーンで群として導入され、
SPRTで採択されていた。

| 項目 | 現在の実装 | 入った群 |
|---|---|---|
| ttPvの伝播 | `search.rs:911` が `is_pv \|\| hit.pv` で受け継ぎ、`search.rs:2130` が1手前から引き継ぐ | 読む側をG2が持つ（LMRの項2） |
| RFPのマージンと深さ上限 | `RFP_MAX_DEPTH = 15`・`RFP_MULT = 76`（`search.rs:45-46`） | G4（+41.1 Elo、[ADR-0113](0113-g4-eval-pruning.md)） |
| razoringのマージン | `alpha - 502 - 306*depth^2`（`search.rs:2548`） | G4（同上） |
| LMRのcutNode項 | `r += 3611 + 985*(TT手なし)`（`search.rs:2213`） | G2（+124.0 Elo、[ADR-0111](0111-g2-lmr.md)） |
| singular率の較正 | 構造はG5で導入。さらに率を下げる較正は[ADR-0141](0141-singular-rate-calibration.md)が−81.2 Eloで棄却 | G5（+48.2 Elo、[ADR-0114](0114-g5-singular.md)） |

**本ADRの仮説2は、すでに実証されていた**。「個別移植だから壊れた。条件ごと
まとめて移せば機能する」は正しい。G2・G4・G5がまさにそれを行い、3群だけで
+213.3 Eloを得ている。棄却された5件は、その群の中で支える条件ごと入った。

5件目のsingularだけは性質が違う。G5で構造（multi-cut・negative extension）が
入った後、[ADR-0141](0141-singular-rate-calibration.md)が率を参照の設計点へ
寄せて−81.2 Eloで棄却した。**乖離が残っているのではなく、乖離を残すほうが
強いと測って決めてある**。

### なぜ誤ったか

**棄却ADRの記述を、現在のコードで確認せずに再訪の材料にした**。
0075・0084・0096・0105は2026-07-28〜29の文書で、ADR-0109のキャンペーンは
その直後（07-30〜08-04）に走っている。棄却の記録は当時の判断であって、
現在の実装ではない。

CLAUDE.mdは「手順を書いたら実行して確かめる」「数値を書くときも出典に
当たる」と定めている。本件は**その規律をコードにも適用すべきだった**例に
なる。棄却ADRを掘り起こすときは、対象がまだ入っていないことを実装で
確かめてから起草する。

## Consequences（改訂）

- **参照追従の線は閉じる**。定数レベルの追従は
  [ADR-0155](0155-reference-walkthrough.md)が220項目超の全数照合で一致を
  確認し、構造の乖離も群1〜3が3030局で−6.7として棄却した。本ADRで
  「棄却された値がまだ残っている」という最後の可能性も消えた
- 残る参照との差は、[ADR-0155](0155-reference-walkthrough.md)の群4（千日手の
  前計算。16手キャップの性能バグを兼ねる）・群5（rootの統合）・群6（小物）
  だけになる。ROADMAPの「次の方向」は本ADRからそちらへ差し替える
- 本ADRが立てた問い「精度の高い評価関数を活かして何をするか」は残る。ただし
  答えは参照追従の側にはない。[ADR-0159](0159-ft-width-1024.md)のFT1024は
  速度で負けており、そちらは速度改善の問題である
- **棄却ADRの再訪には、実装確認の手順が要る**。本ADRは5件の棄却理由を
  読み込み、真因まで分類したうえで、対象がすでに入っていることに
  気づかなかった。文書だけを深く読むほど、実装との乖離に気づく機会が減る

## Consequences（棄却前の見込み。記録として残す）

- 群で効けば、**FT256の現行構成がそのまま強くなる**。
  [ADR-0159](0159-ft-width-1024.md)のFT1024とは独立した成果になる
- FT256で効かずFT1024なら効いた場合、「参照の平衡は参照並みの評価精度を要求する」
  という結論になり、**評価関数を強くする投資の価値が上がる**
- どちらでも効かなければ、[ADR-0155](0155-reference-walkthrough.md)の
  「本エンジンには独自の平衡がある」が、まとめての移植でも成り立つことになる。
  参照追従の線は閉じ、探索の改善は独自の設計へ向かう
- 群が大きいので、**どの項が効いたかは分からない**。効いた場合に内訳を知りたく
  なったら、群から1項ずつ抜いて測り直す（[ADR-0151](0151-speedup-sweep.md)群の
  運用と同じ考え方）
- 実装は[ADR-0105](0105-ttpv-propagation.md)・[0084](0084-lmr-cutnode.md)が
  棄却時に戻されているため、掘り起こしが要る。定数だけで済む
  [0096](0096-rfp-margin.md)・[0075](0075-razoring-margin.md)・
  [0141](0141-singular-rate-calibration.md)とは作業量が違う
