# 0008: 座標系（Square/File/Rank）

- Status: accepted
- Date: 2026-07-17
- 関連ADR: [0002](0002-cargo-workspace.md)

## Context

盤面表現のすべてがこの決定に依存する。bitboardのビット順、利きの
シフト方向、SFEN/USI表記との変換、そしてNNUEのBonaPiece番号が
Squareの添字で決まる。P1で最初に確定すべき決定である。

将棋の座標は「筋（file、右から1〜9）×段（rank、上から一〜九）」で表す。
USIのマス表記は筋数字＋段英字（例: `7g`）、SFENの盤面は9a側（左上）から
段ごとに走査する。

## 選択肢と比較

### 案A: 筋優先

`sq = file * 9 + rank`。SQ_11 = 0（1筋一段、盤の右上）、SQ_12 = 1、…、
SQ_99 = 80（左下）。段方向の移動が ±1、筋方向が ±9 になる。

- 1つの筋の9マスがビット上で連続する。香・飛の縦利きを減算の桁借りで
  求めるQugiy方式（利き生成のADRで検討）が、この連続性を直接使える
- 歩の利きがシフト1命令で書ける（先手の歩の利き = `bb >> 1`）
- やねうら王・Aperyと同じ添字になるため、定数レベルの照合もできる（副次的）

### 案B: 段優先（チェス型）

`sq = rank * 9 + file`。SFENの走査順と添字順が一致し、盤面表示の
ループが素直になる。歩の利きは ±9 シフトでこれも1命令。ただし筋の
9マスがビット上で9飛びになり、縦利きの桁借りトリックが使えない。
表示ループの素直さは変換関数1つで代替できるため、利点が薄い。

## Decision

案Aを採用する。決め手は筋方向のビット連続性である。縦方向の利き
（香・飛の縦、歩）が将棋で最も頻繁に計算される利きであり、これが
シフトと減算の少数命令に落ちるレイアウトを選ぶ。定義は次のとおり。

- `Square` は 0〜80。`sq = file * 9 + rank`（いずれも0起点）。
  SQ_11 = 0、SQ_19 = 8、SQ_21 = 9、SQ_99 = 80
- `File` は 0〜8（FILE_1 = 0が盤の右端）、`Rank` は 0〜8（RANK_1 = 0が盤の上端）
- 方向デルタ（先手視点）: 下 = +1、上 = −1、左 = +9、右 = −9
- `Inv`（180度回転）: `80 − sq`。NNUEの後手視点への正規化に使う
- `Mir`（左右反転）: `file → 8 − file`、すなわち `(8 − file) * 9 + rank`
- USI表記との変換: 筋 = 数字（1〜9）、段 = 英字（a〜i）。SFENの走査は
  段優先だが、変換はパーサ・シリアライザ内に閉じる

Rustでの表現は `Square(u8)` などのnewtype＋関連定数とし、C-likeな
enumは使わない。添字演算とテーブル参照が主用途であり、enumは
変換が煩雑になるだけで網羅性検査の利点が活きないためだ。
値域の防御は `debug_assert!` で行う（ADR-0004の規約に準拠）。

## Consequences

- 歩・香・桂の利きと敵陣判定がシフトとマスクの少数命令で書ける
- SFEN入出力の走査順と添字順が一致しないが、影響は変換関数内に閉じる
- チェス系資料（Stockfish、Chess Programming Wiki）とはrank/fileの
  優先順が逆になる。移植時は添字の読み替えに注意する
