# 0074: SPRTの前に機能検証を行う

- Status: accepted
- Date: 2026-07-27
- 関連ADR: [0027](0027-sprt-framework.md), [0028](0028-pruning-extensions.md), [0072](0072-history-pruning.md)

## Context

[ADR-0072](0072-history-pruning.md)のhistory pruningは、2078局のSPRTを
回した後で「一度も発動していなかった」と判明した。固定深さでノード数を
比べれば5分で分かることに、8並列で数時間を費やした。

原因は、実装した機能が動いているかを確かめる手順がなかったことである。
SPRTは「効果があるか」を測る道具で、「機能しているか」は測らない。
中立の結果が出たとき、それが「効果がなかった」のか「動いていなかった」のか
を区別できない。

同じ失敗は他にも起こりうる。IDEAS.mdの候補には、他エンジンの係数を
参照するものが多く含まれる。係数はそのエンジンのスケールを前提にしており、
前提が違えば発動しない。ADR-0072は値域の理論値だけを見て換算し、
実効分布を見なかった。

もう1つの遠因は、定数の出典が記録されていないことである。
[ADR-0025](0025-move-ordering.md)はhistoryのbonusを `+depth²`、divisorを
16384と決めたが、どちらも根拠を書いていない。
[ADR-0047](0047-continuation-history.md)は「既存main historyと同一」として
それを引き継いだ。両者の整合を確かめる機会が一度もないまま5か月が過ぎた。

## 選択肢と比較

### 案A: SPRTの前に機能検証を必須にする

探索の挙動を変える変更は、SPRTにかける前に「実際に挙動が変わったか」を
測る。ノード数が変わらなければ、その変更は探索に影響していない。

対局時間を守れる。中立の結果を「効果なし」と「不発」に切り分けられる。
測定はローカルで数分で済む。

手順を規約として書く分、着手のたびに1ステップ増える。

### 案B: SPRTの結果が中立だったときだけ診断する

追加の手順を平時に課さない。中立のときだけ原因を追う。

ADR-0072はまさにこの形で、2078局を使ってから診断した。事後では
費やした対局が戻らない。判定に至らず打ち切った場合、
「効果が小さい」のか「不発」なのかが分からないまま記録に残る。

### 案C: テストで担保する

枝刈りごとに「この局面では発動する」という単体テストを書く。

回帰を防げる点は強い。ただしテスト局面の選定が難しく、
発動率のような分布の性質は単体テストで表現しにくい。案Aと排他ではない
ので、有効な機能から順に足していけばよい。

## Decision

案Aを採る。

### 機能検証の手順

探索の挙動を変える変更は、SPRTの前に次を測り、結果をADRに記録する。

1. 固定深さでのノード数を、変更前後で比較する。局面は3つ以上使う。
   ノード数が全局面で一致したら、その変更は探索に影響していない
2. 枝刈り・延長を追加した場合は、発動率も測る。判定が真になった回数を
   判定対象の総数で割る。0.1%を下回るなら、効果はSPRTの検出限界より
   小さいと考えてよい
3. 他エンジンの係数を参照した場合は、参照元のスケール前提が本エンジンで
   成り立つかを実測で確かめる。理論値域の比で換算しただけでは足りない

ノード数の測定はUSI経由で行える。`go` の直後に `quit` を送ると探索が
打ち切られるため、待ちを挟む。

```
(printf 'usi\nsetoption name EvalFile value <net>\nisready\nusinewgame\n'
        'position sfen <sfen>\ngo depth 13\n'; sleep 35; printf 'quit\n') \
  | <engine> | grep "^info depth 13 "
```

発動率の測定は、判定箇所にカウンタを一時的に置いて探索を回す。
このコードはコミットしない。

### 探索定数には出典とスケール前提を書く

探索定数を追加・変更するADRには、次の3つを書く。

- 値の出典（どのエンジンのどの式か）
- その出典が前提とするスケール（評価値、history、depthの単位など）
- 本エンジンでその前提が成り立つ根拠

「実績値を出発点にする」（[ADR-0028](0028-pruning-extensions.md)）だけでは
足りない。実績値は出典のスケールの上でのみ実績である。

参考として、2026-07-27時点で確認したスケールの対応を残す。
評価値は `SIGMOID_SCALE = 600.0`（`training/model.py`）で学習しており、
やねうら王・nodchip系と同じ歩=90スケールである。SEEの駒価値
（`crates/core/src/position.rs` の `PIECE_VALUE`）も同系列の値と一致する。
したがって枝刈りマージンは絶対値のまま比較してよい。historyのスケールは
一致せず、[ADR-0073](0073-history-bonus-scale.md)で揃える。

## Consequences

着手のたびに測定が1ステップ増える。数分の作業で、数時間の対局を守る。

中立の結果を切り分けられる。「発動率は十分だが効果がない」と
「そもそも発動していない」は、次に取る行動が違う。前者は設計の見直し、
後者は前提の修正になる。

ADRに測定結果が残る。後から「この枝刈りはどのくらい効いているか」を
辿れるようになり、定数を再調整するときの出発点になる。

出典とスケール前提を書く欄が増える分、ADRの起草がわずかに重くなる。
[ADR-0025](0025-move-ordering.md)の欠落が5か月見えなかったことと引き換えに
受け入れる。

この規約は探索に閉じる。評価関数と学習の変更はvalid lossという別の
指標を持ち、「実装したが動いていない」はlossが動かないことで検出できる。
