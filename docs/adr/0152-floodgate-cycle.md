# 0152: floodgateの棋譜を定期回収し、分析と定跡追加を決定論の手順にする

- Status: accepted
- Date: 2026-08-09
- 関連ADR: [0063](0063-book-loader-and-mini-book.md), [0074](0074-feature-verification.md), [0122](0122-tooling-language-split.md), [0139](0139-mate1ply-in-search-retry.md), [0146](0146-book-full-width-opening.md), [0149](0149-experiment-runner.md)

## Context

floodgateへ放流を続けており、棋譜がwdoorに溜まっている
（例: `x/2026/player/Himawari+6fd5a66.html`）。オーナーの要望は2つある
（2026-08-09）。

1. 定期的に棋譜を集めて分析し、怪しい挙動から改善案を出す
2. 棋譜に現れる24手目までの局面を定跡に足す。定期実行するので、
   決定論的な操作として確立する

ROADMAPには「優勢時の頓死の精査は、floodgateの棋譜をまとめて精査する回で
扱う」という持ち越しがあり（2026-08-05の投了見落とし）、この仕組みが
その受け皿になる。

**手作業では毎回条件がぶれる。** どの棋譜を集めたか、どの局面を足したか、
どの深さで掘ったかが記録に残らないと、次回の実行と比べられない。
[ADR-0149](0149-experiment-runner.md)と同じ理由で、手順をスクリプトに固定する。

## 決定論の定義

この運用で「決定論的」と呼ぶ条件を先に決める。

- **回収は追記専用。** 取得済みのファイルは再取得も削除もしない。
  入力集合は単調に増えるだけで、ある時点のスナップショットに対する
  以降の操作は再現可能になる
- **分析と定跡追加は、入力集合・エンジンビルド・評価関数・探索条件の
  純関数。** 探索は1スレッド固定深さ（マルチスレッドは非決定）。
  処理順はファイル名・局面のソートで固定する
- **定跡追加は冪等。** 既に定跡が持つ局面（キー一致）はスキップする。
  同じ入力で2度走らせても定跡は変わらない

## 構成（3段＋まとめの1本）

言語の割り当ては[ADR-0122](0122-tooling-language-split.md)に従う。
取得・集計はPython、エンジンを起動する分析と定跡はRustが担う。

### 1. 回収: `scripts/floodgate-fetch.py`

wdoorの対局者ページ（`x/<年>/player/<アカウント>.html`、既定は
`Himawari+6fd5a66`）に載っている対局のCSAだけを
`data/raw/floodgate/<年>/` へ落とす。

- **対局者ページが唯一の情報源。** 当初は年別アーカイブをファイル名の
  部分一致で走査する案だったが、名前の一致だけを頼りにすると関係のない
  対局が混じる。対局者ページならwdoor側がその対局者の棋譜であることを
  保証する（2026-08-09オーナー指示で変更）。アカウント名は固定で、
  年をまたぐときは `--player-url` を年ごとに渡す
- 取得済みファイルはスキップ（追記専用）。取得ログは
  `data/logs/floodgate-fetch.log` へ追記。リクエスト間に既定0.5秒置く

### 2. 分析: `kifu` ツール（Rust、`crates/tools/src/bin/kifu.rs`）

CSA群を読み、1局ずつ再生してレポート（markdown）を出す。探索は
1スレッド・固定ノード数で、同じ入力からは同じレポートが出る。

検査項目は実戦で起きた問題から選ぶ。

| 項目 | 検出 |
|---|---|
| 大悪手 | 自分の手の前後で固定ノード探索の評価が閾値以上落ちる |
| 頓死・詰み見逃し | 終盤N局面で詰み探索を回し、実戦の指し手と突き合わせる（2026-08-05の投了見落としの型） |
| 評価の乖離 | 実戦時の読み筋と再解析の評価が大きく食い違う局面 |
| 時間の使い方 | CSAの消費時間から、序盤の浪費・終盤の切迫を数える |

レポートは `data/logs/floodgate-report-<日付>.md`。**改善案そのものは
このレポートを読んだ人（またはエージェント）が書く。** ツールは疑わしい
局面のSFENと根拠を列挙するところまでを受け持つ。

### 3. 定跡追加: `book seed` サブコマンド（既存 `book` ツールへ追加）

棋譜に現れたply 24以下の局面を種にして、定跡へ足す。

- 種の抽出はCSA群から決定論で行う。ply昇順→SFEN辞書順にソートし、
  重複を除く
- 各種局面を既存 `book gen` と同じ形（MultiPV=width、固定深さ、margin）で
  探索し、エントリを追記する。**1スレッド固定**（gen既定の並列と違い、
  決定論を優先する）
- 定跡が既に持つ局面はスキップ（冪等）。追加した局面数と由来
  （どの棋譜から来たか）をログへ残す
- 深さ・幅の既定は[ADR-0146](0146-book-full-width-opening.md)の実績値
  （深さ28・width 4）を引き継ぐ。1局面34秒なので、1回の追加が
  何局面になるかで所要が決まる。上限は `--max-positions` で切る

### 4. まとめ: `scripts/floodgate-cycle.sh`

回収→分析→定跡追加→`book stats` を1本で回す。定期実行はこのスクリプトの
手動起動から始め、頻度が安定したら自動化を検討する。

## 選択肢と比較

### 定跡追加の探索を並列にする案

速いが、マルチスレッド探索は同じ局面でも選ぶ手が揺れる。決定論の要件に
反するので採らない。所要が問題になったら「種の抽出までを決定論にし、
探索は並列・結果は記録で担保」へ緩める余地はあるが、まず厳格側で始める。

### 実戦の指し手をそのまま定跡に入れる案

探索なしで速いが、負けた対局の悪手も定跡に入る。定跡は「その局面で
何を指すか」の表なので、手の選定は自前の探索で行い、棋譜は「どの局面が
実戦に現れるか」の分布情報としてだけ使う。

## Decision

上記3段＋まとめの構成で実装する。分析ツール（kifu）と定跡追加（book seed）は
別PRに分け、どちらもテスト（CSAパースの正解器照合、種抽出の決定論テスト、
冪等性テスト）を付ける。

## Consequences

- 定跡が実戦分布に追従する。相手の初手網羅（ADR-0146）に続き、
  実際に現れた変化が深さ24まで埋まっていく
- 分析レポートが定点観測になり、頓死・時間問題の再発を毎回同じ物差しで
  見られる。ROADMAPの「棋譜をまとめて精査する回」はこの仕組みで実施する
- 定跡追加は1回あたり数時間かかりうる（局面数×34秒）。実行タイミングは
  計測と重ねない
- wdoorへのアクセスは追記分だけに抑える。取得スクリプトにレート制限を入れる
