# 0097: capture historyを入れ直す（スケールを揃える）

- Status: rejected
- Date: 2026-07-29
- 関連ADR: [0048](0048-capture-history.md), [0089](0089-improvement-criteria.md), [0074](0074-feature-verification.md), [0090](0090-see-pruning.md)

## Context

[ADR-0048](0048-capture-history.md)でcapture historyを試し、872局で
-2.4 Eloの不採択だった。同ADRは疑い先を残している。

> 反証レビューが指摘した「履歴値域±16,384がMVV-LVAの駒得序列を跨ぐ」
> スケール不均衡が疑い先。スケール再設計での再挑戦は可

[ADR-0089](0089-improvement-criteria.md)の軸2（ノード効率）に乗る。
取る手の順序が良くなればβカットが早く起き、ノードが減る。

2026-07-29の3件（[ADR-0090](0090-see-pruning.md) +45.6、
[ADR-0091](0091-see-drop.md) +67.0、[ADR-0085](0085-correction-history-multi.md)
+17.7）はいずれも「判定の材料を正確にする」変更だった。一方で枝刈りの
強度を変える変更（[ADR-0084](0084-lmr-cutnode.md)、
[ADR-0096](0096-rfp-margin.md)）は続けて失敗している。capture historyは
前者に属する。

## スケールの検算

[ADR-0074](0074-feature-verification.md)が求める「出典のスケール前提が
本エンジンで成り立つか」を数値で確かめた。

| | 係数×歩の価値 | 履歴の上限 | 比 |
|---|---|---|---|
| Stockfish | `7 × 208 = 1456` | 10692 | 7.34 |
| 本エンジン（現状の`capture_score`） | `16 × 90 = 1440` | — | — |
| 本エンジンに同じ比を当てると | 1440 | **10575** | 7.34 |
| [ADR-0048](0048-capture-history.md)が使った値 | 1440 | 16384 | **11.38** |

本エンジンの `victim * 16`（歩で1440）は、Stockfishの `7 * PieceValue`
（歩で1456）とほぼ同じスケールである。偶然だが、係数と駒価値の組が
一致している。

**ADR-0048は履歴を1.55倍効かせすぎていた。** 駒得の序列を跨ぐという
指摘は正しく、原因は値域の取り違えだった。

## Decision

`CaptureHistory` を `[動かす駒 32][移動先 81][取る駒種 16]` の表として
持つ。値域は **10692**（やねうら王の値。上の検算で得た10575とほぼ一致）、
初期値は **-678**（Stockfishの値）。

```
capture_score = 駒価値*16 + 成り差*16 - 動かす駒の価値 + captHist
```

更新はβカット時に行う。カットした取る手へ `history_bonus(depth)`、
外れた取る手へ `history_malus(depth)` を与える。式は静かな手と共有する
（[ADR-0073](0073-history-bonus-scale.md)）。

初期値を負にするのは、未探索の取る手をわずかに後ろへ置くためである。
駒得の序列（`victim * 16`）に対して -678 は歩1枚（1440）の半分弱で、
序列は保たれる。

4局面すべてで減った。取る手の順序が良くなり、βカットが早く起きている。

局面1で最善手が変わった。[ADR-0096](0096-rfp-margin.md)の教訓に照らすと
読み抜けを疑うべき場面である。ただし本ADRは枝刈りを緩めておらず、
順序だけを変えている。読む手の集合は同じで、順序が変われば
fail-softの値も変わる。評価値の差（65→33）も小さい。SPRTで確かめる。

## Decision（改訂）

**案を棄却する。** 実装はmainへ入れない。

### スケールの検算は正しかった

[ADR-0048](0048-capture-history.md)の -2.4 から +4.0 へ動いた。値域を
16384から10692へ直したことに効果はあった。反証レビューが指摘した
「駒得序列を跨ぐ」という診断は正しく、原因は値域の取り違えだった。

**それでも閾値に届かない。** 直した先にあったのは中立だった。

### なぜ効かないのか

本エンジンの `capture_score` は成りボーナス込みのMVV-LVAである。

```
victim * 16 + promo * 16 - attacker
```

将棋は成りの価値が大きい（歩90→と金540で+450）。この項があるぶん、
静的スコアだけで取る手が十分よく並んでいる可能性が高い。チェスには
成りがほぼないため、Stockfishでは履歴が並べ替える余地が大きい。

加えて[ADR-0090](0090-see-pruning.md)のSEE枝刈りが、大きく駒損する取る手を
ムーブループの手前で捨てている。履歴が学習する前に候補から消えており、
更新の機会そのものが減っている。

機能検証では固定深さ13の4局面すべてで22〜50%ノードが減った。**順序は
確かに良くなっている。** それでも勝率が動かないのは、削れた分が
既にSEE枝刈りとMVV-LVAで拾えていた範囲と重なるためと考える。

## Consequences

capture historyは持たない。[ROADMAPの候補](../ROADMAP.md#候補)の
「capture SEE pruningへcaptHist項を足す」も前提が消えるため取り下げる。

得られた知見は2つある。

1. **移植元の機構が本エンジンで同じ価値を持つとは限らない。** 将棋の
   成りは、チェスにない大きな静的シグナルである。オーダリングの余地が
   その分だけ小さい
2. **先行する枝刈りが強いほど、後段の履歴は学ぶ機会を失う。**
   [ADR-0090](0090-see-pruning.md)のSEE枝刈りを入れた後に本ADRを測った
   順序が結果に影響している。順序が逆なら違う結果になった可能性はあるが、
   今の構成ではこれが答えである

[ADR-0048](0048-capture-history.md)の疑い（スケール不均衡）は解消できた。
同じ機構をこれ以上追わない。

## Consequences

テーブルは 32×81×16 の i16 で約83KBである。スレッドローカルに持つ。

capture系の枝刈り（[ADR-0090](0090-see-pruning.md)のcapture SEE pruning）は
`captHist` の項を落とした形で入っている。本ADRが採択されれば、その項を
足す余地ができる。1機能=1SPRTなので別ADRとする。

H0だった場合は値域を疑う。10692はStockfishとやねうら王の値で、上の検算とも
合うが、本エンジンのhistory bonus/malus（[ADR-0073](0073-history-bonus-scale.md)）
とのバランスは別問題である。bonusの上限1529に対し値域10692は7倍で、
飽和までに多くの更新を要する。
