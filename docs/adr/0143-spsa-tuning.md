# 0143: 探索定数をSPSAで一括チューニングする

- Status: accepted（第1群を+32.0 Eloで採択。下の「測定」）
- Date: 2026-08-04
- 関連ADR: [0027](0027-sprt-framework.md), [0073](0073-history-bonus-scale.md), [0089](0089-improvement-criteria.md), [0109](0109-reference-parity.md), [0114](0114-g5-singular.md), [0123](0123-stop-and-resume.md), [0141](0141-singular-rate-calibration.md), [0180](0180-hmwr-cli-in-python.md)

## Context

追従（G1〜G10）で入れた探索定数は、参照実装の値をそのまま使っている。
参照実装の定数は参照実装の評価関数に対してチューニングされた値で、
本エンジンの評価関数は自前学習の別物である。ずれの実例は既にある。
singular率は設計点の4.4倍で（[ADR-0114](0114-g5-singular.md)）、原因は
評価値分布の違いと結論された。**singularで起きていることが、margin・
係数を持つ他の箇所で起きていないと考える理由はない**。

SF系はこの問題をSPSA（同時摂動による確率近似）で解いている。全定数を同時に
摂動させて対局し、勝敗の勾配で定数を動かす。評価関数や探索構造が変わった
あとに定数群を回し直すのが標準の運用になっている（fishtestのSPSA基盤）。

本エンジンには対局基盤（[ADR-0027](0027-sprt-framework.md)）があり、
足りないのはSPSAのループだけである。1定数ずつSPRTで動かす現行のやり方は
（[ADR-0073](0073-history-bonus-scale.md)等）、定数間の相互作用を拾えず、
定数の数に対して対局数が線形に増える。

## 選択肢と比較

### 案A: SPSAランナーを作り、定数を群でチューニングする

1回の対局で全対象定数の勾配情報が得られる。相互作用込みで動く。
チューニング結果はハイパーパラメータの塊なので、最後に1群1SPRTで検収する。

### 案B: 1定数ずつSPRTで振る

既存のやり方。20定数×数千局では現実的でない。

### 案C: 定数を触らず構造の変更だけ続ける

構造は参照実装と同等になった（ROADMAP）。定数の適合が未着手のまま残る。

## Decision

案Aを採る。実装と運用は次のとおり。

1. **定数のUSIオプション化**。チューニング対象の定数をビルドなしで
   振れるよう、隠しオプションとして外へ出す（リリースビルドでは固定値へ
   畳む。NPSへの影響がないことをベンチで確認する）
2. **SPSAランナー**。`hmwr spsa` として実装し（[ADR-0180](0180-hmwr-cli-in-python.md)）、
   対局実行は `selfplay` を流用する。中断と再開ができること
   （[ADR-0123](0123-stop-and-resume.md)）
3. **対象の第1群**。LMR係数・futility/razoringマージン・NMPの
   リダクション・SEE枝刈り閾値と駒価値・aspirationのdelta、計20個程度。
   SEE駒価値はROADMAP候補にあった「NNUE時代適合」をここへ吸収する。
   singularのマージンは[ADR-0141](0141-singular-rate-calibration.md)が
   率で較正するので除く
4. **検収**。チューニング後の定数一式を1群として、チューニングに
   使っていない条件のSPRT既定条件で測る。チューニング対局への過適合を
   held-outで検出するためである

### 実装の設計（2026-08-20着手）

エンジン側は `tune` featureで分岐する。featureなしでは各定数が `const` の
ままで、生成されるバイナリは現状と同一になる。featureありでは同名の値を
atomicで持ち、`setoption` で書き換える。LMRのリダクション表のような
導出テーブルは、探索ワーカーの生成時に係数の変化を見て作り直す。SPRTの
検収はfeatureなしのビルドへ定数を焼き込んで行うので、atomic読みのコストは
検収結果に入らない。

実装は `crates/engine/src/tunables.rs` に入り、26項目を配線した
（2026-08-20）。**第1群のうちSEEの駒価値だけは未配線である**。駒価値は
coreクレートのconst表にあり、SEEの駒種順序の表を初期化する定数式にも
使われている。atomic化はcore側の書き換えを伴うので、第1群を走らせる
前に、配線するか第1群から外すかを決めてここへ追記する。

ランナーは `hmwr spsa run <名前>` とする。1反復で複数の摂動を作り、
摂動ごとに `selfplay --max-pairs 1` をθ+側 `--copt`・θ−側 `--bopt` で
並列に走らせる。ペア結果の符号で勾配を推定し、θを更新する。θと反復数は
`data/spsa/<名前>.state.json` へ毎反復書き、再開はそこから読む
（[ADR-0123](0123-stop-and-resume.md)）。対象定数と範囲・c・aは
起動時にファイルで渡し、走行中は変えない。

**Elo見込みの根拠は、評価関数が別物なのに定数が借り物という構造的な
ずれである**。ずれの実測はsingularの4.4倍しかなく、他の定数でどれだけ
回収できるかは事前に見積もれない。だからこそ回収量の測定を最終段の
held-out SPRTに置く。本ADRは単発の探索改善ではなく基盤と定数群の
一括変更なので、[ADR-0089](0089-improvement-criteria.md)の3軸選定は
適用しない。

**注意点は時間条件への過適合である**。10+0.1でチューニングした定数が
floodgateの300+10で最適とは限らない。深さ依存の係数はとくに危うい。
第1群の採択後、300+10側の抜き取り測定を1回入れて乖離の有無を記録する。

**撤退ライン**。第1群のheld-out SPRTがH0なら、SPSAのハイパーパラメータ
（摂動幅・学習率・対局数）を1回だけ調整して再走する。それでもH0なら
「本エンジンの規模ではSPSAの解像度が足りない」と記録して閉じる。

## 測定（2026-08-22、第1群）

### 走行条件

| 項目 | 値 |
|---|---|
| 対象 | 26項目（SEE駒価値を除く第1群。`tunables.rs`） |
| 対局 | 15,000ペア＝30,000局、10+0.1、並列8、adjudicate 2000,8 |
| 摂動と歩幅 | c_endは可動域の1/20、r_end=0.002、fishtest式の減衰 |
| 所要 | 約39時間（407〜489ペア/時） |

26項目中24項目が動いた。動きの大きい順の主要項目は次のとおり
（全体は `crates/engine/src/tunables.rs` の既定値の差分が持つ）。

| 項目 | 既定 | 採択値 | 読み |
|---|---|---|---|
| RFP_IMPROVING | 2686 | 1309 | improving時の緩和を半減。RFPを効かせる |
| RFP_MULT | 76 | 104 | RFPの基本係数+37% |
| RFP_NO_TT_HIT | 21 | 14 | TT不ヒット時の割引を縮小 |
| NMP_DEPTH_DIVISOR | 3 | 4 | NMPのリダクションを浅く |
| ASPIRATION_GROWTH_DIV | 3 | 2 | 窓の拡大を速く |
| LMR_COEF | 2763 | 3182 | LMRを15%深く削る |
| LMR_DEPTH_HIST_DIVISOR | 3220 | 3595 | history補正を弱く |
| QS_SEE_MARGIN | −73 | −60 | qsearchのSEE下限を厳しく |

RFP系3項目がそろって「もっと刈る」方向へ動いた。参照実装のマージンが
本エンジンの評価値分布に対して保守的すぎたという読みで、singular率4.4倍
（[ADR-0114](0114-g5-singular.md)）と同根である。SPSAの健全性は
θ+側の勝率で見た。対称摂動なのでほぼ5割になるのが正常で、実測51.4%だった。

### held-out SPRT（検収）

焼き込んだ定数一式を、featureなしのビルドで既定条件にかけた。

| 項目 | 値 |
|---|---|
| 条件 | `--tc 10+0.1 --concurrency 8 --adjudicate 2000,8`、elo0=0、elo1=5 |
| 対局数 | 2,330（1,165ペア） |
| W-D-L | +1226 =92 -1012 |
| Elo [95%CI] | **+32.0 [+17.9, +46.2]** |
| LLR | +2.89（H1採択） |

**評価関数が別物なのに定数が借り物、という構造のずれは実在した**。
回収量は+32.0で、追従（G1〜G10）以来の大きな単発利得になる。

### 残る宿題

- **300+10側の抜き取り測定**。10+0.1でチューニングした定数の時間条件への
  過適合を1回測って記録する（本ADRのDecisionどおり）
- SEE駒価値の配線判断（「実装の設計」の節）
- 評価関数の世代更新後の再走。以後の運用に組み込む

## Consequences

- 対局リソースの使い方が変わる。SPSAは1サイクル数万局を消費するので、
  SPRTと並走はできない。回す時期を区切る
- 定数がUSIオプションへ出ることで、探索コードの定数参照が一段
  間接になる。リリースビルドで畳み込む設計を守らないとNPSが落ちる
- 採択後は「評価関数の世代更新 → SPSA再走」が運用に加わる。
  [ADR-0135](0135-teacher-data-3b.md)等でネットが更新されるたびに
  回し直す価値が生じる
- チューニング履歴（どの定数がどれだけ動いたか）が、参照実装との
  評価値分布の違いを示す測定データとして残る
