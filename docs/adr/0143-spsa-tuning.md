# 0143: 探索定数をSPSAで一括チューニングする

- Status: accepted（第1群を+32.0 Eloで採択。下の「測定」）
- Date: 2026-08-04
- 関連ADR: [0027](0027-sprt-framework.md), [0073](0073-history-bonus-scale.md), [0089](0089-improvement-criteria.md), [0109](0109-reference-parity.md), [0114](0114-g5-singular.md), [0123](0123-stop-and-resume.md), [0141](0141-singular-rate-calibration.md), [0180](0180-hmwr-cli-in-python.md)

## Context

追従（G1〜G10）で入れた探索定数は、参照実装の値をそのまま使っている。
参照実装の定数は参照実装の評価関数に対してチューニングされた値で、
本エンジンの評価関数は自前学習の別物である。ずれの実例は既にある。
singular率は想定値の4.4倍で（[ADR-0114](0114-g5-singular.md)）、原因は
評価値分布の違いと結論された。**singularで起きていることが、margin・
係数を持つ他の箇所で起きていないと考える理由はない**。

Stockfish系はこの問題をSPSA（同時摂動による確率近似）で解いている。全定数を同時に
摂動させて対局し、勝敗の勾配で定数を動かす。評価関数や探索構造が変わった
あとに定数群を回し直すのが標準の運用になっている（fishtestのSPSA基盤）。

本エンジンには対局基盤（[ADR-0027](0027-sprt-framework.md)）があり、
足りないのはSPSAのループだけである。1定数ずつSPRTで動かす現行のやり方は
（[ADR-0073](0073-history-bonus-scale.md)等）、定数間の相互作用を拾えず、
定数の数に対して対局数が線形に増える。

## 選択肢と比較

### 案A: SPSAランナーを作り、定数を群でチューニングする

1回の対局で全対象定数の勾配情報が得られる。相互作用込みで動く。
チューニング結果はハイパーパラメータの塊なので、最後に1群1SPRTで検収する。

### 案B: 1定数ずつSPRTで振る

既存のやり方。20定数×数千局では現実的でない。

### 案C: 定数を触らず構造の変更だけ続ける

構造は参照実装と同等になった（ROADMAP）。定数の適合が未着手のまま残る。

## Decision

案Aを採る。実装と運用は次のとおり。

1. **定数のUSIオプション化**。チューニング対象の定数をビルドなしで
   振れるよう、隠しオプションとして外へ出す（リリースビルドでは固定値へ
   畳む。NPSへの影響がないことをベンチで確認する）
2. **SPSAランナー**。`hmwr spsa` として実装し（[ADR-0180](0180-hmwr-cli-in-python.md)）、
   対局実行は `selfplay` を流用する。中断と再開ができること
   （[ADR-0123](0123-stop-and-resume.md)）
3. **対象の第1群**。LMR係数・futility/razoringマージン・NMPの
   リダクション・SEE枝刈り閾値と駒価値・aspirationのdelta、計20個程度。
   SEE駒価値はROADMAP候補にあった「NNUE時代適合」をここへ吸収する。
   singularのマージンは[ADR-0141](0141-singular-rate-calibration.md)が
   率で較正するので除く
4. **検収**。チューニング後の定数一式を1群として、チューニングに
   使っていない条件のSPRT既定条件で測る。チューニング対局への過適合を
   held-outで検出するためである

### 実装の設計（2026-08-20着手）

エンジン側は `tune` featureで分岐する。featureなしでは各定数が `const` の
ままで、生成されるバイナリは現状と同一になる。featureありでは同名の値を
atomicで持ち、`setoption` で書き換える。LMRのリダクション表のような
導出テーブルは、探索ワーカーの生成時に係数の変化を見て作り直す。SPRTの
検収はfeatureなしのビルドへ定数を組み込んで行うので、atomic読みのコストは
検収結果に入らない。

実装は `crates/engine/src/tunables.rs` に入り、26項目を組み込んだ
（2026-08-20）。**第1群のうちSEEの駒価値だけはまだ組み込んでいない**。駒価値は
coreクレートのconst表にあり、SEEの駒種順序の表を初期化する定数式にも
使われている。atomic化はcore側の書き換えを伴うので、第1群を走らせる
前に、組み込むか第1群から外すかを決めてここへ追記する。

ランナーは `hmwr spsa run <名前>` とする。1反復で複数の摂動を作り、
摂動ごとに `selfplay --max-pairs 1` をθ+側 `--copt`・θ−側 `--bopt` で
並列に走らせる。ペア結果の符号で勾配を推定し、θを更新する。θと反復数は
`data/spsa/<名前>.state.json` へ毎反復書き、再開はそこから読む
（[ADR-0123](0123-stop-and-resume.md)）。対象定数と範囲・c・aは
起動時にファイルで渡し、実行中は変えない。

**Elo見込みの根拠は、評価関数が別物なのに定数が借り物という構造的な
ずれである**。ずれの実測はsingularの4.4倍しかなく、他の定数でどれだけ
回収できるかは事前に見積もれない。だからこそ回収量の測定を最終段の
held-out SPRTに置く。本ADRは単発の探索改善ではなく基盤と定数群の
一括変更なので、[ADR-0089](0089-improvement-criteria.md)の3軸選定は
適用しない。

**注意点は時間条件への過適合である**。10+0.1でチューニングした定数が
floodgateの300+10で最適とは限らない。深さ依存の係数はとくに危うい。
第1群の採択後、300+10側の抜き取り測定を1回入れて乖離の有無を記録する。

**撤退ライン**。第1群のheld-out SPRTがH0なら、SPSAのハイパーパラメータ
（摂動幅・学習率・対局数）を1回だけ調整して再走する。それでもH0なら
「本エンジンの規模ではSPSAの解像度が足りない」と記録して打ち切る。

## 測定（2026-08-22、第1群）

### 実行条件

| 項目 | 値 |
|---|---|
| 対象 | 26項目（SEE駒価値を除く第1群。`tunables.rs`） |
| 対局 | 15,000ペア＝30,000局、10+0.1、並列8、adjudicate 2000,8 |
| 摂動とステップ幅 | c_endは可動域の1/20、r_end=0.002、fishtest式の減衰 |
| 所要 | 約39時間（407〜489ペア/時） |

26項目中24項目が動いた。動きの大きい順の主要項目は次のとおり
（全体は `crates/engine/src/tunables.rs` の既定値の差分が持つ）。

| 項目 | 既定 | 採択値 | 読み |
|---|---|---|---|
| RFP_IMPROVING | 2686 | 1309 | improving時の緩和を半減。RFPを効かせる |
| RFP_MULT | 76 | 104 | RFPの基本係数+37% |
| RFP_NO_TT_HIT | 21 | 14 | TT不ヒット時の割引を縮小 |
| NMP_DEPTH_DIVISOR | 3 | 4 | NMPのリダクションを浅く |
| ASPIRATION_GROWTH_DIV | 3 | 2 | 窓の拡大を速く |
| LMR_COEF | 2763 | 3182 | LMRを15%深く削る |
| LMR_DEPTH_HIST_DIVISOR | 3220 | 3595 | history補正を弱く |
| QS_SEE_MARGIN | −73 | −60 | qsearchのSEE下限を厳しく |

RFP系3項目がそろって「もっと刈る」方向へ動いた。参照実装のマージンが
本エンジンの評価値分布に対して保守的すぎたという読みで、singular率4.4倍
（[ADR-0114](0114-g5-singular.md)）と同根である。SPSAの健全性は
θ+側の勝率で見た。対称摂動なのでほぼ5割になるのが正常で、実測51.4%だった。

### held-out SPRT（検収）

組み込んだ定数一式を、featureなしのビルドで既定条件にかけた。

| 項目 | 値 |
|---|---|
| 条件 | `--tc 10+0.1 --concurrency 8 --adjudicate 2000,8`、elo0=0、elo1=5 |
| 対局数 | 2,330（1,165ペア） |
| W-D-L | +1226 =92 -1012 |
| Elo [95%CI] | **+32.0 [+17.9, +46.2]** |
| LLR | +2.89（H1採択） |

**評価関数が別物なのに定数が借り物、という構造のずれは実在した**。
回収量は+32.0で、追従（G1〜G10）以来の大きな単発利得になる。

### 300+10の抜き取り（2026-08-22）

10+0.1でチューニングした定数の、長い持ち時間への過適合を確かめた。
採択値と旧定数を300+10で対局させ、150局（オーナー判断で打ち切り）の
固定サンプルを取った。

| 項目 | 値 |
|---|---|
| 条件 | `--tc 300+10 --concurrency 8 --adjudicate 2000,8`、固定局数 |
| 対局数 | 150（75ペアで打ち切り） |
| W-D-L | +79 =19 -52 |
| Elo [95%CI] | **+63.2 [+7.8, +122.0]**（勝率ベースの正規近似） |

CIの下限が正で、**時間条件への過適合はない**。点推定は10+0.1の+32.0より
高めだが、この局数では区別できない。少なくとも「短い持ち時間だけで
効く定数だった」という筋は消えた。

## 測定（2026-09-11〜15、第1群の再走）

評価関数がtanuki系列とrl_e1d8（[ADR-0201](0201-loop-recipe.md)）へ、SMPが
深さのずらし（[ADR-0202](0202-smp-loss-diagnosis.md)）へ変わったので、
「大きな構造変更の後に再走」の条件に当たる。第1群と同じ26項目、同じ
可動域と摂動幅で、第1群の採択値を初期値に15,000ペアを回した（39時間）。

24項目が動いた。大きく動いたのは4つある。RFP_IMPROVING 1309→1093。
QS_FUTILITY_MARGIN 302→249。SEE_CAPTURE_COEF 166→140。NMP_EVAL_BASE
373→406。第1群の大移動（RFP_IMPROVING 2686→1309）に比べれば微調整で
ある。全体は `tunables.rs` の差分が持つ。

### held-out SPRT（検収）

| 項目 | 値 |
|---|---|
| 条件 | 既定（10+0.1、同時8、elo0=0、elo1=5） |
| 対局数 | 3,588（1,794ペア） |
| W-D-L | +1812 =183 -1593 |
| Elo [95%CI] | **+21.2 [+10.4, +32.1]** |
| LLR | +3.06（H1採択） |

**評価関数を変えると定数は動き、再走で回収できる**。第1群の+32.0に
対して+21.2で、世代更新のたびに再走する価値は続いている。SPSAの再走は
無人で回せるので、開発機が空く期間（オーナー不在など）に置くと収まりが
よい。

### 残る宿題

- SEE駒価値の組み込みの判断（「実装の設計」の節）。第2群の対象選定と合わせて決める
- 第2群の起草。singular・ProbCut・correction historyの重み・history
  スケールなど、まだ組み込んでいない定数群が対象になる。singularは率への較正
  （[ADR-0141](0141-singular-rate-calibration.md)）と違い、勝敗で直接
  最適化するので安全に触れる
- 評価関数の世代更新後の再走。以後の運用に組み込む

## 再走の事前登録（2026-10-13、dlshogiのラベルの系列）

前回の再走（2026-09-11〜15）の後、評価関数の教師が替わった。点数はdlshogiの推論で
付け直したもの（S=430）になり、評価値の分布が変わっている
（[ADR-0219](0219-relabel-2b-in-place.md)）。「評価関数の世代更新後の再走」に当たる。
オーナーの指示で走らせる（2026-10-13）。

### 仮説

**第1群の26定数は、dlshogiのラベルの系列の評価関数では最適からずれており、
SPSAの再走で回収できる**。

### 設計

- 動かす変数は、26定数の値だけである
- 固定するものは、前回の再走と同じである。同じ26項目、同じ可動域と摂動幅、
  15,000ペア、10+0.1、並列8、裁定2000,8。初期値は現行の値にする
- 評価関数は、開始時点の `EVAL_FILE` を使い、走行中は切り替えない。
  [ADR-0228](0228-grow-labeled-pool.md)の1回目の判定が出て、切り替えを済ませてから
  キューへ積む
- 検収は、チューニングに使っていない既定のSPRTで行う（elo0=0、elo1=5、上限10,000ペア）。
  baseはmain、candは定数だけを差し替えたもので、どちらも `tune` featureなしで作る
- SPSAの健全性は、θ+側の勝率で見る。対称な摂動なので、5割の近くが正常である

specは `experiments/adr0143-spsa-g3.toml` で、キューが走らせる。検収は定数をコードへ
書き写す作業を伴うので、対話セッションが行う。

裁定の閾値（2000）は評価値の単位に依存する。教師のスケールが替わったので、同じ閾値でも
裁定の掛かる局面は前回と違う。SPSAの両側と検収の両側には同じ条件が掛かるので、
比較は崩れない。

### 解釈の事前登録

| 検収の判定 | 読み | 次の一手 |
|---|---|---|
| H1 | 教師を替えても、定数は動いて回収できる。世代更新のたびの再走を続ける | 定数を取り込む。大きく動いた項目を記録する |
| H0 | 再走で定数が悪くなった。SPSAの対局への過適合か、勾配が雑音に埋もれている | 取り込まない。θ+側の勝率と動いた項目を記録し、撤退ラインに従う |
| 見送り | 現行の定数は、新しい評価関数でもほぼ最適である | 取り込まない。次の再走は、探索か評価関数の構造を変えた後まで待つ |

過去の2回は+32.0と+21.2だった。利得は回を追って小さくなると見込む。

### held-out SPRT（検収、2026-10-15）

22項目を `crates/engine/src/tunables.rs` の既定値へ書き写し、`tune` featureなしのビルドで
既定のSPRTにかけた。機能検証では、固定深さ13で4局面ともノード数が変わった
（−30%〜+49%）。

| 項目 | 値 |
|---|---|
| 条件 | 既定（10+0.1、同時8、elo0=0、elo1=5、上限10,000ペア） |
| 対局数 | 20,000（10,000ペア） |
| W-D-L | +9508 =1275 -9217 |

上限の10,000ペアで判定に至らなかった。[ADR-0217](0217-sprt-pass-cap.md)の既定では見送りに当たる。

**オーナーの判断で、上限を20,000ペアへ延ばして続ける**（2026-10-15）。上限で結果を
見た後の延長である。LLRは境界（+2.94）の手前で、点推定の+5.1は中点（+2.5）より上に
あった。オーナーの言葉は「判断する場所は10,000ごとで良い。見込みがありそうなのに
棄却は辛い」である。

延ばしても、誤ってH1を採択する率は増えない。SPRTの保証は、境界まで走る前提の
ものだからである（ADR-0217）。対立仮説と対局の条件は変えない。同じ棋譜の続きから
走らせ、上限時の結果ファイルは `adr0143-spsa-g3.result.capped-10000` として残した。

判定は事前登録の表に従う。20,000ペアでも判定に至らなければ、そこで延ばすかを
もう一度決める。

## Consequences

- 対局リソースの使い方が変わる。SPSAは1サイクル数万局を消費するので、
  SPRTと並走はできない。回す時期を区切る
- 定数がUSIオプションへ出ることで、探索コードの定数参照が一段
  間接になる。リリースビルドで畳み込む設計を守らないとNPSが落ちる
- 採択後は「評価関数の世代更新 → SPSA再走」が運用に加わる。
  [ADR-0135](0135-teacher-data-3b.md)等でネットが更新されるたびに
  回し直す価値が生じる
- チューニング履歴（どの定数がどれだけ動いたか）が、参照実装との
  評価値分布の違いを示す測定データとして残る
