# 0091: SEEを駒打ちに対応させる

- Status: accepted
- Date: 2026-07-29
- 関連ADR: [0090](0090-see-pruning.md), [0025](0025-move-ordering.md), [0089](0089-improvement-criteria.md)

## Context

`Position::see_ge` は駒打ちに対して常に0を返す。

```rust
if m.is_drop() {
    return 0 >= threshold;
}
```

打った駒がその場で取られる筋を見ていない。「打つ手は損をしない」と
みなす近似である。[ADR-0025](0025-move-ordering.md)でSEEを入れたとき、
移動する手だけを対象にしたまま残っていた。

将棋は打つ手の比率が高い。`GenType::Quiets` は駒打ちを含むため、
この近似は次の2か所へ効く。

- [ADR-0090](0090-see-pruning.md)のSEE枝刈り（静かな手）。タダで取られる
  打ちがすり抜ける
- `MovePicker` のQChecksInit。静止探索で読む「駒損しない静かな王手」の
  選別。取られる王手打ちが常に通る

[ADR-0089](0089-improvement-criteria.md)の軸2（ノード効率）に乗る。
読まなくてよい手を減らす。単独で効く経路は上の2か所で、どちらも
「これまで通っていた損な手を刈る」方向に働く。

## 選択肢と比較

### 案A: 既存のswap構造をそのまま使う

`see_ge` はStockfishのswapアルゴリズムで、「移動先での取り合いを安い駒から
順に解く」形になっている。駒打ちは初期条件が違うだけで、ループは同じで
よい。

| | 取る駒 | 盤に出る駒 | 交換前の駒配置 |
|---|---|---|---|
| 移動 | `piece_on(to)` | `piece_on(from)` | `occupied ^ from` |
| 打ち | なし（0） | 打った駒種 | `occupied \| to` |

打ちでは移動元が盤上にないので `occupied` から抜くものがない。代わりに
打った駒が盤上へ現れるため、飛び駒の利きがそこで止まる。`occupied | to`
とする。

### 案B: 打ちだけ専用の判定を書く

「打った駒に相手の利きがあるか」だけを見る簡易版。

交換の続きを解かない。「歩を打ち、金で取られ、その金を飛車で取り返す」
という筋で、実際には得なのに損と判定する。案Aは同じループを通るので
この筋も解ける。実装量も案Aのほうが少ない。

### 案C: 直さない

現状維持。近似のままでも「刈らない」方向の誤りなので読み抜けは起こさない。

[ADR-0090](0090-see-pruning.md)のSEE枝刈りが効くほど、この取り逃しの
損も大きくなる。

## Decision

案Aを採る。

`see_ge` の入口で、取る駒の価値・盤に出る駒の価値・交換前の駒配置の3つを
手の種類で決め、以降のswapループは共通にする。成りを考慮しない簡略版で
ある点は変えない（駒打ちに成りはない）。

## 検証

`crates/core/tests/integration.rs` に単体テストを足した。5四の後手金が
利く5五へ先手が歩を打つ局面で、`see_ge(m, 0)` が偽、`see_ge(m, -90)` が
真になることを確かめる。誰も利いていないマスへの打ちは `see_ge(m, 0)` が
真である。

## 機能検証（2026-07-29）

[ADR-0090](0090-see-pruning.md)採択後のmainを基準に、固定深さ13で比べた。

| 局面 | 変更前 | 変更後 | 変化 | 評価値 | 最善手 |
|---|---|---|---|---|---|
| 1 | 217,866 | 251,563 | +15% | 16 → 65 | 2g2f → 7g7f |
| 2 | 233,546 | 189,125 | -19% | -50 → -92 | 同じ |
| 3 | 1,533,617 | 1,059,556 | -31% | 754 → 726 | 同じ |
| 4 | 196,122 | 211,527 | +8% | -174 → -95 | 同じ |

2局面で減り、局面3は31%減った。損な打ちを刈れている。局面1と4で
増えたのは、刈った結果として読み筋が変わり別の分岐を深く読んだためと
見ている。

## SPRT結果（2026-07-29）

**H1採択**。525ペア（1050局）で **+67.0 Elo [+46.4, +88.0]**、LLR +3.05。
W-D-L は +602 =46 -402。

判定に1050局しか要していない。本セッションで測った4件のうち最短で、
効果も最大である。

[ADR-0090](0090-see-pruning.md)のSEE枝刈りが+45.6だったことと合わせると、
SEEを使う枝刈りは本エンジンで効きが大きい。近似のまま残っていた駒打ちを
解いただけで、枝刈り本体の導入を上回る効果が出た。将棋は打つ手の比率が
高く、そこを素通ししていた損が大きかったということである。

[ADR-0025](0025-move-ordering.md)でSEEを入れてから5か月、この近似は
誰も測っていなかった。既存実装の近似には、測れば大きい差が残っている
ことがある。

## Consequences

探索の結論が変わる。[ADR-0090](0090-see-pruning.md)のSEE枝刈りと
QChecksInitの両方で、これまで通っていた手が刈られる。

`see_ge` の呼び出しコストは変わらない。分岐が1つ増えるだけで、
ループは同じである。

[ADR-0090](0090-see-pruning.md)がH1採択されるかで、この変更の価値が
変わる。採択されなければ効く経路はQChecksInitだけになる。
