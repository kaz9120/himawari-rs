# 0077: 静止探索にfutility枝刈りとmovecount制限を入れる

- Status: accepted
- Date: 2026-07-28
- 関連ADR: [0024](0024-search-v1.md), [0028](0028-pruning-extensions.md), [0054](0054-qsearch-tt.md), [0074](0074-feature-verification.md)

## Context

本エンジンの静止探索が持つ枝刈りは、stand patによるβカットと、
MovePicker側の `see_ge(m, 0)` だけである（`search.rs` のqsearch、
`movepick.rs` のQCapturesステージ）。

やねうら王は同じ位置に3つの枝刈りを持つ。

```
futilityBase = staticEval + 328
王手をかけず、取り返しでもない手について:
  moveCount > 2 なら捨てる
  futilityBase + 取る駒の価値 <= alpha なら捨てる
  see_ge(move, alpha - futilityBase) が偽なら捨てる
```

静止探索は探索ノードの大半を占める。[ADR-0054](0054-qsearch-tt.md)で
置換表を導入したときは+113.6 Eloを得ており、この領域の改善は効きやすい。

[ADR-0074](0074-feature-verification.md)で評価値スケールが歩=90で一致する
ことを確認済みなので、マージン328と駒価値はそのまま使える。

## 選択肢と比較

### 案A: 3つをまとめて入れる

やねうら王の構成をそのまま移す。静止探索の枝刈りは相互に補完しており、
1つだけ入れても他が受け持つ手を刈れない。たとえばmovecount制限は
「3手目以降は駒価値による判定すら省く」もので、futility判定と組で働く。

[ADR-0028](0028-pruning-extensions.md)の1機能=1SPRTに反するように見えるが、
これらは「静止探索のfutility」という単一の機構の構成要素である。
分割するとどれも単体では効果が出ず、判定に時間だけがかかる。

### 案B: futility判定だけを入れる

最も素直な1機能。movecount制限とSEE閾値は後続の別ADRにする。

ただしmovecount制限（`moveCount > 2`）を欠くと、駒価値の大きい手が
延々と読まれる。やねうら王がこの3つを同じブロックに置いているのは、
判定の順序に意味があるためである。

### 案C: movecount制限だけを入れる

最小の変更。ただし「3手目以降を無条件に捨てる」だけになり、
評価値を見ないため乱暴である。単体では棋力を落とす公算が高い。

## Decision

案Aを採る。3つは「静止探索のfutility」という1つの機構として扱う。

```
futility_base = stand + QS_FUTILITY_MARGIN      (QS_FUTILITY_MARGIN = 328)

ムーブループ内、王手でない手かつ取り返しでない手について:
  count > QS_MOVECOUNT_LIMIT (=2) なら捨てる
  futility_value = futility_base + 取る駒の価値
  futility_value <= alpha なら捨てる
  see_ge(m, alpha - futility_base) が偽なら捨てる
```

やねうら王はここで `bestValue` をfutility値まで引き上げてfail-softの
下限を報告するが、本ADRでは入れない。本エンジンのMultiPVはライン確定ごとに
出力する設計で、窓に依存する値を返り値へ混ぜるとライン間の整合が崩れる。
下限を報告しないだけで、alpha-betaの正しさは保たれる。

「取り返しでない手」の判定には、1手前の移動先マスを使う。やねうら王の
`move.to_sq() != prevSq` に対応する。取り返しは静止探索の主目的であり、
ここを刈ると評価が歪む。

本エンジンのqsearchは1手前の情報を持たないため、`move_stack` を
qsearch内でも更新する配管を足す。[ADR-0047](0047-continuation-history.md)で
導入したスタックをそのまま使う。

王手中（`in_check`）は適用しない。stand patが無く `futility_base` を
定義できないためである。やねうら王も `is_loss(futilityBase)` で
同じ場合を除く。

定数はやねうら王の値をそのまま使う。評価値スケールが歩=90で一致する
ことは[ADR-0074](0074-feature-verification.md)で確認済みである。

検証は同ADRの規約に従い、SPRTの前に固定深さでのノード数変化を測る。
静止探索の枝刈りなのでノード数は減る方向に動くはずで、増えたら
向きを取り違えている（[ADR-0075](0075-razoring-margin.md)の教訓）。

## 機能検証（2026-07-28）

固定深さ13で3局面のノード数を比較した。局面1で36%減り、枝刈りが
効いている。局面2と3は増えた。静止探索の返り値が変わると上位ノードの
枝刈り判断も変わるため、総ノード数は減る方向だけには動かない。

| 局面 | 変更前 | 変更後 | 変化 | 最善手 |
|---|---|---|---|---|
| 1 | 616,335 | 396,638 | -36% | 同じ |
| 2 | 4,839,402 | 5,288,599 | +9% | 同じ |
| 3 | 335,817 | 450,089 | +34% | B*7c → 8c8d |

[ADR-0075](0075-razoring-margin.md)では全局面で大幅に増え、向きを
取り違えたと判明した。今回は減る局面があるため、枝刈りとして機能している。

### やねうら王から外した点

`bestValue` をfutility値まで引き上げる処理を入れていない。本エンジンの
MultiPVはライン確定ごとに出力する設計で、窓に依存する値を返り値へ
混ぜるとライン間の整合が崩れる。fail-softの下限を報告しないだけで、
alpha-betaの正しさは保たれる。

この検証中に、MultiPVの出力が降順を保証していないことが判明した。
枝刈りとは独立した既存の不備であり、別PRで先に直した
（出力スコアを前のラインで頭打ちにする）。

## SPRT結果（2026-07-28）

**H1採択**。621ペア（1242局）で +57.3 Elo [+38.0, +77.0]、LLR +2.91。
W-D-L は +699 =47 -496。

静止探索は探索ノードの大半を占めるため、ここへ枝刈りを足す効果は大きい。
[ADR-0054](0054-qsearch-tt.md)の置換表導入（+113.6 Elo）に次ぐ規模である。

やねうら王が `bestValue` をfutility値まで引き上げる処理は入れていないが、
それでもこの効果が出た。fail-softの下限を報告しないことによる損失は
小さいと見てよい。MultiPVの設計を変えてまで揃える必要はない。

## Consequences

静止探索のノードが減り、同じ時間でより深く読めるようになる。

読み抜けが増える方向のリスクがある。取り返しを除外し、王手中を除くことで
抑える。やねうら王のようにfail-softの下限を引き上げれば上位ノードへ
より正確な値を返せるが、MultiPVの整合を優先して見送った。

`move_stack` をqsearchでも更新するため、continuation historyを
静止探索へ広げる道が開く。現在qsearchのオーダリングは
`cont` を使っていない（[ADR-0047](0047-continuation-history.md)の
スコープ外）。本ADRの配管はその前提になる。

H0だった場合は案Bへ後退し、movecount制限を外してfutility判定だけを測る。
それも中立ならマージン328を将棋向けに調整する。
