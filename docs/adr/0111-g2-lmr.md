# 0111: statScoreとLMRのリダクションを参照実装へ揃える（G2）

- Status: accepted
- Date: 2026-07-30
- 関連ADR: [0109](0109-reference-parity.md), [0110](0110-g1-history.md), [0084](0084-lmr-cutnode.md), [0076](0076-lmr-fixed-point-ttpv.md), [0105](0105-ttpv-propagation.md), [0028](0028-pruning-extensions.md)

## Context

[ADR-0109](0109-reference-parity.md)の追従キャンペーンの第3群にあたる。
[ADR-0110](0110-g1-history.md)（G1）で入れたhistoryを、探索の削減量へ
変換する経路をつくる。

本エンジンのLMRは、リダクション量を深さと手数の表だけで決めていた。
PVノードで1024を引く項があるほかは、historyもノードの状態も見ていない。
参照実装は12項を加減算する。

差は項の数だけではない。**本エンジンのリダクション量は常に正になる**。
参照実装が負にできるのは、ttPvの−2819系・TT手の−2239・statScoreの減算が
効くからである。負にできるから、探索深さを `newDepth + 2` まで許せる。
本エンジンは上限を広げても発火しない構造だった。

[ADR-0084](0084-lmr-cutnode.md)がcutNode項（+3611）だけを入れて912局で
中立だったのは、この構造を欠いたまま強める項を1本足したからである。
打ち消す項がなければ刈りすぎになる。

## Decision

12項をまとめて入れる。項を選ばない。あわせてstatScore・reduction()本体・
LMRの適用範囲・再探索の深さ調整を揃える。

### statScore

historyを削減量へ変換する量である。ノード先頭で0に初期化し、LMRの直前に
その手が駒取りかで2通りに代入する。取る手は `863×駒価値/128 + captureHistory`、
静かな手は `2×mainHistory + contHist[0] + contHist[1]` になる。

読み出しは3か所ある。

- LMRのリダクション（`−statScore×428/4096`）
- history bonusの第3項（`1手前のstatScore/32`）
- fail low時のbonusScale第1項（`− 1手前のstatScore/108`）

**この3つが同じ値を共有して初めて閉じる**。statScoreは「historyを削減量へ
変換する量」であると同時に「削減量を次のhistory更新量へ戻す量」でもある。
G1で後2者を見送っていたのは、statScoreがなかったためである。ここで埋めた。

### Stackへの追加

`tt_pv`・`cutoff_cnt`・`reduction`・`stat_score` を足した。G0で器を作って
あるので、フィールドの追加だけで済んでいる。

`cutoff_cnt` のリセットは次plyではなく2手先である。次plyの値は兄弟をまたいで
貯まる。参照実装のとおりにした。

`reduction` は代入までとし、読む側（子が `priorReduction` として読むdepthの
事後補正）はG4に残した。

### reduction()本体

表を2次元から1次元へ変えた。`2763/128 × ln(i)` を整数化し、深さと手数の
両方をこの表で引く。式は
`基礎値 − 窓幅×585/root窓幅 + (improvingでない場合)基礎値×206/512 + 1133`
になる。

root窓幅（rootDelta）はその反復深化のaspiration窓の幅で、本エンジンは
持っていなかった。`Worker` のフィールドとして配管した。

PVノードで一律1024を引く項は、参照実装に対応物がないため外した。

### LMRの適用範囲

発動条件を `depth >= 2 && moveCount > 1` だけにした。取る手・王手する手・
王手中の3除外を外している。参照実装がこれを許せるのは、statScoreが取る手側も
評価するからである。G1とG2が揃って初めて成立する。

探索深さは `max(1, min(newDepth − r/1024, newDepth + 2)) + PvNode`。上限を
`newDepth` から広げた。再探索はdoDeeperSearch（+48）とdoShallowerSearch（+9）で
newDepthを伸縮し、LMRの深さを上回るときだけcutNodeを反転して呼ぶ。

### ttPvの書き戻しを直した

`tt_pv` はTTに保存していたつもりだったが、書き戻していたのは `is_pv` で
あって `ss->ttPv` ではなかった。参照実装は後者を書く。前者のままでは
伝播が閉じない。

[ADR-0105](0105-ttpv-propagation.md)は「伝播を直しても真になるのは全ノードの
0.46%」として棄却したが、**書き戻しが `is_pv` のままだったことも一因の
可能性がある**。今回は書き戻しも参照実装へ揃えた。

## 機能検証（ADR-0074）

深さ13、4局面。基準はG1完了時点のバイナリである。

| 局面 | G1 | G2 | 変化 |
|---|---|---|---|
| 1 | 169,532 | 192,006 | +13% |
| 2 | 101,760 | 272,954 | +168% |
| 3 | 188,187 | 515,084 | +174% |
| 4 | 104,606 | 152,889 | +46% |

2局面が2倍を超えたため、符号とスケールの取り違えを2通りで確かめた。

**計測で確かめた**。LMR到達点でrの平均は4478〜5000、r<0は6〜8%、
`d − newDepth` の平均は−2.1〜−2.8だった。削る向きに効いている。

**切り分けで確かめた**。探索深さの上限を `newDepth` に戻すと、4局面は
108,363 / 55,733 / 227,838 / 100,255になる。G1完了時点を大きく下回る。
**11項は木を縮める側に働いており、増加は `newDepth + 2` と `+ PvNode` の
延長許容だけから来ている**。

これは移植の目的そのものなので、取り違えではないと判断した。深さを上げると
逆転する。深さ19（局面3は16）では15,959,820から9,267,452へ減る。**深いほど
縮む側が勝つ**。

NPSは1,897,810で、同じ実行で測った基準の1,881,733に対し+0.85%だった。

## SPRT

既定条件（10+0.1、elo0=0、elo1=5、α=β=0.05）でG1完了時点のバイナリと比べた。

```
H1採択 | 508局 | +318 =46 -144 | Elo +124.0 [+94.3,+155.6] | LLR +3.08
```

**+124.0 Eloで採択した**。固定深さでノードが最大2.7倍に増える変更が、
10+0.1という短い持ち時間でこの値を出した。延長を許容した分だけ読みの質が
上がっている。長い持ち時間ではさらに乗ると見てよい。

G1（+88.5）と合わせ、追従の2群で単純加算 +212.5 になる。

## Consequences

historyが探索の削減量へ変換される経路ができた。G1のテーブルはオーダリングと
更新だけでなく、読む深さそのものを動かすようになる。

**浅い深さでノードが増える**。延長を許容する分、固定深さ13では最大2.7倍に
なる。深さ19では減るため、持ち時間が長いほど有利に働く。既定のSPRT条件
（10+0.1）は短い側にあたるので、ここで採択されれば長い持ち時間でも通ると
見てよい。逆に不採択なら、長い持ち時間で測り直す価値がある。

`reduction` フィールドは足したが読んでいない。G4のdepthの事後補正で使う。
1群のあいだ未使用のフィールドが残るが、G0で「読む側を持つ群で足す」と決めた
方針からは外れる。LMRの代入と同じ場所で書くため、ここで足すほうが自然だと
判断した。

作業指示書の要約と原典が3箇所で食い違った。G1の10箇所に続いている。
`tt_pv` の書き戻し、LMRを省いたときの調整が非PVノードの第1手にも掛かること、
`cutoff_cnt` のリセットが2手先であることの3つである。**要約は必ず細部を
落とす**。移植は原典を読んで行う。
