# 0175: SPRTを判定が出るまで走らせ、完了をファイルで検知する

- Status: proposed
- Date: 2026-08-18
- 関連ADR: [0028](0028-pruning-extensions.md), [0087](0087-sprt-resume.md), [0149](0149-experiment-runner.md), [0154](0154-sprt-ops.md), [0163](0163-sprt-hypothesis-choice.md)

## Context

SPRTの走行が上限（`SPRT_MAX_PAIRS`、既定3,000ペア）で止まり、そのたびに人が
「続けるか」を判断している。2026-08-17の1日で3回起きた。

- [ADR-0173](0173-knight-non-promotion-movegen.md): 3,000ペアで判定に至らず、
  上限を8,000へ上げて `--resume`。3,837ペアでH1
- [ADR-0174](0174-mate1ply-knight-promotion.md): 8,000ペアでも足りない見込み

**必要な局数は事前に見積もれるが、見積もる意味がない**。GSPRTの正規近似
（`sprt.rs:67`）でLLRは局数に比例して伸びる。

```
LLR = (s1 - s0) × (2·mean - s0 - s1) × n / (2·var)
```

真のEloが `elo0` と `elo1` の中点より上なら正へ、下なら負へドリフトする。
中点は既定条件（elo0=0、elo1=5）で約+2.5、非劣性（elo0=−5、elo1=0）で
約−2.5である。[ADR-0173](0173-knight-non-promotion-movegen.md)の実測から
ペアあたり分散を逆算すると var ≈ 0.118 で、必要局数はこうなる。

| 真のElo | 既定条件 | 非劣性 |
|---|---|---|
| 0 | H0側へ収束 | 26,879局 |
| +3 | 134,359局 | 12,217局 |
| +5 | 26,879局 | 8,960局 |
| +11.2 | 7,727局 | — |

**真のEloが中点に近いほど遅い**。この関係は走らせる前には分からない。真のEloを
知っていれば局数を見積もれるが、それを知るために測っている。**見積もりは
走らせれば分かることを先回りで計算しているだけで、上限の根拠にならない**。

## 課題は3つある

| 課題 | 現状 |
|---|---|
| 上限で止まる | `--max-pairs` 到達が終了条件になっている |
| 完了の検知 | 終了コードとログ最終行。**プロセスが生きている間しか使えない** |
| 再開の判断 | 人が続行を決める |

[ADR-0087](0087-sprt-resume.md)の `sprt-run.sh` は異常終了からの復帰を自動化
したが、終了コード2（判定に至らず）はそのまま返して終わる。**「落ちたら拾う」
は自動化されていて、「まだ判定が出ていないから続ける」は手作業のまま**である。

3つ目が本質になる。SPRTの状態は棋譜jsonlに全部あるので（[ADR-0087](0087-sprt-resume.md)）、
**「判定が出たか」だけをファイルで表せば、完了の検知はプロセスの生死から
独立する**。

## 選択肢と比較

### 案A: 上限を撤廃し、判定が出るまで走る。完了をファイルへ残す

`sprt-run.sh` が終了コード2を「継続」として扱い、上限を広げて `--resume` する。
判定が出たら `data/sprt/<名前>.result` へ結果を書く。**このファイルの有無が
完了の定義**になる。

真のEloが中点ちょうどなら理論上収束しないので、暴走を防ぐ硬い上限は残す。

### 案B: 上限の既定値を大きくするだけ

1行で済むが、その値の根拠がない。大きすぎれば暴走を止められず、小さければ
同じ問題が再発する。**上限は「収束の判定基準」ではなく「安全弁」であるべき**
という区別が付かないままになる。

### 案C: 現状維持（人が続行を判断する）

判断のたびに文脈を読み直す必要があり、セッションをまたぐと引き継げない。
今回のように1日3回起きるなら、自動化の対象である。

## Decision

**案Aを採る**。

### 完了の表現

判定（H1・H0）が出たときだけ `data/sprt/<名前>.result` を書く。1行1項目の
`key=value` で、機械にも人にも読める形にする。

```
name=adr0173-knight
decision=H1
elo=+11.2
ci_low=+3.7
ci_high=+18.8
games=7674
llr=+2.92
elo0=0
elo1=5
finished_at=2026-08-17T14:20:31Z
```

**このファイルが存在すれば完了、なければ未完了**という規則にする。判定に
至らないまま安全弁で止まった場合は書かない。**中途半端な結果を「完了」と
記録しない**ためである。

### `sprt-run.sh` の動き

1. `.result` があれば内容を表示して即座に終了する（冪等。[ADR-0149](0149-experiment-runner.md)）
2. 棋譜があれば `--resume` で続きから始める
3. 終了コード2（判定に至らず）なら、`--max-pairs` を広げて再開する
4. 判定が出たら `.result` を書いて終了する
5. 硬い上限 `SPRT_HARD_MAX_PAIRS`（既定60,000ペア＝12万局）に達したら、
   `.result` を書かずに終了コード2で終わる

段階的に広げるのではなく、**最初から硬い上限まで通す**。途中で区切る理由が
ないからである。`--max-pairs` は暴走防止の安全弁へ降格する。

### 硬い上限の根拠

60,000ペア（12万局）は、非劣性で真のEloが+0.5のときの必要局数（約48,000ペア）
を上回る値として置く。これを超えて判定が出ないなら、真のEloは中点のごく近傍に
あり、**そもそもその対立仮説で答えの出ない変更**である。局数を積むより仮説の
立て方を見直すべき状況なので、止めて人が判断する。

## Consequences

- SPRTの起動が「投げて `.result` を待つ」だけになる。上限到達のたびに続行を
  判断する必要がなくなる
- **セッションが切れても引き継げる**。次に `sprt-run.sh` を叩けば、棋譜から
  続きを走り、完了していれば即座に結果を返す
- 1回の走行が長くなる。真のEloが中点近傍の変更では数時間〜十数時間になりうる。
  **経過は `data/logs/sprt-<名前>.log` と `sprt-summary.py` でいつでも読める**
  ので、走らせたまま他の作業へ移れる
- 硬い上限に達した走行は `.result` を持たない。この状態は「判定に至らず」と
  して[ADR-0163](0163-sprt-hypothesis-choice.md)の判断（非劣性へ落とす・条件を
  変えて測り直す・棄却）へ回す
- **エージェントが起動するときはプロセスを親から切り離す**（2026-08-18追記）。
  ツールのバックグラウンド実行のまま走らせたところ、2回とも数十分で回収されて
  止まった（756局・47分と808局・50分）。標準出力を捨てても起きたので出力量とは
  無関係で、呼び出し元のプロセスグループごと回収されている。`sprt-detach.py` が
  `start_new_session=True` で新しいセッションへ移して起動する。
  **切り離してよいのは、本ADRで状態がファイルに載ったからである**。進捗はログ、
  完了は `.result` で分かるので、プロセスを手元で掴んでおく理由がない。
  設計の意図が運用でそのまま効いた形になった
- **SPRTのEloの読み方に注意書きが要る**。逐次検定は閾値を超えた瞬間に止まるので、
  上振れしたタイミングで停止しやすい。H1採択時の点推定は真値より高めに偏る。
  SPRTが保証するのは「中点より上」であって点推定の精度ではない。換算率のような
  精度の要る数値は局数を固定して測る。この注意は[ADR-0163](0163-sprt-hypothesis-choice.md)へ
  追記する
