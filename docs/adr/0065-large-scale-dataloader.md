# 0065: 学習データをバッチ一括抽出とチャンク読みで供給する

- Status: accepted
- Date: 2026-07-26
- 関連ADR: [0043](0043-pyo3-bridge.md), [0061](0061-psv-memmap-dataset.md), [0064](0064-dense-ft-gradient-mps.md)

## Context

[ADR-0064](0064-dense-ft-gradient-mps.md)で学習の計算側が
518,500 samples/sになり、律速がデータローダへ移った。
現行ローダは1プロセスで117,000 rec/sしか出ない。

同時にデータ量の制約も変わった。19.9億局面は79.7GBあり、
RAM 48GBに載らない。ADR-0061が選んだ全ロード＋forkは使えない。

現行ローダの構造に2つの無駄がある。`PsvDataset.__getitem__` は
1局面ごとにPyO3を呼ぶ。`collate_psv` はPythonのループで特徴を
連結し直す。実測では抽出単体が269,000 rec/s、経路全体が
117,000 rec/sで、半分以上をPython側の処理が占めていた。

## 選択肢と比較

### 案A: memmap＋DataLoaderのshuffle=True

ADR-0061の案A。前処理が要らない。実測5,303 samples/sで、
79.7GBへのランダムアクセスがページキャッシュに収まらない。論外である。

### 案B: 事前シャッフル＋mmap順次読み

ADR-0061の案D。ファイル側を混ぜておき、読み出しを順次にする。
I/Oは解決するが、Python側の1件ずつの処理が残る。上限は
117,000 rec/s前後にとどまる。

### 案C: 案B＋バッチ一括抽出

案Bに加えて、抽出をバッチ単位のRust呼び出しへ変える。
`extract_batch` はバッチ全体を受け取り、rayonで並列に抽出して
numpy配列を直接返す。その間GILを解放するため、DataLoaderの
workerプロセスを使わずに全コアを使える。

実測は次のとおり。batch=16384、bench200k.psvを入力とした。

| 経路 | スループット |
|---|---|
| `extract_features` 単体（1件ずつ） | 269,000 rec/s |
| 現行経路（`__getitem__`＋`collate_psv`） | 117,000 rec/s |
| `extract_batch`（rayon＋GIL解放） | 708,965 rec/s |
| `extract_batch`＋インデックスgather | 673,620 rec/s |

## Decision

案Cを採用する。3つの部品からなる。

第1に、`crates/py` に `extract_batch` を追加する。
戻り値は `(stm_idx, stm_off, opp_idx, opp_off, targets)` の
numpy配列5本で、EmbeddingBagがそのまま受け取れる形にする。
展開に失敗した局面とscore_limitで除外した局面は、
バッチから落として詰める。

第2に、`training/dataset.py` に `PsvBatchLoader` を追加する。
prefetchスレッドが次のバッチを先に用意し、GPU計算と重ねる。
`extract_batch` がGILを解放するので、Pythonスレッドで並列に動く。

mmap時はチャンク単位でシャッフルする。ファイル上の連続した
1M局面（40MB）を読み、チャンク内を混ぜてからバッチに切る。
読み出しがシーケンシャルに保たれ、先読みが効く。
バッチがチャンク境界をまたぐ端数は次のチャンクへ繰り越す。

チャンク内シャッフルだけでは全体の一様性を保証できない。
そこで入力ファイルを事前にシャッフルしておく。

第3に、`psv shuffle` を2パスのバケット法に変える。
パス1で各レコードをランダムなバケットへ振り分け、パス2で
バケット単位にメモリ上でシャッフルして連結する。1バケットは
2GBを目標とし、メモリ使用量を入力サイズから切り離す。
一時ファイルは使い終わり次第消す。

`train_big.psv`（3.4GB、86,115,727局面）で検証した。
所要10.9秒、レコードの多重集合は入力と一致し、99.99999%の
レコードが位置を変えた。253ファイル・79.7GB・19.9億局面の
本番データでは、38バケットで所要3分だった。

実学習のスループットは次のとおり。370M局面（14.8GB、全ロード）で
449,000 samples/s、19.9億局面（79.7GB、mmapチャンク読み）で
281,000 samples/sである。前者は `extract_batch` の708,965 rec/sと
計算側の518,500 samples/sに挟まれた値で、両者が重なって動いて
いることを示す。後者はディスクI/Oが加わる分だけ落ちるが、
ADR-0061の案A（memmapにランダムアクセス）の5,303 samples/sに対して
53倍である。

## Consequences

- 全ロードで足りる規模では、律速が計算側（518,500 samples/s）へ戻る。
  mmapが要る規模ではディスクI/Oが律速になり、281,000 samples/sに
  落ちる。次に速度を上げるなら、この順に手を入れることになる
- DataLoaderのworkerプロセスが要らなくなる。ADR-0061が
  forkを明示した理由（spawnによるデータセット複製）も、
  worker内でスレッドを使う危険も、まとめて消える
- 事前シャッフルに入力と同容量の一時ディスクが要る。79.7GBの
  入力なら、バケットと出力で160GBを使う
- 旧経路（`PsvDataset` と `collate_psv`）は当面残す。
  `--batch-loader` を既定にしたうえで、次の学習が一巡したら消す
- チャンク内シャッフルは事前シャッフルとセットで意味を持つ。
  未シャッフルのファイルを直接食わせると、バッチが同一対局の
  連続局面に偏る
