# 0084: LMRにcutNode項を入れる（cutNodeの配管を含む）

- Status: rejected
- Date: 2026-07-28
- 関連ADR: [0076](0076-lmr-fixed-point-ttpv.md), [0028](0028-pruning-extensions.md), [0074](0074-feature-verification.md)

## Context

[ADR-0076](0076-lmr-fixed-point-ttpv.md)でLMRのリダクションを1024倍の
固定小数にした。やねうら王の項をそのまま換算せずに使える土台ができた。
だが現状で足されている項は `is_pv` の -1024 だけである。

```rust
let mut r = lmr_reduction_x1024(depth, count);
if is_pv {
    r -= 1024;
}
```

やねうら王・Stockfishは10個以上の項を持つ。そのうち最大のものが
cutNode項である。

```cpp
// Increase reduction for cut nodes
if (cutNode)
    r += 3611 - 985 * !ttMove;
```

cutNodeは「このノードはβカットが起きると予想される」という印である。
親がnull windowで子を呼ぶとき、親から見て「この子はどうせ悪い」と
分かっているノードに立つ。予想が当たれば1手目で切れるので、外れた手を
深く読む価値は低い。だから強く削る。

本エンジンの `search` はこの印を持たない。ADR-0076でttPv項を単独導入
したとき -43.8 EloのH0だった。ttPv項はリダクションを弱める方向にしか
働かず、強める側の大項がないため釣り合いが取れなかったと見ている
（[ADR-0076](0076-lmr-fixed-point-ttpv.md)）。cutNode項はその強める側の
唯一の大項で、他の弱める項の前提になる。

## 選択肢と比較

### 案A: cutNodeを配管し、LMRへ定数項を1つ足す

`search` に `cut_node: bool` 引数を足し、Stockfishと同じ規則で伝播する。
LMRでは `if cut_node { r += 3611 }` とする。

伝播の規則は次のとおり。null windowで子を呼ぶとき、親がcutNodeなら子は
allNode、親がallNodeなら子はcutNodeになる。だから反転して渡す。

| 呼び出し位置 | 子へ渡す値 |
|---|---|
| root（反復深化の入口） | `false` |
| rootの2手目以降（null window） | `true` |
| PV探索・PV再探索 | `false` |
| ムーブループのnull window（非LMR） | `!cut_node` |
| LMRの浅い探索 | `true` |
| LMR後の全深さ再探索 | `!cut_node` |
| NMPの子 | `!cut_node` |
| ProbCutの確認探索 | `!cut_node` |
| singularの検証探索 | `cut_node`（同じノードなので反転しない） |

LMRの浅い探索が常に `true` なのは、リダクション後の探索が「たぶん
alphaを超えない」という予想の下で行われるためである。Stockfishも
同じ扱いをする。

`!ttMove` の項（+985）は同時に入れない。1変更=1SPRTの粒度を守る
（[CLAUDE.md](../../CLAUDE.md)）。

### 案B: ttMove項も同時に入れる

やねうら王の式をそのまま `3611 - 985 * (tt_move != NONE)` として入れる。
出典に忠実だが、H0のときにどちらの項が原因か切り分けられない。

### 案C: 入れない

cutNode項なしでLMRの他の項を積む。ADR-0076のttPv項が示したとおり、
弱める側の項だけでは釣り合わない。cutNodeを避けたままLMRを育てる道は
細い。

## Decision

案Aを採る。

`LMR_CUT_NODE_R = 3611`（1024倍固定小数）。出典はやねうら王
`yaneuraou-search.cpp` のLMR reduction計算である。スケールの前提は
[ADR-0076](0076-lmr-fixed-point-ttpv.md)で確認済みで、本エンジンの
`lmr_reduction_x1024` はやねうら王の `reductions[d]*reductions[mn]` と
係数466対455（差2.4%）で一致する。したがって項の重みを換算せずに使える
（[ADR-0074](0074-feature-verification.md)のスケール前提の確認）。

3611/1024 ≈ 3.5手ぶんのリダクションを、cutNodeでのみ上乗せする。

配管そのものは探索の挙動を変えない。項を足して初めて変わる。両者を
1つのADR・1つのPRで扱う。配管だけを先に入れても、使われない引数が
残るだけで意味がないためである。

## 機能検証（2026-07-28）

`scripts/verify-feature.sh` で固定深さ13のノード数を比較した。

| 局面 | 変更前 | 変更後 | 変化 | 評価値 | 最善手 |
|---|---|---|---|---|---|
| 1 | 498,549 | 326,266 | -35% | 41 → 39 | 6i7h → 2g2f |
| 2 | 477,923 | 305,946 | -36% | 102 → -92 | 同じ |
| 3 | 1,546,105 | 2,737,877 | +77% | 995 → 1017 | 同じ |
| 4 | 356,888 | 394,255 | +10% | -162 → -131 | 8c8d → 7b7c |

2局面で35%前後減り、リダクションが効いている。局面3で77%増えたのは、
削った探索がalphaを超えて全深さで読み直す回数が増えたためと見ている。
LMRは「削って外れたら読み直す」構造で、削りを強めるとノード数は
一方向には動かない。

局面2の評価値が102から-92へ振れた。強く削った結果、深さ13時点での
読みが変わっている。最善手は変わらない。局面1と4は最善手が変わったが、
評価値の差はどちらも数十点で、優劣が入れ替わる幅ではない。

発動率は測っていない。cutNodeはLMRの判定に入る全ノードのうち、
null windowで呼ばれた側すべてに立つ。探索木の大半を占めるため、
[ADR-0074](0074-feature-verification.md)の0.1%基準は自明に満たす。

## SPRT結果（2026-07-28、打ち切り）

912局（456ペア）で **-1.1 Elo [-22.3, +20.0]**、LLR -0.16。W-D-Lは
+437 =35 -440。判定に至る前に打ち切った。

打ち切りはオーナー判断である。LLRは0付近を456ペア動かず、H0側へ倒れる
にしても数千局を要する形だった。いま必要なのは数Eloの積み上げではなく、
効果の大きい機能を試す回転数だと判断した（2026-07-28）。

## Decision（改訂）

**案Aを棄却する。** cutNode項を単独で入れても効果はない。

改訂の理由は、この結果が「値が大きすぎた」ではなく「単独では中立」を
示すためである。ノード数は局面1・2で35%前後減り、リダクションは確かに
強まっていた（機能検証）。それでも勝率が動かない。削って浮いた時間を、
別の場所で失っている。

Stockfish系でcutNode項が効くのは、リダクションを弱める側の項が10個以上
並んでいて、その中で釣り合いを取っているからだと考える。強める項だけ、
弱める項だけを取り出すと、どちらも中立か悪化になる。
[ADR-0076](0076-lmr-fixed-point-ttpv.md)のttPv項が -43.8 だったのと
表裏の関係にある。

LMRの項は1項=1SPRTで積めない。この見立てが正しければ、次にLMRへ
手を入れるときは項をまとめて移植し、群として測るべきである。

## Consequences

配管（`search` の `cut_node` 引数）ごと入れない。使う項がないまま引数を
残しても、警告を抑える記述が増えるだけで意味がない。実装は
`feat-adr0084-cutnode` ブランチに残す。項をまとめて移植する形で再挑戦
するとき、伝播規則の表とあわせて出発点になる。

LMRの項を1つずつSPRTで積む方針は、本ADRとADR-0076の2件で否定された。
[IDEAS.md](../IDEAS.md)の「LMRのその他の項」（1項=1SPRT）は、この
知見に合わせて書き換える。

副産物として、MultiPV出力の降順が崩れる既存の不具合を見つけた。本ADRの
実装で探索の返り値分布が変わり、テストが落ちて発覚した。修正は別PRで
mainへ入れてある。
