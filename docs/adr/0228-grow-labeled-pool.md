# 0228: dlshogiで点数を付けた局面の母集団を、重複なく足して増やし続ける

- Status: proposed
- Date: 2026-10-08
- 関連ADR: [0206](0206-entering-king-mix.md), [0210](0210-teacher-mix-control.md), [0219](0219-relabel-2b-in-place.md), [0224](0224-selection-bench.md), [0225](0225-dedup-20b.md), [0227](0227-cell-dataset.md)

## Context

dlshogiで点数を付けた局面で学習すると強くなる（[ADR-0219](0219-relabel-2b-in-place.md)）。
その局面を、どう選び、どう増やすかを測ってきた。結果は「足す」と「入れ替える」で
きれいに分かれた。

| 動かし方 | 実験 | 結果 |
|---|---|---|
| 重複だけを除く | [ADR-0224](0224-selection-bench.md)・[ADR-0225](0225-dedup-20b.md) | +27.3・+22.8 |
| 量を増やす | 1億 → 20億 | 大きく効く |
| 別の系列の局面を足す | [ADR-0206](0206-entering-king-mix.md)・[ADR-0210](0210-teacher-mix-control.md) | +37.3。量の20%増だけでは効かない |
| 自然な分布の局面を減らす・入れ替える | ADR-0224・[ADR-0216](0216-defense-oversample.md)・[ADR-0227](0227-cell-dataset.md) | −65.9・−23.8・−58.4 |

オーナーは方針を決めた（2026-10-08）。**dlshogiで点数を付けた局面をどれだけ増やせるか、
の勝負にする**。最終的に200億局面になってもよい。細かい選び方より、重複なく局面を
足し続けることを優先する。

## Decision

母集団を、同じ型を繰り返して増やす。

1. **集める**。入玉5億、floodgateの全対局（wdoorの年別アーカイブ、2008〜2026年）、
   tanukiの残り58.5億などから候補の局面を取り出す
2. **そろえる**。今の学習データと同じく1手静止化する
3. **重複を除く（点数を付ける前）**。台帳（`hmwr data ledger filter`）と突き合わせ、
   初めて見る局面だけを残す。重複の判定は点数を付ける局面そのもので行うので、
   静止化の後に通す
4. **点数を付ける**。dlshogiの推論1回、S=430（[ADR-0219](0219-relabel-2b-in-place.md)）
5. **足す**。母集団へ混ぜ、台帳にも登録する（`hmwr data ledger add`）
6. **確かめる**。母集団がおよそ10億増えるごとに、全体を2周で学習して現行とSPRTで比べる

台帳は、点数を付けた全局面と検証集合の盤面ハッシュを持つ。同じ局面に二度点数を
付けることと、検証用の局面が学習へ混ざることを防ぐ。

### 制約

- ディスク: 1局面40バイトで、200億局面は約800GBになる。開発機のディスクは926GBで、
  空きは約60GBしかない。どこかの時点で外付けのストレージかクラウドが要る
- 点数を付ける速さ: 開発機で約2,300局面/秒、10億局面に約5日。200億まで開発機だけで
  進めると約100日かかる。AWSの準備が整えば並列にできる（オーナーが用意中）

## 最初の回: 入玉5億

入玉5億は、floodgateで入玉した対局の局面である。重複を除いて約4.7億を足すと、母集団
（17.4億）の約2割が終盤・入玉寄りの局面になる。最初の確かめは10億を待たず、この回の
後に行う。別の系列を足す最初の回なので、効くかどうかを早く知りたい。

### 仮説

**重複を除いた17.1億に、入玉5億を重複なく足して2周学習したネットは、現行
`dl20u_2ep` より強い**。

### 測定の設計

- 動かす変数は、母集団に入玉5億を足すかどうか。量（17.4億→約22億）と系列
  （floodgateの入玉の対局）が一緒に動く。今回は「実際に使う母集団どうし」の比較として
  読み、量と系列は分けない
- 母集団は、`dl20u`、付け直し済みの入玉の候補 `ek_dl430`（ADR-0227で作った2,400万）、
  新しく付け直す入玉の局面を、全体シャッフルで混ぜる
- 学習のレシピは `dl20u_2ep` と同じ。2周、batch 16384、peak_lr 1e-3、λ0.7、seed 0、
  兄弟群 `rank_tanuki_210M`、検証 `valid_tanuki_dl430_q1`。ゼロから学習する
- 比較は `dl20u_2ep` 対 `pool1_2ep`。同一ビルドのネット差し替えで、どちらも並べ替えを
  施さない。SPRTは既定（elo0=0、elo1=5）、上限10,000ペア

### 解釈の事前登録

| 判定 | 読み | 次の一手 |
|---|---|---|
| H1 | 入玉の系列を足すと強くなる。ADR-0206の+37.3と同じ向き | 並べ替えて現行と切り替える。floodgateの全対局の回へ進む |
| H0 | 入玉寄りの局面が2割になると、分布の偏りが勝つ。ADR-0227と同じ向き | 切り替えない。入玉の局面の比率を下げて足す回を設計する（全部ではなく一部を足す） |
| 見送り | 効きは±2.5の中にある | 切り替えない。母集団は保ち、次の回（floodgate）を足してから10億の時点でもう一度測る |

## 実行

specは `experiments/adr0228-ek-batch.toml` である。まず台帳を `dl20u`・`ek_dl430`・
検証集合で初期化する。続けて入玉5億を全体シャッフル・静止化し、台帳と突き合わせて
付け直す（約57時間）。最後に台帳へ足し、母集団を混ぜ、2周の学習（約28時間）とSPRTを走らせる。合計で約4日を
見込む。

ディスクの空きを保つため、各段で前の出力を消す。母集団を混ぜる段は、全体シャッフルでは
なく織り交ぜ（`hmwr data merge --consume`）で行う。入力はどれもシャッフル済みなので、
残り件数に比例した確率で織り交ぜれば一様な並びになる。入力を末尾から読みながら切り詰める
ので、空きは出力1本ぶんで済む。最初は `hmwr data mix --consume` で書いていたが、
これは入力をファイル単位でしか消さない。68GBの `dl20u` を読み終えるまで空きが
足りないと分かったので、付け直しの途中で差し替えた（2026-10-08）。`dl20u` は母集団 `pool1` に吸収されて
消える。`dl20u` は `train_7860M_q1` から重複除去で作り直せる。ADR-0227で作った1億の2本
（`cell_a0_100M`・`cell_a05_100M`、計8GB）も、分析を終えたので消す。

## 追記（2026-10-13）: SPRTの上限を30,053ペアへ延ばす

`dl20u_2ep` 対 `pool1_2ep` のSPRTの上限を、走行中に10,000ペアから30,053ペアへ延ばす
（オーナー判断、2026-10-13）。対立仮説（elo0=0、elo1=5）と対局の条件は変えない。

決めた時点の途中経過は、5,152ペアで+3.6 [−3.0, +10.1]、LLR +0.48である。
決めたのは上限へ達する前である。ただし途中経過を見た後の変更なので、読むときはそれを割り引く。

延ばす理由は3つある。

- 上限を延ばしても、誤ってH1を採択する率は増えない（[ADR-0217](0217-sprt-pass-cap.md)）
- ADR-0217が上限を置いた主な理由は、キューの後続を待たせることだった。今回は後ろに
  待つ実験がない
- 別の系列を足す最初の回で、効きの大きさを知っておきたい。足しても+3前後なのか、
  それとも差がないのかで、以後の回の見込みが変わる

30,053は開始局面（`start_sfens_ply24`）の件数である。selfplayは開始局面を順に使うので、
ここまでは同じ開始局面を二度使わない。約525ペア/時で、延ばした分は約38時間かかる。

解釈の事前登録は変えない。30,053ペアで判定に至らなければ見送りと読む。

走行中の対局を止めて、同じ棋譜の続きから再開する。再開でキューのworktreeはmainへ
揃い、エンジンを作り直す。対局を始めたコミットからmainまでの差はリリースの版の
更新だけで、エンジンのコードは変わっていない。両側は同じバイナリを使う。

### 再開の前に確かめたこと

入力の合計が10億局面以上あると、`hmwr data merge` は最初の抽選で落ちた。#710が直した。
入力を消し始める前だったので、データは失っていない。再開の前に次を確かめた。

- 重複除去の件数は合う。読んだ500,006,044局面から、入力の中の重複54,651,513と、
  台帳にあった26,194,484を除いて419,160,047局面になる。見込み（約4.7億）より少ないのは、
  入力の中の重複のためである
- 入力は厳密には一様な並びではない。先頭から末尾へ、点数の絶対値の平均が
  `dl20u` で1503から1646へ増える。重複除去が最初の1件だけを残すので、後ろほど
  重複しにくい局面が残るためと見ている。学習は100万局面のチャンクを無作為な順に読むので、
  この傾きは学習の順序へ出ない。`dl20u_2ep` も同じ条件で学習している
- `pool1` を100万局面ずつ20か所で抜き取った。140手目以降の局面の比率は18.5〜19.9%で、
  入玉寄りの局面はどのチャンクにもほぼ同じ比率で入っている
- 検証集合（`valid_tanuki_dl430_q1`）の損失は、`dl20u_2ep` が0.44929、`pool1_2ep` が
  0.44967である。差は誤差の規模（[ADR-0158](0158-mirror-factorizer.md)の0.00136）の内側にある

## 追加の測定: 入玉の開始局面での対局

SPRTの棋譜（10,434局の時点）を集計すると、対局は入玉の場面へほとんど届いていない。

- 終局理由は裁定が95%で、入玉宣言は1局、最大手数は3局である
- 手数の中央値は94手、90%点は132手である。足した入玉の局面は、手数の平均が約145である
- 終局時にどちらかの玉が敵陣にいた対局は4.4%である

足した局面が効く場面を、通常の開始局面のSPRTは見ていない可能性がある。
[ADR-0206](0206-entering-king-mix.md)と同じ型で、入玉の開始局面から指して確かめる。

### 仮説

**入玉の開始局面から指すと、`pool1_2ep` は `dl20u_2ep` より強い**。

### 測定の設計

- 動かす変数は評価関数だけである。`dl20u_2ep` 対 `pool1_2ep` で、どちらも並べ替えを
  施さない
- 固定するものは、SPRTと同じである。同一ビルド、10+0.1、裁定2000,8、置換表64MB、
  最大320手
- 開始局面は `openings/entering_king_ply40.txt` の2,000件で、1件を1回ずつ使う。
  2,000ペアを指し切り、Eloを推定する。約4時間かかる
- 開始局面は、足した教師と同じ入玉5億から抜いたものである。開始局面そのものや、
  その近くの局面を `pool1_2ep` は学習している。この測定は `pool1_2ep` に有利へ傾く

採否はこの測定で変えない。切り替えるかどうかは、上のSPRTだけで決める。

### 解釈の事前登録

| 95%区間 | 読み | 次の一手 |
|---|---|---|
| 下端が0を超える | 入玉の場面では強くなっている。通常の開始局面のSPRTがそれを見ていない。ただし有利へ傾く測定なので、大きさは割り引く | 以後の回の確かめに、入玉の開始局面の対局を添える。floodgateの入玉宣言負けの推移を見る |
| 0をまたぐ | 有利へ傾く測定でも差が見えない。17億の土台では、入玉の系列を足す利得が小さい | 入玉の局面を集める優先度を下げ、次の回（floodgateの全対局）へ進む |
| 上端が0を下回る | 入玉の場面で弱くなった。付け直した点数が入玉の局面で合っていない疑いがある | 入玉の局面でdlshogiの点数と対局の結果を突き合わせてから、次の回へ進む |

specは `experiments/adr0228-ek-openings.toml` である。
