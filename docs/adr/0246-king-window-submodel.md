# 0246: 玉の近傍5×5を小さなNNで読む部分モデルを、ノード数固定の対局で測る

- Status: proposed
- Date: 2026-10-24
- 関連ADR: [0245](0245-input-variants-screening.md), [0237](0237-effect-count-inputs.md), [0171](0171-ft-pairwise-product.md), [0066](0066-halfkp-factorizer.md)

## Context

ADR-0245の議論の続きで、オーナーと「差分計算をしないなら、NNUEの形に縛られない設計にしてよい」と
話した（2026-10-23）。その中で出た案が、玉のまわりだけを見る小さなNNを、いまのkp＋eの横に置く
部分モデルである。オーナーは窓を5×5とし、7×7は広げすぎと判断した。序盤の重さは定跡で避けられる。

部分モデルを考えた根拠は、学習済みのHalfKPの表を分解した測定である（スクラッチで測った）。

- 表の重みのうち、玉の位置に依る成分は27.2%（局面に出る頻度で重みを付けた値）。残りは玉の位置に依らない
- 玉に依る成分のうち、玉から5×5の窓に入る駒が30.1%、7×7の窓で46.8%を占める
- 玉の位置に依る成分は、少数の型でほぼ表せる。型4つで60%、16で90.2%。型は頻出の玉の升
  （6八が22.9%、5九が14.3%など）に対応する

HalfKPは玉と駒の対を1つずつ足すだけで、「金が6七にいて、7七に敵の利きが2枚ある」のような
窓の中の組み合わせは、後段に任せるしかない。ADR-0245のA9（`kw5`）は同じ窓の升を表の行として
足す線形の形で、組み合わせは見ない。部分モデルは窓の升を並べて小さなMLPに通すので、
組み合わせを直に扱える。A9と並べれば、窓の情報のうち線形で取れるぶんと、組み合わせのぶんを分けられる。

## 選択肢と比較

### 出力をどこへつなぐか

#### 案J1: 後段の連結ベクトルの末尾へつなぐ

FTの活性と利きの活性の後ろに、両玉の出力を並べる。後段が他の入力と組み合わせて使える。

#### 案J2: 評価値へ直接の線形和で足す

「玉の危険度」が点数としてそのまま見える。見せる活動には向くが、後段が他の入力と組み合わせられない。

### 速くする工夫をいつ入れるか

#### 案K1: 窓の中身をハッシュにして出力を使い回す

1手で窓の中身が変わらない割合は、自玉の5×5で駒と利きを見て47.0%だった（棋譜400局、38,477手）。
探索中の当たり率は測っていない。

#### 案K2: この段では入れない

埋め込みと第1層はどちらも線形なので、「升の位置×トークン」ごとの32次元の行へ畳み込める。
1つの玉の計算は、25行の足し算（800回）と、窓の外の入力と第2層の積和（約500回）で済む。
キャッシュの前に、この大きさで足りるかを見たい。

## Decision

J1とK2を採る。この段は質を測る段で、ADR-0245と同じくノード数固定で比べるので、速さは結果に効かない。
J2は質が出てから、見せる形として検討する。

### 部分モデルの形

1. 玉を中心にした5×5の窓を、玉の側から見た向きで25升に並べる。後手の玉は盤を180度回してから読む
2. 升のトークンは、駒の状態30通り（盤外・空き・自分の14種・相手の14種）×自分の利き4段階×相手の利き4段階の
   480通り。利きはF2と同じ数え方で、3で打ち切る
3. トークンを16次元へ埋め込み、位置の順に並べて400次元にする。埋め込みの表は升の位置で共有し、
   位置の情報は並べる順が持つ
4. 窓の外の入力として、相手の持ち駒7種の枚数（その駒の最大の枚数で割る）と、玉の側の手番かを足す（8次元）
5. 408→32→8のMLPに通す。中間と出力は0〜1へクリップし、出力は127倍して連結ベクトルへ入れる
6. 両玉に同じモデルを当て、手番側の玉・非手番側の玉の順に、連結ベクトルの末尾へ置く。
   後段の入力を32の倍数に保つため、16次元の後ろを0で埋めて32列にする

構成名は `e<E>` の後ろに `k<出力の幅>` を書く（`1024x16x32e64k8`）。推論は `crates/engine/src/submodel.rs`、
学習は `training/model.py` の `SubModel` が持つ。重みはf32のままネットのファイルへ載せる
（版13・版14）。学習はほかの層と一緒に端から端まで行い、補助の的は持たない。

## 測定の設計

### 仮説

**玉の近傍5×5の組み合わせを読む部分モデルを足すと、同じ1億局面・同じレシピで学習したネットの、
ノード数固定の対局での質が上がる**。

### 動かす変数

部分モデルの有無だけを動かす。比べる案C1は `1024x16x32e64k8` で、ADR-0245のA0（`1024x16x32e64`、F2）に
部分モデルを足した構成である。

### 固定するもの

ADR-0245の「固定するもの」と同じにする。データ `sel_dedup_100M`、学習のレシピ（1周、batch 16384、
peak_lr 1e-3、λ0.7、seed 0、FTクリップ1.0、兄弟群 `rank_tanuki_210M`、検証 `valid_tanuki_dl430_q1`）、
後段16→32→1、FT幅1024、`eff_ctrl` との1手30万ノード固定・1,000ペアの対局である。

暗黙に動く変数を点検した。

- 乱数の系列。部分モデルの層を作るぶん、初期化で乱数を消費する順序がずれる。ADR-0245と同じく数Elo規模で、
  区別できる差（±25）より小さい
- 後段の入力の幅。連結ベクトルが32列広がり、第1層の重みが増える。部分モデルに含まれる違いとして扱う
- 学習1ステップの時間。ステップ数で揃えるので結果には効かない。所要は記録する

### 解釈の事前登録

質QはADR-0245と同じく `eff_ctrl` → 案のEloで、A0のQ（+185.6）との差ΔQで読む。区別できる差の線は±25に置く。

| 結果 | 読み | 次の一手 |
|---|---|---|
| ΔQが+25以上 | 窓の組み合わせは、HalfKPと利きにない情報を持つ | 探索中のキャッシュの当たり率とNPSを測り、速さの設計（K1）へ進む |
| ΔQが±25の内 | 1億・1,000ペアの規模では、窓の組み合わせの情報は見えない | A9と比べ、窓の情報そのものが見えないのかを確かめる |
| ΔQが−25以下 | 想定外。入力の作り方と学習の不具合を疑い、点検する | 点検の結果を書く |

A9の結果が出ていれば、C1とA9の差も読む。C1がA9より25以上良ければ、窓の情報のうち組み合わせのぶんが効いている。
差が±25の内なら、線形の足し算（A9）で足りる。

### 合格の条件

この段は棋力の主張をしないので、SPRTは行わない。コードをmainへ入れる条件は次のとおりである。

- 既定の構成（`1024x16x32e64`）で探索が変わらないこと。`hmwr verify` の組み込み4局面で、
  ノード数・評価値・最善手が変更前と一致する
- 部分モデルの入力が、学習（PyO3）と推論で同じ値になること。推論の評価値が学習側の模型の出力と、
  量子化の丸めの範囲で一致すること。テストで突き合わせる
- 畳み込んだ表で計算した値が、学習側の形（埋め込みを並べて第1層に通す）の値と一致すること

### 読み

C1のQは+206.2で、A0の+185.6との差ΔQは+20.6である。事前登録の「ΔQが±25の内」の行に当たる。
1億・1,000ペアの規模では、窓の組み合わせの情報は見えない。

この行の次の一手は「A9と比べ、窓の情報そのものが見えないのかを確かめる」である。A9はまだ走っていない
（ADR-0245の順番ではC1の後に置いてある）。C1とA9の差は、A9の結果が出てから読む。

StatusはA9との比較が残るので、proposedのまま残す。

## Consequences

- 構成名に `k<K>` を書くと、玉の近傍の部分モデルが入る。書かない構成のコードと探索は変わらない
- 部分モデルの入力は、学習側へ側の入力の1行の後ろにつないで渡す。ローダの戻り値の形は変えていない
- 部分モデルを持つネットのファイルは、版13・版14になる。構成の変換（`load_resized`）は利きの構成と同じく、
  同じ構成のファイルだけを読む
- 速さはこの段では測らない。評価のたびに両玉の窓を作るので、NPSは下がる。質が出たら、キャッシュの当たり率と
  NPSを測って速さの設計を決める
