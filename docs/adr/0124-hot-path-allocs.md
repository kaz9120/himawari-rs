# 0124: 挙動を変えない高速化を群でまとめて測る

- Status: accepted
- Date: 2026-08-01
- 関連ADR: [0056](0056-tt-prefetch.md), [0067](0067-ft-dimension-512.md), [0089](0089-improvement-criteria.md), [0099](0099-nnue-dot-sdot.md), [0101](0101-movelist-uninit.md), [0122](0122-tooling-language-split.md)

## Context

[ADR-0109](0109-reference-parity.md)〜[0119](0119-g10-book.md)の追従が一巡し、探索の構造は
参照実装と同じになった。**次に伸ばせるのは速度である**（[ADR-0089](0089-improvement-criteria.md)
の3軸のうち1つ目）。

プロファイルを取り直した。深さ25、1スレッド、26050サンプル（13秒ぶん）。
`scripts/profile.sh` の既定は深さ19だった。追従で枝刈りが強くなり、深さ19
では探索が112msで終わる。サンプルが1.2秒ぶんしか取れなくなっていた
（[ADR-0122](0122-tooling-language-split.md)で既定を25へ上げた）。

| 箇所 | self時間 |
|---|---|
| NNUEのFT更新（`nnue_acc.rs:82`） | 25.2% |
| NNUEの隠れ層（`nnue_acc.rs:91`） | 9.5% |
| `partial_insertion_sort`（`movepick.rs:753`） | 5.6% |
| `score_quiets`（`movepick.rs:750`） | 4.5% |
| `attackers_to` | 7.2% |
| `attacks::attacks` | 6.9% |
| `Tt::probe` | 3.0% |
| `libsystem_malloc` | 2.4% |

**いちばん大きいのはNNUEだが、そこを削る本命（FTのi8量子化）は評価値が変わる**。
[ROADMAPの候補](../ROADMAP.md#候補)にある「量子化の再検討」がそれで、SPRTで棋力を
確かめる必要がある大きな仕事になる。

本ADRは別の枠を扱う。**評価値もノード数も1ビットも変えない改善を積む**。
[ADR-0099](0099-nnue-dot-sdot.md)（SDOT）と同じ扱いで、機能検証で一致を確かめ、
NPSだけを見る。

## 測り方の問題

**1件ずつでは測れない**。個々の候補は0.2〜0.7%で、NPSの測定誤差（機体の温度や背景の
負荷で数%動く）に埋もれる。SPRTにかけても+1 Elo未満で、既定条件では検出できない。

[ADR-0109](0109-reference-parity.md)の追従が「1群=1SPRT」を採ったのと同じ理由が立つ。
**挙動を変えない高速化は群でまとめ、群の合計をNPSで測る**。

群に入れる条件を決める。

- 機能検証（[ADR-0074](0074-feature-verification.md)）で全局面のノード数が一致すること。
  一致しないものは挙動を変えているので、この枠では扱わない
- プロファイルに根拠があること。「速そう」だけで入れない

## この環境で効かない手がある

**ソフトウェアprefetchは使えない**。[ADR-0056](0056-tt-prefetch.md)でTTのprobeへ入れ、
144局で-33.9・LLR -0.24で打ち切っている。Apple Siliconの統合メモリはレイテンシが小さく、
prefetch命令の利得が出なかった。

`score_quiets` は1手あたりhistoryを7回引く。continuation historyは巨大でランダム
アクセスなので、キャッシュミスが主因のはずだと考えたが、**同じ理由で効かない**。
候補から外す。

他エンジンの手法をそのまま持ち込めない例である。CLAUDE.mdの「その値が何に支えられて
いるかまで移す」は、定数だけでなく最適化の手法にも当てはまる。

## Decision

第1群として、ホットパスのヒープ確保を消す。

| 候補 | self時間 | 中身 |
|---|---|---|
| `refresh_top` の `Vec::with_capacity(64)` | 0.43% | NNUEの全計算で毎回確保。`NnueState` にバッファを持たせて使い回す |

`NnueState` に `scratch: Vec<u32>` を足す。`entries` と同時に借りられないので、
`std::mem::take` で取り出して戻す。takeは空Vecとの交換なので確保が起きず、戻すときに
容量が残る。

### 第2群: NNUEのaccumulatorから無駄なコピーを消す

| 箇所 | 消えるもの |
|---|---|
| `push` | 1024バイトのゼロクリア。`do_move` のたびに走るが、この値は一度も読まれない |
| `pop` | `Vec::pop` のdrop処理 |
| `ensure` | 512バイトの往復コピーを片道に |
| `refresh_top` | バイアスの要素ごと代入をやめ、境界チェックを256回から1回に |

`Vec::push`/`pop` をやめ、起動時に確保した領域を `top` 添字で使い回す。`acc` は前回の
残骸を残すが、`computed[c]` が偽の間は読まれないので挙動は変わらない。**この不変条件は
暗黙にせず、docコメントと `debug_assert!` 4箇所で固定する**。

確保量は `MAX_PLY + 16 = 144`。`push` は5箇所にあり、いずれも直後の再帰へ `ply + 1` を
渡す。再帰先の `search` と `qsearch` はどちらも冒頭の `ply >= MAX_PLY` で `push` する前に
返るので、積まれる最大は128段になる。

### 第3群: 探索ホットパスの間接参照と除算

| 箇所 | 消えるもの |
|---|---|
| `REDUCTIONS` の `OnceLock` | 指し手ごとのAcquireロード（aarch64では `ldar`）。`Worker::new` で1回だけ取る |
| `stack: Vec<StackEntry>` | 添字アクセス71箇所の境界チェック。`Box<[StackEntry; MAX_PLY + 10]>` で長さが定数になる |
| `lmp_limit` の除算 | 除数が実行時に決まる `udiv`（12〜20サイクル）。`u32` なので `/2` は `>>1` と同値 |
| `score_quiets` の `check_sq` | 512バイトの初期化。`Bitboard` は `u128` でニッチがなく `Option<Bitboard>` が32バイトになる。`[Bitboard; 16]` と `u16` マスクに分けて258バイトへ |

`REDUCTIONS` は `f64::ln` を含むので const 化できない。**値を定数配列として焼き込むのも
避ける**。1ulpの差で `as i32` の切り捨てが変わり、探索が変わりうる。

### 測定: 群でまとめないと見えなかった

**単独ではどれも検出できなかった**。

| 群 | 単独でのNPS |
|---|---|
| 第1群 | 測定不能（0.43%） |
| 第2群 | -0.18%、-0.22% |
| 第3群 | +0.99%（振れ±8%の環境） |

第2群が見えないのは意外だったが、計算が合う。1ノードは約660ns（1.5M nps）で、1024バイトの
memsetはL1内で10ns程度である。誤差（±1.5%）と同じオーダーになる。

3群を合わせ、定跡生成を止めた静かな環境で7周測った。

```
| バイナリ | NPS（7周の平均） | 比 |
| base | 1,544,732 | — |
| cand | 1,586,612 | +2.71% |
```

**7周すべてでcandがbaseを上回った**（偶然なら1/128）。baseの振れが1,493,870〜1,563,173、
candが1,565,190〜1,600,294で、範囲が重ならない。平均の差だけでなく分布が分離している。

### 残る候補

| 候補 | self時間 | 見立て |
|---|---|---|
| `Shared` のfalse sharing | 1スレッドでは0% | アトミック7個が合計28バイトで同一キャッシュラインに乗る。`stop` は全スレッドが全ノードで読み、`nodes` は2048ノードごとに `fetch_add` で書く。**`Threads=4` 以上で測らないと意味がない。第4群として別に扱う** |
| `MovePicker` の候補手バッファ | 0.51% + 0.19%（再確保） | 毎ノードで `Vec::with_capacity(64)` を確保する。固定配列にすると `MAX_PLY`=128 の再帰で622KB積むので、スレッドのスタックサイズを明示する必要がある |
| `evaluate` の `concat` | 未計測 | 512バイトをゼロ初期化してから2回の `clip_to_u8` で全上書きする。`clip_to_u8` が `&mut [u8]` を取るためLLVMが完全上書きを証明できず、memsetが残っている可能性がある |
| `partial_insertion_sort` | 5.6% | 静かな手のソート。[ADR-0100](0100-movepick-argmax-simd.md)でargmaxはSIMD化したが本体は素のまま |
| `attackers_to` | 7.2% | `see_ge` 2.17%、`mate_1ply` 1.76%、`update_check_info` 1.37%、`is_mate_move` 1.37% に分散。呼び出し側が必要とする情報は部分的なので、全部を計算しない道がありうる |
| `generate_board_moves` の駒種分岐 | 2.66% | 駒種ごとに単相化すれば分岐が消えるが、**指し手の生成順が変わる**。ムーブオーダリングが変わるのでこの枠から外れ、SPRTが要る（2026-08-01オーナー判断で見送り） |

## Consequences

- 3群で+2.71%が得られた。**群でまとめる判断が正しかった**。単独ではどれも誤差の内側で、
  1件ずつ測っていたら「効果なし」と誤って棄却していた
- **どの群がどれだけ効いたかは分からない**。単独測定はすべて誤差の内側だったので、
  切り分けの手がかりがない。1件ずつ測れないことの代償である。次に同じ枠で積むときも、
  同じ判断を繰り返すことになる
- 機能検証で全局面のノード数が一致することを毎回確かめる。一致しなければ、挙動を変えて
  しまっているので設計を見直す
- prefetchを候補から外したことで、メモリアクセスの改善はデータ構造の変更（量子化、
  レイアウト）に絞られる。この環境では命令レベルのヒントが効かない
- 群でまとめて測るため、どの候補がどれだけ効いたかは分からない。効果が出なかったとき、
  群のどれが足を引っ張ったかを切り分けるには測り直しが要る。1件ずつ測れないことの代償である
