# 0124: 挙動を変えない高速化を群でまとめて測る

- Status: proposed
- Date: 2026-08-01
- 関連ADR: [0056](0056-tt-prefetch.md), [0067](0067-ft-dimension-512.md), [0089](0089-improvement-criteria.md), [0099](0099-nnue-dot-sdot.md), [0101](0101-movelist-uninit.md), [0122](0122-tooling-language-split.md)

## Context

[ADR-0109](0109-reference-parity.md)〜[0119](0119-g10-book.md)の追従が一巡し、探索の構造は
参照実装と同じになった。**次に伸ばせるのは速度である**（[ADR-0089](0089-improvement-criteria.md)
の3軸のうち1つ目）。

プロファイルを取り直した。深さ25、1スレッド、26050サンプル（13秒ぶん）。
`scripts/profile.sh` の既定は深さ19だったが、追従で枝刈りが強くなり、深さ19では探索が
112msで終わってサンプルが1.2秒ぶんしか取れなくなっていた（[ADR-0122](0122-tooling-language-split.md)で
既定を25へ上げた）。

| 箇所 | self時間 |
|---|---|
| NNUEのFT更新（`nnue_acc.rs:82`） | 25.2% |
| NNUEの隠れ層（`nnue_acc.rs:91`） | 9.5% |
| `partial_insertion_sort`（`movepick.rs:753`） | 5.6% |
| `score_quiets`（`movepick.rs:750`） | 4.5% |
| `attackers_to` | 7.2% |
| `attacks::attacks` | 6.9% |
| `Tt::probe` | 3.0% |
| `libsystem_malloc` | 2.4% |

**いちばん大きいのはNNUEだが、そこを削る本命（FTのi8量子化）は評価値が変わる。**
[ROADMAPの候補](../ROADMAP.md#候補)にある「量子化の再検討」がそれで、SPRTで棋力を
確かめる必要がある大きな仕事になる。

本ADRは別の枠を扱う。**評価値もノード数も1ビットも変えない改善を積む。**
[ADR-0099](0099-nnue-dot-sdot.md)（SDOT）と同じ扱いで、機能検証で一致を確かめ、
NPSだけを見る。

## 測り方の問題

**1件ずつでは測れない。** 個々の候補は0.2〜0.7%で、NPSの測定誤差（機体の温度や背景の
負荷で数%動く）に埋もれる。SPRTにかけても+1 Elo未満で、既定条件では検出できない。

[ADR-0109](0109-reference-parity.md)の追従が「1群=1SPRT」を採ったのと同じ理由が立つ。
**挙動を変えない高速化は群でまとめ、群の合計をNPSで測る。**

群に入れる条件を決める。

- 機能検証（[ADR-0074](0074-feature-verification.md)）で全局面のノード数が一致すること。
  一致しないものは挙動を変えているので、この枠では扱わない
- プロファイルに根拠があること。「速そう」だけで入れない

## この環境で効かない手がある

**ソフトウェアprefetchは使えない。** [ADR-0056](0056-tt-prefetch.md)でTTのprobeへ入れ、
144局で-33.9・LLR -0.24で打ち切っている。Apple Siliconの統合メモリはレイテンシが小さく、
prefetch命令の利得が出なかった。

`score_quiets` は1手あたりhistoryを7回引く。continuation historyは巨大でランダム
アクセスなので、キャッシュミスが主因のはずだと考えたが、**同じ理由で効かない。**
候補から外す。

他エンジンの手法をそのまま持ち込めない例である。CLAUDE.mdの「その値が何に支えられて
いるかまで移す」は、定数だけでなく最適化の手法にも当てはまる。

## Decision

第1群として、ホットパスのヒープ確保を消す。

| 候補 | self時間 | 中身 |
|---|---|---|
| `refresh_top` の `Vec::with_capacity(64)` | 0.43% | NNUEの全計算で毎回確保。`NnueState` にバッファを持たせて使い回す |

`NnueState` に `scratch: Vec<u32>` を足す。`entries` と同時に借りられないので、
`std::mem::take` で取り出して戻す。takeは空Vecとの交換なので確保が起きず、戻すときに
容量が残る。

### 第2群以降の候補

実装が中規模なので分ける。着手のたびにこのADRへ追記する。

| 候補 | self時間 | 見立て |
|---|---|---|
| `MovePicker` の候補手バッファ | 0.51% + 0.19%（再確保） | 毎ノードで `Vec::with_capacity(64)` を確保し、静かな手が多いと伸ばしている。`MoveList` は[ADR-0101](0101-movelist-uninit.md)でスタック化済みなのにここは残った。固定配列にすると `MAX_PLY`=128 の再帰で622KB積むので、スレッドのスタックサイズを明示する必要がある |
| `generate_board_moves` の駒種分岐 | 2.66% | 盤上の自駒を1つずつ回し、駒ごとに `attacks()` を呼ぶ。駒種が毎回変わるので分岐予測が外れる。駒種ごとにビットボードを回せば分岐が消える。参照実装もそうしている。ループのセットアップが14回に増える代償があるので、測って決める |
| `partial_insertion_sort` | 5.6% | 静かな手のソート。[ADR-0100](0100-movepick-argmax-simd.md)でargmaxはSIMD化したが本体は素のまま |
| `attackers_to` | 7.2% | `see_ge` 2.17%、`mate_1ply` 1.76%、`update_check_info` 1.37%、`is_mate_move` 1.37% に分散。呼び出し側が必要とする情報は部分的なので、全部を計算しない道がありうる |

## Consequences

- 第1群だけではNPSに現れない。0.43%は測定誤差の内側にある。**malloc呼び出しが減ることは
  確実なので入れるが、効果の確認は群がまとまってからになる**
- 機能検証で全局面のノード数が一致することを毎回確かめる。一致しなければ、挙動を変えて
  しまっているので設計を見直す
- prefetchを候補から外したことで、メモリアクセスの改善はデータ構造の変更（量子化、
  レイアウト）に絞られる。この環境では命令レベルのヒントが効かない
- 群でまとめて測るため、どの候補がどれだけ効いたかは分からない。効果が出なかったとき、
  群のどれが足を引っ張ったかを切り分けるには測り直しが要る。1件ずつ測れないことの代償である
