# 0165: BonaPiece集合をブロック単位のレイアウトへ変える

- Status: accepted
- Date: 2026-08-15
- 関連ADR: [0074](0074-feature-verification.md), [0151](0151-speedup-sweep.md), [0156](0156-bucket-accumulator-cache.md), [0164](0164-bona-piece-bitset.md)

## Context

[ADR-0164](0164-bona-piece-bitset.md)はBonaPiece集合の構築から分岐と
テーブル引きを消したが、速度は誤差内（+0.17〜0.26%）にとどまった。
原因はそのADRで特定してある。**律速は命令数ではなく、ビットセットへの
read-modify-writeの回数だった。**

集合は25語（`[u64; 25]`）の連続ビットセットで持っていた。BonaPieceの
盤上ブロックは81ビットで、64の倍数ではない。**どのブロックも語をまたぐので、
1ブロックを置くのに2〜3語のRMWが要る。** 盤上18ブロックで40〜60回になり、
駒を1枚ずつ回していた頃の42〜46回と変わらなかった。

## 選択肢と比較

### 案A: ブロックごとに独立した語を持つ

集合を19個の `u128` に分ける。手駒が1ブロック（BonaPiece 0..89）、盤上が
9カテゴリ×2色で18ブロック（各81ビット）になる。**どのブロックも語を
またがないので、構築は代入だけで済み、差分を取るときもRMWが要らない。**

`FinnyEntry.bits` は200バイトから304バイトへ増える。1件が768バイトから
832バイトになり、162件で121.5KBから131KBになる。M4のL1d（128KB）を
わずかに超える。

### 案B: ブロックを64ビット境界へ詰め直す

81ビットのブロックを128ビット境界でなく64ビット境界へ並べ直せば、
語あたりの無駄が減る。採らない。**BonaPiece番号と格納位置の対応が
崩れるので、差分から特徴インデックスを復元する計算が要る。** 案Aは
`block_base(b) = F_PAWN + 81*(b-1)` の1式で済む。

## Decision

案Aを採る。**実測は+1.07% NPS**（2026-08-15）。

### 測定

方向を入れ替えた7周の交互測定を、暖機の有無で2組取った。同一バイナリの
対照も挟んである。

| 測定 | cand の優位 |
|---|---|
| base先行（暖機なし） | +0.91% |
| cand先行（暖機なし） | +1.07% |
| base先行（暖機あり） | +1.27% |
| cand先行（暖機あり） | +1.01% |
| 対照（暖機なし） | 2本目が +1.47% |
| 対照（暖機あり、前） | 2本目が −0.34% |
| 対照（暖機あり、後） | 2本目が −1.10% |

**4回すべてでcandが正で、値は+0.91〜1.27%に収まる。** 対照は暖機後に
負へ振れており、順序効果ではcandの優位を説明できない。ADR-0151の群N
（4回すべて正で+1.17%を採用）と同じ判定になる。

絶対値は測定回をまたいで2,021,705から1,962,000まで下がった。熱による
低下で、ADR-0151の「測定回をまたいだ絶対値の比較はしない」がここでも
当てはまる。交互測定の内側の比だけを使っている。

### プロファイルでの裏取り

同条件（深さ25・1スレッド・2000Hz）で取り直した。

| 箇所 | ADR-0164適用後 | 本ADR適用後 |
|---|---|---|
| `refresh_top`（関数） | 8.05% | 7.05% |
| 集合の構築（`nnue_acc.rs:291`） | 4.08% | 1.83% |

**構築行は2.25ポイント減り、関数全体では1.0ポイント減った。** 差の
1.25ポイントは差分抽出のループへ移っている。反映済み集合の更新を同じ
ループへ畳んだためで、代わりに304バイトのコピーが1本消えている。
関数全体の1.0ポイントはNPSの+1.07%と整合する。

### 出力が変わらないことの根拠

ブロックの並びはBonaPiece番号の昇順と一致する。手駒（0..89）の次に
`F_PAWN` から81ずつ盤上ブロックが続く並びで、`BOARD_CATEGORIES` の順が
`F_PAWN`・`F_LANCE`… と同じであることがこれを保証する。

したがって差分の走査順は語で区切っていた頃と変わらず、**`adds`・`subs` は
これまでと同じ並びで `ft_update` へ渡る。** 配列がバイト単位で同一なので、
加算順序の可換性を持ち出すまでもなく結果は一致する。

検証は3段で行った。

- 並びの前提を `board_categories_match_bona_order` で固定した。全カテゴリで
  `board_base` と `block_base` が一致し、最後のブロックの81升で `FE_END` を
  使い切ることを確かめる
- 集合の一致を300局面×2視点で照合した（`bona_piece_bits_matches_one_by_one`）。
  正解器は `for_each_bona_piece` で、視点側と相手側を入れ替える故障注入で
  このテストが実際に落ちることも確認した
- 機能検証（[ADR-0074](0074-feature-verification.md)）は深さ13・20で全4局面の
  ノード数・評価値・最善手が一致した

## Consequences

- `FinnyEntry` が768バイトから832バイトになり、162件で131KBになった。
  M4のL1d（128KB）を超える。**それでも速くなったのは、実際に触るのは
  現局面の玉位置の1件だけで、162件を舐める経路がないためである。**
  [ADR-0156](0156-bucket-accumulator-cache.md)が測った局所性（差分の平均6.93行）は
  この変更で動かない
- BonaPieceの並びに依存するコードが1つ増えた。`block_base` は
  「盤上ブロックが81ずつ規則的に並ぶ」ことを式で使う。前提が壊れたら
  `board_categories_match_bona_order` が落ちる
- ADR-0164と合わせて、`refresh_top` は着手前の8.12%から7.05%になった。
  NPSでは通算+1.2〜1.3%にあたる。速度1%あたり3.5 Elo（10+0.1、
  [ADR-0159](0159-ft-width-1024.md)の換算）では4〜5 Elo相当である
- 残る大きな項目は `MovePicker::next`（18.65%）と `evaluate`（17.43%）である。
  起草時はこれを「ADR-0151が測って候補外」と書いたが、**命令アドレス単位で
  プロファイルを帰属させ直すと違っていた**（2026-08-15、同日中に訂正）。
  ADR-0151が測ったのは `partial_insertion_sort` の挿入方法（群M）と
  prefetch（ADR-0056経由）で、呼び出しの入口・出口、表引きの境界検査、
  clipの命令選択は手つかずだった。**合わせて+2〜3%の余地が残っている。**
  候補はROADMAPへ置いた
- 「self時間の大きい行はもう手が尽きた」と関数単位のプロファイルだけで
  判断すると間違える。**帰属先が呼び出し行に集まると、その内側の構造も
  ADRの記述も見えなくなる。** 行単位・命令単位まで落として初めて、
  `next` が1手返すたびに2,720バイトのフレームを確保していることや、
  ソートの時間の大半が分岐予測ミスであることが見えた
