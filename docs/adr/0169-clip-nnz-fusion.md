# 0169: 活性の構築と非ゼロチャンクの列挙を1パスにまとめる案を棄却する

- Status: rejected
- Date: 2026-08-15
- 関連ADR: [0151](0151-speedup-sweep.md), [0159](0159-ft-width-1024.md), [0164](0164-bona-piece-bitset.md), [0167](0167-nnue-kernel-instructions.md), [0168](0168-ft-dim-reorder.md)

## Context

FT1024の差し引きは[ADR-0168](0168-ft-dim-reorder.md)の並べ替えで−8.8 Elo
まで縮んだ。**黒字まで3.3%、H1採択まで5.1%である。** どこから取るかを
プロファイルで探す（並べ替え後、深さ25・1スレッド・24,344サンプル）。

| 箇所 | self時間 |
|---|---|
| `evaluate` 合計 | 24.29% |
| ├ `forward_hidden`（第1層が主） | 14.69% |
| └ `clip_to_u8` | 7.23% |
| `refresh_top` | 9.79% |
| `apply_range` | 2.87% |

**第1層の列駆動は2段構えになっている。** `clip_to_u8` がアキュムレータを
clipped ReLUに掛けて活性を書き（FT1024で両視点2KB）、`find_nnz` がその
2KBを読み直して非ゼロを含む4列チャンクの添字を作る。書いたばかりの値を
読み直す形である。

## 選択肢と比較

### 案A: 活性を作りながら数える

`clip_to_u8` のループで、clipした値がレジスタにあるうちにチャンクの
非ゼロ判定を取る。`find_nnz` は64バイト単位で判定を組むので、clipの
ループも64要素単位にすれば同じ形に乗る。**2KBの往復とループ1本が消える。**

### 案B: `refresh_top`（9.79%）を削る

玉が動いた視点の全計算である。[ADR-0156](0156-bucket-accumulator-cache.md)の
玉位置キャッシュと[ADR-0165](0165-bona-block-layout.md)のブロック配置が
入っており、残るのは `ft_update` のメモリ帯域そのものになる。FT1024では
特徴1つあたり1KBを読むので、削る余地が見えない。

### 案C: 後段のL1を半減する（`1024x16x32`）

第1層の演算が半分になり、14.69%の大半が浮く。ただし2026-08-13の
オーナー判断で保留している（Stockfishで実績のある後段の形を保ちたい）。
学習からやり直しになる点もコストになる。

## Decision

**案Aを実装して測り、棄却した。** 案Bは削る先が見えず、案Cはオーナー判断で
保留中である。案Aはエンジン内で完結し、評価値も変わらないので、まず測る
対象として素直だった。

**着手前の見立ては「数%」だった。** `find_nnz` は512チャンクを32回の
ループで走査し、1回あたり15命令ほど使う。第1層本体（159.7チャンク ×
8命令）に対して4割弱にあたるので、その一部でも消えれば黒字ラインの
3.3%に届く計算だった。

## 測定（2026-08-15）

`clip_and_scan` を書き、`evaluate` がアキュムレータを直接渡す経路
（`forward_from_acc`）を通した。連結ベクトルを作ってから通す経路との
ビット一致はテストで確かめている。探索も一致した（深さ16、2局面）。

| バイナリ | NPS（ノード数固定200万・6周） | 差 |
|---|---|---|
| 融合なし | 1,569,098 | — |
| **融合あり** | 1,565,217 | **−0.25%** |

**誤差の範囲で、利得はない。** プロファイルでも `evaluate` は24.29%から
24.57%へ動かなかった。

**消えたはずの往復は、もともと隠れていた。** 融合版では `clip_to_u8` に
付いていた6.49%が、アキュムレータを読む行へそのまま移った。律速は
書いた活性の読み直し（L1キャッシュ上の2KB）ではなく、**アキュムレータ本体の
読み出し**（両視点4KB、i16）である。`find_nnz` の走査はその待ち時間に
隠れており、消しても表に出てくるものがなかった。

## Consequences

- **命令数やメモリ往復の削減が速度に結びつかない例は4件目になった。**
  [ADR-0164](0164-bona-piece-bitset.md)のBonaPiece集合、
  [ADR-0167](0167-nnue-kernel-instructions.md)のclip飽和命令化と
  popcount表引き、そして本ADRである。**NNUE推論はメモリ待ちが律速で、
  命令を減らす方向の改善は一巡した**と見てよい
- コードは入れない。利得がない以上、`evaluate` から第1層までの経路を
  2本持つ理由がない
- **残り3.3%の取り先は案Cか、容量側になる。** 案Cは後段の形を変える
  判断が要る。容量側は[ADR-0168](0168-ft-dim-reorder.md)が見つけた
  死んだ次元（FT1024で147次元が完全にゼロ、513次元がゼロ率0.95以上）を
  活かす線で、速度ではなくノード効率で差し引きを黒字にする
- 速度側で残る未着手は出力バケット（[ADR-0137](0137-output-buckets.md)）と
  利きの差分テーブル（[ADR-0148](0148-effect-table.md)）だが、どちらも
  第1層とアキュムレータには効かない
