# 0070: 開発をPRベースにし、変更の種別でマージ条件を分ける

- Status: accepted
- Date: 2026-07-27
- 関連ADR: [0027](0027-sprt-framework.md), [0068](0068-sprt-driven-versioning.md), [0069](0069-release-notes-automation.md)

## Context

これまでmainへ直接コミットしてきた。1人開発では回っていたが、
2つの理由で限界が見えている。

第1に、変更の性質によって必要な検証が違う。探索や評価関数の変更は
SPRTでH1採択されなければ取り込まない（[CLAUDE.md](../../CLAUDE.md)）。
一方、リファクタや文書更新にSPRTは要らず、CIが通れば十分である。
この違いが運用として明示されておらず、その都度の判断に委ねられている。

第2に、[ADR-0068](0068-sprt-driven-versioning.md)でバージョン番号の
位置（MINOR/PATCH）を変更の種別に対応させた。種別を判定する場所が
要る。判定をコミット時の裁量に任せると、番号の意味がぶれる。

自動化の土台としてもPRが要る。マージ時にバージョンを上げる、
リリースノートを組み立てる（[ADR-0069](0069-release-notes-automation.md)）
といった処理は、変更の種別が機械的に読める形になっていて初めて書ける。

## 選択肢と比較

### 案A: mainへの直接コミットを続ける

手数が最も少ない。ただし種別の判定が裁量に残り、自動化の足場もない。

### 案B: すべての変更をPR経由にする

変更の種別をPRテンプレートで宣言し、種別ごとにマージ条件を変える。
1人開発でもPRを作る手間が増えるが、判断の基準が仕組みに移る。

### 案C: 棋力向上だけPR、それ以外は直接コミット

SPRTが要る変更にだけPRを使う。手数は案Bより少ないが、
「どちらの経路で入れるか」という判断が新たに増える。例外を設けない
という方針（ADR-0068のPATCH）と噛み合わない。

## Decision

案Bを採る。すべての変更をPR経由にし、テンプレートを2種類置く。

### PRの種別とマージ条件

| 種別 | 対象 | マージ条件 | バージョン |
|---|---|---|---|
| 棋力向上 | 探索・評価関数・時間管理など、強さが変わる変更 | CIが緑、かつSPRTでH1採択 | MINOR |
| その他 | リファクタ、文書、ツール、CI、依存更新 | CIが緑 | PATCH |

`.github/PULL_REQUEST_TEMPLATE/` に2つのテンプレートを置く。
棋力向上のテンプレートには、SPRTの条件と結果（対局数、W-D-L、
Elo±CI、LLR）を書く欄を設ける。この欄がそのままコミットの
`SPRT:` トレーラとRESULTS.mdの記録になる。

GitHubは複数テンプレートを `?template=` で選ぶ仕様のため、既定の
テンプレートは置かない。PRは `gh pr create --template strength.md`
のように種別を明示して作る。既定を用意して片方に倒すと、
選択が省略されて種別の宣言が形骸化する。

種別の判定はテンプレートの選択で決まる。どちらか迷う変更は
「その他」に倒す。棋力が変わらないと思って入れた変更が実は
影響していた場合は、次の棋力向上PRのSPRTで検出される。

### ブランチ運用

mainへの直接pushをやめる。GitHubのブランチ保護でmainを保護し、
PR経由のみを許す。作業ブランチの命名は縛らない。

保護は管理者にも適用する（`enforce_admins: true`）。1人開発では
オーナーが自分自身であり、バイパスを許すと保護が常時素通りになる。
緊急時は保護設定を一時的に解除して対処する。

設定は次のとおり。

- PR必須。承認は求めない（自分のPRは自分で承認できないため）
- ステータスチェック `check`（CIのジョブ名）を必須にする
- force pushとブランチ削除を禁止する

なおブランチ保護はpublicリポジトリか、privateならGitHub Pro以上でしか
使えない。本リポジトリは2026-07-27にpublicへ切り替えた。それに先立ち、
229件のコミットに残っていた勤務先ドメインのメールアドレスを個人の
ものへ書き換えている。

### バージョンの更新

当面は手作業で上げる。PRのマージ前に、そのPR内でCargo.tomlの
バージョンを更新する。MINORのときはマージ後にタグを打つ。

自動化は仕組みが動いてから足す。マージ時にバージョンを上げる
ワークフローは、mainへの自動コミットとブランチ保護の折り合いを
つける必要があり、先に運用を固めたほうが設計しやすい。

## Consequences

- 1人開発でもPRを作る手間が増える。代わりに、変更の種別と
  マージ条件が仕組みとして残る
- 種別の判定がPRテンプレートに移る。コミット時の裁量が減り、
  ADR-0068のバージョン番号の意味が保たれる
- CIはすでに `pull_request` で走る（`.github/workflows/ci.yml`）。
  追加の設定は要らない
- SPRTの実行はローカルのまま。CIで対局を回す構成は持たない。
  結果をPRへ貼る運用にする
- mainへの直接pushができなくなる。管理者も例外ではない。
  緊急時は保護設定を一時的に解除して対処する
- 自動化は段階的に進める。第1段階はテンプレートとブランチ保護、
  第2段階はマージ時のバージョン更新とタグ付けとする
