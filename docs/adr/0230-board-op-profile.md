# 0230: 探索時間に占める盤面操作の割合を測り、盤面の持ち方を決める材料にする

- Status: accepted
- Date: 2026-10-16
- 関連ADR: [0229](0229-roadmap-visible-focus.md), [0148](0148-effect-table.md), [0099](0099-nnue-dot-sdot.md), [0139](0139-mate1ply-in-search-retry.md)

## Context

[ADR-0229](0229-roadmap-visible-focus.md)の注力の段階1は、盤面の持ち方を決める段である。
Bitboardをやめる案も含めて、測定で決めると書いた。判断の分かれ目は1つで、
**盤面操作が探索時間の大きな割合を占めるか**である。大きければ配列へ寄せる案を本気で
検討する。小さければBitboardのまま利き数を併せ持つ試作に進む（issue #742）。

これまでのプロファイル（`hmwr profile`）はself時間の上位を出すだけだった。
盤面操作の関数は呼び出し元へインライン展開されるので、self時間の表では
`NnueState::evaluate` や `MovePicker::init_quiets` に溶けて見えない。
処理の種類ごとの割合を出すには、インライン展開まで遡った呼び出し連鎖が要る。

## 測り方

### 条件

| 項目 | 値 |
|---|---|
| バイナリ | origin/mainの53250e0。`CARGO_PROFILE_RELEASE_DEBUG=1` と `-C target-cpu=native` でビルドした |
| 評価関数 | `pool1_2ep_reorder.hmwr`（`hmwr/config.py` の現行） |
| サンプリング | samply、2000Hz |
| 置換表 | 256MB（エンジンの既定） |
| 機械 | Apple M4 Pro（性能コア10・効率コア4） |

局面は2組で測った。組み込みの4局面は序盤から中盤に偏る。終盤寄りの組として、
`openings/profile_late_positions.txt` を足した。100手以上の対局から12局面を採った。

| 組 | 局面 | 深さ（1スレッド） | 深さ（8スレッド） |
|---|---|---|---|
| 序中盤 | 組み込みの4局面 | 27（局面3は24） | 27（局面3は24） |
| 終盤寄り | `profile_late_positions.txt` の12局面 | 18 | 16 |

終盤寄りの8スレッドだけ深さを16に下げた。深さ18では局面9と局面11が
60秒を超えて終わらなかった（1スレッドでは43秒と15秒で終わる）。

計測の間、別のワーカーのテストと仮想マシン（CPU 30%前後）が動いていた。
load averageは1.4〜4.5だった。本ADRの数字は割合なので、背景の負荷で全体が
遅くなっても大きくは動かない。

### 分類の規則

`hmwr profile report --categories` が分類する。atosの `-i` でインライン展開を
含む呼び出し連鎖を復元し、葉から根へ辿って最初に当たった種類へ1サンプルを数える。
例外が2つある。

- 1手詰めと `do_move`・`undo_move` は外側を優先する。1手詰めの中の `is_legal` は
  1手詰めとして数える
- `attackers_to` と `attacks` は下請けとして扱う。呼び出し元の種類へ数える

表の「うち利き」は、その種類の時間のうち `attackers_to`・`attacks` の中にいた分である。
利きを差分で持つと置き換えられる見込みの部分に当たる。

### 再現の手順

```
CARGO_PROFILE_RELEASE_DEBUG=1 RUSTFLAGS="-C target-cpu=native" cargo build --release -p himawari-usi
hmwr profile record <バイナリ> --depth 27 --threads 1 --out data/profile/adr0230-builtin-t1.json.gz
hmwr profile record <バイナリ> --depth 18 --threads 1 \
  --positions openings/profile_late_positions.txt --out data/profile/adr0230-late-t1.json.gz
hmwr profile report data/profile/adr0230-late-t1.json.gz <バイナリ> --categories
```

プロファイルは `data/profile/adr0230-*.json.gz` に、デバッグ情報付きのバイナリは
`data/bin/adr0230-prof/` に置いた。

## 測定から言えること

**盤面操作は探索時間の3分の1から4割を占める**。小さいとは言えない。
仮に盤面操作がすべてただになっても、NPSは1.5倍（序中盤）から1.75倍（終盤寄り）
が上限である。

**ただし、時間の中身はBitboardが得意な処理に偏っている**。いちばん大きいのは
指し手生成の12〜14%で、行き先の集合を語単位で作る処理である。配列へ寄せると、
ここは速くならず遅くなる見込みが高い。`do_move`・`undo_move` は4%弱で、
盤面の持ち方を変えて得られる余地は小さい。

**利きを引く処理は14〜23%あり、最大の使い手は1手詰めである**。終盤寄りでは
1手詰めだけで11%を利きの計算に使う。SEEが2〜3%で続く。ここは利きを差分で持てば
表を引くだけになる。

比べる相手は、利きを差分で持つ維持費である。[ADR-0148](0148-effect-table.md)の
工程3では、`do_move`・`undo_move` で追従させるだけでNPSが7.19%落ちた（2026-08の
エンジン、使う側なし）。利きを引く時間の半分を表引きへ置き換えられれば、
浮く分は序中盤で約8%、終盤寄りは約11%になる。維持費とは同じ桁にあり、終盤寄りでは上回る。

ここから言えるのは次の2点である。

1. **配列へ全面的に寄せる案は、測定からは支持されない**。最大の盤面操作である
   指し手生成がBitboard向きで、配列に寄せると損をする側に回る
2. **Bitboardを残して利きを併せ持つ案なら、NPSで元を取れる見込みがある**。
   維持費（約7%）と、置き換えられる利きの計算（14〜23%）が同じ桁にある。
   1手詰めとSEEを表引きへ書き換えるところまで含めて測る必要がある

副次の観察が2つある。

- 8スレッドでも割合はほぼ変わらない。終盤寄りの指し手の順序付けだけが17.8%から
  22.0%へ増えた。共有のhistoryへの書き込みの取り合いが疑わしいが、測っていない
- 8スレッドの固定深さの探索は、終盤寄りの2局面で1スレッドより遅くなった。
  深さ18で60秒を超えた

## Decision

**Bitboardを残し、利きを差分で併せ持つ**（2026-10-17オーナー判断）。
配列へ全面的に寄せる案は採らない。

根拠は上の測定である。盤面操作は探索時間の32〜43%で、最大は指し手生成だった。
ここはBitboardが得意な処理である。利きを引く時間（14〜23%）と、利きの維持費
（ADR-0148の−7.19%）は同じ桁にあり、使う側まで作れば元を取れる見込みがある。

次の一手は試作である。[ADR-0148](0148-effect-table.md)の `EffectTable` を
`do_move`・`undo_move` へ接続し、1手詰めとSEEを表引きへ書き換える。設計は
Issue #743（技巧と山田将棋の読解）をふまえ、試作の別ADRで決める。

### 合格の条件

本ADRは測定で、時間を使う実験を起動しない。試作に進むときは別のADRを起こし、
合格の条件をそこで書き切る。そのADRが比べる数字は2つある。

- 維持費: `do_move`・`undo_move` の割合の増分と、NPSの低下
- 浮いた分: 1手詰め・SEE・合法性判定の割合の減少

## Consequences

- `hmwr profile record` が `--threads` と `--positions` を受け付けるようになった。
  `hmwr profile report --categories` で処理の種類ごとの割合が出る。試作の前後で
  同じ表を並べられる
- 分類の規則は `hmwr/tools/profile.py` の `CATEGORIES` が持つ。関数名を変えたら
  規則も追従させる。追従を忘れると、その処理は「探索のその他」へ落ちる
- 割合はサンプリングの推定である。序中盤の8スレッドは58,291サンプルで、
  30%前後の項目の標準誤差は0.2ポイント程度にとどまる
- 見直しのトリガーは、評価関数の構造を大きく変えたときである。NNUEの推論の
  割合が動けば、盤面操作の割合も動く
