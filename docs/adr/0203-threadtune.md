# 0203: 動作環境の最適なスレッド数を、1コマンドの自己対局で決める

- Status: accepted
- Date: 2026-09-06
- 関連ADR: [0083](0083-windows-static-crt.md), [0122](0122-tooling-language-split.md), [0199](0199-roadmap-inventory.md), [0200](0200-thread-scaling.md), [0202](0202-smp-loss-diagnosis.md)

## Context

最適なスレッド数は動作環境で変わる。放流機のSurface Pro 9はPコア2＋
Eコア8の混成で、電力の壁もあり、開発機（M4 Pro）で測った曲線
（[ADR-0200](0200-thread-scaling.md)）をそのまま当てられない。いまは
6スレッドで動かしているが根拠はない（[ADR-0199](0199-roadmap-inventory.md)）。

オーナーの要望は「コマンド1つで様々検証して良い数字を出す」で、
別のバイナリではなく**1バイナリで完結する**ことである（2026-09-06）。
放流機にはPythonも開発環境もなく、配布物のzipだけがある。

## Decision

エンジン本体に `himawari threadtune ...` のモードを足す。引数なしなら
これまでどおりUSIエンジンとして動く。対局の相手は自分自身で、同じ
実行ファイルを子プロセスとしてUSIで起動する。探索の経路には触れず、
増えるのは埋め込みの開始局面（約90KB）だけである。

そのために、USIクライアント（`usi_engine`）と対局ループ（`game`）を
開発ツール側から `himawari-usi` のライブラリへ移した。依存はstdと
`himawari-core` だけなので、配布物の依存ゼロ
（[ADR-0122](0122-tooling-language-split.md)）は保つ。引数の解析は
clapを使わず手で書く。開発ツールは同じパスで再輸出して参照する。

### 測り方

2段で絞る。NPSだけでは決められない。Lazy SMPはスレッドを増やすほど
効率が落ち（[ADR-0200](0200-thread-scaling.md)）、混成コアでは遅い
スレッドが足を引く。最後は自己対局で決める。

1. **持続クロックでのNPS**。最大スレッド数で数分回して温度を落ち着かせて
   から、候補ごとに `go movetime` で数局面を読ませ、合計NPSを取る。
   温度の漂いを均すため、候補を昇順→降順の往復で測る。NPSが直前の候補
   から8%以上伸びない候補は落とす（増やしても速くならないなら、効率の
   損失で負ける）
2. **自己対局で登る**。現在の設定（`--current`、省略時はNPS最良）を起点に、
   隣の候補と対局する。同時1局で、両側が交互に指すので同じ機械で公平に
   比べられる。信頼区間が0を跨がなければ勝った側へ進み、跨げば
   **少ないほうを採る**（熱と電力が少ない側に倒す）。予算（`--hours`）を
   対局の数で割り、1組あたりの局数を決める

開始局面は配布物に含まれないので、`start_sfens_ply24` の先頭1,000局面を
実行ファイルへ埋め込む。

### 出力

NPSの表、対局ごとのElo±CI、推奨のスレッド数を1行で出す。電源モードと
AC接続の注意も出す。混成コアでは電源の設定のほうがよく効くためである。
`--pairs` で1組の局数を直接決められ、`--nps-only` はNPSの表だけで止まる。

### 精度の限界

10+0.1で1局30秒強なので、1時間に約110局しか回らない。4時間で
440局、隣り合う2組へ分けると1組220局でEloの幅は±35になる。
それより小さい差は区別できず、「少ないほう」の規則で決まる。
一晩（8時間以上）を勧める。

## 追記: 放流機での実測（2026-09-08オーナー報告）

Surface Pro 9（論理12）で走らせたところ、推奨は12スレッドだった。
12で放流すると、それまで一度も出ていなかった切れ負けが出た（2局）。
6へ戻して運用している。

棋譜を読むと、終盤は残り時間ぎりぎりで指しており（残り21秒で20秒）、
安全の余白はNetworkDelay2の1.12秒しかない。開発機で残り12秒の局面を
1〜14スレッドで読ませても実消費は計画に対して最大+30msで、エンジン内の
停止は遅れていない。最後の手は2秒以上超過しており、疑うのはエンジンの
外である。12スレッドで論理コアを全部埋めると、指し手をサーバへ中継する
クライアントのプロセスが動けず、数秒待たされる。6なら6本空いている。

**この道具は自分が中継役なので、その遅れを見られない**。候補の上限の
既定を論理コア−2に変え、READMEに理由を書いた。時間管理側の余白を
外の遅れに合わせて自動で広げる案は、別のADRで扱う。

## Consequences

- 配布物は1ファイルのまま。使い方はREADMEの「最適なスレッド数を測る」に置く
- `himawari-tools` が `himawari-usi` に依存する。ツール側のパス
  （`himawari_tools::game` など）は再輸出で変えていない
- 放流機で測った結果はADR-0199のConsequencesの「放流機の最適スレッド数」
  へ記録する
