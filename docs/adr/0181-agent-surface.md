# 0181: エージェントの作業面を実態へ合わせ、機械で判定できる規律は設定へ移す

- Status: accepted
- Date: 2026-08-20
- 関連ADR: [0098](0098-agent-permissions.md), [0149](0149-experiment-runner.md), [0178](0178-textlint-gate.md), [0180](0180-hmwr-cli-in-python.md)

## Context

エージェントが毎回読むのは `CLAUDE.md` と `.claude/` である。ここが実装と
ずれると、規約どおりに動くほど遠回りになる。

Opus 5 を対象にプロンプト監査を回したところ、12件の指摘が出た。重いものは
3つある。

1つ目は、`.claude/settings.json` の許可リストが呼び方と噛み合っていない。
文書はどこでも `hmwr ...` と書くのに、許可されているのは `./bin/hmwr ...` の
3件だけだった。PATH経由で呼ぶ限り一致しないので、読むだけの操作でも毎回
確認が入る。ADR-0098が待機の停止を解いた目的が、入口の変更（ADR-0180）で
半分戻っていた。

2つ目は、`CLAUDE.md` が消えたディレクトリを指していた。「`scripts/` の各
スクリプトが `data/logs/<名前>.log` へ追記する」と書いてある。ADR-0180で
`scripts/` に残るのは `setup.sh` だけになった。パス形式も
`data/logs/<領域>-<名前>.log` へ変わっている。同じファイルの別の節が正しい
形を書いているので、1つの文書が同じ規則を2通りに述べる状態だった。lintの
入口も `npm run lint` と `hmwr doc lint` の2本立てで、前者は「入口は `hmwr`」
という自分の規則に反していた。

3つ目は、規則の本文に事件の記録が埋まっていた。「2026-08-14の点検で4件
見つかった。存在しないビルドfeature、2世代前のネットを指す取得コマンド…」の
ような経緯が約30行あり、毎リクエスト運ばれていた。強調も30箇所あり、
どれが本当に効かせたい規則か区別できなくなっていた。

監査は旧世代モデル向けの定型文（think step by step、prefill、`budget_tokens`、
出力語数の上限）を1件も見つけていない。himawari-cliスキルが載せるコマンド
28個とフラグも、`--help` を叩いて全件実在を確かめた。壊れていたのは、
実装の変化に文書と設定が追随していない部分だけである。

## 選択肢と比較

### 案A: 文書だけ直す

ずれた記述を実態へ合わせ、経緯をADRへ移し、強調を絞る。

安く済む。ただし `cargo fmt` やコミット本文の括弧のように、機械で判定できて
違反すると痛い規則が散文のままになる。散文の規則は文脈が長くなるほど薄まる。

### 案B: 文書を直し、機械で判定できる規律は設定へ移す

案Aに加えて、`.claude/settings.json` へ許可・確認・拒否の規則とStopフックを
置く。散文には「何が止まるか」だけを1箇所書く。

規則の重複が減り、違反が確実に止まる。設定を書く手間と、フックが毎回走る
時間（`cargo fmt --check` で0.9秒）を払う。

### 案C: 規律をすべてフックにする

textlintもフックで止める。

`hmwr doc lint` は10.7秒かかる。文書を触らないセッションでも毎回払うことに
なり、CIが既に同じ検査を持っている（ADR-0178）。採らない。

## Decision

案Bを採る。

### 許可リスト

呼び方を実態へ合わせ、読むだけの操作を足した。PATH経由の `hmwr` を12件、
`./bin/hmwr` を5件置く。対象は次の12個である。

```
--dry-run  doc lint  env       verify      bench       sprt show
sprt wait  ci wait   net eval  book stats  profile report  league summary
```

`doc lint` は `--fix` で文書を書き換えるので、厳密には読み取り専用ではない。
それでも許可する。書き換わるのはgit管理下のMarkdownだけで、CIが同じ検査を
持ち、取り消しが `git checkout` で済むからである。ADR-0098が禁じたのは任意
コード実行と、mainへ取り込む判断であって、この種の可逆な整形ではない。

`Bash(cargo run --release -p himawari-tools --bin verify:*)` は残す。
README.mdが直接呼ぶ形を逃げ道として案内しており、死んだ規則ではない。

### 確認と拒否

`CLAUDE.md` が「確認するのは破壊的で戻せない操作だけ」と定めているので、
force push・履歴の書き換え・`data/` の削除は `deny` ではなく `ask` に置く。
`ask` は `allow` より優先されるため、将来許可リストを広げても抜けない。

`Cargo.toml` も `ask` にした。「触らない」の対象はrelease-pleaseが管理する
バージョン欄であって、依存の追加まで禁じる意図ではない。ファイル全体を
`deny` にすると正当な依存追加が通らなくなる。

`deny` は `git push origin main` の1件だけにした。mainへの直接pushは、
確認を通してでも行わない唯一の操作である。前方一致の規則なので
`git push origin HEAD:main` のような書き方は素通りする。これは事故を減らす
柵であって、証明ではない。

### Stopフック

セッションの終わりに2つ検査する。どちらも失敗したら終了コード2で止め、
理由をエージェントへ返す。

| 検査 | 目的 | 実測 |
|---|---|---|
| `cargo fmt --check` | CIの `rustfmt --check` で落ちる前に気づく | 0.9秒 |
| コミット本文の入れ子括弧 | release-pleaseが黙って止まるのを防ぐ | 0.1秒未満 |

括弧の検査は `origin/main..HEAD` の範囲だけを見る。全履歴を見ると過去の
コミットで毎回止まり、他人の作業も巻き込む。判定は `\([^()]*\(` の一致で
行い、全角の括弧と単独の半角括弧は通す。

コミット直前ではなくセッションの終わりに置いた理由がある。標準のコミットは
本文を `$(cat <<'EOF' ... )` で包むので、コマンド文字列を見る限り本文の
括弧と包みの括弧を区別できない。コミット後の `git log` を読めばこの曖昧さは
消える。

### 文書

`CLAUDE.md` は267行から260行になった。減った分より、内訳のほうが重要である。
事件の経緯（約30行）を落とし、強調を29箇所から12箇所へ絞り、消えた
`scripts/` への参照とlintの二重入口を直した。「valid loss」と「検証損失」で
割れていた呼び名は「検証損失」へ揃えた。

himawari-cliスキルには `hmwr sprt net` と `hmwr env` を足した。前者は
「ビルドを固定して評価関数だけ差し替える」という、名前から推測しにくい
機能である。

残した重複もある。PGOをペアに使わない、機能検証の意味、教師データ分布と
物差しの4件は `CLAUDE.md` とスキルの両方にあるが、内容が一致していて実際に
機能している。矛盾していない重複は直さない。

## Consequences

規約どおりに動くほど確認が減る。ADR-0098が測った「読み取り専用の操作を
許可する」原則が、ADR-0180後の入口でも成立する。

散文の規則が3つ減り、そのぶん確実になった。`cargo fmt` とコミット本文の
括弧は、忘れても止まる。

払うものが2つある。Stopフックは文書だけのセッションでも約1秒走る。設定を
変えたセッションではフックが読み込まれないので、`/hooks` を開くか開き直す
必要がある。

見直すトリガーは3つある。`hmwr` にサブコマンドが増えて読むだけの操作が
許可リストから漏れたとき、`cargo fmt --check` が1秒を大きく超えたとき、
そして次のモデル世代へ移るときである。プロンプトはモデルごとの成果物なので、
ある世代で効いている記述が次の世代では重りになる。
