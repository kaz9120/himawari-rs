# 0239: 利きの持ち方を6案で比べ直し、都度作る利きの地図を先に、技巧型のバイト表を次に測る

- Status: accepted（案Eはmainへ入れた。案Bは測って棄却した）
- Date: 2026-10-17
- 関連ADR: [0232](0232-effect-table-prototype.md), [0230](0230-board-op-profile.md), [0148](0148-effect-table.md), [0151](0151-speedup-sweep.md), [0237](0237-effect-count-inputs.md), [0029](0029-mate-search.md), [0159](0159-ft-width-1024.md)

## Context

[ADR-0232](0232-effect-table-prototype.md)の試作は合格しなかった。位置の逆引きの表
（`EffectTable`）を探索のワーカーに持たせ、戻しで同じ差分を当て直した（案U2）。
維持費は−8.7%、表引きで浮いた分は+3.2%で、正味は−4.3%だった。合格の線は−1.0%である。
`EffectTable::update` は単独で探索時間の5.24%を占めた。
同ADRの事前登録では、次に案U3（旧値を積む戻し）、その次に案T2（技巧型のバイト表）を測る順だった。

オーナーの方針（2026-10-17）は、利きの更新の高速化に全力を注ぐことである。
Bitboardをやめる案まで含めて、あらゆる実装を検討する。表引きで取り返す側も、
勝負の選択肢として真剣に検討する。

今の実装には重い点が3つある。

1. 戻しで同じ更新を当て直している。進めと戻しで2回払う
2. 逆引きの表 `to_sq`（81升×位置のBitboard）を、利きが増減した升ごとに1ビットずつ書き換えている
3. 飛び駒の利きを丸ごと計算し直している。伸びた方向だけを足す形ではない

U3は1つ目しか直さない。本ADRは、U3とT2の2択に限らず、実装の選択肢を総当たりで比べ直す。
そのうえでADR-0232の事前登録の順を組み替える。

問いは「どの利きの持ち方を、どの順で測れば、段階1を最短で閉じられるか」である。

## 材料

### 1手で触る量（数えた値）

差分更新の費用は、1手で触る駒と、利きが増減した升の数で決まる。これを数えた。
時間は測っていない（ADR-0233のSPRTが開発機を使っているため、計測は控えた）。

数え方は次のとおりである。`openings/actdump_positions.txt` の200局を3手おきに再生し、
王手のかかっていない局面の全合法手を1手ずつ進めた。盤の再生にはPythonのcshogiを使い、
利きは本エンジンと同じ定義で数えた。触る駒の集合は `EffectTable::update` と同じで、
移動元・移動先の駒と、そこへ利く飛び駒である。序中盤は対局の24〜83手目、
終盤寄りは84手目以降とした。

| 量（1手あたりの平均） | 序中盤 | 終盤寄り |
|---|---|---|
| 局面数 | 3,900 | 3,758 |
| 静かな手: 触る駒 | 2.49 | 2.57 |
| 静かな手: 利きが増減した升（逆引きの書き換え回数） | 10.6 | 12.6 |
| 　うち飛び利きの伸縮 | 5.1 | 6.4 |
| 駒取り: 触る駒 | 2.54 | 2.58 |
| 駒取り: 逆引きの書き換え回数 | 13.2 | 13.6 |
| 　うち飛び利きの伸縮 | 9.0 | 8.3 |
| 駒打ち: 逆引きの書き換え回数 | 4.8 | 4.3 |
| 全合法手の書き換え回数の分布（p50 / p90 / p99） | 6 / 16 / 23 | 5 / 15 / 28 |

書き換え回数は中央値の5〜6から、上位1割では15を超える。今の更新はこの回数だけ
ループを回すので、ループの終わりの分岐が予測しにくい（推測）。

### 1手詰めの候補が、利きの地図だけで落ちる割合（数えた値）

「利きの地図」を、手番側の駒の利きの和集合A1と、2枚以上利いている升の集合A2の
2枚のBitboardと定義する。今の `mate_1ply` の候補（玉の近傍と桂の王手升への移動・打ち）
のうち、地図だけで詰みでないと決まる割合を数えた。

落とす規則は2つで、どちらも今の `is_mate_move` と同じ値を返す。

- 玉に取られる: 玉の隣へ動かす手で、移動先がA2にない（打つ手ならA1にない）。
  移動元が手番側の飛び駒の利きの終点にあるときは、背後から利きが通りうるので落とさない
- 逃げ場が残る: 玉の近傍で、相手の駒がなくA1にない升を逃げ場とする。逃げ場から
  「動かした駒の利き（玉を除いた占有で引く）」と移動先を除いて、まだ残れば落とす。
  移動元が飛び駒の利きの終点にあるときは、開き王手で埋まりうるので落とさない

手を指しても手番側の利きが増えるのは、動かした駒の利きと、移動元を空けて伸びる飛び利きだけである。
玉を除いて伸びる利きは、指す前から王手がかかっていない限り生まれない。
どちらの規則も、増える分を上から押さえているので、落とした候補は必ず詰みでない。

| 量 | 序中盤 | 終盤寄り |
|---|---|---|
| 1局面あたりの候補 | 4.6 | 10.1 |
| 地図だけで落ちる候補 | 95.8% | 94.0% |
| 　うち玉に取られる | 69.2% | 59.9% |
| 地図で空いている逃げ場（1局面あたり） | 3.67 | 3.44 |
| 空いている逃げ場が1つ以上ある局面 | 99.7% | 98.3% |

今のコードも「玉に取られる」候補は落としている。ただし候補ごとに `attackers_to` を引く。
残りの約3割の候補は `is_mate_move` まで進み、逃げ場ごとに `attackers_to` を引く。
地図があれば、候補1つは数命令で落ち、`is_mate_move` へ進むのは4〜6%になる。

### SEEが取り合いなしで決まる割合（数えた値）

移動先に相手の利きがなく、移動元の背後からも相手の飛び利きが通らない手では、
SEEは取り合いに入らず `captured − threshold >= 0` で決まる。その割合を数えた。

| 手の種類 | 序中盤 | 終盤寄り |
|---|---|---|
| 静かな手 | 68.9% | 59.2% |
| 駒取り | 21.1% | 35.3% |
| 駒打ち | 46.4% | 46.5% |

### 参照実装の読解

技巧のC++版とやねうら王のソースを読んだ（2026-10-17のHEAD）。ビルドと実行はしていない。

技巧の `ExtendedBoard` は、色ごと・升ごとに利き数1バイトと飛び利きの方向1バイトを持つ。
詰め物と駒の配列を含めて608Bである。手ごとに448Bを複写し、戻しは添字を戻すだけにする
（`position.cc:339`・`:514`）。短い利きは5段×3筋のパターンをSSEで加減算し、1回あたり12命令ほどで済む。
飛び利きは方向ビットに沿って1升ずつ切る・延ばすスカラーのループである。
使い手は評価関数（駒・升・利き数の特徴）が主で、ほかに玉の移動の合法性判定と1手詰めがある。
1手詰めは8近傍の利き数を `pshufb` でまとめて読み、打つ手は1MiBの事前表で絞る。
指し手生成とSEEには使っていない（どちらもソースにTODOが残る）。

やねうら王の `LONG_EFFECT_LIBRARY` は利き数と方向を484Bで持ち、戻しは同じ差分を逆符号で当て直す。
既定のエディションでは無効で、有効にするのは利き数を評価関数の入力に使う `HALFKPE9` などに限る。
`config.h:293` には「do_move()は少し遅くなる」とだけ書かれ、数字はない。
1手詰めと合法性判定のためだけに維持費を払う構成を、参照実装は既定で採っていない。

技巧のRust版（第33・34回のアピール文書）は、u128のBitboardに利き数の表と、利きを使う1手詰めを
載せている。SIMDは自動ベクトル化で、Apple M1/M2でも動く。本エンジンと同じ組み合わせの先行例である。

山田将棋は配列盤で、升ごとに利く駒の背番号ビット（64bit）と方向ビットを持ち、
進め・戻しのたびに差分を当てる（第21回の原文）。使い道は手生成とオーダリングで、
費用の数字は書かれていない。海底（第27回）は利き数と方向、馬歩（第22回）は背番号の64bitを持つ。
どれも費用の数字はない。

## 選択肢と比較

### 案A: 今の表（位置の逆引き）＋旧値を積む戻し（ADR-0232の案U3）

進めるときに、書き換えた `to_sq` の行の旧値と `from_sq` の旧値を積む。戻しは積んだ値を書き戻すだけで、
利き先の計算をしない。重い点の1つ目だけを直す。

### 案B: 技巧型のバイト表を複写で戻す（ADR-0232の案T2）

色ごと・升ごとに利き数1バイトと飛び利きの方向1バイトを持つ（324B、詰め物込みで約384B）。
手ごとに前の表を複写し、戻しは添字を戻すだけにする。短い利きはパターンの加減算、
飛び利きは方向ビットに沿った伸縮で更新する。重い点の3つをすべて直す。
攻め駒の位置は持たない。必要なら方向ビットとBitboardの線から引き直す。

### 案C: 駒背番号のビット（山田将棋・ADR-0148のオーナー案）

升ごとに利いている駒の背番号を64bitで持つ。書き換え回数は案Aと同じで、1回が64bitになる。
複写なら648Bに背番号の配列が付く。駒の背番号の管理が `Position` の不変条件に加わる。

### 案D: 利きのBitboardをバイトへ展開し、利き数をSIMDで加減算する

利き数だけを持つ（162B、詰め物込みで192B）。触る駒の新旧の利きのBitboardの差を
バイト列へ展開し、81升分をまとめて加減算する。戻しは複写である。
AVX-512は `vpmovm2b` 1命令で64升を展開できるが、NEONは表引きと比較で1ベクトル3命令ほどかかる。
触る飛び駒の集合は、移動元・移動先からの `attackers_to` 相当で毎回求める。

### 案E: 維持せず、必要なノードで利きの地図を作る

上で定義した地図（A1・A2）を、使うノードで1回だけ作る。歩と桂は集合のシフトでまとめて引き、
ほかは駒ごとに表を引いて足す。玉から遠い短い駒は、玉の近傍へ届かないので省ける。
維持費はゼロで、`Position` も `Worker` も変えない。

### 案F: Bitboardをやめて配列盤へ

柿木・なのは・山田将棋の形である。利きの表から指し手を生成できれば、指し手生成の
「うち利き」（5〜6%）が消える。一方で、ADR-0230で最大の盤面操作だった指し手生成
（12〜14%）は、行き先の集合を語単位で作るBitboardの得意な処理である。駒打ちの生成は
特に配列で遅くなる。盤・指し手生成・1手詰め・SEE・合法性判定・perftの検証を
すべて書き直す。

根拠は案ごとに次のとおりである。

- A: 進めはU2と同じ約170に、書き換えた行の旧値を積む約25を足す。戻しは `from_sq` 2.5行と
  `to_sq` 12行を書き戻すだけで約50になる
- B: 384Bの複写はNEONの `ldp`/`stp` で各12回。短い利きは技巧と同じパターンの加減算を
  静かな手で2回、駒取りで3回。飛び利きの伸縮は表の「うち飛び利き」の5〜9升を1升約6命令で歩く

- D: 触る駒2.4個の新旧の利きの差を2本ずつ展開する。NEONは1本約30命令、
  触る飛び駒を探すのに約50命令かかる
- E: 歩・桂の集合シフト約20、短い駒10個ほど各約10、飛び駒5個ほど各約30で1色約250。
  玉から遠い短い駒を省くと約150になる

確認済みの数字は、U2の5.24%と−8.7%、「1手で触る量」の表だけである。ほかは推測である。

**速さだけなら、維持しない案Eがいちばん有利に見える**。1手詰めの節約の大半は
「候補を地図で一括して落とす」ことから来る。その地図は維持しなくても1ノード約200命令で作れる。
維持する表が案Eに勝てるのは、地図を作る費用（1手詰めの呼び出し1回あたり）が、
表の維持費（1手あたり）を上回るときだけである。
案Bの見込みは案Eと±2%の差に収まり、どちらが勝つかは測らないと分からない。

それでも維持する表は要る。段階3の利き数の入力（[ADR-0237](0237-effect-count-inputs.md)）は、
手ごとに「利き数が変わった升」が要る。都度計算では全升を数え直すことになる。
複写で戻す案Bなら、前の表が1つ下の段に残っているので、両者をSIMDで比べれば変わった升が出る。
技巧の評価関数はこの形で差分を取っている（`psq.cc:274-292`）。
やねうら王が利きの表を評価関数の入力のあるエディションでだけ有効にしているのも、同じ事情と読める。

## Decision

**事前登録の順を「案U3→案T2」から「案E→案B」へ組み替える**。

1. 第1段は案E（都度作る利きの地図）である。地図を1手詰めの絞り込み、SEEの取り合いなしの判定、
   玉の移動の合法性判定に使う。維持費がなく、`Position` と `Worker` の状態を増やさない
2. 第2段は案B（技巧型のバイト表を複写で戻す）である。同じ3処理を、地図の代わりに表から読む。
   案Eに対する正味と、段階3の土台としての費用を測る

決め手は2つある。案Eは、利きの表のどの案よりも維持費の見込みが小さく、取り返す側の大半を
維持なしで取れる。もう1つは、段階3が要る「利き数が変わった升」を、案Bだけが複写のついでに
安く出せることである。案Bの更新は重い点の3つをすべて直し、命令数の見込みは案U2の3分の1ほどである。

案Eを先にするのは、案Bの比べる相手を正しくするためでもある。表で浮く分の大半は、
表がなくても地図で取れる。案Bを素のmainと比べると、地図の効きを表の手柄に数えてしまう。

採らない案と理由は次のとおりである。

- 案A（U3）: 保留する。正味の見込みは序中盤が−3〜+1%となり、案Bより悪い。重い点の2つ目と3つ目が残る。
  攻め駒の位置を引ける利点は、SEEと指し手生成で合わせて2〜4%である。案Bが棄却され、
  位置の要る使い手が見つかったときに再開する
- 案C: 書き換え回数が案Aと同じで、背番号の管理が `Position` の不変条件を増やす。
  ADR-0148が採らなかった理由は変わらない
- 案D: NEONでは展開の費用が案Bの飛び利きの伸縮より重い。案Bの短い利きの更新の実装の一案として残す。
  AVX-512の機械では案Bと並べて測る価値がある
- 案F: 指し手生成で損をし、書き直しの範囲が最大である。見直しのトリガーは、案Bの表から
  指し手生成を引く試作で、Bitboardの生成より速いと測れたときである

### 統制: 木を変えない

どの段も、返す値を1ビットも変えない範囲に限る。1手詰めは候補の順を変えず、
地図や表で落とすのは詰みでないと決まった候補だけにする。ADR-0232と同じく、
固定深さのノード数の一致で正しさを確かめ、SPRTにはかけない。

### 仮説と固定するもの（実験の規律の4点）

1. 仮説: 1手詰め・SEE・玉の合法手は、維持しない利きの地図で大半を取り返せる。
   維持する表は、地図に対して正味で−1%以内に収まる
2. 動かす変数: 各段で足す1つだけ。読む値は上の表の比較である
3. 固定するもの: 評価関数（`hmwr/config.py` の現行）、局面の組（組み込みの4局面と
   `openings/profile_late_positions.txt`）、深さ（19と18）、置換表256MB、1スレッド、
   機械（開発機のM4 Pro）、交互測定の周回数（7周）。キューは止め、SPRTとほかのワーカーの
   ビルドが走っていない時間に測る
4. 事前登録: 下の「合格の条件」と「結果の読み方（事前登録）」

### 合格の条件

- Eloの判定: SPRTにかけない。探索の木を変えない変更なので、対局の差はNPSの差だけから来る。

- Elo以外の条件:

  - 1手詰めの返り値: 書き換え前の `mate_1ply` と、`mate_tests.rs` の全局面で同じ手を返す
  - ミクロな計測の検査値: 下の `hmwr bench board` の検査値が、比べる2本で一致する
  - 速さ（案E）: e0に対するe2のNPSが、2組の平均で+1.5%以上である。+1.5%はADR-0151の誤差の幅である
  - 速さ（案B）: e2に対するb2のNPSが、2組の平均で−1.0%以上である。

- 採否: 案Eは正しさと速さを満たしたら、e2までをmainへ入れる（fix型）。

ADR-0232では分類器が新しい関数を知らず、表の更新が「探索のその他」へ落ちた。

### ミクロな計測の入口（`hmwr bench board`）の仕様

今の `hmwr` には、手の進め戻しと表の更新だけを測る入口がない。`hmwr bench` は探索ごと測るので、
評価関数の推論（23〜29%）と置換表が混ざり、背景の負荷で±1.5%動く。
`crates/tools` の `perft` は `hmwr` から呼べず、探索のワーカーが持つ表を通らない。
次の入口を足す（実装は手順0のPRで行う）。

- コマンド: `hmwr bench board <バイナリ...> [--positions パス] [--depth N] [--runs N] [--log 名前]`。
  バイナリは `crates/tools` の新しい `boardbench` で、`hmwr build pair` が `bench` と一緒に作る。
  2本以上を並べると、`hmwr bench` と同じく交互に測る
- 手の進め戻しを1か所に集める: 探索のワーカーが使う進め戻しの関数を、`Position` と利きの状態を
  持つ小さな型（仮に `SearchBoard`）へ移す。`Worker` も `boardbench` もこの型を呼ぶ。
  e0ではこの型が `Position` だけを包む
- 歩き方: 各局面から、合法手を全幅で深さN（既定2）まで進め戻す。葉ではさらに駒取りだけを1手進め、
  静止探索の手の混ざり方に寄せる。局面の既定は組み込みの4局面と `openings/profile_late_positions.txt`
- 測る段: 同じ歩き方を4回回し、段ごとに足す処理を変える。1回目は進め戻しだけ。
  2回目は王手でない各ノードで `mate_1ply` を呼ぶ。3回目は各ノードの駒取りで `see_ge`（閾値0と−90）を呼ぶ。
  4回目は各ノードの擬似合法手で `is_legal` を呼ぶ。差を回数で割り、1回あたりのnsを出す
- 出力: 周ごとに1行のJSON。段ごとのns、呼び出し回数、検査値を持つ。検査値は `mate_1ply` の返す手、
  `see_ge` と `is_legal` の返り値を混ぜたハッシュで、比べる2本で一致しなければ終了コード1で止まる
- 所要: 1周1〜2秒を目安に深さと局面を選ぶ。1コアだけを使う
- 読み方: 進め戻し1回あたりのnsの差が維持費、`mate_1ply` 1回あたりのnsの差が1手詰めの効きである。
  NPSの計測の前に、見込みの命令数と桁が合っているかを確かめる

### 計測前の追記（2026-10-18）

第1段の実装で、上の仕様から3点を変えた。合格の条件と結果の読み方は変えていない。
どれも計測を回す前に書いている。

1. `boardbench` の段を5つにした。`is_legal` の前に「擬似合法手を生成するだけ」の段を挟み、
   `is_legal` の1回あたりは、その段との差で出す。生成の時間を `is_legal` に数えないためである。
   進め戻しの値は指し手生成を含む。2本の差は維持費になる
2. SEEと玉の移動が読む地図は、`StateInfo` の遅延スロットに置いた。ノードで初めて読むときに作り、
   以後は同じノードで使い回す。王手のpin情報（ADR-0151群K）と同じ形である。
   SEEは指し手の順序付けと探索の枝刈りの両方から呼ばれるので、呼び出しごとに作ると
   1ノードで何度も作ることになる。「`Position` を変えない」は守れなかった。
   スロットの分だけ `StateInfo` が64B増え、`do_move` で未計算の印を書く。この費用はe2の値に載る
3. 1手詰めの地図は `mate_1ply` の入口で作る。手番側の地図で、銀・金・玉は相手玉の周り5×5の駒だけを数える。
   使うのは玉の周り3×3の値と飛び利きの集合だけで、そこは盤全体の地図と一致する

e0は手順0のコミット（`6eb57c2`、PR #842）である。e1・e2はブランチ `fix-adr0239-effect-map` に積んだ。

正味の大半は1手詰めから来た。e1だけで終盤寄り+3.18%、e2で足したSEEと玉の移動は

## 第2段の計測前の追記（2026-10-18）

b1の実装を、計測を回す前に書いておく。合格の条件と結果の読み方は変えていない。

- 表は `EffectCounts`（`crates/core/src/effect_count.rs`）で、色ごとに利き数と飛び利きの方向を
  96バイトずつ持つ。全体で384Bになる。`SearchBoard` が段の配列を持ち、進めるときに前の段を
  16バイトずつ複写してから差分を当てる。戻しは段を下げるだけで、null moveでは表に触らない
- 差分は5つの処理で当てる。動かした駒の利きを外す。取られた駒の利きを外す。
  空いていた移動先へ届いていた飛び利きを、移動先の奥で切る。移動元へ届いていた飛び利きを、
  空いた移動元の奥へ延ばす。最後に動かした駒の利きを移動先に足す。
  短い利きも飛び利きも、利く升をBitboardで求めて1升ずつ数を足し引きする。
  SIMDの加減算（技巧の5段×3筋のパターン）は使っていない
- 最初の版は `boardbench` の進め戻し1回あたりで+27nsだった。複写が `memcpy` の呼び出しになり、
  短い利きが `attacks` の呼び出しを経ていたので直した（`e3d0c27`）。直した後は+21nsである。
  探索の1ノードが500ns前後なので、維持費は−4%前後と見込む。止める線（−5.0%）に近い
- 正しさは、全合法手を深さ2まで辿って差分と作り直しを突き合わせるテストで確かめた。
  デバッグビルドでは、`SearchBoard` が進め戻しのたびに作り直しと突き合わせる。
  `hmwr verify adr0239-maint --depth 13` は2組の全局面でe2と一致した

## 測定（第2段、2026-10-18）

### 読み

維持費は見込み（−3〜−4%）を少し外れて−4.84%だった。表で浮く分は+1.54%で、
見込みの「地図に対して±2%」の範囲には入ったが、維持費を取り返すには3倍ほど足りない。

浮く分が小さいのは、比べる相手のe2がすでに大半を取っているからである。
1手詰めの候補は地図で94〜96%落ちるので、表で速くなるのは地図を作る費用だけになる。
SEEと玉の移動は、地図でも表でも探索全体での割合が小さい（e2で+0.1%ほど）。
案Eを先に測ったのは、まさにこの切り分けのためだった。表で浮く分の大半は、表がなくても取れる。

表を残す理由だった段階3の入力（利き数が変わった升）は、都度計算で作る。
入力が要るのは評価関数を呼ぶノードだけで、表の維持は全ノードで払う。
費用の比べ方はADR-0237で改めて決める。

案Dで短い利きの更新を速くしても、維持費のうち複写と飛び利きの伸縮は残る。
正味の差は3.4%で、短い利きの分だけで埋まる大きさではないと見る（推測）。案Dの試作はしない。

## Consequences

- ADR-0232の事前登録（案U3→案T2）は本ADRが置き換える。ADR-0232はsupersededにする。
  試作のブランチ `fix-adr0232-effect-prototype` の使う側の書き換え（`see_ge_with` の分割など）は、
  第2段で読み直して使える部分を使う
- 案Eが入ると、利きの情報が要る探索の改善（[ADR-0233](0233-check-extension-hanging.md)〜
  [ADR-0236](0236-entering-king-path.md)）は、表がなくても地図を引ける。各ADRの「ADR-0232が合格しない場合」の
  経路が地図で安くなる
- 案Bが入ると、`Worker` に手ごとの表の段が増える。深さ128で約48KBになり、M4のL1（128KB）の
  一部を使う。実際に触るのは探索中の深さの分だけである
- 案Bのバイト表は、短い利きの更新にSIMDを使う。開発機のNEONと選手権のx86（AVX2・AVX-512）の両方で
  動く書き方が要る。技巧のRust版は自動ベクトル化で両方に対応した。最初はそれに倣い、
  足りなければ `core::arch` の命令を機械ごとに書く
- 見積もりの大半は推測である。ミクロな計測で1回あたりのnsが出たら、本ADRの表へ実測を足して較正する
- 見直しのトリガーは2つある。評価関数の推論の割合が大きく変わったときは、浮く分と維持費の比が動く。
  段階3の入力に利き数以外（攻め駒の位置など）が要るときは、案Aと案Cを測り直す
