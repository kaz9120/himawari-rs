# 0067: FT次元を256から512へ拡大する

- Status: accepted
- Date: 2026-07-26
- 関連ADR: [0034](0034-nnue-architecture.md), [0037](0037-nnue-file-format.md), [0039](0039-trainer-v1.md), [0066](0066-halfkp-factorizer.md)

## Context

学習データを19.9億局面へ拡大した結果、モデルの容量が制約に変わった。
根拠はtrain lossとvalid lossの動きにある。

| ネット | データ量 | train loss | valid loss | 差 |
|---|---|---|---|---|
| halfkp_370M | 3.7億 | 0.48580 | 0.50949 | 0.0237 |
| halfkp_1900M_fact | 19.9億 | 0.48697 | 0.49513 | 0.0082 |

読み取れることが2つある。

第1に、train lossがまったく下がっていない。データを5.4倍にしても
0.48580から0.48697へ動いただけで、むしろわずかに上がった。
3210万パラメータのHalfKP 256x2-32-32が表現できる下限に達している。

第2に、汎化ギャップが0.0237から0.0082へ縮んだ。過学習は解消した。

つまりvalid lossはtrain lossへ漸近しつつあり、データを足しても
改善の余地は残り0.008しかない。次の一手はモデル容量になる。

P7で構造を純粋HalfKPでフリーズしたのは、当時のデータ量では容量を
増やすと過学習したためである。その前提が19.9億局面で崩れた。

## 選択肢と比較

### 案A: データをさらに増やす

start_time=1695872823の127ファイル（約10億局面）が未取得で、
29.9億まで増やせる。取得は安い。ただし改善の上限が
train loss 0.487で頭打ちになるため、伸びは逓減する。

### 案B: エポック数を増やす

同じデータを2周以上する。train lossが飽和しているので下がる余地が
小さく、汎化ギャップが再び広がる方向に働く。

### 案C: output bucket（局面フェーズで最終層を分岐）

チェスでは駒数が単調に減るためフェーズ指標として使える。将棋は
取った駒が持ち駒になるだけで総数が減らないので、同じ設計を
そのまま持ち込めない。手数や盤上駒数など別の指標を設計する必要が
あり、それ自体が独立した検討になる。

### 案D: FT次元 256→512

FTのパラメータが3210万から6420万へ倍増する。NNUEの表現力は
ほぼFTが決めるため、容量拡大の効果が最も大きい。
評価計算のコストも倍増し、NPSが落ちる。

### 案E: 隠れ層拡大（32→64）

パラメータ増は l2 が 512×32 から 1024×64 へ増える程度で、
FTの3210万に対して小さい。容量律速の解消には足りない。

## 切り替え方法の比較

512に一本化するか、256と併存させるかも決める必要がある。
NPSと評価精度のトレードオフは局面や持ち時間で変わりうるため、
当面は両方を測れる形が望ましい。

### 方法1: 定数を書き換えて512に一本化する

変更は最小だが、256へ戻すにはコードを書き換えることになる。
両者を並べて比較できない。

### 方法2: コンパイル時のfeatureで切り替える

`FT_OUT` を `#[cfg(feature = "ft512")]` で分岐させる。
定数であることは変わらないので、実行時のコストはゼロである。
配列サイズもアキュムレータの構造も現状のまま動く。
バイナリは2種類になるが、`selfplay` は `--baseline` と
`--candidate` に別々のパスを渡せるため、比較の運用にはむしろ合う。

### 方法3: 実行時に切り替える

`FT_OUT` を定数から変数にする。アキュムレータは
`[[i16; FT_OUT]; 2]` で探索スタックに埋め込まれているため、
ヒープ確保とインデックス計算が増え、NPSが落ちる。
const genericsで型パラメータ化する道もあるが、探索コード全体へ
型が伝播し、実行時に選ぶには結局enumでのディスパッチが要る。
得るものに対して代償が大きい。

## Decision

案Dを方法2で実装する。FT次元をコンパイル時featureで切り替え、
既定は256、`--features ft512` で512にする。

案Dの決め手は、容量律速の主因がFTにあることである。全パラメータ
3210万のうち、FTが3210万を占める（l2〜l4は合わせて1万7千）。
容量を増やすなら、まずFTを触るのが順序として正しい。

方法2の決め手は、実行時コストがゼロであることと、どちらが良いかを
まだ決められないことである。512がNPS低下を取り返せるかは、持ち時間や
局面の性質で変わりうる。一方に絞る判断は、複数の条件で測ってから
下したい。

実装は定数の分岐で済む。

```rust
#[cfg(not(feature = "ft512"))]
pub const FT_OUT: usize = 256;
#[cfg(feature = "ft512")]
pub const FT_OUT: usize = 512;
```

SIMDは `as_chunks::<16>()` によるレーン分割で書かれており、
16の倍数なら次元に依存しない。アキュムレータもスライス演算で
組んである。

学習側は `training/model.py` の次元を、PyO3モジュールが公開する
`himawari.FT_IN` `himawari.FT_OUT` `himawari.HIDDEN` から読む。
定数を二重に持たないので、推論と学習で次元の食い違う事故が起きない。
512で学習するときは `maturin build --features ft512` で作った
モジュールを入れる。

バイナリ名は両方とも `himawari` になるため、ビルド後に
`himawari-ft512` へ複製して保存する運用にする。取り違えは
`.hmwr` のヘッダにある次元チェックが弾く。

`.hmwr` はヘッダにアーキテクチャの次元を書き、不一致を読み込み
エラーにする（ADR-0037）。256のネットを512のバイナリで読む事故は
起きない。

nn.bin互換ローダ（`nnue_compat.rs`、ADR-0039）は256を前提に
書かれている。モジュールごと `cfg` で消す案も試したが、上位クレートへ
featureが伝播せず、`--features himawari-engine/ft512` だけでは
ビルドが通らなくなった。そこでモジュールは常に残し、`load_nn_bin` の
冒頭で `FT_OUT != 256` を検出してエラーを返す形にした。テストだけ
`#[cfg(all(test, not(feature = "ft512")))]` で外している。

NPSの低下は実測して記録する。評価計算のコストが倍増するため、
低下が大きければ探索の損が評価精度の得を上回りうる。判定はSPRTで
行う。

| 項目 | 256 | 512 | 比 |
|---|---|---|---|
| FTパラメータ | 3210万 | 6420万 | 2.00 |
| `.hmwr` サイズ | 64.2MB | 128.4MB | 2.00 |
| NPS（初期局面、1スレッド） | 1,245,532 | 760,107 | 0.61 |
| NPS（初期局面、8スレッド） | 8,985,950 | 5,806,781 | 0.65 |
| train loss（19.9億、factorizer込み） | 0.48678 | TBD | |
| valid loss（19.9億、factorizer込み） | 0.49513 | TBD | |

NPSは乱数ネットで測った。実ネットでは枝刈りの効き方が変わるため、
512の学習が済んだところで測り直す。

NPSが0.65倍ということは、実効的な探索深さが約0.6手ぶん浅くなる。
将棋では倍のNPSがおよそ+60〜70 Eloに相当するとされるので、
-40 Elo前後の損になる。512はこれを評価精度で取り返す必要がある。
valid lossに換算すると、19.9億での差0.0138が+243.8 Eloだった比率から、
おおよそ0.002の改善が損益分岐点になる。

## Consequences

- 評価ファイルが64MBから128MBへ倍増する。配布物の扱いは
  ADR-0060の方針（データは配布物に含めない）のままで変わらない
- アキュムレータのメモリが1手あたり倍になる。探索スタックの
  常駐量が増え、キャッシュ効率の落ちる可能性をもつ
- ビルドが2種類になる。CIは既定の256を回し、512は手元で確認する。
  featureは `himawari-engine/ft512` を上位クレートへ伝播させる
- 学習時間が延びる。19.9億局面の1エポックは150分から
  200分前後になる見込み
- NPS低下がSPRTで取り返せなくても、256を消さずに残す。持ち時間や
  局面によって有利不利の変わる可能性があるため、両方を測れる状態を
  当面は保つ。一本化の判断は複数条件での計測が揃ってから行う

## 結果（2026-07-26）

19.9億局面・factorizerありの同条件で学習し、SPRTで比較した。

| 項目 | 256 | 512 |
|---|---|---|
| train loss | 0.48678 | **0.48338** |
| best valid loss | 0.49513 | **0.49374** |
| 学習所要 | 149分 | 269分 |

train lossが0.0034下がった。データを5.4倍にしても動かなかった値が、
容量を倍にすると下がった。容量律速という診断は正しかった。

しかしSPRTは **-72.8 Elo [-96.1,-50.2]**（968局、LLR -2.96でH0採択）
だった。NPSが0.65倍になる損が、valid loss 0.00139の得を上回った。
事前の見積もりは-15 Elo前後だったので、実測はそれより60 Elo悪い。
10秒+0.1という短い持ち時間では、探索の浅くなる影響がより重く効く。

既定の256を維持する。512のバイナリ（`data/bin/himawari-ft512`）とネット
（`data/nets/halfkp_1900M_ft512.hmwr.best`）は残す。持ち時間を長くした
条件での再評価に備える。featureで切り替えられるようにした
判断は、この再評価を可能にする点で活きた。

次の方向は「容量を保ったままNPSを取り戻す」になる。FT重みのi8量子化
（ROADMAPの候補の「量子化の再検討」）はメモリ帯域を半減させるため、
512の重さを直接削れる。
