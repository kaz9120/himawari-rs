# 0100: 指し手の最大スコア探索をSoA＋SIMDにする

- Status: superseded（[0110](0110-g1-history.md)）
- Date: 2026-07-29
- 関連ADR: [0099](0099-nnue-dot-sdot.md), [0089](0089-improvement-criteria.md), [0025](0025-move-ordering.md), [0074](0074-feature-verification.md)

## Context

[ADR-0099](0099-nnue-dot-sdot.md)で取ったプロファイルの第2位が
`MovePicker::pick_best` で、self時間の17%を占めていた。NNUEの推論に
次いで重く、指し手生成（6%）や合法性判定（3.5%）より大きい。

`pick_best` は採点済みの手から最大スコアの1手を取り出す。

```rust
scored: Vec<(Move, i32)>,

fn pick_best(&mut self) -> Option<Move> {
    let mut best = 0;
    for i in 1..self.scored.len() {
        if self.scored[i].1 > self.scored[best].1 { best = i; }
    }
    Some(self.scored.swap_remove(best).0)
}
```

段階生成では、この呼び出しを手の数だけ繰り返す。n手すべてを取り出すと
比較はn(n-1)/2回になる。中盤の静かな手は100手を超えるため、1ノードで
5,000回近い比較が走る。

比較が重いのは回数だけが理由ではない。`(Move, i32)` を並べた配列では
スコアが8バイトおきに散らばる。1つのSIMDレジスタに載る有効な値が
半分になり、幅で稼げない。

## 選択肢と比較

### 案A: partial insertion sort（Stockfish方式）

生成時に閾値以上のスコアの手だけを挿入ソートし、取り出しをO(1)にする。
比較の総数は最も少ない。

同点の手の並び順が現在と変わる。挿入ソートは安定ではなく、閾値の
取り方でも順序が動く。指し手の順序が変われば探索の出力が変わり、
[ADR-0089](0089-improvement-criteria.md)の軸1（出力を変えない高速化）
から外れる。効果を測るにはSPRTで棋力ごと比べることになり、
速度の改善なのか順序の改善なのかを切り分けられない。

### 案B: 優先度付きキュー

ヒープで持てば取り出しはO(log n)になる。

nが100前後では定数倍が効き、線形走査より速くなる保証がない。同点の
順序も崩れる。案Aと同じ理由で軸1から外れる。

### 案C: SoA＋SIMDで最大値を探す

指し手とスコアを別の配列に分け、スコア列だけをSIMDで走査する。
アルゴリズムはO(n²)のまま変えない。

最大値を求める走査と、その値が最初に現れる位置を探す走査の2回に
分かれる。どちらも8要素ずつ進むため、1要素ずつの比較より速い。
同点は最小の添字を選ぶため、現在の `>` による走査と結果が一致する。

## Decision

案Cを採る。

決め手は出力が変わらないことである。案Aと案Bは比較回数そのものを
減らせるが、指し手の順序が変わるため探索の出力が動く。順序の変更は
それ自体が棋力に効く可能性があり、速度の改善と混ざると評価できない。
[ADR-0099](0099-nnue-dot-sdot.md)と同じく、まず出力を変えない範囲で
削り切る。

案Aは魅力的な候補として残る。ただし着手するなら「オーダリングの
変更」として単独で測るべきで、本ADRとは別の判断になる。

### 出力が変わらないことの根拠

`pick_best` の戻り値と、呼び出し後の配列の状態が現在と一致すればよい。

戻り値は最大スコアの手である。同点のときは、現在の実装が `>` で
比較するため最小の添字が残る。SIMD版も最大値と一致する最初の位置を
返すので同じになる。配列の状態は `swap_remove` をそのまま使うため
変わらない。指し手とスコアを2本の配列に分けても、同じ添字で
`swap_remove` する限り対応は保たれる。

一致は単体テストで守る。素直な線形走査との比較を、同点を多く含む
乱数列で長さ1〜39まで回す。SIMDの幅で割り切れない端数も通す。
最終確認は[ADR-0074](0074-feature-verification.md)の機能検証で、
4局面のノード数が変わらないことを見る。

### 計測

探索全体のNPSは861k→1071k（+24.4%、4局面・深さ19・1スレッド）。
機能検証では4局面すべてでノード数・評価値・最善手が変わらなかった。
SPRTは **+106.7 [+79.4,+135.4]**（574局、LLR +2.99でH1採択）。

self時間17%の除去だけなら1.20倍が上限で、実測の1.24倍はそれを超える。
スコア列だけを連続で走査するようになり、キャッシュラインの利用効率が
上がった分と考えている。

Elo/NPSの効率は[ADR-0099](0099-nnue-dot-sdot.md)と大きく違う。0099は
NPS +20.5%で+59.7 Elo、本ADRはNPS +24.4%で+106.7 Eloだった。95%CIは
接する程度で重ならない（0099の上限+80.2、本ADRの下限+79.4）。同じ
「NPSを上げる変更」でも効き方が揃わないことになる。原因は追えていない。
本ADRのbaselineは0099を含まないmainであり、両者を積んだ状態での
NPSは測り直しが要る。

## Consequences

`MovePicker` のフィールドが1本増える。`scored` への push は
`push_scored` に置き換わり、指し手とスコアを2本へ同時に積む。
片方だけを操作すると対応が崩れるため、追加も削除も必ず対で行う。
これは型では守られない。

アルゴリズムはO(n²)のままなので、手が極端に多い局面での比較回数は
減らない。効くのは定数倍だけである。ここが足りなければ案Aへ進む
ことになるが、そのときは出力が変わる前提で測り直す。

ヒープ確保（`Vec::with_capacity`）は残る。プロファイルではmallocが
1.4%を占めており、`MoveList` のゼロ埋め（memset 1.8%）と合わせて
別ADRで扱う。
