# 0058: 反復深化の次イテレーション開始を時間予測で抑止する

- Status: rejected（固定比率はADR-0059の係数積の粗い近似にすぎず、統合した）
- Date: 2026-07-25
- 関連ADR: [0021](0021-time-management.md), [0059](0059-easy-move-scaling.md)

## Context

floodgateに初参戦した（2026-07-24〜25、27局19勝8敗、レート3186）。
実戦棋譜を見ると、1手あたりの消費時間が想定を超えていた。

floodgateの持ち時間は300秒＋1手10秒加算である（CSAの
`Increment:10`）。現行の配分式（ADR-0021）は
`avail = 残り時間 / max(48 − game_ply/2, 16) + byoyomi + inc`
なので、初手のoptimumは `300000/47 + 10000 = 16.4秒` になる。

910戦（2026-07-25 00:00、Himawari勝ち）で後手Himawariが指した26手の
消費時間は、18, 21, 25, 22, 21, 18, 21, 24, 20, 46, 19, 27, 27, 21,
13, 26, 14, 20, 38, 21, 20, 18, 18, 21, 10, 0 秒だった。平均21.1秒で、
optimumの1.3倍にあたる。合計549秒に対し、使える総量は
`300 + 10×26 = 560秒` である。

search.rs:319 の反復深化ループは `stopped() || over_optimum()` で
終了を判定する。判定はイテレーション完了時にしか行われないため、
optimum直前に次のイテレーションを開始すると、そのイテレーションが
終わるまで走り続ける。この超過を止めるため、判定を
`elapsed >= optimum × 0.6` に変える案を検討した。

## 選択肢と比較

### 案A: 次イテレーション開始時に時間を予測して抑止する

イテレーション完了時の判定を `elapsed >= optimum` から
`elapsed >= optimum × ratio` に変える。変更は1か所で済む。

### 案B: 直前イテレーションの所要時間から次を見積もる

イテレーションごとの実測時間を記録し、`前回の所要 × 分岐係数`が
残り時間に収まるかを判定する。

### 案C: maximumを下げて対処する

`avail × 3` を縮める。maximumは切れ負け防止の安全弁なので、
通常手の抑制に転用すると本来の役割を失う。

## Decision

いずれも採用しない。本ADRを不採択とし、論点をADR-0059へ統合する。

起草後にStockfishとやねうら王の実装を確認したところ、前提が誤って
いた。両者は打ち切りを比率で判定していない。optimum自体を係数の積で
伸縮させ、比率1.0で判定する。

```cpp
totalTime = optimum * fallingEval * reduction * bestMoveInstability
          * highBestMoveEffort;
if (elapsedTime > std::min(totalTime, double(maximum)))
    → stop
```

係数の値域は fallingEval が 0.576〜1.728、reduction が約0.70〜1.08、
bestMoveInstability が 1.077〜、highBestMoveEffort が 0.693〜0.838
である。最善手が安定した局面での典型的な積は
`1.0 × 0.70 × 1.077 × 0.72 ≈ 0.54` になる。

つまり案Aの「固定0.6」は、この係数積の平均値を定数で近似したもので
しかない。ADR-0059で係数を導入すれば0.6は係数に吸収され、独立した
決定として残す意味がなくなる。局面ごとの伸縮を持たない分、案Aは
係数方式より劣る。評価が下落している局面（読み抜けが進行している
局面）でも一律に0.6で打ち切ってしまう。

配分式そのものについても、想定したほど悪くないことが分かった。
やねうら王の配分は次のとおりで、将来の加算をプールに含めてから
残り手数で割る。

```cpp
MTG = min(max_moves_to_draw - ply + 2, move_horizon) / 2;
remain_estimate = time + inc * MTG + byoyomi * MTG;
t1 = minimumTime + remain_estimate / MTG;
```

300秒＋10秒加算・ply=1で `(300000 + 10000×50) / 50 = 16.0秒` となり、
Himawariの現行式（16.4秒）とほぼ一致する。終盤の厚みには差がある
（やねうら王は `move_horizon = 100 − min(ply, 80)` でMTGを絞るため、
ply=80・残り100秒で20秒を配る。Himawariは16.25秒）。この差は
配分式の再設計として別途扱う（ROADMAPの候補の「時間配分式の再設計」）。

## Consequences

- 1手の消費がoptimumを超える現象は残る。ただしStockfishとやねうら王も
  イテレーション境界で判定するため同じ現象が起きており、異常ではない。
  両者は係数積でtotalTimeを平均的に0.5〜0.6倍へ縮めることで実効的に
  抑えている。同じ効果はADR-0059で得る
- floodgateでの実測（平均21.1秒、optimumの1.3倍）は、係数を持たない
  ことの帰結として説明できる。ADR-0059の採択後に再測定する
- 本ADRのContextにある実測値は、ADR-0059の出発点として引き続き参照する
