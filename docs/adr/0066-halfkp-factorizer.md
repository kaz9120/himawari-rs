# 0066: 学習時だけ駒単独の仮想特徴を併用する（factorizer）

- Status: accepted
- Date: 2026-07-26
- 関連ADR: [0034](0034-nnue-architecture.md), [0045](0045-remove-effect-tower.md), [0064](0064-dense-ft-gradient-mps.md)

## Context

HalfKPは玉の位置と駒の組で重みを持つ。`halfkp_index` は
`king * FE_END + bona_piece` で、実特徴は81×1548 = 125,388通りある。

この構造には学習上の弱点がある。玉が1マス動くだけで、盤上の全駒が
別の重みを参照する。同じ「6八に金がいる」という事実を、玉の位置81通り
それぞれで学び直すことになる。データ量を増やしても、出現の少ない
玉位置の重みは薄いままである。

学習データを370M局面から19億局面へ増やす([ADR-0065](0065-large-scale-dataloader.md))
にあたり、量を活かす仕組みを併せて入れたい。

## 選択肢と比較

### 案A: 何もしない

データ量だけで押す。実績はある。370M局面への拡大では
+161.6 Eloを得た。ただし玉位置ごとの分断は残る。

### 案B: 駒単独の仮想特徴を並列に持つ

学習時だけ、玉位置に依らない特徴（BonaPiece単独、1548通り）を
実特徴と並列に引く。FTの出力は実特徴と仮想特徴の和になる。

```
z = ft(idx) + ft_p(idx % FE_END) + bias
```

玉位置をまたいで駒の価値を共有するため、出現の少ない組でも
仮想特徴側の統計が効く。書き出し時に仮想特徴の重みを実特徴へ
畳み込むので、推論側の構造とファイル形式は変わらない。

```
W_final[k * FE_END + p] = W_real[k * FE_END + p] + W_virtual[p]
```

### 案C: 案Bに玉位置単独の仮想特徴も足す

K単独（81通り）を加える案。ただしHalfKPでは玉の位置が
アキュムレータ全体の定数オフセットになるだけで、`ft_bias` と
役割が重なる。得るものが小さい。

## Decision

案Bを採用する。`--factorized` フラグで選ぶ。

決め手は、推論側を一切変えずに済むことである。仮想特徴は
学習時のみ存在し、`.hmwr` へ書き出す前に実特徴へ畳み込む。
評価関数の速度も、ファイル形式も、Rust側のコードも変わらない。
効果がなければフラグを外すだけで元に戻る。

畳み込みの正しさは等価性で確かめた。仮想特徴つきモデルの出力と、
畳み込んだ重みを実特徴だけのモデルへ入れた出力が一致する。

学習パラメータは1548×256 = 396,288個増える。FT全体の3210万に対して
1.2%であり、速度への影響は測定できる水準にない。

効果はSPRTで測る。データ拡大分と切り分けるため、19億局面の学習を
factorizerなしとありの2本立てで回し、それぞれ `halfkp_370M` を
基準に判定する。

## Consequences

- 推論側は不変である。`.hmwr` の形式もRust側のコードも変わらない
- 学習の初期値はゼロにする。学習開始時点の挙動は現行と同じになる
- 効果が確認できたら既定にする。確認できなければフラグごと消す
- 仮想特徴を残したままのチェックポイントは、`folded_ft_weight()` を
  通さずに重みを読むと値がずれる。書き出しは `quantize.py` 経由に
  限る
- 玉位置単独の仮想特徴（案C）は入れない。必要になれば別ADRで扱う
