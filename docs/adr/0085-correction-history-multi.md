# 0085: correction historyを3系統に増やす

- Status: accepted
- Date: 2026-07-28
- 関連ADR: [0046](0046-correction-history.md), [0084](0084-lmr-cutnode.md), [0074](0074-feature-verification.md)

## Context

[ADR-0046](0046-correction-history.md)でcorrection historyを導入し、
**+44.6 Elo** を得た。探索値と静的評価の乖離を蓄積し、次に同種の局面へ
来たとき静的評価を補正する仕組みである。

キーは歩構造（盤上の歩＋持ち歩枚数）1系統だけである。

```rust
let corr = self.corr.get(stm, self.pos.pawn_key()) / 8;
```

Stockfishは同じ仕組みを5系統持ち、重み付きで合成する。

```cpp
return (6384 * pcv + 3583 * micv + 6492 * (wnpcv + bnpcv) + 6725 * cntcv) / 32768;
```

歩構造・minor piece・非歩駒（先手/後手）・continuation（直前の指し手）の
5本である。1本あたりの寄与は小さくても、合成すると静的評価の系統誤差を
広く拾える。

[ADR-0084](0084-lmr-cutnode.md)で、LMRの項を1つずつSPRTで積む方針は
2件続けて否定された。効果の小さい変更を1件ずつ測るより、関連する機能を
群として入れて測るほうが、判定にかかる対局数あたりの情報量が大きい。
correction historyの系統追加はその形に合う。

## 選択肢と比較

### 案A: 2系統を足して3系統にする

追加するのは次の2本である。

1. 歩以外の盤上駒キー（`non_pawn_key`）。成駒を含み、持ち駒は含めない
2. continuation correction history。直前の指し手の [駒][移動先] を条件にする

将棋にはStockfishのminor pieceに対応する自然な区分がない。桂・銀・香を
minorと呼ぶ根拠は将棋側にない。区分を発明するより、まず「歩以外」で
盤面全体を1本にまとめる。

`non_pawn_key` は歩構造キーと対称に差分更新できる。`pawn_key` の更新箇所が
「歩のとき」なのに対し、こちらは「歩でないとき」に入る。実装が機械的で、
ランダム対局テストで差分と全計算の一致を検証できる。

continuation correction historyは局面のキーを使わない。`move_stack[ply-1]`
から直前の指し手を取るだけで、core側の変更が要らない。

### 案B: Stockfishの5系統をそのまま移植する

先手/後手別の非歩駒キーと、minor piece相当のキーを別々に持つ。

キーが増えるほど差分更新の対象が増え、`do_move` が重くなる。将棋は
持ち駒があり、駒種の入れ替わりが激しい。5本を差分で保つコストは
NPSに響く。まず2本足して効果を見てから広げる。

### 案C: 補正の強さを上げる

系統を増やさず、現状の `/8` を `/4` にする。

これはパラメータ調整で、機能追加ではない。系統が1本のままでは、
拾える系統誤差の種類が増えない。

## Decision

案Aを採る。

合成は次のとおり。分母を32768に揃え、重みの合計を4096にする。

```
corr = (2048*pawn + 1024*non_pawn + 1024*cont) / 32768
```

合計4096/32768は、歩構造のみだった頃の `/8` と等しい。**補正の強さは
変えず、内訳だけを3系統に分ける。** 変数を1つに絞り、結果を
「補正が強すぎた/弱すぎた」ではなく「系統を分けた効果」として読める
ようにする。

歩構造の重みを他の2倍にしたのは、+44.6 Eloの実績がある唯一の系統だから
である。Stockfishの比（6384 : 6492 : 6725）はほぼ均等だが、あちらは
5系統すべてが実績の上で釣り合っている。本エンジンは歩構造だけが実測済み
なので、そこを厚くした状態から始める。

更新は3系統とも同じbonus（`(best - static_eval) * depth / 8` を±128に
クランプ）を使う。系統ごとにbonusを変える案は、変数が増えるので採らない。

`ContinuationCorrectionHistory` のgravityは既存の `CorrectionHistory` と
同一（値域±1024）にする。

## 機能検証（2026-07-28）

`scripts/verify-feature.sh` で固定深さ13のノード数を比較した。

| 局面 | 変更前 | 変更後 | 変化 | 評価値 | 最善手 |
|---|---|---|---|---|---|
| 1 | 498,549 | 156,765 | -69% | 41 → 66 | 6i7h → 2g2f |
| 2 | 477,923 | 251,115 | -47% | 102 → -64 | 同じ |
| 3 | 1,546,105 | 2,550,348 | +65% | 995 → 541 | 同じ |
| 4 | 356,888 | 469,917 | +32% | -162 → -78 | 同じ|

補正が静的評価を動かすため、枝刈りの判断が広く変わる。局面1で69%減り、
局面3で65%増えた。評価値の変化も大きい（局面3で995→541）。correction
historyは静的評価そのものを書き換える機能なので、この振れ幅は想定内である。

差分更新のコストを見るため、初期局面 `go movetime 4000` のNPSを測った。

| | NPS |
|---|---|
| 変更前 | 1,211,119 |
| 変更後 | 1,218,413 |

+0.6%で誤差の範囲。`non_pawn_key` の差分更新は `do_move` あたり数命令で、
NPSに影響しない。

`non_pawn_key` の差分更新は、ランダム対局のテストで全計算との一致を
検証している（`crates/core/tests/integration.rs`）。歩構造キーと同じ
枠組みである。

## SPRT結果（2026-07-28）

**H1採択**。2205ペア（4410局）で **+17.7 Elo [+7.8, +27.7]**、LLR +2.98。
W-D-L は +2253 =129 -2028。

判定に4410局を要した。効果がelo1=5より十分大きいものの、
[ADR-0077](0077-qsearch-futility.md)の+57.3のような水準ではないためである。

補正の強さを変えず内訳だけを3系統に分けて +17.7 Elo が出た。系統を増やす
ことで拾える系統誤差の種類が増えた、という当初の見立てを支持する。
歩構造1系統で +44.6 だったことと合わせると、correction historyはこの
エンジンで効きの大きい機構である。

このSPRTは1391ペアの時点で外部から停止され、
[ADR-0087](0087-sprt-resume.md)の `--resume` で再開して判定まで到達した。
中断耐性がなければ2782局を捨てて回し直すことになっていた。

## Consequences

`StateInfo` が8バイト増える。`do_move` の差分更新が数命令増える。
NPSへの影響は機能検証で確認する。

`Worker::new` の引数が13個になった。history系をまとめる構造体を作る
リファクタは、このADRの範囲外とする（棋力の変更と混ぜない）。

H0だった場合の切り分けは2つある。重みの配分を変えて再測するか、
系統そのものを疑うかである。前者はパラメータ調整なので、まず後者を見る。
`non_pawn_key` は盤上の駒がほぼ全部入るため、局面の識別が細かすぎて
テーブルが疎になっている可能性がある。歩構造キーが効くのは、歩の配置が
局面の型を粗く表すからである。その場合は、駒種を絞ったキー（大駒だけ、
金銀だけ）へ作り替える。
