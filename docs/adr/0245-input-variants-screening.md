# 0245: 評価関数の入力の表し方を、ノード数固定の対局で並べて測る

- Status: proposed
- Date: 2026-10-23
- 関連ADR: [0229](0229-roadmap-visible-focus.md), [0237](0237-effect-count-inputs.md), [0241](0241-mailbox-board-research.md), [0242](0242-effect-acc-speed.md), [0230](0230-board-op-profile.md), [0213](0213-freeze-structure-focus.md), [0127](0127-net-shape-bench.md), [0159](0159-ft-width-1024.md), [0158](0158-mirror-factorizer.md)

## Context

### オーナーとの議論（2026-10-23）

配列盤（[ADR-0241](0241-mailbox-board-research.md)）で利きを常に持てるようになったので、
評価関数の入力を見直す議論をした。オーナーの問題提起は「BonaPieceの表現から抜け出せないか」である。
BonaPiece（駒×升）とその玉位置との組（HalfKP）は、特徴を単純に書けるので大規模な機械学習に向き、
NNUEまで続いてきた。代わりに表が大きく、後段の計算量も大きい。実装の手間が大きい特徴でも、
いまはClaudeが書ける。特徴の設計を人とClaudeが担い、モデルは密で小さくしたい。

議論で、目指す形を次のように整理した。

- 評価関数そのものは差分の状態を持たず、毎回計算する。材料は配列盤が手ごとに保つ盤の情報
- 表現力は、表の大きさではなく、特徴に込めた将棋の知識で稼ぐ
- ノード数固定の対局で現行の方式に並ぶか上回り、1評価の時間が現行（差分更新と推論の合計）以下

### 根拠になる測定

[ADR-0237](0237-effect-count-inputs.md)で、81升×（駒・自分の利き0〜3・相手の利き0〜3）の
特徴（37,584行、幅64）をHalfKPに足した。1手30万ノード固定の対局で、1億局面の学習では
+185.6（下端+168.9）、20億局面では+110.2（下端+95.1）だった。HalfKPの表（125,388行、幅1024）は、
遮りや「2枚以上」のような関係を学べていない。教師を20倍にしても差は消えなかった。

### 速さの材料（2026-10-23、スクラッチで測った）

棋譜400局（`data/sprt/adr0219-dl20-vs-main.jsonl` の先頭、38,477手）を再生し、入力の表し方ごとに
1視点あたりのトークン数を数えた。「1手で変わる行」は消す行と足す行の合計である。

|---|---|---|---|---|

| 升・駒・利き4段階（ADR-0237のF2） | 37,584 | 81 | 15.7 | 19 |

| 両玉の5×5の窓（駒・利き・相対位置） | 23,200 | 36 | 9.6 | 35 |
| 両玉の7×7の窓 | 45,472 | 61 | 16.3 | 59 |

| 脅威（升なし） | 638 | 5.6 | 2.4 | 1.2 |
| 玉の逃げ道 | 80 | 16 | 1.8 | 11 |
| 打ち場所 | 56 | 5.5 | 1.1 | 2.0 |

時間は、乱数の重みで表引きの和と後段を測るベンチで見積もった。行は一様な乱数で選ぶ。
同じベンチで組み立てた現行の評価関数（HalfKPの差分、利きの差分、対の積、後段）は370ナノ秒である。
配列盤のmain（88f1c30）は1スレッドで1,692,350 NPS（`hmwr bench`、200万ノード×3周）で、
評価関数まわりはプロファイルで探索時間の約40%を使う。1ノードあたり約240ナノ秒になる。

升の表し方3通り×玉との位置3通り×追加する特徴6種のon/off×幅4通りの2,304パターンのうち、
370ナノ秒に収まったのは、毎回計算で488、差分計算で1,930だった。毎回計算で収まるのは
幅32が396/576、幅64が91/576、幅128が1/576、幅256が0/576である。

この見積もりは実機と数倍ずれうる。行を一様な乱数で選ぶので大きな表ほど遅く出る。
特徴を盤から作る時間が入っていない。合成した現行値370ナノ秒と実機の240ナノ秒も合っていない。
差分計算の値は1手ぶんで、祖先から数手分を当てる実際の探索より軽い。

## 選択肢と比較

### 速さで先に足切りするか

#### 案S1: 見積もりの速さで、予算を超える案を落としてから質を測る

学習と対局の本数を減らせる。ただ、見積もりは数倍ずれうるので、効く案を捨てるおそれがある。

#### 案S2: 速さで落とさず、ノード数固定で質だけを先に測る

速さは、効いた案についてClaudeが実装を詰めれば縮められる。効く情報かどうかは後から取り返せない。
ADR-0237の段階1と同じ考え方である。

### 比べる相手

#### 案C1: いまの最良（`eff_f2`）と直接対局させる

採否を決めるならこれがよい。差の誤差は1,000ペアの±15前後で済む。

#### 案C2: 原点（`eff_ctrl`、HalfKP＋FT1024で利きを立てない）と対局させる

全案が同じ原点からの差で並ぶ。`eff_f2` の+185.6も同じ条件で測った値なので、同じ表に置ける。
案どうしの差は引き算になり、誤差は±21前後に広がる。

### 1案で何を動かすか

#### 案V1: 特徴の種類・細かさ・FTの後の処理を、因子ごとに1つずつ動かす

効いた因子を切り分けられる。ただ、対の積が効くかどうかは、入れる特徴によって変わりうる。
細かさも特徴の表し方の一部である。

#### 案V2: 細かさとFTの後の処理まで含めた「入力の表し方」1つを1案とする

案の中のどの要素が効いたかは切り分けない。材料集めの段ではこれで足りる。

## Decision

**案S2・案C2・案V2を採る**。この段の目的は採否ではなく、入力の表し方ごとの質を同じ物差しで並べる
材料集めである（オーナー判断、2026-10-23）。FTの幅・重みの型・後段は、この段では動かさない。
差分計算の工夫は、有力な表し方が見つかってから考える。

### 各特徴の定義

視点ごとに盤を反転し、自他は視点から見る。利きは盤上の生の利きで、玉の利きを含め、ピンは無視する。
その升の駒自身の利きは数えない。ADR-0237のF2と同じ数え方である。

| 名前 | 1つのトークン | 立つ条件 |
|---|---|---|
| `f2` | 升・駒（空き・自他14種）・自分の利き0〜3・相手の利き0〜3 | 81升すべて |
| `l2` | 升・駒・自分の利き0か1以上・相手の利き0か1以上 | 81升すべて |
| `thermo` | 升・駒、および升・自他・段階k | 升・駒は81升すべて。段階は利きがk枚以上のとき（k=1,2,3） |
| `minatt` | 升・駒・自分の最小の攻め駒・相手の最小の攻め駒 | 81升すべて |
| `threat` | 駒・升・最小の攻め駒・紐の有無 | 玉以外の駒が相手に利かされているとき |
| `escape` | 玉の自他・方向・状態（盤外・自駒・敵駒・敵の利きがある空き・安全な空き） | 両玉の8近傍すべて |
| `drop` | 自他・持ち駒の種類・段階k | その持ち駒を持ち、相手玉の5×5の窓に安全な空き升がk升以上あるとき（k=1〜4） |
| `mobility` | 駒・段階k | 歩と玉以外の駒で、自駒のない利き先がk升以上あるとき（k=1〜8） |
| `kw5` | 玉の自他・駒・自分の利き・相手の利き・玉からの相対位置 | 両玉の5×5の窓の中の升 |
| `hand` | 自他・持ち駒の種類・何枚目か | 持っている持ち駒ごと |

最小の攻め駒の階級は、歩・香・桂・銀・金と成り駒・角・飛・馬・龍・玉の10と「なし」である。

## 測定の設計

### 仮説

**入力の表し方を変えると、同じ1億局面・同じレシピで学習したネットの、ノード数固定の対局での質が
変わる**。上乗せでは、利き以外の関係（脅威・逃げ道・打ち場所・駒の働き・玉との位置）がHalfKPと利きに
ない情報を持つ。置き換えでは、関係を持つ入力がBonaPiece×玉の表の代わりを務める。

### 動かす変数

入力の表し方だけを動かす。案ごとに構成名が1つ決まる。

### 固定するもの

- データは[ADR-0224](0224-selection-bench.md)の重複除去の1億（`sel_dedup_100M`）。ADR-0237と同じ
- 学習のレシピは `eff_f2` と同じ。1周、batch 16384、peak_lr 1e-3、λ0.7、seed 0、FTクリップ1.0、
  兄弟群 `rank_tanuki_210M`、検証 `valid_tanuki_dl430_q1`。ゼロから学習する
- 後段は16→32→1、HalfKPのFTは幅1024
- 対局は `eff_ctrl` との1手30万ノード固定、1,000ペア、開始局面 `start_sfens_ply24`、hash 64、
  並列8、裁定2000,8、最大手数400。ADR-0237の段階1と同じ

暗黙に動く変数を点検した。

- 乱数の系列。側の表の行数が案ごとに違うので、初期化で乱数を消費する順序がずれる。
  ADR-0237の段階4で書いたとおり、この違いは対局で数Elo規模である。区別できる差（下の±25）より小さい
- 側の表の大きさと、1局面で立つトークンの数。表し方そのものに含まれる違いとして扱う
- 学習1ステップの時間。ステップ数で揃えるので結果には効かない。所要は記録する
- 対局の所要。毎回計算するので、案ごとに1ノードの時間が違う。ノード数固定なので結果には効かない

### 解釈の事前登録

各案の質Qは、`eff_ctrl` → 案のEloである。上乗せの案は、A0のQ（+185.6）との差ΔQで読む。
案どうしの差は2つの測定の引き算なので、誤差を±21前後と見て、区別できる差の線を±25に置く。

| 群 | 結果 | 読み |
|---|---|---|
| A1〜A3 | ΔQが+25以上 | A0より良い表し方。利きの入力の既定の候補にする |
| A1〜A3 | ΔQが±25の内 | A0と区別できない。速さやトークン数が有利なら、そちらを候補にする |
| A1〜A3 | ΔQが−25以下 | A0より劣る。その表し方は情報を落としている |
| A4 | ΔQが+25以上 | 利きの側でも対の積が効く。置き換えの群の対の積の扱いを支持する |
| A4 | ΔQが±25の内か−25以下 | 利きの側の対の積は効かない |
| A5〜A9 | ΔQが+25以上 | 足した特徴は、HalfKPと利きにない情報を持つ |
| A5〜A9 | ΔQが±25の内 | 1億・1,000ペアの規模では、足した特徴の情報は見えない |
| A5〜A9 | ΔQが−25以下 | 想定外。特徴抽出と学習の不具合を疑い、点検する |
| B1〜B3 | Qが+160以上 | HalfKPなしで、HalfKPと利きの組（A0）に並ぶ。置き換えを本命にする |
| B1〜B3 | Qが0以上+160未満 | 原点（HalfKPだけ）は超えるが、A0には届かない |
| B1〜B3 | Qが0未満 | 関係を持つ入力だけでは、BonaPiece×玉の表の代わりにならない |

B1〜B3の間の差は、Bの中での読み（玉との位置や追加の特徴がどれだけ埋めるか）に使う。
採否はこのADRでは決めない。次の段（幅を絞る、組み合わせる）の材料にする。

この段は棋力の主張をしないので、SPRTは行わない。コードをmainへ入れる条件は次のとおりである。

## Consequences

- 構成名に、側の入力の表し方（`-<名前>[_<名前>…]`）と、側の対の積（`p`）を書けるようになる。
  既定の構成と、表し方を書かない構成は従来どおりで、既定のネットの経路は変わらない
- 新しい表し方の側のaccumulatorは、評価のたびに作り直す。速さは測らない
- 毎回作り直す経路のNPSを、乱数の評価関数で測った（`hmwr bench`、100万ノード×3周を交互、2026-10-23）。
  `1024x16x32e64` が1,688,988、`1024x16x32e64-f2_threat` が835,531（−50.5%）、
  `1024x16x32e1024p-f2_hand` が150,631（−91.1%）だった。ノード数固定の対局は片側だけが遅くなるので、
  所要は上乗せの1本で学習0.6時間と対局3時間前後、置き換えの1本で学習1時間と対局11時間前後の見込みである。
  12本で約70時間になる
- specは1案1本にする（`experiments/adr0245-<案>.toml`）。学習データは同じ条件なら作り直さないので、
  各specの頭で用意し、最後のB3だけが消す
- 見直しのトリガーは2つある。上乗せで効いた特徴が出たら、置き換えの群へ足して測り直す。
  置き換えがA0に並んだら、幅を絞る段（FT幅32・64）のADRを起こす
