# 0129: 学習時だけの補助ヘッドでFTの表現を厚くする

- Status: proposed
- Date: 2026-08-02
- 関連ADR: [0034](0034-nnue-architecture.md), [0064](0064-dense-ft-gradient.md), [0066](0066-feature-factorizer.md), [0120](0120-after-parity.md), [0126](0126-mate-score-in-training.md), [0127](0127-net-shape-bench.md)

## Context

[ADR-0127](0127-net-shape-bench.md)で8構成を測り、**容量を増やしても棋力が上がらない**と
分かった。FTを256から512へ太らせるとvalid lossは0.00193下がるのに、ノード数を揃えた対局でも
基準に勝てない（−11.3 [−61.0, +38.4]）。**器を大きくしても、入れる中身が増えていない。**

### 教師信号が細い

FTは局面のトークナイザである。HalfKPの特徴125,388個それぞれに256次元のベクトルを持ち、
盤面に立っている38個ぶんを足して局面を表現する。パラメータは**3210万**で、ネット全体の
99.94%を占める。

それに対して、1局面から得られる教師信号は**評価値というスカラー1つ**である。しかも
`sigmoid(score/600)` で潰すので、実質的な情報量は数ビットしかない。

word2vecが単語の意味を捉えられるのは、「文脈から単語を当てる」という数万クラスの分類を
解かせているからである。**信号の太さが違う。** 評価値だけで学習したFTが
「評価が近い局面が近くなる」表現に落ち着くのは必然で、それ以上の構造を学ぶ理由がモデルの
側にない（2026-08-02オーナー指摘）。

### 使える教師がすでにデータにある

`PackedSfenValue` は評価値のほかに次を持つ（`crates/core/src/packed_sfen.rs`）。

| フィールド | 中身 | 情報量 |
|---|---|---|
| `move16` | PVの初手 | 指し手の分類。数百通りから1つ |
| `game_result` | 手番側の最終勝敗（勝ち1・負け−1・引き分け0） | 3値 |
| `game_ply` | 初期局面からの手数 | 進行度に使える |

**`move16` は使っていない。** [ROADMAPの候補](../ROADMAP.md#候補)に「教師との指し手一致率の
計測」があるだけで、学習には入っていない。

## 選択肢と比較

### 案A: 評価値だけで学習する（現行）

いまの形。実装が単純で、学習時間も最小になる。ただし上のとおり信号が細く、3210万
パラメータを数ビットで導いている。

### 案B: 出力ヘッドを増やし、推論でも使う

WDL・進行度を推論時にも出し、時間管理や枝刈りへ供給する（[ADR-0120](0120-after-parity.md)の
多ヘッド案）。表現が厚くなるうえ、探索の判断材料も増える。

ただし推論のコストが増える。ADR-0127で分かったとおり、**このエンジンでは速度が支配的**で、
1ノードあたりの費用を増やす変更は精度の得を食い潰す。探索側の作り込みも要る。

### 案C: 学習時だけ補助ヘッドを足し、書き出し時に捨てる

FTの出力から評価値と並列に指し手・勝敗を予測させ、損失を合算して学習する。書き出しでは
補助ヘッドを捨てるので、**推論の構造と速度はまったく変わらない。**

[ADR-0066](0066-feature-factorizer.md)のfactorizerと同じ形である。あちらも学習時だけ
仮想特徴を並列に持ち、書き出し時に実特徴へ畳み込む。

1回の学習で済むのが利点である。ただし評価値ヘッドは推論と同じ3層（L1→L2→1）のままなので、
**そこがタスクを解いてしまうぶん、FTへの圧力が漏れる。**

### 案D: FTを事前学習してから、評価値の後段を載せる

2段階に分ける（2026-08-02オーナー提案）。

```
フェーズ1（FT事前学習）— ヘッドはすべて線形1層
  FT ┬→ Linear(512→1)   評価値
     ├→ Linear(512→88)  指し手from
     └→ Linear(512→81)  指し手to
  → FTだけ残し、ヘッドは全部捨てる

フェーズ2（評価関数の学習）
  凍結したFT → L1(32) → L2(32) → 1
```

**評価値ヘッドも線形1層にするのが要点である。** 評価値を当てる圧力は残したまま、ヘッド自身が
タスクを解く余地をなくす。どのヘッドも自力では解けないので、FTが表現を持つしかなくなる。

word2vecやBERTの流れがこれである。事前学習で表現を作り、下流タスクは別に載せる。将来
マスク予測へ広げるとき、**評価値ラベルのないデータも事前学習に使える**という利点も生きる。

## Decision

**案Cと案Dの両方を3億局面で学習し、リーグ戦で比べる。** どちらが効くかを事前に決めない。

**決め手は、どちらも推論コストを増やさずに教師信号だけを太くできることである。** ADR-0127の
結論は「速度が支配的だから容量を増やせない」だった。両案ともその制約の外側にある。学習時間は
増えるが、対局には1ミリ秒も足さない。

案Bを採らないのは、多ヘッドの供給先（時間管理・枝刈り）を作り込む前に、**そもそも表現が
厚くなるのかを確かめたい**からである。案CかDで表現が厚くなると分かれば、案Bはその上に載る。

### 200万局面の予備実験では案Cが勝った。ただし案Dの評価にはならない

実装の動作確認を兼ねて、200万局面で回した（2026-08-02）。

| 条件 | valid loss | 所要 | データ通過 |
|---|---|---|---|
| 基準（補助ヘッドなし） | 0.54996 | 29.6秒 | 200万 |
| **案C（λ_move=0.1）** | **0.54771** | 31.8秒 | 200万 |
| **案C（2エポック）** | **0.53341** | 60.7秒 | 400万 |
| 案D フェーズ1（事前学習） | 0.55318 | 30.2秒 | 200万 |
| 案D フェーズ2（FT凍結） | 0.56165 | **6.2秒** | 400万 |
| 案D' フェーズ2（凍結しない） | 0.55117 | 29.0秒 | 400万 |

データ通過量を400万に揃えると案Cが圧勝している。**しかしこれは案Dへの反証にならない。**
フェーズ1のvalid lossが0.55318で、まだ学習途中のFTを凍結しているためである。事前学習は
大量のデータで表現を作る前提の手法で、本番19.9億に対して200万は0.1%にすぎない。

副産物として、[ADR-0130](0130-freeze-ft.md)のFT凍結が**4.8倍速**（330k samples/s）だと
実測できた。「一桁速くなる見込み」と書いたが、実測は5倍である。

### 何を予測させるか

| ヘッド | 教師 | 損失 |
|---|---|---|
| 評価値（本来の目的） | `sigmoid(score/600)` と勝敗の混合 | BCE（現行のまま） |
| 指し手 | `move16` | クロスエントロピー |
| 勝敗 | `game_result` | 3クラスのクロスエントロピー |

合計の損失は `value_loss + λ_move × move_loss + λ_wdl × wdl_loss` とする。

**まずλ_wdl=0に据え置き、moveヘッド単独で始める。** value targetにはλ=0.7の混合で
`game_result` がすでに入っており（`train.py --lambda`）、勝敗ヘッドが足す新情報は
引き分けの分離程度しかない。本命の新信号は `move16` である。λ_moveは0.1前後から始め、
valueの学習を壊さない範囲で振る。

### ヘッドは線形1層にする

補助ヘッドはFT出力（2視点連結の512次元）からの線形1層とする。ヘッドを深くするほど、
タスクをヘッド自身が解いてしまい、FTへ表現を押し込む圧力が弱まる。word2vecの類推を
採る以上、答えも同じで、あちらの出力も線形softmaxである。169クラスなら9万パラメータ弱で、
学習コストは無視できる。

### 指し手のラベルはfromとtoに分ける

指し手を1つのクラスにすると、`from(81+持ち駒7) × to(81) × 成り` で1万を超える。dlshogi系は
移動方向で畳んで2187クラスにするが、方向の定義を書き起こす必要がある。

**まずfromとtoを別々のヘッドにする。** 88クラスと81クラスの分類2つで、合計169クラスに
収まる。組み合わせの情報が落ちるのに加えて、**成りはどちらのヘッドにも現れず完全に落ちる。**
拾うなら成り判定の2値ヘッド1つで足りるが、まずは落としたまま始める。目的は指し手を正確に
当てることではなく**FTに指し手の手がかりを持たせること**なので、精密さより実装の軽さを取る。
効きが見えたら畳み方を見直す。

### 効いたかはリーグ戦で測る

**valid lossでは判断しない。** [ADR-0127](0127-net-shape-bench.md)で、lossと棋力が逆相関
することが分かっている。補助ヘッドを足すとvalue lossはむしろ悪化しうるが、それは
「評価値の暗記精度を捨てて別の軸を学んだ」だけかもしれない。

判断は[ADR-0128](0128-round-robin-league.md)のリーグ戦で行い、採否は最終的にSPRTで決める。

## Consequences

- 学習時間が増える。補助ヘッドの順伝播・逆伝播が乗る。3億局面で50分が60〜70分になる見込み
- ハイパーパラメータが2つ増える（λ_move・λ_wdl）。振り方を誤ると本来のvalue学習を壊す。
  まずλ=0から始めて現行と一致することを確かめ、そこから上げる
- **推論側は1バイトも変わらない。** 評価ファイルの形式も、探索も、速度もそのまま。効かなければ
  学習側の分岐を消すだけで戻せる
- `move16` を使うので、このフィールドを持たない教師データは補助ヘッドを学習できない。
  hao_depth9は持っている
- 表現が厚くなったかを直接測る手段がない。**指し手の的中率**は学習ログに出せるので、
  少なくとも「指し手を学べているか」は確認できる
- 効きが確認できたら、[ADR-0127](0127-net-shape-bench.md)のFT512を再測定する価値が
  生まれる。「容量を増やしても上がらない」は細い信号の下での結論であり、信号を太くすれば
  容量が活きる可能性が残る
- **案Dが通れば、評価値を使わない事前学習への道が開く。** マスク予測（盤面の駒を隠して
  当てる）なら教師データすら要らず、棋譜だけで回せる。指し手を系列として扱う案は差分計算と
  相容れないが、事前学習した表現をFTへ蒸留する形なら制約を回避できる。**ネットワーク構造を
  いじるより、事前学習のほうに伸びしろがある**という見立てである（2026-08-02オーナー判断）
- 案Cと案Dは排他ではない。案Dのフェーズ1で作ったFTを初期値に、案Cの同時学習を続ける形も
  組める。まず単独で測ってから考える
