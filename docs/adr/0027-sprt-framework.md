# 0027: 強さ検証基盤（SPRT）

- Status: accepted
- Date: 2026-07-18
- 関連ADR: [0006](0006-ci-test-bench.md), [0019](0019-usi-architecture.md), [0021](0021-time-management.md), [0026](0026-repetition.md)

## Context

P3以降の探索変更は「1機能=1SPRT」で強さを確認してから取り込む。
その前提となる自動対局と統計判定の基盤を、P3の最初に作る。
ここで決めるのは対局マネージャの形態、統計モデル、既定の対局条件、
終局判定の持ち場。

## 選択肢と比較

### 対局マネージャの形態

Ayaneなど既存のPython製ツールは実績があるが、依存が増え、
並列対局の制御も別言語に出る。自前のRust実装はUSIクライアントを
書く手間がかかるものの、coreクレートの局面管理・千日手判定を
そのまま再利用でき、ワークスペース内で完結する。
tools配下の自前実装を採用する。

### 統計モデル

trinomial（勝ち・引き分け・負けの3値）は実装が簡単だが、
同一開始局面を先後入れ替えて指すペア対局の相関を無視し、
信頼度を過大に見積もる。将棋は先手有利が明確でペア運用は必須の
ため、fishtestと同じpentanomial（ペア得点の5値）を採用する。

## Decision

- `selfplay` バイナリをtoolsに追加する。ベースラインと候補の
  2エンジンをUSIサブプロセスとして起動し、N並列で対局させる
- 対局は常にペア単位。開始局面集から1局面を引き、先後を
  入れ替えて2局指す。ペア得点（0, 0.5, 1, 1.5, 2）を
  pentanomial度数に集計する
- SPRT判定: GSPRTの正規近似でLLRを逐次更新する。既定は
  elo0=0、elo1=5、α=β=0.05。上下いずれかの閾値到達で打ち切る
- 既定の対局条件はフィッシャー10秒+加算0.1秒。NPSの環境差を
  排除した再現用に、ノード数固定モードも用意する
- 開始局面集はSFEN 1行1局面のテキストファイルをパス指定で読む。
  当面は公開の互角局面集を使い、リポジトリには含めない
- 終局判定はマネージャ側でcoreを使って行う。
  合法手なし=詰み、千日手=引き分け（連続王手は判定に従い反則負け）、
  手数上限（既定320手）=引き分け、`bestmove resign` =投了。
  非合法手は即負けとして記録する
- スコアによる早期終局（両者の直近評価値が閾値を超えて一致した
  場合の勝敗打ち切り）はオプションとし、既定は無効
- 出力: 対局数、W-D-L、pentanomial度数、Elo±95%信頼区間、LLRを
  逐次表示する。棋譜は開始SFENと指し手列をJSONLで保存する
- 入玉宣言勝ち（win）は宣言勝ちADRの実装後に対応する

## Consequences

- 探索変更のマージ条件を「SPRT合格」に統一でき、この運用開始が
  P3出口条件の1つになる
- pentanomial集計のため対局は必ずペアで完結させる。中断時の
  端数1局は集計から捨てる
- 終局判定がcoreに依存するため、ルール系のバグはエンジンと
  マネージャで共通になり自己対局では検出できない。perftと
  詰将棋テストで別途担保する
- 宣言勝ち未実装の間、相入玉の将棋は手数上限の引き分けに流れる
- elo1=5の検出には数千〜数万局が要る。1台のローカルマシンで
  回す前提のため、序盤は時間条件を短くして対局数を稼ぐ
