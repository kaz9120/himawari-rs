# 0101: MoveListのゼロ埋めをやめる

- Status: accepted
- Date: 2026-07-29
- 関連ADR: [0099](0099-nnue-dot-sdot.md), [0100](0100-movepick-argmax-simd.md), [0089](0089-improvement-criteria.md), [0074](0074-feature-verification.md), [0068](0068-sprt-driven-versioning.md)

## Context

[ADR-0099](0099-nnue-dot-sdot.md)のプロファイルで、`_platform_memset` が
self時間の1.8%を占めていた。呼び出し元をたどると大半が
`MovePicker::next` である。

`MoveList` は最大合法手数593を上回る608要素の固定長バッファを持ち、
`Default` が全要素を `Move::NONE` で埋める。

```rust
pub struct MoveList {
    moves: [Move; 608],
    len: usize,
}
```

`Move` はu32なので2,432バイトになる。`MovePicker::next` は段階ごとに
`MoveList::default()` を作るため、1ノードで2〜3回、合計5〜7KBをゼロで
書く。書いた値は `push` が上書きするか、`as_slice` が返さない領域で
あり、1バイトも読まれない。

コストはmemsetの1.8%だけではない。5〜7KBの書き込みはL1を丸ごと
入れ替える量で、同じノードで使う置換表エントリや履歴表を追い出す。

## 選択肢と比較

### 案A: MaybeUninitで初期化しない

`[MaybeUninit<Move>; 608]` に変え、`push` で書き込み、`as_slice` は
先頭 `len` 要素だけを初期化済みとして返す。

`MoveList` の公開APIは `push` `len` `is_empty` `clear` `as_slice` と
`IntoIterator` だけで、すべて `as_slice` を経由する。内部配列への
直接アクセスは `moves.rs` 内の2か所に閉じているため、影響範囲が小さい。

### 案B: MovePickerがMoveListを1つ持ち回す

`MovePicker` のフィールドに `MoveList` を持ち、段階ごとに `clear()` で
使い回す。unsafeは要らない。

`MovePicker` が2,432バイト太る。生成の回数は減るが、初期化そのものは
残る。1ノードあたり2〜3回が1回になるだけである。

### 案C: 放置する

2,432バイトのゼロ埋めはSIMDストアで数十サイクルであり、絶対値としては
小さい。プロファイルで1.8%が観測されている以上、放置の根拠にならない。

## Decision

案Aを採る。書いた値が一度も読まれないためである。案Bは生成回数を
減らすだけで、無駄な書き込み自体は残る。

### 型を変えるだけでは消えなかった

`[MaybeUninit<Move>; 608]` へ変えてもNPSは+0.5%しか動かなかった。
プロファイルを取り直すと、memsetの絶対量が変わっていない
（374ms→391ms、同じ探索）。逆アセンブルで理由が分かった。

```
add  x0, sp, #0x50
mov  w1, #0x988        ; 2,440バイト = MoveList全体
bl   _bzero
```

`MoveList { moves: [MaybeUninit::uninit(); N], len: 0 }` と構造体を値で
組み立てると、LLVMが未初期化の配列を含むアグリゲートを定数へ畳み、
`undef` を0として具体化する。`#[inline]` を付けても変わらなかった。

`len` だけをポインタ経由で書く形にすると、2,440バイトの `bzero` は
バイナリから消えた。

```rust
let mut this = MaybeUninit::<MoveList>::uninit();
unsafe {
    (&raw mut (*this.as_mut_ptr()).len).write(0);
    this.assume_init()
}
```

未初期化のまま置きたいときは、型で示すだけでは足りない。値として
組み立てた瞬間にアグリゲート定数になる。フィールド単位で書く必要が
ある。この落とし穴は他の固定長バッファにも当てはまる。

### 計測

| 実装 | NPS | main比 |
|---|---|---|
| main（ゼロ埋めあり） | 1,279k | — |
| MaybeUninit（構造体を値で構築） | 1,282k | +0.5% |
| MaybeUninit（`len` だけ書く） | 1,301k | +1.68% |

4局面・深さ19・1スレッド、3回ずつ交互に測った平均である。

### SPRTは非劣性で回す

既定条件（elo0=0、elo1=5）ではなく、elo0=-5、elo1=0 で回す。

+1.68%からの期待Eloは5前後である。[ADR-0099](0099-nnue-dot-sdot.md)は
NPS +20.5%で+59.7 Elo、[ADR-0100](0100-movepick-argmax-simd.md)は
NPS +24.4%で+106.7 Eloだったので、NPS 1%あたり2.9〜4.4 Eloになる。
elo1=5 の閾値は期待値そのものであり、既定条件では判定に至らないまま
数千局を費やす見込みが高い。

非劣性で確かめるのは「弱くなっていない」ことだけである。速度が
上がったことは機能検証とNPSで示せており、SPRTに求めるのは害がない
ことの確認に絞る。

### 結果と打ち切りの判断

1,228局（614ペア）で **+3.7 [-14.0,+21.4]**、LLR +0.38。判定に至る前に
打ち切った（2026-07-29オーナー決定）。

打ち切った理由は、対局で確かめられることが残っていないためである。
機能検証で4局面のノード数・評価値・最善手が完全に一致しており、探索の
出力は変わらない。変わるのは同じ読みを何秒でこなすかだけで、それは
NPSで測ってある（+1.68%）。推定値+3.7はNPS分の差として筋が通る。

判定まで回すと、真値が-5と0の間にないことを示すために数千局を要する。
得られるのは「弱くなっていない」の確証だけで、95%CIの下限-14.0が
-5を割っているとはいえ、点推定は正である。ここに対局リソースを積むより、
次の候補へ回すほうが得る物が大きい。

序盤の推定値は当てにならなかった。114局の時点では-24.4 [-86.3,+35.9]で、
符号すら逆だった。[ADR-0097](0097-capture-history.md)でも同じことが
起きている。数百局の値を見て方向を判断しない。

### コミットの型はfix

[ADR-0068](0068-sprt-driven-versioning.md)の `feat` は「SPRTでH1採択
した変更」であり、ここでいうH1は既定条件（elo1=5）を指す。非劣性
SPRTの採択は「-5より悪くない」であって、強くなったとは言えない。

バイナリは変わるが棋力の向上を示していないため、`fix`（PATCH）とする。
速度の改善を測定限界以下の精度で積むとき、この扱いを既定にする。

## Consequences

`MoveList` にunsafeが3か所入る（`Default`、`push`、`as_slice`）。
不変条件は「`moves[..len]` は初期化済み」の1つで、`len` を増やすのは
`push` だけである。フィールドはprivateのまま保つ。

未初期化領域を読むコードを書くと未定義動作になる。現在のAPIでは
`as_slice` 以外に読み出す手段がなく、`len` を超えて読むことはできない。
Miriで確かめたいが、`std::simd` と `target_feature` を使うコードは
Miriで動かない。単体テストと `debug_assert` で代替する。

`MoveList::default()` の実装は、見た目より壊れやすい。フィールドを
足すときは、それも同じ方法で初期化しないと未初期化のまま読むことに
なる。将来フィールドが増えたら、この関数を読み直す必要がある。

memsetはこれで消えたが、`MovePicker` のVec確保（malloc 1.4%）は残る。
プロファイル上位の3件（NNUE隠れ層、指し手選択、FT差分更新）を叩いた
あとでは、残りは1%台の項目ばかりになる。速度軸はここでいったん
打ち止めにし、次はノード効率か終盤の正確さへ戻る。
