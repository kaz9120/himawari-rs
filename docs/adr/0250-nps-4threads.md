# 0250: 探索木を変えずに4スレッドのNPSを10%上げる

- Status: accepted（4スレッドで+13.99%、1スレッドで+11.53%。固定深さのノード数は全局面で一致）
- Date: 2026-10-30
- 関連ADR: [0056](0056-tt-prefetch.md), [0074](0074-feature-verification.md), [0124](0124-hot-path-allocs.md), [0151](0151-speedup-sweep.md), [0156](0156-bucket-accumulator-cache.md)

## Context

オーナーの指示（2026-10-30）は、mainの4スレッドのNPSを測り、探索木を変えずに10%上げることである。
対象は既定の構成 `1024x16x32e64` と現行の評価関数 `pool1_2ep_f2_reorder` に限る。

mainの4スレッドは約601万NPSで、2スレッドの約299万、1スレッドの約153万とほぼ比例していた。
並列の損失は小さいので、1スレッドあたりの処理を速くする方針を採った。

4スレッド・深さ25のプロファイル（Apple M4 Pro）では、突出した関数は無かった。目立ったのは3つである。

- 置換表の読み出し（`probe_tt`）で待たされる時間が約3%あった
- 玉が動いた視点の全計算（`refresh_top` と `ft_update`）が周辺込みで約9%あった
- 指し手の並べ替え（`partial_insertion_sort`）が約5%あった

## 選択肢と比較

候補ごとに入れて測り、効いたものだけを残した。条件は[ADR-0151](0151-speedup-sweep.md)を引き継ぐ。
固定深さのノード数が全局面で一致することと、2本を交互に測って差が出ることである。

### 採ったもの

| 変更 | 4スレッドのNPS |
|---|---|
| 子ノードの置換表とeval hashを、手を進めた直後に先読みさせる | +3.85% |
| correction historyの4系統を、手を進めた直後に先読みさせる | +1.77% |
| continuation correction historyの2か所を、`set_current_move` で先読みさせる | +1.64% |
| 連結ベクトルと非ゼロ位置の配列のゼロ埋めをやめ、Finnyから探索の段への2KBの複製を更新のパスに畳む | +0.75% |
| 置換表の先読みを、進める前に求めた子のキー（`key_after`）で行う | +1.85% |
| 指し手ループで、合法と分かった時点で先読みを始める | +1.21% |
| 並べ替えを、分割と標準の安定ソートに分ける | +2.30%（1スレッド） |
| 遡れない視点を、最上段でなく1段下でFinnyから作り、差分で上げる | +1.34%（1スレッド） |

各行の値は1つ前の版と交互に3〜4周測った差である。誤差は±1.5%ほどあるので、合計は最後の測定と一致しない。

#### 先読み

[ADR-0056](0056-tt-prefetch.md)は置換表の先読みを棄却した。根拠は144局のSPRT（LLR −0.24）で、NPSは測っていない。
先読みは探索木を変えないので、NPSで測り直した。効いたのは、読んだ値で分岐する表である。
置換表、eval hash、correction historyがそれに当たる。

#### 並べ替え

元の挿入ソートは閾値以上の手を1つずつ先頭側へ入れ替えてから、並べ済みの区間へ挿入していた。
これは「見つけた順に入れ替える分割」と「先頭の区間の安定な降順ソート」に分けられる。挿入は同点を後ろに置くので安定である。
分割のあとに標準の安定ソートをかければ同じ並びになり、手が多いときのO(n²)の移動が減る。閾値より下の手の並びも元と一致する。

#### 全計算を1段下で行う

一時的な計測（1局面、1,500万ノード）では、評価の約3割で全計算が走っていた。その約7割は
玉の動いた段から5段以上離れていた。置換表に評価値があると途中の段は評価されず、計算済みの段が無いまま葉に着く。
最上段で全計算すると、葉の兄弟が1つずつ全計算をやり直す。

そこで親の段でFinnyから作り、最上段へは差分で上げる。親の段のBonaPiece集合は現局面の集合から最上段の差分を戻して作る。
集合の差はビットの反転なので、戻す順序に依らない。遡る段数は1・2・4・上限なしを試し、差が誤差の範囲だったので1にした。

### 効かなかったもの

| 変更 | 結果 |
|---|---|
| `panic = "abort"` でビルドする | −0.19% |
| FT重みの行を、差分更新とFinnyの更新の前に先読みさせる | −0.12% |
| `ft_update` の範囲検査を1回にまとめる | +0.07%（1スレッド） |
| 第1層の疎な積和で、アキュムレータを2組に分けてSDOTの依存を切る | +0.11%（1スレッド） |
| continuation correctionの先読みを、合法と分かった時点へ早める | −0.59% |
| 進める前のキーを、指し手ループと `make_move` の2回求めないようにする | +0.03%（重複の除去として残した） |

FT重みの行と積和は、同じノードの中で独立に読むので、アウトオブオーダー実行と自動の先読みで既に隠れていたと読める。
先読みは関数をまたいで離れた場所で使う値にだけ効いた。

## Decision

採ったものをすべて入れる。種別は棋力に影響しない変更（`fix`）で、SPRTにはかけない。

### 合格の条件

- Eloの判定: なし。探索木が変わらないので、対局は中立にしかならない（ADR-0074）
- Elo以外の条件: 固定深さのノード数・評価値・最善手が、mainと全局面で一致すること。
  4スレッドのNPSがmainより10%以上高いこと

## 結果（2026-10-30）

固定深さ13・18・22の組み込み4局面と、深さ16の中終盤6局面で、ノード数・評価値・最善手がmainと一致した。

NPSは1手500万ノード×組み込み4局面、置換表は既定で、mainと交互に7周測った。
計測の途中でload averageが28まで上がったが、7周すべてで候補がmainを上回り、分布は重ならない
（main 5,948,519〜6,066,979、候補 6,750,677〜6,891,519）。

| スレッド | main | 候補 | 比 |
|---|---|---|---|
| 4 | 6,011,019 | 6,851,927 | +13.99% |
| 1（深さ24、5周） | 1,519,559 | 1,694,840 | +11.53% |

ログは `data/logs/bench-adr0250-nps4.log` にある。

## Consequences

- 先読みは配列盤の構成で効く。coreの盤で探索する構成（`core-search`）には子のキーを求める関数が無いので、
  置換表は今の局面のキーで先読みさせる。外れるだけで結果は変わらない
- [ADR-0124](0124-hot-path-allocs.md)の「ソフトウェアprefetchは使えない」は、この測定で覆った。
  先読みの候補を外す根拠には使わない
- 全計算の段を変えたので、玉の移動が多い局面ほど効く。終盤の速さは測っていない
