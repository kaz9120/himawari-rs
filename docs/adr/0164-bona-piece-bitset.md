# 0164: BonaPiece集合の構築を駒ごとの走査からブロック配置へ置き換える

- Status: accepted
- Date: 2026-08-15
- 関連ADR: [0074](0074-feature-verification.md), [0124](0124-hot-path-allocs.md), [0151](0151-speedup-sweep.md), [0156](0156-bucket-accumulator-cache.md)

## Context

次の開発に入る前の棚卸しとして、プロファイルを取り直した（2026-08-15
オーナー指示）。深さ25・1スレッド・2000Hzで4局面を読ませ、18,726サンプルを
集めた。条件は[ADR-0151](0151-speedup-sweep.md)の第3次プロファイルと同じで
ある。

| 箇所 | self時間 | 第3次（2026-08-09） |
|---|---|---|
| `MovePicker::next` | 18.08% | 17.0% |
| `NnueState::evaluate` | 17.44% | 18.6%（`ensure`） |
| `NnueState::refresh_top` | 8.12% | 項目なし |
| `attacks`＋`attackers_to` | 15.53% | 15.9% |
| movegen系 | 8.32% | 7.3% |
| `affine_relu` | 1.46% | 11.4% |

**`refresh_top` が新しく上位に現れた。** [ADR-0156](0156-bucket-accumulator-cache.md)で
入れた玉位置キャッシュの経路で、玉が動いた視点を同じ玉位置のキャッシュとの
差分で作る。行単位では `nnue_acc.rs:291`（BonaPiece集合の構築）が4.43%、
`ft_update` が1.36%を占めた。

`affine_relu` の11.4%から1.46%への低下は、インライン化の境界が動いて
`evaluate` へ合算されたものである。行単位では `nnue_acc.rs:176`
（`forward_hidden` の呼び出し）が9.22%にあたる。

`MovePicker` の2大項目は触らない。`score_quiets`（5.84%）は巨大表への
ランダムアクセスが主因で[ADR-0056](0056-tt-prefetch.md)がprefetchの
無効を実測済み、`partial_insertion_sort`（6.63%）はADR-0151の群Mが
3通りの実装で−2.5%を確かめて棄却している。

## 選択肢と比較

集合の構築は `for_each_bona_piece` が駒を1枚ずつクロージャへ渡す形だった。

```rust
for sq in pos.occupied() ^ kings {
    f(bonapiece::board_bona_piece(c, pos.piece_on(sq), sq));
}
for owner in [Color::Black, Color::White] {
    for pt in PieceType::HAND_KINDS {
        for i in 1..=pos.hand(owner).count(pt) {
            f(bonapiece::hand_bona_piece(c, owner, pt, i));
        }
    }
}
```

逆アセンブルすると盤上駒1枚あたり24命令ある。内訳は `piece_on` の配列読み、
パニック経路のための駒種のスタック退避、`board_base` の網羅性から出た2本の
分岐、起点テーブルの引き、そしてビットセットへのread-modify-writeである。
手駒は枚数ぶんのループが展開され、1枚ごとにスタックへのRMWが並ぶ。

### 案A: 番号付けの規則性を使ってブロックで配置する

BonaPieceの番号付けは規則的である。盤上は81升ぶんのブロックが
(視点側, 相手側) の対で9カテゴリぶん並び、手駒は枚数ぶんの連番になる。
成り小駒4種は金へ畳まれ、その集合は `Position::golds` の合成板
（[ADR-0151](0151-speedup-sweep.md)群F）と一致する。玉は特徴に入らない。

駒を1枚ずつ回らず、駒種ごとのbitboardをブロックの起点へシフトして入れ、
手駒は連続ビットのマスクを1回ORすれば同じ集合になる。後手視点の升の反転
（`Square::inv`）は、81ビットの並びを180度回す `reverse_bits` 1命令で済む。
`occupied() ^ kings` の合成も要らなくなる。

### 案B: 集合そのものをpush/popで差分維持する

do_moveのたびにBonaPieceのビットセットをXORで更新し、`refresh_top` での
再構築をなくす。回数比で負ける。`refresh_top` はnodesの13.4%でしか
走らないのに対し、pushは全ノードで走る。1回の再構築を消すために約7.5回の
pushへ費用を移すことになり、評価しないノードでは何もしないという遅延方式
（[ADR-0035](0035-nnue-accumulator.md)）の利点も壊れる。

## Decision

案Aを採る。ただし**速度の利得は誤差内で、効果を主張しない。**

機能検証（[ADR-0074](0074-feature-verification.md)）は深さ13・20で全4局面の
ノード数・評価値・最善手が一致した。集合の中身が変わらないので、差分
（adds/subs）の並びも `ft_update` へ渡る配列も同一で、評価値は1ビットも
動かない。

NPSは方向を入れ替えた7周の交互測定を2回行った。

| 測定 | 結果 |
|---|---|
| base先行 | cand +0.50% |
| cand先行 | cand +0.16% |
| 同一バイナリの対照（base対base） | 2本目が +0.24% |

**対照のドリフトが+0.24%あり、cand の利得はその幅に収まる。** ドリフトを
差し引くと+0.17〜0.26%になる。符号は両方向で正だが、単独では分離しない。
ADR-0151の群H（+0.33%）・群K（+0.22%）と同じ水準で、同ADRの運用に従い
参考値として扱う。

採るのは、害がなく、次の一手の土台になるためである。挙動不変を3段で
確認しており、集合をブロックとして扱う視点が入る。

### なぜ見込みに届かなかったか

着手前の見積もりは、命令数から+2.5〜3.5%だった。実測はその10分の1に
とどまる。プロファイルを取り直すと理由が見える。`refresh_top` は8.12%から
8.05%へ、置き換えた行は4.43%から4.08%へしか動いていない。

**律速は命令数ではなくビットセットへのRMWの回数である。** 旧実装は盤上36枚と
手駒の枚数ぶんで42〜46回のRMWを出す。新実装は分岐とテーブル引きを消したが、
1ブロックが2〜3語にまたがるため、盤上18ブロックで40〜60回のRMWになる。
**回数は減っていない。** 命令数の削減はメモリ待ちに隠れた。

### 次の一手（未着手）

RMWを消すには、ビットセットのレイアウトをブロック単位に変える。手駒2語と
盤上18ブロック×2語を別々に持てば、各ブロックへ直接書けてRMWがゼロになる。
`FinnyEntry.bits` は200バイトから304バイトへ増える。差分抽出の走査順が
変わるので `adds`/`subs` の並びも変わるが、`ft_update` のi16加減算は可換
かつ結合的なので結果はビット一致する（ADR-0151群Aと同じ根拠）。

これは設計変更にあたるため、今回の枠には入れない。ROADMAPの候補へ置く。

## Consequences

- BonaPieceの番号付けの前提（ブロック幅81、`inv` の向き、金群の畳み方）に
  依存するコードが増えた。前提が壊れたときに黙って間違うので、300局面×2視点で
  `for_each_bona_piece` と集合が一致するテストで塞いだ。`rev81` のシフト量を
  1ずらす故障注入で、このテストが実際に落ちることも確かめてある
- `for_each_bona_piece` は学習データの書き出しと `posgen` が使うため残る。
  正解器としての役割を兼ねる
- コードは85行増えた。速度が誤差内なので、増分に見合う実利は「次の一手の
  土台」だけである。レイアウト変更に着手しないなら、この変更の価値は薄い
- プロファイルの読み方として、self時間の大きい行が命令数で決まっているとは
  限らないことが1件加わった。ADR-0151群Mは「線形走査は入力分布に合っていれば
  置き換えるほど遅くなる」、本件は「命令を削ってもメモリ待ちに隠れる」で、
  どちらも減る仕事量の見積もりを命令数だけで立てた失敗である
