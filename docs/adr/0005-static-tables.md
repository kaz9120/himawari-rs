# 0005: 静的テーブル生成戦略

- Status: accepted
- Date: 2026-07-17
- 関連ADR: [0003](0003-toolchain.md)

## Context

盤面表現層は多数の静的テーブルを使う。近接駒の利き、between/line、
Zobrist乱数、採用方式によっては飛角の占有テーブル（PEXT/magic採用時、
数百KB〜数MB）である。生成タイミングを決める。

## 選択肢と比較

### 案A: build.rsで生成

生成コードがビルドスクリプトに分離される。クロスコンパイルやキャッシュの
取り扱いが面倒で、生成ロジックのテストも書きにくい。

### 案B: const fnでコンパイル時生成

起動コストゼロ。生成関数がふつうのRustコードなのでテストできる。
定数文脈でそのまま使える。nightly採用（ADR-0003）によりconst評価の
表現力の制約はほぼない。大きなテーブルはコンパイル時間と
バイナリサイズを悪化させる可能性がある。

### 案C: LazyLockで実行時初期化

サイズ制約がないが、定数文脈で使えず、起動時コストが生じる。

## Decision

すべての静的テーブルをconst fnで生成する（案B）。対象は近接駒の利き、between/line、段筋マスク、Zobrist乱数
（seed固定のxorshift等で再現性を固定）である。利き生成方式のADR
（P1で起草）で占有テーブルを採用した場合は、それも含む。

const fnの生成関数には、生成結果の性質を確認する単体テストを併置する
（例: 利きテーブルと素朴実装の全マス一致）。

## Consequences

- 起動コストゼロ、生成ロジックはテスト可能、すべて定数文脈で使える
- 生成コードが増えるとコンパイル時間が延びる。インクリメンタルビルドが
  体感で遅くなった時点（目安: クリーンビルド1分超）で、原因のテーブルだけ
  LazyLockへ逃がすことを検討する
- build.rsは採用しない。生成ロジックはライブラリコードとして残る
