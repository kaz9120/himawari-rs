# 0081: 開発環境をスクリプトで再現可能にする

- Status: accepted
- Date: 2026-07-28
- 関連ADR: [0003](0003-toolchain.md), [0028](0028-pruning-extensions.md), [0053](0053-docs-structure.md), [0080](0080-net-release.md)

## Context

開発機をApple M4 ProからWindows機（Core i7-1255U、WSL2）へ移す。
24時間稼働させて開発を進める意図がある。

現状、環境構築の手順はどこにもまとまっていない。ツールチェインは
`rust-toolchain.toml` が指すが、教師データの取得手順は
[DATASETS.md](../DATASETS.md)に散文で書かれ、学習済みネットは
ローカルファイルとしてしか存在しない。SPRTのコマンドは
[ADR-0028](0028-pruning-extensions.md)に既定条件が書かれているだけで、
毎回手で打っている。

移行を機に、新しいマシンで手順どおりに流せば同じ状態になる形へ整える。

もう1つ、マシンごとに変わる値の扱いを決める必要がある。
[ADR-0028](0028-pruning-extensions.md)はSPRTの並列度を8と定めたが、
これはApple M4 Pro（高性能コア10）での値である。移行先は
高性能コア2・効率コア8の構成で、同じ8を使うと効率コアに載った対局だけ
探索が浅くなり、測定がぶれる。

## 選択肢と比較

### 案A: スクリプト3本と手順書で揃える

`setup.sh`（ツールチェイン）、`fetch-dataset.sh`（教師データ）、
`env.sh`（マシン依存の値）を置き、[SETUP.md](../SETUP.md)から辿れるようにする。

手順が実行可能な形で残るため、文書と実態が乖離しにくい。
シェルスクリプトなのでWSL2でもmacOSでも読める（`setup.sh` はLinux専用）。

### 案B: Dockerで固める

環境差をコンテナで吸収する。再現性は最も高い。

ただしSPRTは計測が目的であり、コンテナのオーバーヘッドが測定へ乗る。
NPSが数%落ちるだけでも、10+0.1秒の対局では到達深さが変わる。
学習でGPUを使う場合の設定も増える。計測を主目的とするリポジトリには
向かない。

### 案C: 手順書だけ書く

スクリプトを作らず、[SETUP.md](../SETUP.md)に手順を並べる。
実装コストは最小。

コマンドが文書の中にしかないため、実行されないまま古くなる。
[DATASETS.md](../DATASETS.md)の取得手順が既にこの状態で、
`curl` の例が1系統ぶんしか書かれていない。

## Decision

案Aを採る。`scripts/` に4本置く。

| スクリプト | 役割 |
|---|---|
| `setup.sh` | APT・gh CLI・rustup・Python/PyTorch を入れてビルドとテストまで通す |
| `fetch-dataset.sh` | HuggingFaceから254ファイルを取得し、train/validを作る |
| `env.sh` | マシンごとに変わる値を自動で決める。他のスクリプトから source する |
| `sprt.sh` | 既定条件でSPRTを回す |

`release-net.sh`（[ADR-0080](0080-net-release.md)）と合わせて5本になる。

### 2026-07-29追記: 測定と待機の手順もスクリプトへ

起草時の4本は環境構築が中心だった。日々の測定手順は手で組み立てていた
が、同じ事故を繰り返したため固めた。オーナーの方針でもある
（「必要なものはどんどん整備して意図を明確にしていく。再現性が高まる」）。

| スクリプト | 役割 | 固めた理由 |
|---|---|---|
| `verify-feature.sh` | 機能検証（[ADR-0074](0074-feature-verification.md)） | 局面と深さが記録に残らず条件がぶれた |
| `build-pair.sh` | SPRT用のbaseline/candidateを作る | `target-cpu=native` の付け忘れ、stashの取り違え、競合中のビルドが起きた |
| `sprt-summary.sh` | ログから結果を抜き、貼れる形で出す | 数値の転記ミスは後から気づけない |
| `watch-sprt.sh` | SPRTの判定を待つ（[ADR-0098](0098-agent-permissions.md)） | 待機の複合コマンドが権限の許可規則に一致しない |
| `watch-ci.sh` | PRのCI確定を待つ（[ADR-0098](0098-agent-permissions.md)） | 同上 |

`build-pair.sh` は未コミットの変更があると中断する。SPRTにかけるのは
コミット済みの状態だけにするためで、[ADR-0070](0070-pr-based-workflow.md)の
ブランチ運用と揃えてある。

`sprt-summary.sh` の終了コードは判定を表す（0=H1、1=H0、2=判定に至らず）。
呼び出し側が結果で分岐できる。

### マシン依存の値は自動で決め、上書きできるようにする

`env.sh` が物理コア数を検出し、SPRTの並列度を決める。
値は環境変数で上書きできる。

物理コアを数える理由は、SPRTが1局1スレッドで回るためである。
論理プロセッサ数まで積むと持ち時間の消化が不安定になる。

Apple Siliconでは高性能コアだけを数える。効率コアは大きく遅く、
混ぜると同じ持ち時間でも到達深さがばらつく。

上限は8とする。[ADR-0028](0028-pruning-extensions.md)の既定条件に
合わせ、コアが余っていても超えない。過去の測定と条件を揃えるためである。

### ADR-0028の並列度8の位置づけを改める

同ADRの「既定条件」に含まれる `--concurrency 8` は、Apple M4 Proでの
値として読む。マシンが変われば同じ8でも意味が変わるため、
上限として扱い、実際の値は `env.sh` がマシンに合わせて決める。

SPRTの結果を比較するときは、同じマシン・同じ並列度で測ったものだけを
並べる。異なるマシンの結果を直接比べない。

### 教師データはスクリプトで再取得する

移行にあたって77GBを物理コピーせず、HuggingFaceから取り直す。
`fetch-dataset.sh` が254ファイルの取得・サイズ検査・前処理を行う。

取得の再実行を安全にする。妥当なサイズのファイルは飛ばし、
中断しても続きから進む。HuggingFaceは存在しないパスに対して
15バイトの「Entry not found」を返すため、サイズで検出する。

加工済みの `train_1900M.psv`（80GB）は生データから3分で作れるため、
運ばない。

## Consequences

新しいマシンでの立ち上げが、スクリプト2本と `gh release download`
で済むようになる。手順が実行可能な形で残るため、文書と実態の乖離も
起きにくい。

`scripts/` が増える分、保守の対象も増える。ツールチェインや
データセットの構成が変わったら追随が要る。文書だけの場合と違い、
壊れれば実行時に分かる。

マシンをまたいだSPRT結果の比較ができなくなる。同じ変更でも
マシンが違えば到達深さが変わり、Eloの出方も変わる。移行後は
ベースラインを取り直し、以後の比較は新しいマシンで揃える。

移行先は性能が大きく落ちる（マルチスレッドで1/4〜1/5と見込む）。
SPRTの所要時間は数倍になる。24時間稼働で埋め合わせる前提だが、
判定に至らない打ち切りが増えるようなら、`elo1` を上げるか
持ち時間を短くする運用の見直しが要る。

学習はCPUのみになる（内蔵GPUでのPyTorchは実用的でない）。
現在の主戦場が探索改善であり、評価関数は確定しているため当面は
支障がない。学習が必要になったらApple Silicon機へ戻す。
