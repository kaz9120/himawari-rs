# 0007: エンジンのバージョニング戦略

- Status: accepted
- Date: 2026-07-17
- 関連ADR: [0003](0003-toolchain.md), [0006](0006-ci-test-bench.md)

## Context

探索エンジンのバージョンは複数の場面で参照される。USIの `id name` として
GUIに表示され、対局ログや大会・floodgateでビルドを識別し、SPRT測定では
「どのビルド同士を比べたか」の記録になる。番号の付け方とタグ運用を
決めずに開発を進めると、後から過去のビルドを特定できなくなる。

決めるべきことは3つある。番号の体系、いつからバージョンが意味を持つか、
devビルドの識別方法である。

## 選択肢と比較

### 案A: 厳密なSemVer

ライブラリ向けの規約で、public APIの互換性がMAJOR/MINORの判定基準になる。
エンジンバイナリにはpublic APIがなく、判定基準が実態に合わない。

### 案B: Stockfish型（強さリリース番号）

リリース番号（16, 17, …）が「SPRTで確認された強さの節目」を意味する。
devビルドは日付とコミットハッシュで識別する。エンジンの実態に合うが、
SPRT基盤がないP3以前には適用できない。

### 案C: CalVer

リリース時期は伝わるが、強さの節目も互換性も読めない。利点が薄い。

## Decision

本ADRの適用範囲はエンジンバイナリの番号運用とタグ運用に限る。
NNUE評価関数ファイルの識別は含まない（後述）。

開発段階で使い分ける2段階式とする。番号は `workspace.package.version` を
唯一の情報源とし、Cargoのバージョンとエンジンの表示バージョンを一致させる。

開発中（1.0まで）は 0.MINOR.PATCH を使う。

- フェーズ出口を通過するたびにMINORを上げ、gitタグ `v0.x.0` を打つ。
  0.1.0 = P0（現在）、0.2.0 = P1出口、0.3.0 = P2出口、0.4.0 = P3出口、
  0.5.0 = P4出口
- 1.0.0 = P5出口（自前学習NNUEが駒割評価にSPRTで有意勝ち）。
  エンジンとして完成した節目を1.0とする
- 最初の対外リリース（GitHub Release、CPU別バイナリ）は0.3.0（P2出口、
  GUIで対局できる完動エンジン）から行う

1.0以降は案Bに移行する。MAJORをSPRT合格の蓄積を束ねた強さリリースで上げ、
PATCHをバグ修正に使う。

devビルドの識別は、`option_env!("HIMAWARI_BUILD_ID")` でコミットハッシュを
埋め込む方式とする（build.rs不採用の方針と整合。ADR-0005）。環境変数は
CI・リリースビルドで設定し、USIには `id name Himawari 0.3.0 (abc1234)` の
形式で出す。未設定のローカルビルドは `id name Himawari 0.3.0-dev` とする。
この表示の実装はP2のUSIアーキテクチャADRに委ねる。本ADRで決めるのは
番号体系とタグ運用までとする。

NNUE評価関数ファイルの扱いは、方向性のみ次のとおり定め、
方式の確定は後続ADRに委ねる。

- ネットワークファイルはバイナリとは独立した識別子を持つ
  （内容ハッシュによる命名を想定）。方式は評価ファイルフォーマットの
  ADR（P4で起草）で決める
- 1.0以降の「リリース」はバイナリ＋デフォルトネットワークの組として定義し、
  リリースタグがネットワークの識別子を固定する。SPRTの記録もこの組に
  対して行う
- ネットワークの実体はgitに入れず、GitHub Releasesの成果物として配布する。
  学習の再現条件（教師データ、設定）との対応は学習運用のADR（P5で起草）で
  管理する

## Consequences

- フェーズ出口のタグとツールチェイン固定（ADR-0003）により、過去の
  任意の節目のバイナリを再現できる
- SPRT測定の記録にはタグまたはコミットハッシュを使える。強さの履歴が
  バージョン履歴と対応する
- ローカルビルドはコミットハッシュを持たないため、厳密な識別は
  CI経由のビルドに限られる。SPRT用ビルドをCI成果物に寄せる動機になる
- フェーズ構成が変わった場合（フェーズの分割・追加）はMINORの対応表が
  ずれる。その際はこのADRを更新する
