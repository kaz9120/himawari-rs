# 0102: 残り手数の見積もりをmove horizon方式にする

- Status: rejected
- Date: 2026-07-29
- 関連ADR: [0021](0021-time-management.md), [0059](0059-easy-move-scaling.md), [0089](0089-improvement-criteria.md), [0074](0074-feature-verification.md)

## Context

時間配分の分母が[ADR-0021](0021-time-management.md)の初期式のままである。

```rust
let rem_moves = (48u64.saturating_sub(u64::from(game_ply) / 2)).max(16);
let avail = my_time / rem_moves + limits.byoyomi + inc;
```

分母は96手目以降16で固定される。実戦は150手を超えるのに「あと16手」と
見積もり、毎手6.25%を投じる。ADR-0021自身が「配分式は最初は素朴でよい」
と書いており、見直しは予定されていた。

### 実測

floodgateの300+10と相似比（持ち時間/加算 = 30）を揃えた30+1で
自己対局させ、1手ごとの消費と到達深さを測った。

| 区間 | 1手の消費 | 残り持ち時間 | 到達深さ | 評価値 |
|---|---|---|---|---|
| 0〜20手 | 1.0〜2.5s | 30→23s | 18〜20 | cp ±40 |
| 40〜60手 | 1.0〜2.7s | 15→9s | 17〜19 | cp ±150 |
| 110手以降 | 1.0〜1.5s | **2.2sに張り付き** | **12〜15** | cp -507〜+1115 |

自分の30手目で持ち時間の70%を使い切っている。110手以降は加算分だけで
指し、到達深さが序盤より4〜7段浅い。評価値が1手ごとに500〜1000cp
振れており、読み負けている。

floodgateの負け11局が「105手以上・終盤10手の消費7〜9秒」だった事実
（RESULTS.md（当時の計測記録。現在はCHANGELOGとADRが持つ））と同じ形である。

### 軸との関係

[ADR-0089](0089-improvement-criteria.md)の3軸（速度・ノード効率・
終盤の正確さ）に時間配分は含まれない。3軸は1手の探索効率を測る軸で、
1局を通じた時間の配り方とは直交する。時間配分は独立した軸として
[ADR-0059](0059-easy-move-scaling.md)が+69.3 Eloで実証済みであり、
本ADRはその続きに位置づく。

**単独で効く仮説**: 将棋の勝敗は終盤で決まる。現行の配分は序中盤に
偏り、終盤の到達深さを序盤より4〜7段浅くしている。分母を実際の
対局長に合わせれば序中盤の消費が減り、その分が終盤に残る。深さの
逆転を解消すれば強くなる。

## 選択肢と比較

### 案A: 早期打ち切りの判定材料を増やす

[ADR-0059](0059-easy-move-scaling.md)のscale係数を強化する。
bestMoveChangesのスレッド集約、安定度のロジスティック化、
root fail-low延長が候補になる。

[ROADMAP.md](../ROADMAP.md)の教訓「判定材料の精度を上げると効く」に
合致する。ただし浮かせた時間の行き先がない。現行の分母は浮いた分を
そのまま序中盤で溶かす。配分カーブを直さない限り、この案の利得は
残り時間として積み上がるだけで終わる。

### 案B: 分母をmove horizon方式にする

やねうら王の `source/timeman.cpp` と同じ形にする。引き分けまでの
残り手数と、対局長の見積もり（move horizon）の小さいほうを採り、
自分の手番だけを数える。

```
move_horizon = MoveHorizon + 20 - min(ply, 80)     # 加算・秒読みあり
move_horizon = MoveHorizon + 40 - min(ply, 40)     # 切れ負け
MTG = min(max_moves_to_draw - ply + 2, move_horizon) / 2
```

`MoveHorizon` の既定は160である。分母は手数とともに縮み、終盤ほど
1手に厚く配る。

### 案C: 案Bに MinimumThinkingTime を含めて完全移植する

やねうら王は `optimum = minimumTime + remain_estimate / MTG` として、
`MinimumThinkingTime`（既定2000ms）から `NetworkDelay` を引いた
1880msを底上げに使う。分母を大きくした分をこの項が埋め合わせる。

## Decision

案Bを採用する。`MinimumThinkingTime` は持ち込まない。

### 分母だけを差し替える理由

現行式とやねうら王の式は、`minimumTime` の項を除けば同型である。

```
現行        : avail = my_time / MTG_old + byoyomi + inc
やねうら王  : avail = minimumTime + my_time / MTG + byoyomi + inc
```

やねうら王の `remain_estimate = time + inc * MTG + byoyomi * MTG` を
`MTG` で割ると `time / MTG + inc + byoyomi` になり、現行式と一致する。
将来受け取る加算分を予算に入れる考え方は、本エンジンが既に採っていた。
違いは分母の定義だけである。よって変更は1点で済む。

分母の比較を示す。`MaxMovesToDraw` は256とした。

| game_ply | 現行 | 本ADR |
|---|---|---|
| 0 | 48 | 90 |
| 40 | 28 | 70 |
| 80 | 16 | 50 |
| 160 | 16 | 49 |
| 200 | 16 | 29 |
| 240 | 16 | 9 |

序盤は約2倍薄く、240手では約2倍厚くなる。序中盤で温存した分が
終盤に回る形である。

### MinimumThinkingTime を持ち込まない理由

[CLAUDE.md](../../CLAUDE.md)は「他エンジンの係数を借りるときは、その
出典が前提とするスケールが本エンジンで成り立つかを実測する」と定めて
いる。1880msが配分に占める割合を持ち時間別に出す。

| 持ち時間 | optimum に占める1880msの割合 |
|---|---|
| 300+10（floodgate） | 12% |
| 30+1（相似比を揃えた追試） | 59% |
| 10+0.1（SPRT既定、[ADR-0028](0028-pruning-extensions.md)） | 90% |

10+0.1では1手1.88秒となり、5手で持ち時間が尽きる。30+1でも配分の
6割をこの項が占める。**この定数が前提とするスケールは、本エンジンが
SPRTを回せる持ち時間では成り立たない。** 測れない定数は入れない。

やねうら王がこの項で分母の拡大を埋め合わせている以上、案Bは
やねうら王より薄い配分になる。これは承知のうえで進める。薄すぎる
場合の兆候は「終局時に持ち時間が余る」ことなので、機能検証で確かめる。

### MaxMovesToDraw への依存

分母の終盤側の縮みは `MaxMovesToDraw` から来る。未設定（0）のときは
やねうら王と同じく100000として扱い、分母は50で下げ止まる。この場合
終盤に厚く配る効果は出ない。floodgateとSPRTの双方で256を設定する
運用が前提になる。

### 実装

`moves_to_go()` を `timeman.rs` に置き、`TimeManager::new` へ
`max_moves_to_draw` を渡す。定数は5個増える。

```rust
const MOVE_HORIZON: u64 = 160;
const HORIZON_BONUS_SUDDEN: u64 = 40;
const HORIZON_DECAY_SUDDEN: u64 = 40;
const HORIZON_BONUS_INC: u64 = 20;
const HORIZON_DECAY_INC: u64 = 80;
```

出典はやねうら王 `source/timeman.cpp` の `TimeManagement::init` で、
値はすべて既定のまま使う。`maximum = avail × 3` は触らない。
[ADR-0059](0059-easy-move-scaling.md)のscale上限が2.17なので、
`over_total` の判定に3倍の上限は届かない。ここを動かしても挙動は
変わらないため、変更を分母1点に絞る。

### 検証

[ADR-0074](0074-feature-verification.md)の機能検証は、時間制限の
ない探索（`go depth N`）に影響しないことの確認になる。時間管理は
optimumがNoneの経路を通らないため、固定深さのノード数は完全一致
するはずである。

配分が変わることは30+1の自己対局で確かめた。固定深さのノード数は
4局面すべてで一致し、探索そのものには影響していない。

| 区間 | 消費（前） | 深さ（前） | 消費（後） | 深さ（後） |
|---|---|---|---|---|
| 0〜20手 | 1.67s | 19.1 | 1.46s | 17.9 |
| 20〜60手 | 1.66s | 17.7 | 1.40s | 16.0 |
| 60〜110手 | 1.25s | 16.8 | 1.26s | 16.2 |
| **110〜160手** | 1.02s | **14.4** | 1.25s | **15.2** |

自分の30手目時点の残り持ち時間は12.9秒から17.4秒へ増えた。
110〜160手の区間で残りが2.1秒から6.8秒になり、到達深さが0.8段
深くなっている。狙いどおり序中盤の消費が終盤へ回った。

代償は中盤である。20〜60手で1.7段浅くなった。中盤1.7段の損と
終盤0.8段の得を、どちらが重いかはSPRTで決める。

なお `MaxMovesToDraw` による分母の縮みは158手以降でしか働かない。
対局長の中央値は125手（RESULTS.md（当時の計測記録。現在はCHANGELOGとADRが持つ）の直近SPRT）なので、
典型的な対局で効いているのは序中盤の温存だけである。

SPRTは[ADR-0028](0028-pruning-extensions.md)の既定条件で行った。

## 結果

**-107.2 Elo [-150.9,-66.6]**（234局、117ペア、LLR -1.40で打ち切り）。
CIが0を大きく下回ったため、判定の確定を待たずに止めた。棄却する。

負けの内訳は、勝ちの少なさより負けの多さに出ている。117ペアで
+77 =10 -147 だった。

### 何が間違っていたか

配分を一律に薄くしたことである。中盤の到達深さが1.7段落ち、終盤で
0.8段戻した。差し引きで損になった。

[ADR-0059](0059-easy-move-scaling.md)が+69.3を得たのは、**局面ごとに
見分けて**縮めたからである。安定した局面では0.53倍に縮め、荒れた
局面では2倍以上に伸ばす。本ADRは見分けずに全局面の分母を2倍にした。
最善手が終盤までひっくり返り続ける18%の局面からも時間を奪っている。

分母の見直しという着眼そのものは実測に裏づけられていた。序中盤の
30手で持ち時間の70%を使い、終盤の深さが序盤より浅い事実は変わらない。
しかしその是正を一律の係数で行うと、必要な局面から時間を奪う副作用が
利得を上回る。

### 測定から分かった別の事実

30+1の自己対局160手で、1手ごとに「最終的な最善手が確定した深さ」を
測った。

| 指標 | 値 |
|---|---|
| 最善手が確定した深さの中央値 | **1** |
| 到達深さの中央値 | 17 |
| 最善手が確定して以降に使った時間 | 総消費の**78.6%** |
| 無駄率90%以上の手（深さ1の手が最終手） | 132手（**82%**） |

82%の手は深さ1の指し手がそのまま最終手になる。一方で18%の手は
最善手が後から変わる。**時間を削る余地は大きいが、削ってよい局面と
そうでない局面の見分けが要る。** 一律の削減が失敗した理由がここに
ある。

## Consequences

- 棄却する。分母は[ADR-0021](0021-time-management.md)の式のまま残す
- 実装は `feat-adr0102-move-horizon` ブランチに残す。見分けの仕組みが
  そろった後なら、分母の見直しが再び意味を持つ可能性がある
- 教訓は[ADR-0096](0096-rfp-margin.md)と同じ形である。時間配分の係数も
  条件と組でしか意味を持たない。分母だけを他エンジンから借りても、
  それを支える見分けの仕組みが違えば結果は移らない
- 次は案A（判定材料の精度）へ進む。「浮かせた時間の行き先がない」
  という本ADRの想定は誤りだった。行き先を作る前に、削ってよい局面の
  見分けを鋭くするほうが先である
